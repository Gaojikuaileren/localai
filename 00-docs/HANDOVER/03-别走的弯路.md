# 03 · 别走的弯路

> 写给**第一次打开这个仓库的人**。你不需要知道任何历史,也不需要认识任何缩写。
> 每一条都写成三段:**症状(你会看到什么)· 真因 · 怎么避开**。
> 之所以写症状,是因为——**只写「要小心 X」你认不出自己正在踩**。
>
> 排序按「**你什么时候会踩到**」:第 0 天 → 第一次跑命令 → 第一次提交 →
> 第一次找决议号 → 第一次改断言 → 第一次批量改文件 → 第一次出包 → 第一次收工。
> 从头读一遍约半小时。**读完就照做**,不要只读不做——本节里至少四条,
> 是「知道了也还会踩,除非你真的把那两行配置敲进去」。

## 使用说明 · 这份文档里的数字都会过期

这个项目自己的第一条纪律写在 `00-docs/COORDINATOR-HANDOFF.md` 开头:

> 「**不要引用本文件里的任何数字** —— 它们写下的那一刻就开始过期。」

本节照办。**凡是出现具体数字的地方,都同时给了你自己重新量的那条命令**,
并且标注了我量它的日期(**2026-09-02**,`main` 在 `46d76ee`)。
读到一个数就当它是「那天的读数」,不是事实;**要事实就跑那条命令**。

同理,本节**不写「现在什么在跑」**——那种话第二天就是假的。
要知道某个东西在不在跑,本节给的是**怎么看**,不是**它现在怎么样**。

第二段**只有在「出过包的那台机器」上才有意义**,而且要联网:

```bash
head -2 dist/client/VERSION.txt | tail -1       # 出厂包版本戳
git remote -v ; git rev-list --left-right --count origin/main...main
```

### ★★ 为什么用 `;` 而不是 `&&` —— 这是本节的第一条真弯路

**症状**:你把上面这些用 `&&` 串成一条,粘贴进终端,输出比预期少几行。
你以为「少打了两行」,继续往下做。

**真因**:`&&` 遇到第一个非零退出码就**整条中止**,后面的命令**一条都不执行**。
而 `dist/` 不在版本控制里(`.gitignore` 里 `dist/` 那一行,落在 `--- Python ---`
注释段下面,与 `build/` 并排——它是 Python 打包惯例,却同时盖住了本项目**真正的出货目录**)。
所以在任何一份新 clone 上,`head -2 dist/client/VERSION.txt` 必然失败,
**它后面的所有命令永远不会跑**。

```bash
git ls-files dist | wc -l     # 2026-09-02 实测:0(一个字节都没进 git)
# 自己演一遍 && 会怎么吞掉后面:
( head -2 nonexistent.txt && echo "这行永远不会打印" ) ; echo "---"
( head -2 nonexistent.txt  ; echo "这行会打印" )
```

**怎么避开**:一律用 `;`。**「没跑」和「跑过了是空的」在终端上长得一模一样**——
这正是这个仓库自己反复记的那个形状。

> ★ 附带一条**文档与实况不一致**,而且它是最贵的那种:
> `00-docs/COORDINATOR-HANDOFF.md` §1 那条「重建状态的一条命令」——
> **仓库自己给的那条**——就是用 `&&` 串的,而且**同样包含 `dist/client/VERSION.txt`**。
> ⇒ 照仓库自己的交接文档做,在一份新 clone 上会在中途静默断掉。
> 自证:`grep -n 'ls-remote' 00-docs/COORDINATOR-HANDOFF.md`(量于 2026-09-02,在第 12 行)。

# 第 0 天 · 你还没写一行代码就已经踩到的三条

## 0.1 ★★★ 六道提交闸**一道都没有挂上**,而它和「全绿」长得一模一样

**症状**:你 clone 完,改了几个文件,`git commit`,一路顺利。你觉得代码很干净。

**真因**:这个项目的六道提交检查全部写在 `.githooks/pre-commit` 里,
而**让 git 去用这个目录的那条配置不跟着仓库走**:

```bash
git config --get core.hooksPath
# 2026-09-02 在本机返回一条【绝对路径】:E:\.meine\.Proj_Soft\.Proj\.localAI\.githooks
git config --local --get core.hooksPath    # 它存在 .git/config 里
ls .git/hooks | grep -v '\.sample$'        # 2026-09-02 实测:空(没有任何真钩子)
```

`.githooks/pre-commit` **本身是被 git 跟踪的**,跟着仓库走;
但 `core.hooksPath` 在 `.git/config` 里,而 **`.git/config` 从来不会被克隆**。
⇒ 在一台新机器上,**本节后面讲的六道闸对你一个都不生效**。

**怎么避开**——clone 之后的第一件事,两行,缺一不可:

```bash
git config core.hooksPath .githooks     # ★ 用相对路径,别抄本机那条绝对路径
git config core.autocrlf false          # ★ 见 0.2,这不是可选项
```

> ★ 这里有个值得记住的反讽:第 ① 道闸**禁止代码里出现绝对路径**,
> 理由是「换块盘它就变成一句错话」;而**安装这道闸的那行配置自己就是一条绝对路径**,
> 躺在闸看不见的地方。仓库整个搬个位置,六道闸会**静默地**全部失效,没有任何提示。

## 0.2 ★★ 新 clone 的 `core.autocrlf` 默认是 `true`,你的第一次提交就会撞行尾护栏

**症状**:`git add` 时打印一堆
`warning: in the working copy of 'x', LF will be replaced by CRLF`;
接着第一次 `git commit` 被第 ③ 道闸拒绝,说你「改到了没打算改的部分:行尾」。

**真因**:**这个仓库没有 `.gitattributes`**——行尾完全靠本地那一条配置。

```bash
git ls-files | grep -i gitattributes | wc -l      # 2026-09-02 实测:0
```

在一个空仓库里,git 默认 `core.autocrlf=true`(我在隔离仓库里实测过,一 `git add` 就报警告)。
本机的主工作树上是 `false`——但那也在 `.git/config` 里,**不跟着 clone 走**。

**怎么避开**:见 0.1 的第二行。**不做的话,你写的每一份文件都会在提交那一刻被改写行尾。**

## 0.3 ★★★ 仓库里**没有**的东西 —— 换一台机器,这些都要你自己准备

**症状**:后端起不来 / 门禁大段大段地说「没跑到」/ 面板点「确定」什么也不发生 /
`bin\Release\...\localai-client.exe` 说文件不存在。你以为仓库不完整。

**真因**:`config/paths.toml` 是**唯一路径配置源**,它定义**五个逻辑根**,
而**只有 `code` 这一个在 git 里**。

| 东西 | 在 `paths.toml` 里的键 | 缺了会怎样 |
|---|---|---|
| `models` / `assets` / `state` / `cache` 四个根 | `[roots]`(2026-09-02 都在 `D:\AI\` 下) | 后端起不来。**换盘只改这一个文件** |
| 记忆套件的 venv | `[memory].venv` | 记忆套件跑不了;门禁会**如实报「没跑到」而不是假绿** |
| PostgreSQL 18 + 两个 Qdrant 实例 | `[memory].pg_data` / `qdrant_*` / `qdrant_s2_*` | `10-core/memory/` 那批套件连的是**真库**,起不来就跑不了 |
| `{state}\secrets` 与 `{state}\identity` | `[state].secrets` / `.identity` | ★★ 这两个目录**有意排除出备份**(见 `90-ops/backup/`)。换机 = **新 hub_id + 新 CA + 全部客户端重新配对**——这是设计,不是故障,`paths.toml` 里逐字写了理由 |
| 模型权重 | `models` 根 | 面板会回 `loader_absent`,那是**如实的**,不是 bug |
| `dist/`(出货产物)· `bin/` `obj/`(构建产物) | 不在 git | 新 clone 里**没有任何可运行的东西**;要跑客户端自检得**先 `dotnet build`** |

自己量:

```bash
sed -n '/^\[roots\]/,/^$/p' config/paths.toml       # 五个根今天指向哪
grep -n 'venv\|pg_port\|qdrant_http_port' config/paths.toml
git ls-files dist 20-client-win/app/bin | wc -l     # 2026-09-02 实测:0
```

**怎么避开**:门禁自己会把跑不到的**逐条列出来并说明原因**——
它的设计目标写在 `90-ops/run-tests.ps1` 文件头,是**诚实**而不是覆盖率。先看清单再动手:

```bash
powershell -NoProfile -ExecutionPolicy Bypass -File 90-ops\run-tests.ps1 -ListOnly
```

# 第一天 · 命令跑不起来

## 1.1 ★★ 照脚本自己的用法说明写 `pwsh`,而本机没有 pwsh

**症状**:`pwsh: command not found`。

**真因**:`90-ops/run-tests.ps1` 的**用法头逐字写着** `pwsh -File 90-ops\run-tests.ps1`,
而这台机器上只有 Windows PowerShell 5.1。

```bash
command -v pwsh || echo "没有 pwsh"      # 2026-09-02 实测:没有
sed -n '/^#  用法:/,/^#  退出码/p' 90-ops/run-tests.ps1
```

**怎么避开**:一律用 `powershell`,不用 `pwsh`。

## 1.2 ★★ `powershell -File` 被直接拒绝,报的是 SecurityError

**症状**:
```
无法加载文件 ...ps1,因为在此系统上禁止运行脚本。
    + FullyQualifiedErrorId : UnauthorizedAccess
```

**真因**:本机 ExecutionPolicy 除 `Process` 外全作用域 `Undefined`(等价 Restricted)。
我实测过两个方向:不带 `-ExecutionPolicy Bypass` ⇒ SecurityError、退出码 1;带上 ⇒ 正常跑完。

```powershell
Get-ExecutionPolicy -List
```

**怎么避开**:**每一条**跑 `.ps1` 的命令都写成
`powershell -NoProfile -ExecutionPolicy Bypass -File <脚本>`。

> ★ 正确写法散落在 `STATE.md` 与 `ASSERTION-PITFALLS.md` 里,
> **而脚本自己的用法头没写**——新人最先读的偏偏是脚本的用法头。
> 这是本仓最典型的「文档说的 ≠ 今天的实况」。

## 1.3 ★ 门禁脚本要用 PATH 上的**系统 python**,别拿某个 venv 去跑

**症状**:`90-ops/gate/` 下的脚本报一堆 `ModuleNotFoundError`,或者 PASS 数明显偏低。

**真因**:门禁脚本调的是裸 `python`;拿 `speech` 或 `memory` 那种专用 venv 去跑,
会因为缺依赖报**假 FAIL**。

**怎么避开**:跑门禁前确认你在哪个解释器上:

```bash
python -c "import sys; print(sys.executable)"
```

## 1.4 ★ 本节里的 python 命令,中文输出会变乱码

**症状**:你照抄本节的某条 `python` 命令,输出里的中文全是 `���`。你以为文件坏了。

**真因**:Git Bash 的终端代码页与 python 默认的输出编码对不上。**文件没坏,只是打印坏了。**

```bash
python -c "print('中文测试')"                        # 乱码
PYTHONIOENCODING=utf-8 python -c "print('中文测试')"  # 正常
```

**怎么避开**:本节里**凡是会打印中文的 python 命令,前面加 `PYTHONIOENCODING=utf-8`**。
(仓库里的门禁脚本自己在开头做了 `sys.stdout.reconfigure(encoding="utf-8")`,所以它们不受影响;
受影响的是你临时敲的那些。)

# 第一次提交 · 六道闸会怎么拦你

`.githooks/pre-commit` 里串着**六道闸**。它们**只在「本次提交真的动了相关东西」时才跑**。
作者把理由写在文件里,值得抄给你:

> *20 秒的钩子如果每次提交都跑,人会开始习惯性 `--no-verify` —— 那等于没有钩子。*

**先按症状查是哪一道**(这张表是给你在被拒绝的那一刻用的):

| 你在终端上看到 | 是哪道闸 | 什么时候触发 | 有没有放行口 |
|---|---|---|---|
| `✗ 绝对路径: <文件>` | ① 绝对路径 | 动了**非豁免**文件 | **无** |
| 屏幕几分钟不动,然后贴出一段测试输出 | ② 快速自检 | 动了 `10-core/` 下 `gateway`、`gpu-broker`、`memory` | **无** |
| 「改到了没打算改的部分:**行尾**」 | ③ 行尾 churn | 动了已存在的文件 | `LOCALAI_ALLOW_EOL_CHANGE=1` |
| 「中央三文档由第 0 条车道串行并入」 | ④ 中央三文档 | 动了 `DECISIONS.md` / `PROJECT_PLAN_v3.0.md` / `STATE.md`,且**当前分支不是 main** | `LOCALAI_ALLOW_CENTRAL_DOCS=1` |
| 「文件里有**不可见的控制字符**」 | ⑤ 控制字符 | 动了任何**文本**文件 | **无(有意的)** |
| 「决议包里写了 D 号,而 DECISIONS.md 里没有对应的编号标题」 | ⑥ D 号落地 | 动了 `DECISIONS.md` 或 `00-docs/decision-packets/` | 在**那份包里**写一行 `DRAFT-D:`(见 2.6) |

自己核对这张表(闸的形状会变,别信我抄的):

```bash
grep -n 'LOCALAI_ALLOW' .githooks/pre-commit     # 只有 ③④ 有环境变量口子
# 六段各自的抬头(★ 第 ① 道没有编号,它是整个文件的抬头):
grep -nE '^#  pre-commit —|^#  .*\(2026-08-[0-9]{2} 加' .githooks/pre-commit
```

> ### ★★★ 一条通用纪律:**不要用 `--no-verify`**
> 它会把**六道一起**关掉。真需要放行的,用上表那一列**窄口子**——
> 它们会在终端上留一行明说,不是隐藏后门。
> 判词:**看不见的豁免和没有闸是一回事。**

## 2.1 ✗ 绝对路径

**症状**:`✗ 绝对路径: foo.py` + 一行行号和原文。

**真因**:代码里禁止出现 `X:\` 或 `X:/` 形式的盘符路径,**连注释里的也拦**。
豁免名单只有几类(源码里是 `is_exempt()`):`config/paths.toml` · `00-docs/*` ·
`.githooks/*` · `.gitignore` · `*.md`,外加一份第三方评测语料。

我在隔离仓库里**两个方向都红测过**:
一个含 `D:\AI\models` 的 `.py` ⇒ 被拒、HEAD 没有前进;同样内容放进 `.md` ⇒ 放行。

**怎么避开**:去 `config/paths.toml` 加一个键,从那里读。**不要去找绕过钩子的办法。**

> ★ 这不是过严:`run-tests.ps1` 的作者自己在注释里抄了一行真实路径当例子,当场被拦,
> 他在注释里记了一笔说钩子是对的——因为那行路径会随换盘变成一句错话。

## 2.2 ★★ 提交静默几分钟,你以为它挂了

**症状**:你改了 `10-core/gateway/` 里的一个文件,`git commit`,
屏幕打印一行「跑一遍自检…」然后**什么都不动**,好几分钟。

**真因**:第 ② 道闸会同步跑整个 `90-ops/run-tests.ps1`,
**输出全部重定向进 `/tmp/localai-precommit.log`**,屏幕上看不到进度。

★ 这里有一条**注释即留痕**的活教材:钩子自己的注释**两处**把它叫「20 秒的钩子」,
而 `run-tests.ps1` 的文件头逐字写着:

> 「★ 这里原来写的是「约 20 秒」。2026-08-06 实测:22 个套件 1217 条断言,**190 秒**。」

⇒ **钩子的注释描述的是被换掉的那一版**。以文件头那句为准,而那句也是 2026-08-06 的读数。

**怎么避开**:
- **不要以为它挂了,不要 Ctrl-C**;
- 想看进度就另开一个窗口 `tail -f /tmp/localai-precommit.log`;
- **用带超时的工具跑 `git commit` 时把超时给到 600 秒**——默认两分钟会把它掐死在中间;
- 提交信息**先写文件再 `git commit -F <文件>`**。

## 2.3 ★★★ 「我只加了 5 行,git 说我改了 300 行」

**症状**:提交被拒:
```
git 数 +201/-200,而内容(去 \r 后)只变了 1 行
⇒ 有 200 行只有行尾被改了 · 文件里的 \r 数 200 → 0
```

**真因**:这个仓库的行尾是**逐文件混合**的(`DECISIONS.md` 全 LF,
`ASSERTION-PITFALLS.md` 全 CRLF——同一个目录里两种都有),
而你的工具**整体重写了文件**。这个坑在本仓连踩三次才修对。

我在隔离仓库里红测过这一道:提交一个 CRLF 文件,再整体改成 LF 并加一行 ⇒ **当场被拒**,
而且它把 `\r` 计数 `200 → 0` 直接印在拒绝信息里。

**怎么避开(按可靠性排序)**:
1. ★ **取原始字节重来**:`git show HEAD:<文件>` 出来,只在锚点后拼上你那一段,
   其余**一个字节都不碰**——这是三次里唯一一次修对的做法;
2. 别用会整体重写文件的编辑器去改一份混合行尾的文件;
3. 真要整体规范化行尾,用 `LOCALAI_ALLOW_EOL_CHANGE=1`(**不要** `--no-verify`)。

★★ **先看它印的那行 `\r` 计数,它可能自证这是误报**:两边 `\r` 数**相等**
(尤其都不是 0 却相等)多半是 git 默认 myers 配对出来的幽灵 ⇒ **换算法重数**:
`git -c diff.algorithm=histogram commit ...`。★ 这**不是**放行口,是换一种数法。

## 2.4 ★ 中央三文档在你的分支上改不动

**真因**:`DECISIONS.md` / `PROJECT_PLAN_v3.0.md` / `STATE.md` 各有唯一的
「当前状态」与 D 号计数器,两处同时写必打架。判据看的是**分支名不是 main**。

**怎么避开**:把内容写进**你自己的决议包** `00-docs/decision-packets/<你的包>.md`,
由并入那条车道逐处 Edit 进中央文档。

★★ 以下**不在**闸内,**你自己直接写**:
`00-docs/ASSERTION-PITFALLS.md` · `00-docs/worklog/` · 你自己新建的决议包。
理由写在拒绝文案里:*它们是追加式的,而学到教训的那条车道最有资格写它。*

## 2.5 ★★★ 「不可见的控制字符」—— 而那个字符不是你放的

**症状**:你改了 `20-client-win/admin/Views/ModelsView.cs` 里**任意一行**(哪怕只是个空格),
提交被拒:
```
提交被拒绝 — 文件里有不可见的控制字符。
      ModelsView.cs  —— 1 个不可见控制字符
```

**真因**:这个文件里**今天躺着一个 0x07(BEL)**。它是既有缺陷,不是你带进来的。
第 ⑤ 道闸扫的是**整个暂存文件的内容**,不是你的 diff ⇒ **你只要碰这个文件就会被它拦**。

病因在一句注释里:写的是 `%LOCALAPPDATA%\LocalAI\admin\settings.json`,
而落盘的字节是 `LocalAI` + **0x07** + `dmin` ——
生成这行的脚本把 `\a` 当成转义吃掉了。**终端和编辑器都显示不出来,串替换也匹配不上。**

## 4.1 ★★★ 你的反向断言撞在「解释它已经被删了」的那句注释上

**症状**:你写「源码里不得再出现 `Foo`」,东西明明删干净了,断言**还是红**。
或者反过来——「不得出现 X」**恒绿**,因为 X 只出现在注释里。

**真因**:**本仓的习惯正是「删掉之后把原文留在注释里说明为什么删」**
⇒ **越是写得负责任的代码,越容易把这类断言弄红**。
最狠的一次:断言撞上的是**它自己那条消息字符串**里的针。

**怎么避开**:
- **先去注释再判**。C# 用 `Selftest.CodeOnly(src)`(它同时剥注释**与字符串字面量**);
  Python 用 `assert_helpers` 里的 `code_only` / `_nodoc`;

- ★★ **绝对不许的两种修法**:① 把断言删掉(那正是这条坑最想诱你做的);
  ② 把注释改写成绕开断言的样子——那是把代价转嫁给下一个读代码的人。

## 4.2 ★★★ 新装的护栏**没红过**

**症状**:护栏装上了,一路绿灯,你很满意。

**真因**:一道**写坏了从此什么都不拦**的闸,和一道**判据变准了**的闸,
在终端上**长得一模一样**。

真实案例(就在第 ⑤ 道闸上):第一版用「内容里有没有 NUL」判二进制,
而 `$(printf '\000')` 在命令替换里**带不出 NUL** ⇒ 模式变成空串 ⇒
`grep -q ""` 匹配一切 ⇒ **每个文件都被当成二进制跳过,整条护栏是个空壳**。

**怎么避开**:**每装一道护栏,必须亲手让它红一次,而且两个方向都要验**——
① 造一个该拦的,确认 `exit 1` **且 HEAD 没有前进**;② 造一个不该拦的,确认放行。
★ 只验「不再误报」是不够的:那和「从此什么都不拦」分不开。

> ★ 做法参考本节 2.1 / 2.3 / 2.5:**在临时目录另起一个空仓库**,
> 只把 `.githooks/pre-commit` 拷进去、`git config core.hooksPath .githooks`,
> 在那里造红。做完即删,主仓库一个字节都不用动。

## 4.3 ★★ 你的判据在另一种输出布局下**整段不跑**

**症状**:断言在你手里绿,在门禁里也绿,而它**一条都没执行**。

**怎么避开**:★ **验证之前,先确认你的判据真的会命中一个【已知的例子】。**
命不中已知例子的判据,它的绿什么也不说明。

## 4.4 ★★ 你的临时测量工具本身没被验过

**症状**:你用 `grep -c` 数残留、数调用点,得出一个数,据此下结论。

**真因**:那个 grep 命中的是别的东西——数进了你自己刚写的注释;
命中的是名字里含同一个词的别的东西;量的是车道工作树而不是 main。

**怎么避开**:**尺子本身要先被验**——拿一个你**已知答案**的输入喂给它,对上了再用。

## 4.5 ★ 判据问错了问题

**症状**:断言问「我是什么身份」(我是不是管理员 / 我在哪个工作树),
而你想知道的是「我做不做得到」。

**怎么避开**:能用「**够不着**」代替「判断」就用够不着。

*git 结构上禁止两个 worktree 同时检出 `main`* —— 那是一个够不着,不是一次判断。
★ 而它也**如实写清了自己回答不了什么**:这道闸只回答「在哪儿改」,

# 第一次批量改文件(字节 / 行尾 / 编码)

> ★★ 这一族的全部危险在于**它是静默的**:用文本模式读回去的校验脚本会说「没问题」。

## 5.1 ★★★ 你的「文本模式」工具在悄悄改行尾

**症状**:整份 diff 全变、多行锚点全部失配,而你的校验脚本说「没问题」。

**真因**:`sed -i` 和 Python 的**文本模式**读写都会静默把 CRLF 换成 LF(**连空操作也会**);
反过来 `pathlib.Path.write_text` 会把 LF 换成 CRLF。

**怎么避开**:批改仓库文件一律 `read_bytes` / `write_bytes`。
★ 改前先量两边的 CR 数——**用 `tr`,别用 `grep -c`**:

```bash
tr -cd '\r' < <文件> | wc -c
```

★ 另记一笔:`open(p,'wb')` 会在 `write` **之前**先清空文件——中途出错就什么都没了。

## 5.2 ★★★ 落盘的字节与你看到的文本不是一回事

**症状**:路径 `dist\admin` 在终端上显示成 `distdmin`,读起来像少打了字;
而你的串替换**匹配不上**。

**真因**:用 Python 写文本时字符串里的 `\a` `\b` `\f` `\v` 被当成转义 ⇒ `\a` 变成一个 0x07。

**怎么避开**:生成含 Windows 路径的文本时**别写反斜杠转义**——
用 `r''` 原始字符串,或 `chr(92)` 拼出来。**修的时候只能按字节改。**
(树里现在就躺着一个实例,见 2.5。)

## 5.3 ★★ `.ps1` 要 BOM,`.cmd` 不要 BOM —— 两者要求相反

**症状**:`.ps1` 里的中文变乱码、脚本解析失败;或者 `.cmd` 末尾的 `pause` 被吞掉、窗口一闪而过。

**真因**:PowerShell 5.1 读**没有 BOM** 的 `.ps1` 会按 cp936 解;
而 `.cmd` **有 BOM** 会让首行 / `pause` 失效。

**怎么避开**:写完**复查字节**,别信编辑器显示。全仓自查:

```bash
PYTHONIOENCODING=utf-8 python - <<'PY'
import subprocess, pathlib
fs = [f for f in subprocess.run(["git","ls-files"],capture_output=True,text=True,
      encoding="utf-8").stdout.split("\n") if f.strip().strip('"').lower().endswith((".ps1",".cmd"))]
for f in fs:
    f = f.strip().strip('"'); p = pathlib.Path(f)
    if not p.exists(): continue
    b = p.read_bytes(); bom = b.startswith(b"\xef\xbb\xbf")
    body = b[3:] if bom else b
    if f.lower().endswith(".ps1") and not bom:
        print("无 BOM 的 .ps1:", f, "含非ASCII=", any(x > 127 for x in body))
    if f.lower().endswith(".cmd") and bom:
        print("有 BOM 的 .cmd:", f)
PY
```

2026-09-02 我的读数:7 个 `.ps1` 没有 BOM,其中**只有 `90-ops/lan/lan-firewall.ps1` 含非 ASCII**
(所以只有它今天真的会出问题);没有任何 `.cmd` 带 BOM。★ 这两个数会变,自己跑。

## 5.4 ★ 判据依赖了非 ASCII 字符或 markdown 排版

**症状**:判据在你的终端上好用,换个终端就失灵;
或者你把「已踩 8 次」写成加粗 `**8**`,而判据去数纯文本。

**怎么避开**:判据不要依赖排版,也不要依赖终端编码。

## 6.6 ★ 「自检 PASS 数」有**四种量程**,互相不能比

**症状**:你拿出包形态跑出来的数,去跟开发树的基线比,发现「少了一千多条」,

| 形态 | 怎么跑 | 它测得到什么 |
|---|---|---|
| **fast 层** | `powershell -NoProfile -ExecutionPolicy Bypass -File 90-ops\run-tests.ps1` | 只有 Python 套件 + 契约闸,**不含**任何客户端/管理端断言 |

| **仓库形态自检** | 直接跑 `20-client-win\app\bin\Release\...\localai-client.exe --selftest` | exe 旁边**有源码** ⇒ 结构/接线类断言跑得了。★ **要先 `dotnet build`,`bin/` 不在 git 里** |
| **出包形态自检** | 跑 `dist\client\` 里那个 exe | exe 旁边**没有源码** ⇒ 那批断言**整段不跑**,既不计 PASS 也不计 FAIL、更不计 SKIP |

### ★★★ 三条口径纪律(引它们比讲道理管用)

1. **`FAIL=0` 与「门禁过了」不是一回事。** 门禁可以报 `FAIL=0` 而**退出码是 1** ——

2. **SKIP ≠ 通过。**「这个形态下测不了」与「本该跑得了却没跑成」是两件事,门禁把它们分开印。
3. **跑不了和跑过了必须长得不一样。**

# 第一次收工 / 交回

## 7.1 ★★★ 「跑完了」而 git 里**一条提交都没有**

**症状**:你自己觉得活干完了,报告写得很详细,**数字也是真的**。

**真因**:活躺在工作树里没提交。这在本项目历史上**两天内发生了六次**,
而**六次里没有一次是当事人主动说「我没提交」的**——全都报告「跑完了」。

**怎么避开**:收工判据是**机器判据**,不是自述:

```bash
git status --porcelain | wc -l            # 必须是 0
git rev-list --count main..HEAD           # 必须 > 0(在你自己的分支上)
```

> **两个数不是 `0` 和 `>0` ⇒ 当作没跑完。** 不管报告写得多详细、数字多好看。
>
> ★ 为什么要**在读报告正文之前**跑:报告里那些实跑数字**是真的**——
> 它们就是在那个没提交的工作树里跑出来的。
> **先读正文会让你相信它跑完了,而那与「提交了没有」无关。**

**判词:只有活干完而没提交 = 没干完。**

## 7.2 ★★ 红测回退时把自己的真实改动一起抹掉

**症状**:你为了验护栏改红了一处,验完想还原,`git checkout -- <文件>`,
然后发现**本轮的真实改动也没了**。

**怎么避开**:用**反向编辑**退回去,退完 `git diff --stat` 对一眼。

## 7.3 ★★ 删工作树时把 gitignore 的产物一起删掉

**症状**:`git worktree remove` 说 `dirty=0`,你放心删,`bin/` `obj/` `dist/` 跟着没了。

**真因**:`dirty=0` **不覆盖被 gitignore 的内容**,而 `remove` 不加 `--force` 也会一起删。

**怎么避开**:删之前查一遍:

```bash
git -C <那个工作树> status --porcelain --ignored | wc -l
```

(★ **一行可能代表一整个目录,不等于「会被删掉的文件数」**)。

## 7.4 ★ 工作树的**目录名在说谎**,分支名才算

**症状**:你按目录名去找某条车道,改错了树。

**真因**:目录是按当初开工时的名字建的,后来分支换了。

>
> ⇒ **判词:一张假的欠债表比没有更坏** —— 没有表的人知道自己不知道;
> 而看着一张写着 0 的表的人,**以为自己知道**。

★ 这三条的原文都在 `90-ops/gate/check_decision_numbers.py` 的注释里,可以直接读:

```bash
git log -S"跑不了和跑过了必须长得不一样" --oneline --reverse --date=short --format='%h %ad %s' | head -1
```

★ **这个方法有一个已知的边界**:`git log -S` 找的是「这个字符串的出现次数发生变化」的提交。
如果同一个想法**先以略微不同的措辞**出现过,你会找不到更早的那次。
⇒ 表里的「首次落地」应读作「**这句逐字如此的话**首次进入仓库」,不是「这个想法首次出现」。

### 另外几句同样在用、值得知道的

- **一个承诺了动作的确认框,比没有按钮更坏。**
- **一个不知道自己进度的进度条,是在假装它知道。**
- **摘要与判据分家的时候,红的永远不是摘要。**
- **一条太宽的规矩装不了闸,因为它会天天误报,而误报会训练人绕过它。**
- **判据看得见的,不问它自称是什么。**
