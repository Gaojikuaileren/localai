## 2. 执行顺序

### 第 1 步 · 启动下载(后台) + 装 llama.cpp(前台)

**这是唯一的真正前置。** `P1-thresholds.md` §6 里 llama.cpp 标着 ❌,
而 **A1–A3 / B 组全部 / C1–C3 都依赖它** —— 共 10 项,占 17 项中的绝大多数。

策略:**先试官方预编译版**,能跑就不自己编。
不行再用 `90-ops/devshell.ps1` 自编译(cl 19.38 · nvcc 13.2 · cmake 3.31.6 · ninja 1.12.1)。

**2026-07-26 实况**:release **b10107**(发布于 2026-07-24)提供两个 Windows CUDA 包:

| 包 | 大小 | 判定 |
|---|---|---|
| `llama-b10107-bin-win-cuda-12.4-x64.zip` | 235.6 MB | ❌ **CUDA 12.4 根本不支持 sm_120** —— Blackwell 消费卡要 12.8+ |
| **`llama-b10107-bin-win-cuda-13.3-x64.zip`** | 137.7 MB | ✅ **选它**。另需 `cudart-llama-bin-win-cuda-13.3-x64.zip`(372.9 MB) |

**驱动侧已确认可用**:`nvidia-smi` 报 `CUDA UMD Version: **13.3**`(驱动 610.62)——
恰好够,不需要升驱动。

> ⚠ **含不含 sm_120 仍须实测断言**:包名只说 CUDA 版本,不说编了哪些 arch。
> 装完立刻跑冒烟测试,**看它是真用了 GPU 还是静默回落到 CPU**。
> 这仍是**唯一可能让第 1 步从 10 分钟变成 1 小时**的分叉。
> ⚠ 自编译时记得 `-Xcompiler /utf-8`,否则 C4819 警告刷屏。

**下载工具的一个坑(实测)**:`hf_transfer` 在 huggingface_hub **1.24** 已废弃,
换成了 **Xet** 传输。副作用:`.incomplete` 文件的大小**不反映真实进度**
(看着像卡在 0 字节,实际在下)。判断进度要看目录总大小,不要看单个文件。

### 第 2 步 · 不依赖 llama.cpp 的项 —— ★ 步内必须串行,不能并行

> **★ 这一步原本写成「三项并行」,那是错的。** D1/D2 要跑 ComfyUI(峰值 **11 GiB**),
> 而 A7 是「每 5 秒采 NVML 总量取 P99」——**两者同时跑,A7 的 P99 会被污染成 14 GiB 以上**。
> A7 的产出就是 `desktop_floor`,而它按 §8.1.1 改一次要走**哈希绑定批准**。
> **并行执行必然产出一个废数,而废数的代价很高。**

| 序 | 项 | 谁动手 | 前置断言 |
|---|---|---|---|
| **2a** | ✅ **桌面显存基线的采集方式** | 我 | 无 —— **已于 2026-07-26 实测确定,见下** |
| **2b** | **A7 · 桌面重负载显存上界**(30 分钟窗口) | **你**(见 §4) | ★ **开测前断言:NVML 已用 ≈ 桌面基线,且无任何 AI 侧进程** |
| **2c** | D1 · SDXL 栈峰值 · D2 · 单张出图耗时 | 我 | A7 窗口已结束 |

**2a 的结论(已完成)**:

```
nvidia-smi --query-compute-apps          →  12 个 PID 全部 [N/A]   ← WDDM 确实拿不到逐进程
nvidia-smi memory.used                   →  883 MiB               ← 基准
\GPU Adapter Memory(*)\Dedicated Usage   →  900 MiB   差 1.9%  ✓
\GPU Process Memory(*)\Dedicated Usage   →  1121 MiB  差 27%   高估
\GPU Process Memory(*)\Local Usage       →  501 MiB   差 43%   低估
```

| 用途 | 用什么 |
|---|---|
| **桌面总量基线**(A7 采样 · A1–A4 的增量法) | `nvidia-smi --query-gpu=memory.used` 或 `\GPU Adapter Memory(*)\Dedicated Usage` |
| **逐进程归因**(「谁在吃显存」) | `\GPU Process Memory(*)\Dedicated Usage` —— **只能排序,不能求和**(高估 27%,共享分配被重复计入) |

> **★ A 组其实不需要逐进程归因**:A1 用进程数增量 · A2 用逐个装载的增量 ·
> A3/A4 单独装载 · A7 用 AI 全关时的总量。**NVML 总量就够。**
> 所以原来那条前置卡的是「工具 + 纪律」,不是「归因能力」。
>
> **★ 增量法的成立条件(必须遵守,否则 A2 会漏一个真洞)**:
> 测量窗口内桌面负载不变;窗口前后各记一次基线;**漂移 > 100 MiB 该轮作废**。
> 理由:`speech.lite` 的 ±10% 判据只有 **±0.14 GiB**,而桌面自身抖动区间是 **0.69–1.09 GiB** ——
> 不定这条纪律,测出来的是桌面的抖动,不是组件的显存。

**A7 值得优先做**,因为它决定「日常桌面负载下 AI 侧还剩多少可用」——
这是显存分配的地基数字。真实悬崖是 **3.72 GiB**(= 15.92 − 11.4 − 0.8),不是文档旧写的 4.5。

> ⚠ **不达标时不能靠降 cap** —— cap 按 §8.1.1 不含桌面,降它腾不出一个字节(D24)。
> 唯一有效的动作是**换常驻组成**。

### 第 3 步 · llama.cpp 就位后

顺序按**依赖关系**排,不按编号:

```
A1 每进程 CUDA context
      ↓ (A1 的实测值是 A2/A3/A4 预算表的输入)
A2 daily 常驻峰值  ──┐
A5 ASR+TTS 能否合并 ─┤→ 二者共同决定 A2 是否达标
                     │
B1 KV cache 实测 ────┘
      ↓
B2 prefill 延迟 → C1 daily 吞吐 → C2 端到端首 token
      ↓
A3 deep 峰值 + offload 比例 ⇄ C3 deep 吞吐
      ↑ 这两项任一不达标 → 30B-A3B 出局,改 14B dense
      ↓
B3 长上下文衰减
A4 asset 模式峰值
A8 CPU ASR 实时率 → C4 ASR/TTS 延迟
E5 Vigil CPU 占用
```

**A3 ⇄ C3 是 P1 最可能触发换方案的一对。** v2.1 估的 15.3 GiB 已经超阈值(15.0),
且 offload 比例与速度代价**从未实测**。做好 30B-A3B 出局的心理准备 —— 那不是失败,
那正是 P1 存在的理由。

### 第 4 步 · 填表 + 逐项结论

**P1 验收条件不是「测完」,是「每项都有书面结论」**(接受 / 换方案 / 待议)。
没有结论的实测不算完成 —— 这条是 `AUDIT_v2.0.md` M1 的直接产物。

## 7. ★ 唯一的硬阻塞:语音栈与 VLM 从未选型

**现状**(2026-07-26 全库核实):

```
TTS   —  方案书 2264 行里只有 4 处出现「TTS」,没有一处写用什么实现
         grep piper/kokoro/xtts/coqui/f5/sherpa/melo/vits  →  现行文档零命中
ASR   —  停在 runbook 的「Whisper / Parakeet」,一个带斜杠的二选一
VLM   —  只有「vlm.small 2.5 GiB」这个估算,没有任何模型名
```

**它挡住 17 项里的 4 项**:A2(`speech.full`/`speech.lite`/`vlm.small` 三行)·
**A5 整项**(「ASR+TTS 能否合并」没有两个对象)· C4(TTS 首字节 + WER)· A8(CPU ASR)。
这四项连「⚠ 待议」都写不诚实 —— **待议要求有实测值,而这里是根本没开测**。
P1 验收要的是「所有项都有实测值且每项都有书面结论」,**按现状不可能满足**。

**但它不挡第 1、2 步。** 硬期限是**进第 3 步之前**。

**解法:半小时的联合决策,不是选型定稿。**

> §14 P1 的标题就是「**先于任何选型定稿**」—— 现在做选型定稿会自相矛盾。
> 正确说法是「**指定待测候选**」,登记进本文件 §1 下载表即可,
> **不必抬成 DECISIONS 条目**(§12.1 的门槛是「不易反悔」,而换 TTS 只是重下 1–4 GB,
> 且 A5/C4 的「不达标时」本来就写着「换 ASR/TTS 实现」)。

要定死**四件事**:

| # | 要定什么 | 为什么这么问 |
|---|---|---|
| 1 | **ASR 去掉斜杠定一个**,并写明**推理框架** | A5「能否合并」直接取决于两侧是否同框架(CTranslate2 vs PyTorch vs NeMo) |
| 2 | `speech.full` 的 **TTS 是什么** | 全库零信息 |
| 3 | `speech.lite`(「GPU ASR + CPU TTS」)**两侧各是什么** | WER 对比的可比性取决于 lite 的 ASR 是不是同一模型的小尺寸 |
| 4 | `vlm.small` **是什么** | A2 的一行 |

> **★ 一条硬约束不能漏**:A2 的判据是「实测 vs §8.1.2 估算偏差 ≤ 10%」,
> 所以选到的实现要对得上 `speech.full` 4.0 GiB 权重 · `speech.lite` 0.9 · `vlm.small` 2.5。
> **若体积明显对不上,必须先走 DECISIONS 改 §8.1.2 的估算再测,顺序不能反** ——
> 否则那不是「测出了问题」,是**把估算表测废了**。

**一条合法的退路(只对 VLM 有效)**:界面诚实规则 1 已规定未测行固定显示「估算(P1-A2 未测)」,
所以把 `vlm.small` 从 A2 必测行移出、在 §6 登记为「P1 不测,保持估算」是**合法且不制造不诚实**的。
**但 TTS 没有这条退路** —— A5 与 C4 的一半没它就是零。
