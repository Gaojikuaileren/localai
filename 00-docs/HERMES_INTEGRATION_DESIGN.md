> 编制日期: 2026-08-03 · 依据 **D65**(采纳裁定)
> 状态: **设计定稿,执行推后**。本文件是"怎么接"的规格,不是"要不要接"的评估(那部分已由 D65 结掉)。
> 格式定义: v3.0 §12.1 · 判据与推翻条件是本文件最重要的字段

> ★ **本轮不写任何代码。** 客户端搭建由另一路会话推进,本设计与其无交集(不改 `20-client-win`)。

## 0. 一句话

在 P6 引入一层 **Agent Worker**(当前选定实现 = Hermes,MIT,可替换),
它只负责**规划与 loop**;身份、记忆、权限、审批、执行、回滚、显存**全部留在 LocalAI**。
接法是把它**注册成网关别名表里的一个后端**——对客户端而言它就是一个模型。

### ★ 先澄清两件最容易读错的事

**① 它不取代本地模型 —— 它一个 token 都不产。**
Hermes 没有模型、不带权重、**不占 VRAM**。它的活是「把一件事拆成 N 步 · 记着做到第几步 ·
第 4 步失败了重试」;每一步真要"想"的时候,它**回头问网关**,产 token 的**始终**是我方本地模型
(别名由 capability alias 定,D29)。它自带的 provider 与模型选择在 §5 是明确不采用项。
⇒ **不是「本地模型的替代」,是「本地模型的使唤者」**:同一个模型从一次对话调一次,变成一个任务调 N 次。
显存压力来自这个**使用方式**的变化,不是来自多了一个模型(⇒ DD-9 的租约)。
★ 早期讨论里把它称作"P6 的脑"是**用词不准**——模型才是脑,它是工头。已在 PLAN/DECISIONS 一并改口径。

**② 是外接,不是融入。**
**没有一行 Hermes 的代码进我们的仓库或进程。** 我方新增的只有:一层 adapter(HTTP + 扁平 DTO)、
一份 MCP 服务端、一份配置。Hermes 是独立安装物,钉 commit,跑在隔离环境里,独立进程/运行时/网络栈,
**它崩了不影响主栈**。替换成本 = 改别名表里一个后端 + 重写 adapter。
**绝不 fork、绝不 patch**(沿用 signal-cli 那轮的纪律)——要改行为只能靠配置与 adapter。
唯一的"借鉴"是照 `/learn` 的**流程形状**用我方语言写 DD-6,**停在思路/接口层**
(照 AIRI 报告 §9 那条边界)。

## 1. 为什么是这一层(净账,承 D65)

| | |
|---|---|
| **省下** | agent loop 自研(P6 清单里唯一没有对应交付项的**调度层**)· 技能候选生成流程 · MCP 客户端 |

## 2. 调用链(定稿)

```
客户端(WPF)
   │  只知道一个别名: agent.default          ← 客户端零改动
   ▼
Gateway   身份 · 档位 · 别名路由 · E1 入口闸 · E4 出境闸 · 审计
   │  别名解析到 agent-worker 后端
   ▼
Agent Worker(Hermes · 隔离环境 · 无自带工具 · 无自带记忆)
   │                                   ▲
   │ 工具调用 = MCP over HTTP          │ 它的上游模型回指 Gateway(第二次穿闸)
   ▼                                   │
LocalAI MCP 服务端  ── 按会话挂载的工具池(§6.2)
   ├─ 只读工具 ────────────────────────→ 直接执行
   └─ 有副作用 → ActionManifest → 哈希绑定批准 → ai-exec 执行 → 隔离区 → 回滚
```

**两次穿过网关**是这个设计的核心收益:E1、E4、审计、档位、别名路由**自动全覆盖**,
不需要为 Agent 单独再造一套。代价是必须防环(见 DD-1)。

### ★ 在「两层 MCP」里的定位(承 `decision-packets/two-layer-mcp-decisions-2026-08-03.md` §2)

> **Agent Worker 是【层一的一个驾驶者】,不是第三层。**

它落在层一「谁驾驶」这一维上,与 `assistant.fast` / `assistant.deep` **同层**。三条推论:

1. **工具池受层一禁区逐条约束**:无 `mem.*` · 无 `settings.*` · 无 delete 语义 · 无出网工具 ·
   无 `secret.request` · `ops/**` 与 `{state}/ctl/**` 在硬黑名单里。
2. **绝不触达层二。** 层二入口 `\\.\pipe\LocalAI.Ctl`,其 ACL 拒绝服务账户;
   worker 无论跑在容器还是本机账户,都在被拒之列。**`agent-worker` 在层二没有名字。**
3. ★ **别与 `ext-operator` 搞混,两者方向相反**:`agent-worker` **有**层一工具池(受裁剪)、
   层二无名;`ext-operator` 层一工具池**恒为空集**、层二才有命令面。
   **不可互相复用,不可合并成一档。**

⇒ 本设计**不新开平面,也不改层一禁区表的任何一条**。

## 3. 设计决定(DD-1 … DD-16)

### DD-1 · Hermes 是「模型」,不是「服务」

在网关别名表里它与 `llama-server` 同级,解析为 `agent.default`。
- **防环**:worker 回指网关的请求带 `X-LocalAI-Loop-Depth`,>1 直接拒;
  单次 agent 任务的模型调用次数有硬上限,越线终止并如实报告"没做完",**不静默截断**。
- **不做**:不让客户端直连 worker;worker 不出现在客户端的任何配置里。

**★ 加 `agent.default` 别名时的三条硬接口约束(M0a 已把它们焊进代码,顺序错了网关直接起不来):**

`registry.toml` 的 `local_only`(bool)与 `agent_allow`(数组)**已改为必填**,
且 `agent_allow` 取值必须来自 `gateway.py` 的**封闭表 `KNOWN_AGENTS`** ——
**不许 `"*"`、不许空数组、不许未登记值**,任一违反即 `RegistryError` **拒绝启动**。

1. `[aliases."agent.default"]` 里**必须**补 `local_only` 与 `agent_allow`;
2. **先**把 `"agent-worker"` 加进 `KNOWN_AGENTS`,**再**写 registry —— 顺序反了 = 拒绝启动;
3. DD-4 裁定 `egress=false`,故 `local_only` 取值须与之不互斥(`local_only=true` 与 `egress=true` 互斥,有断言)。

★ **`agent_allow` 绝不得写 `["vigil"]` 或 `["pet"]`** —— 反向全表断言规定
「允许 vigil/pet 的别名有且只有 `assistant.resident`」,写了网关当场拒启动,**这是有意的**(D69)。

★ **可直接照抄的护栏形状**:`assistant.resident` 那条**反向全表断言**
(「不存在任何 `agent_allow` 含 X 且 egress=true 的条目」)——
把 DD-4 的 `egress=false` 从一个**配置字段**升级成一条**结构性断言**,
这样"将来某次先跑通把它翻成 true"就必然表现为**测试变红 + 有 diff + 要留决议**,而不是悄悄发生。

### DD-2 · 工具池由 LocalAI 投喂;Hermes 自带的工具与 MCP 配置一律清空

依据 [§6.2](PROJECT_PLAN_v3.0.md:358)「**按会话挂载工具池,而非运行时判断**」——
低档位会话在建立时其工具池里就**不存在**高风险工具。这条纪律要穿过 worker 边界:
worker **不得拥有自己的工具注册表**,它的全部工具由 LocalAI 在会话建立时通过一个
**会话级 MCP 端点**投喂(token 一次性、随会话失效)。

★ 连带照搬两条:
- [§6.3.1](PROJECT_PLAN_v3.0.md:713) **目标是工具身份的一部分,不是参数**。
  `execute@workstation` 与 `execute@lan-pc-2` 是两个工具。做成参数它就能被不可信计划者操纵。
- `gpu.apply@workstation` **永不进入任何 Agent 工具池**(P4 原条款,一字不改)。

⚠ **这条落不了地则整个方案要改**:若 Hermes 不支持"工具由调用方注入、自带注册表可完全清空",
DD-2 不成立 ⇒ 见 §7 待核实第 3 条。

**★ 与两层 MCP 决议包的两处对接(承 §2.2):**

**① 工具池的权威是 `config/tools.toml`,不是本设计另立的一份。**
D68 规定工具池按 `(subject, device_tier, member_id, workspace)` **静态挂载**——
与 DD-2 的「worker 不得拥有自己的注册表」是**同一条纪律穿过 worker 边界,不是两套机制**。
⇒ `tools.toml` 是**权威**,DD-2 的会话级端点只是**投喂管道**。

**② ★ 传输方式待裁,不得默认。**
本文档 §2 的图画的是 **MCP over HTTP**;而决议包 **D73 裁定层一全链路无 HTTP、走命名管道 + 父子/SID 双校验**。
两者不必然冲突(token 可以走管道),但**若 DD-2 落地成 HTTP,就引入了一条 D73 明令不存在的网络面**。

| 选项 | 含义 |
|---|---|
| **管道**(决议包立场,倾向) | 层一零网络面;与 D73 一致;但 worker 在容器里时跨边界拿管道需另行核实 |
| **HTTP** | 与本文档现图一致、容器天然可达;**但须单独按三通道表新开一行并补齐 fail-closed**,不得沿用"反正在回环" |

★ 这条与 §6 的隔离路线选择**耦合**:选容器(路线 A)则管道跨边界成问题;
选 AppContainer/本机(路线 C/B)则管道自然。**两件事应一并裁定。**

### DD-3 · 调用方身份走 mTLS,不走 PID

D30 现行机制是 **端口→PID→WMI GetOwner**([STATE.md:130](STATE.md:130)),
只在同机进程上成立;worker 一旦进隔离环境(DD-7),流量从虚拟网卡进来,**PID 查不到**。
且现行策略**拒 ai-asset/ai-exec**,顺手用 ai-exec 跑它会被网关直接拒掉。

⇒ 复用 P3b 已建成的 CA,签一张 **`worker` 类客户端证书**;主体类型是新的一档
(不是 device、不是 member)。Edge 注入已验证指纹的那套机制原样复用。

### DD-4 · 新增权限档位 `agent-worker`(不得复用 `trusted-local`)

`trusted-local` 含 **L4 写**与 **S2 读**,给 worker 等于把可执行面和最敏感记忆一起交出去。新增一行:

| 维度 | `agent-worker` | 依据 |
|---|---|---|
| 记忆读 | **非 S2**,且**不含 L4** | 照 [§4.4.3 第 4 条](PROJECT_PLAN_v3.0.md:281):读工作流步骤 = 给攻击者一张可执行面的地图 |
| 记忆写 | **一律 pending**,不得直写 | DD-5 |
| 工具 | 会话挂载的只读集 + **提交 ActionManifest 的能力** | 无直接执行 |
| 凭证 | `secret.request` **不在其工具池** | 照 §3.2 `trade.execute` 先例 |
| 出境 | `egress=false` | 需要外网时由 LocalAI 代理并过 E4 |

★ **铁律套用**:「任何白/黑名单,先问加一个新值默认落哪边」——
新档位在**所有** allowlist 里必须显式落在**拒绝侧**。
这是 P3a 第 10 条缺陷(`caller`/`egress` 裸值 = denylist,新档位默认放行)的直接教训,
本次新增档位是它的第一个真实回归场景。

### DD-5 · 记忆:新增 provenance `agent_worker`,**结构性** forced pending

和 S3 处理 `web_content` 同一手法 —— **BEFORE INSERT 触发器强制 pending**,不是应用层判断。
Hermes 自带 memory 关闭或重定向到临时 scratch,scratch **随会话销毁**。
挡不住它写自己的工作区,但能挡住它的产出进库 —— 这是唯一可执行的边界。

**★ 实测落点(2026-08-03 勘察),两处即可:**

| 侧 | 位置 | 动作 |
|---|---|---|
| Python | `10-core/memory/repo.py:118` `_ALLOWED_PROVENANCE` | 加 `"agent_worker"` |
| SQL | `10-core/memory/schema.sql:22` `CREATE TYPE mem.provenance AS ENUM` | 加同名值 |

校验点共四处会自动生效(`repo.py:144/396/591` + `gate.py:350`),**不需要另加判据**。
★ 方向本来就对:`_ALLOWED_PROVENANCE` 是 **allowlist**,新值默认落**拒绝**侧,符合铁律。

★ **反面教训已有确切修法,照抄即可,别重蹈**:
S3 那条 `pr_derived_forced_pending` 是写成 **CHECK** 的,而
**CHECK 是行级的、INSERT 与 UPDATE 上同样生效** ⇒ 它想说"入队时必须停在待审",
写成的却是"**永远** pending" ⇒ 候选转不到终态 ⇒ 队列清不空 ⇒ 熔断永不恢复 = **永久 DoS**。

修法(`schema-p3a.sql:754-783`)是**拆成两半**:
- CHECK 只保留**与状态无关**的那一半 —— `pr_derived_conf_cap`(置信度封顶);
- 「必须停在待审」改由 **BEFORE INSERT 触发器 `mem.tg_pending_initial_state()`** 强制,**只管入队那一刻**。

⇒ **`agent_worker` 的强制 pending 复用那个已有触发器,绝不新加 CHECK。**

### DD-6 · L4 技能候选七步流水线

```
Hermes 生成候选
 → pending_review
 → 静态检查(依赖 / 命令 / 文件路径 / 网络目标 / 提示注入面)
 → 无密钥沙箱内的确定性测试
 → 固定源码 + 依赖 + 版本哈希
 → 用户批准【具体哈希】
 → 签名后进 L4
任何修改 ⇒ 新哈希 ⇒ 重新批准
```

★ **硬前置**:「批准具体哈希」依赖 [P7 的审批界面](PROJECT_PLAN_v3.0.md:2307)。
在 P7 之前,候选只能积压在 `pending_review`,**不得开任何临时放行通道**。
积压越线沿用 §4.4.2 已有的熔断。

### DD-7 · 隔离是**进程级**,不是账户级

★ Windows 防火墙(WFP)**不过滤回环流量**,账户 ACL 也管不了 TCP ⇒
把 worker 跑成 `ai-exec` **挡不住**它直连 18081,绕开网关与 E1/审计
([STATE.md:405](STATE.md:405) 那条技术债对它默认成立)。

⇒ **WSL2 / Hyper-V 容器,独立网络栈**;出站白名单只有 Gateway 的一个地址+端口,其余默认拒。
挂载:只读输入目录 + 临时可写 scratch。
**不可见**:记忆库 · `{state}/secrets` · `config/*.toml`(`self_protect` 通配)· `{code}/00-docs`(§6.7.4)。

**二选一,不得都不做**:① 容器化隔离,或 ② 先给 `llama-server` 加鉴权。
→ 这是 §6 唯一的待决项。

**★ worker 的网络能力 = 一条连接,别无其它。** 出站白名单只有 Gateway 的地址+端口:
调模型走它、调工具(MCP)也走它。**直连 `llama-server:18081` 不在白名单;自己连云端模型商同样不在。**
需要访问外网时它**只有提议权、没有执行权** —— 由 LocalAI 代理去取,过 **E4 出境闸**、目标须在
`egress_registry` 白名单内;`e4_egress.py` **签名里没有 override 参数**,放行能力在结构上不存在,
worker 无法"说服"网关破例。

★ **无外网顺带挡住的两样,单独记账**(将来若有人为图方便给容器开外网,要知道自己一起丢掉了什么):
① **自动更新与技能包下载** —— DD-10 的"禁自动更新"因此不只是纪律,是物理事实;
② **遥测上报** —— agent 框架普遍默认带遥测,这里被一并断掉。**这是隐私底线,不是加固项。**

★ 与此相对的**真风险在回程**:一旦开 `web.fetch` 类工具,取回的网页内容进 loop
= 本项目最大的提示注入入口,而 **E4 方向 B(响应回程)仍是空的** ⇒ 已钉为 **H2 硬前置**(§4)。

### DD-8 · trace 翻译层是**交付项**,不是可选项

P3a 四门里 **溯源 1.0 是硬线**。loop 的中间步骤发生在 worker 进程内、用它自己的格式。
必须翻译进我方审计模型:每次工具调用记 **会话 · 轮次 · 工具 · 参数哈希 · 结果摘要 · 耗时**;
模型调用本身经网关已自动有记录。

**验收口径**:一次 agent 任务结束后,**能从审计重建完整动作链,不存在"中间发生了什么不知道"的空档**。
做不到这条 ⇒ 四门验收退化,不得进入 H2。

### DD-9 · agent 会话必须持租约,受 P4 仲裁

一次任务 = N 次模型调用,期间与桌宠/同传抢同一块 **8.52**(日常配置 7.99,**只剩 0.53**)。
- 申请租约失败 ⇒ **排队或降级,不抢占**;
- 长任务心跳续租;
- 用户一键中止,与 P6 **全局急停**同一按钮(§12.3:不经确认、AI 不可拦截)。

### DD-10 · 版本纪律:钉 commit · 适配层 · 禁自动更新

全部交互经我方一层 adapter(HTTP 契约 + 扁平 DTO)。
契约**语义贫瘠**——只传扁平 DTO,禁对象图/回调/共享内存(沿用 signal-cli 那轮许可核实带回的习惯)。
升级 = 重跑全套断言 + 一条 D 记账。**生产环境禁自动更新。**

### DD-11 · 开 / 关两态:三档开关 · 开关自身不可被 Agent 触碰 · fail-closed

**先记一条现状**(半年后别忘了为什么要接):**没有 worker 时我方没有任何自我调度能力。**
现有的三样都不是调度 —— §4.7.6 **确定性 L4 白名单**(不经模型,条件到了就响)·
S8 **L4 执行器**(已批准工作流的播放器,且库是空的)· `route.py` **记忆选路**(检索选路,与任务无关)。
连单轮工具调用都还未建(P6 的 MCP 工具池未勾选)。⇒ 关闭态 = 回到"能对话、能按死规则响",**不是降级,是原状**。

**三档,粒度对齐 H1–H3:**

| 档 | 能力 | 前置 |
|---|---|---|
| **0 · 关闭**(默认) | worker 进程不启动 · MCP 端点不监听 · 工具池不挂载 · `agent-worker` 无活动会话 | — |
| **1 · 只读** | 可拆步骤、可读(白名单内 `fs.read` / 非S2非L4 `mem.search`),**无任何副作用** | H2 |
| **2 · 含副作用** | 可提交 ActionManifest → 哈希审批 → `ai-exec` 执行 → 隔离区 → 回滚 | H3(P6 权限区域 + 全局急停) |

**★ 开关自身不进入任何 Agent 工具池** —— 照 `gpu.apply@workstation` 与「档位切换工具不得进入任何
Agent 的工具池」的先例(§12,PLAN 行 1457)。**worker 不能自己把自己打开,也不能给自己升档。**
改档归权限档位管,与"谁能改 GPU 状态"同一套(D37 六元组)。

**fail-closed 与如实告知:**
- worker 不可达 / 证书过期 / 租约申请失败 ⇒ **自动回落普通对话并说明原因,不假装在干活**;
- 运行中关闭 = **全局急停语义**(§12.3:一键中止、不经确认、**AI 不可拦截**);
- 客户端须能看见当前档位与"正在跑第几步",不留看不见的后台活动。

**关闭态的一条结构性好处(外接形态白送):**
关闭 = **进程根本不在**,不是"代码还在里面只是没走那个 if"。
按本项目固定审查视角(「看着有防护、实际没有」)——**这个关闭没有可绕的分支**。
唯一仍然可用的是**已批准并签名的 L4 技能**:它们是独立资产,不依赖 worker 存在。

### DD-12 · 多客户端:**调度集中,执行分布** · 每会话一个短命实例

**只在主机装一个 worker,且应当只有一个。** 理由四条:
① 它不产 token,第二台 PC 装了还是要回主机要模型;
② 装在客户端侧它就成了我方不控制的调用方,绕开 DD-2 的工具池投喂与 DD-3 的身份;
③ 租约仲裁在主机,多实例 = 多个不受 Broker 仲裁的显存需求源,P4 四件套失效;
④ 审计要单一真相源,动作链散在两台机器上就重建不出来(DD-8 验收口径当场破)。

**但"手"每台全功能端都要有 —— 这是 P6 清单里没写的一块。**
照 §6.3.1,`lan-pc-2` 的会话工具池里只挂 `execute@self`,**不存在** `execute@workstation`;
又照 D52,**数据默认只在本机 ⇒ `lan-pc-2` 上的文件主机根本看不见**。
⇒ **ActionManifest 在主机生成,由目标机上的执行器落地**;隔离区与回滚也在目标机本地。

**★ 多成员隔离(风险,须在 H1 前定案):**
Hermes 官方定位是**单租户个人 Agent**,而我方是两名家庭成员 + 多设备 + D45「成员 × 设备」可见范围。
**若其内部状态跨会话共享,A 成员的内容可能漏进 B 成员的会话 —— 这是可见范围事故,不是功能 bug。**

| | 做法 | 判断 |
|---|---|---|
| A | 单实例多会话,证明其内部隔离 | ✗ 等于「信任 Hermes 的实现诚实」—— 正是 S5 缺陷 11(`unseal_for_client` 硬编码 TRUSTED_LOCAL)那个形状 |
| B | **每会话一个短命 worker 实例**(容器起停) | ✅ **推荐**:隔离从"信任实现"变为**结构上不共享**;天然对齐 DD-5「scratch 随会话销毁」 |
| C | 单实例串行 | 简单,但两人同时用即排队 |

推荐 **B**,代价是容器起停延迟(可池化预热)。
**并发本身不需要新机制**:走 P4 已有的多客户端争用四件套(单一权威+副本 · 推送非轮询 · 世代号 ·
预留先于装载)+ D42.6 前台跟随 / 冲突可见。

### DD-13 · 主机管理端的生命周期板块(检测 / 安装 / 更新 / 卸载 / 自检)

**形状复用 VB-CABLE 那一套**(客户端已实现:检测 → 安装 → 更新 → 卸载,安装前官方签名校验),
放在**主机管理端**(D48:仅回环)。差异有三处,都必须照顾到:

**① 版本检测的语义是「是否 = 我方钉定的 commit」,不是「是否最新」。**
面板三行:`已装版本` / `我方钉定版本` / `是否匹配`。
不匹配 ⇒ **拒绝启动 worker 并说清要做什么** —— 与 S2 编码指纹、B10 GPU 指纹**同一 fail-closed 手法**。
★ 上游有新版**不提示升级**(DD-10 禁自动更新);升级 = 一条 D 记账 + 重跑全套断言。

**② 提权分两段(D46 逼出来的)。**
启用 WSL2/Hyper-V 是**系统能力变更 ⇒ 要管理员 ⇒ 可能重启**,而客户端在 Medium 完整性不提权。
- **第一段(一次性)**:引导用户**亲手双击签名的 `.cmd`**(照铸身份那次的做法),面板如实说明"这一步需要管理员,由你运行";
- **第二段(其后全部)**:安装/更新/卸载均在用户态完成,面板一键即可。

**③ 卸载要自证卸干净**(承「每次备份自证可恢复」的习惯)。执行五项并**跑卸载后自检**逐项确认:
容器/发行版删除 · scratch 清空 · **worker 证书吊销**(复用 P3b 已实测的吊销链,吊销后 401)·
MCP 端点停止监听 · 别名表移除条目。
★ **不动两样**:已批准签名的 **L4 技能**(独立资产)与**审计记录**。残留物**进隔离区留证,不直接删**。

**安装物与校验**:**随产品自带、离线部署**(DD-16),不让用户自取。
承 faster-whisper「默认联网拉权重」的教训 —— **构建期预置,运行期不联网**。
仍保留"指定本地安装包"作为备用入口;若从官方源取则**必须校验哈希/签名**(签名形式待核实,见 §7)。

> ★ **口径更正(2026-08-03,D65 补)**:本节初稿写的是「D41 贩卖未裁前不随产品分发,
> 照 signal-cli 先例引导用户自取」——**套错了先例**。signal-cli 那条纪律的根因是
> **AGPLv3 §13 的网络源码义务**;**Hermes 是 MIT**,允许商业使用、修改、集成进闭源产品、
> 再分发与销售,唯一义务是**保留版权与许可声明**。⇒ 自带分发本就允许,见 DD-16。

**★ 清单机制照抄 `AudioDriverManifest.cs`(2026-08-03 勘察),连它挨过的审计一起抄:**

- **可覆盖**:`{state}\agent-worker\manifest.json` 存在就用它,否则用内置 —— 换版本不用重发客户端;
- **★ 但下载来源必须钉死在编译进程序里的域白名单**。理由是那次审计的原话:
  用户清单会**压过**内置清单,而它同时带 `Url` + `Sha256` ⇒ 一个本地明文文件就能把地址改成任意 URL、
  期望哈希改成那份恶意包的哈希(**自证自洽必过校验**),随后提权运行。
  **哈希闸只保证"下的和清单说的一致",挡不住"清单本身被换掉"。**
- **失败不给"仍然继续"**:哈希对不上 ⇒ 当场删除;哈希为空 ⇒ 不允许自动下载,退回"请自备安装包"。
- ★ 那份文件里还留了一条纪律,一并继承:
  **"凭印象写一串十六进制不是默认值,是伪造证据 —— 那比没有更危险。"**

**★ 但信任模型必须换,不能照抄**:VB-CABLE 的把关是 **Authenticode**(官方签名的 exe);
worker 是**容器镜像 / 发行版 tar,没有 Authenticode** ⇒ 必须回到**钉死 SHA-256**。
★ 而 DD-16 的自带分发在这里反而**更严**:产物是**我方构建的**,哈希由构建过程产出、确定可知,
**不需要"从官方域下载"这条链,也没有留空哈希的理由**。

**★ 版本不匹配时的报错形状,照抄 `start-stack.ps1` 的显存闸**:
它对超出实测档的 `-Ctx` **拒绝启动并说清要做什么**(而不是 default 兜底 —— 原写法正是这样被绕过的);
`-Force` 允许强行继续但**打印被绕过的是哪道闸**。worker 版本不匹配照此办理。

**集成度 = 安装后自检(把 H1 最小环复用成验收)**:
起容器 → mTLS 握手 → 别名路由 → 一次**不带工具**的对话 → **审计能重建完整链** → 停容器。
**绿了才允许把 DD-11 的开关从档 0 升到档 1。** 写成断言,进回归口径。

### DD-14 · worker 是**可选依赖**:没有它,主栈必须照常运行

★ **前车之鉴**:07-30 那次 `e4_egress` 事故 —— `gateway.py` 里 import 了一个**没入库**的模块,
`ModuleNotFoundError` 让**整个网关一天起不来**,6 个测试文件里 4 个连收集都过不去。
worker 若被写成硬依赖(写死 import 或启动时连接),它不在时会复现同一个形状。

**★ 好消息(2026-08-03 勘察):这条大半已经免费成立,但有一个必须守住的编码约束。**

**① 「别名后端不在」的降级路径已经存在。**
`start-stack.ps1:133` 的原话:**「其它别名的后端没起(会返回 503 带缺口,这是设计)」**。
⇒ worker 既然是**别名后端**(DD-1),它不在时天然走这条路 —— `agent.default` 返回 503 带缺口,网关照常活着。
★ 这是 DD-1 那个决定的**第三个收益**:E1/E4/审计免费覆盖 · 客户端零改动 · **可选依赖免费成立**。

**② 「模块 import 得动」的断言也已经存在,而且是扫目录的。**
`10-core/gateway/test_imports.py` 扫 `gateway/*.py`(排除 `test_` 与 `__init__`)逐个 `importlib.import_module`。
它正是 07-30 那次事故之后加的,注释写着「**它只做一件事,而且是所有别的测试成立的前提**」;
**刻意不写死清单**,因为「写死的清单迟早会漏掉新加的模块,那正是这次要防的事」。

⇒ **只要 worker 适配层落在 `10-core/gateway/`,这条断言自动覆盖它,不需要新写。**
⇒ 换来的是一条**硬编码约束**:

> **适配层模块必须在 worker 完全不存在时 `import` 得动。**
> 顶层不得 import 任何 worker 侧 SDK 或可选依赖;**连接必须惰性**(调用时才建,不在模块加载期建)。

**仍需守的:**
- 网关**不得**在导入期或启动期依赖 worker 的存在;
- worker 缺失/未安装/已卸载 ⇒ 主栈启动、自检**照常全绿**;
- 客户端侧:agent 入口不显示或置灰并说清原因(DD-11 档 0),**不伪造**;
- ★ 日常启停**不得需要管理员**(`start-stack.ps1:14`「普通终端即可,不需要管理员」)——
  提权只在 DD-13 第一段那次一次性的系统能力启用里发生。

### DD-15 · 与用户自有 Hermes 共存:**不接管、不复用、不改动**

场景真实:Hermes 是流行的开源 Agent,用户完全可能在自己的 PC 上装一份自用。
那一份是**全权限**的(官方安全说明:边界就是运行它的 OS 账户),能读用户文件、能上网、可能带插件。

**六条:**
1. **命名与路径完全分离** —— 我方那个**不叫 Hermes**,叫 `LocalAI Agent Worker`;
   自有容器名/发行版名/数据目录,**绝不使用 Hermes 默认路径**。用户那份不受任何影响。
2. **★ 绝不"发现已有就拿来用"** —— 检测到本机已有 Hermes:**不接管、不复用、不修改**,
   面板只如实显示「检测到一份不属于 LocalAI 的 Hermes,我们不会使用也不会改动它」。
   复用 = 把一个我方**不控版本、不控配置、可能带插件**的实例拉进信任链。
3. **身份是唯一判据,不看端口、不看进程名** —— 我方 worker 凭 mTLS 客户端证书(DD-3)。
   用户那份没有证书 ⇒ **连不上 Gateway**。★ 这是 DD-3 选 mTLS 而非 PID 的又一个收益:
   共存问题被**已有机制**挡住,不需要新防线。
4. **非主机客户端不显示安装按钮**(DD-12:worker 只在主机一个),只显示告知行。
5. **卸载以我方安装台账为准,绝不按名字匹配删除** —— 防止误删用户资产(承"隔离而不删除")。
6. **UI 措辞不出现 "Hermes"** —— 功能来源写「主机上的 Agent Worker」。
   用户不需要知道里面是谁,也就不会混用。

### DD-16 · 自带分发(vendored):用户不装,我们预置 —— 但**形态一个字不改**

**裁定(2026-08-03,用户):走「自带分发」。** 安装包内预置我方构建的 worker,离线部署,
用户**零感知、不需要自取**。

**★ 先把三种「融入」分清楚 —— 采纳的是 A,B/C 明确否决:**

| | 是什么 | 达成"免安装" | 代价 |
|---|---|---|---|
| **A · 自带分发**(采纳) | 安装包预置我方构建物,首次启用一键部署 | ✅ | 近乎为零 |
| **B · fork 源码定制** | 自己维护一个分支 | 无额外收益 | 升级成本失控:上游安全修复要自己 backport;DD-10 的"钉 commit + 适配层"失去意义 |
| **C · 进程内融合** | 编译进主栈 | 无额外收益 | **整套安全设计作废**(见下) |

**C 为什么不能碰(五条,前两条是硬的):**
1. **安全边界当场消失** —— 官方安全说明:边界就是运行它的 OS 账户,进程内代码与主进程同权限。
   融进主栈 ⇒ 它的权限 = 主栈权限 ⇒ 记忆库 / `{state}/secrets` / 模型口全部敞开,**DD-7 整节作废**,
   而 DD-7 是本设计里唯一挡住「提示注入 → RCE」的东西;
2. **「关闭」不再是真关闭** —— DD-11 那条"关闭 = 进程根本不在、没有可绕的分支"退化为
   "代码还在里面只是没走那个 `if`",**正是本项目固定审查视角里的「看着有防护、实际没有」**;
3. **AIRI 的 BLOCKER-2 被请回来** —— D65 能通过而 airi 不能,唯一实质原因就是 HTTP 边界消掉了语言/运行时鸿沟;
4. **多成员隔离没了** —— DD-12 的"每会话一个短命实例"做不到,退回"信任它内部不串"(S5 缺陷 11 的形状);
5. **崩溃传染** —— 从"它崩了不影响主栈"变成"它崩了拖垮主栈"。

**B 为什么不必要:** 我方需要的定制只有四样 —— 清空工具注册表 · 关 memory · 关 plugins/hooks · 锁死 provider。
这四样**应当在配置层可达**(§7 待核实 3、4 正是在验证)。
★ 反过来说:**若这四样只能改源码才关得掉,结论不是"去 fork",而是触发 D65 推翻条件 1
(退回"只借鉴不跑进程")** —— 一个关不干净的东西,fork 出来一样关不干净。

**⇒ 自带分发只改"产物怎么到用户机器上",不改架构:**
worker 仍是**独立进程 · 独立网络栈 · mTLS 身份 · 可一键卸载 · 关闭即不存在**。

**硬前置(唯一一条):**
**依赖树 license checker 必须先跑**(§7 待核实 5)。MIT 只覆盖本体;
若依赖树中出现 **AGPL/GPL** 传染项,则退回"引导用户自取"(照 signal-cli 的真实理由,而非误套)。
按 D41 两台账纪律:**代码许可与权重许可分开记**;保留原版权与 MIT 许可声明是自带分发的唯一义务。

## 6. 待决(须显式裁定,不得默认)

**隔离路线二选一:**

- **A · 容器化**(WSL2 / Hyper-V):worker 拿独立网络栈,出站白名单可真正生效。
  代价:多一层运维;D30 的 PID 身份必然失效 ⇒ DD-3 的 mTLS 变成**必做**。
- **B · 先给 `llama-server` 加鉴权**:直接消掉 [STATE.md:405](STATE.md:405) 那条技术债,
  worker 可留在本机。代价:要动后端启动参数与 `start-stack.ps1`,且**只堵了这一个口**,
  将来任何新增本机后端都要重做一遍。

- **C · AppContainer**(★ 2026-08-03 追加):**AppContainer 默认拒绝回环访问** ——
  这是 Windows 上**不启用 WSL/Hyper-V 也能禁回环**的唯一机制,因而是三条里**唯一零提权**的。
  代价:把一个普通程序投进 AppContainer 需要带安全能力属性创建进程,可行性**待核实**;
  且它只隔离网络与部分对象命名空间,文件侧仍需 ACL 配合。

倾向 **A**,因为它同时解决"将来还会有别的低信任进程"这个类问题;但 B 的收益(消技术债)独立成立,
**两条不冲突,做 A 也应该顺手做 B**。

★ **DD-16 采纳「自带分发」后,这道选择题的权重变了**:用户要消掉的"自己动手",
**一大半其实是启用 WSL2 那一步(要管理员、可能重启),不是装 Hermes 本身**。
⇒ **若路线 C 成立,它同时满足「零提权」与 DD-7 的隔离要求**,应优先核实。
★ 待用户裁定,不默认。

4b. **★ 多会话隔离**(承 DD-12):单实例并发多会话时,状态/记忆/技能是否跨会话共享?
   官方 FAQ 把它定位为**单租户个人 Agent** ⇒ 默认假设"会串",除非取证证明不串。
   证不出来就走 DD-12 选项 B(每会话一实例)——**不赌它诚实**。
4c. 容器起停延迟实测(决定 DD-12 选项 B 是否需要池化预热)。
5. **★ 依赖树 license checker —— DD-16「自带分发」的唯一硬前置**。
   ⚠ **2026-08-03 勘察确认:这不是"待核实",是"未开工"** —— 全仓库不存在任何 SBOM / 许可台账文件,
   AIRI 报告 §10 欠的那份至今没补。要产出一份具体文件(建议 `00-docs/license-ledger.md`),

7. **★ AppContainer 可行性**(§6 路线 C):能否把一个普通程序投进 AppContainer 并**保住"默认拒绝回环"**?
