## 3. 两侧中止怎么实现的 —— 以及**一处对任务书的偏离**

### 3.1 两侧各自**独立**保证自己会停

| | Edge(持有 mTLS 连接) | 网关(真正在 yield chunk) |
|---|---|---|
| 快的那条 | `LiveStreams.AbortAll`,`/admin/devices/revoke` 里同步调用,**~20ms** | —— |
| 一定会发生的那条 | 流里每 1s 复查 `Store.IsActive(fp)` | 流里每 1s 复查 `membership.active_device(fp)` |
| 掐断动作 | 补 SSE error 帧 → `ctx.Abort()` | 补 SSE error 帧 → 结束生成器 → `r.aclose()` |

### 3.2 ★ 偏离:**没有**做「Edge 推一条通知给网关」那条跨进程约定

任务书预留了「中止那条跨进程约定」并要求成对落地。**我没有做它**,理由两条:

1. **推通知会失败**(两个进程;网关可能没起/正在重启)。一旦它是网关侧的唯一通路,
   一次失败就是「Edge 断了、网关还在吐」—— 正是任务书点名要防的**「断了一半」**。
2. **把设备变成非 active 的入口不止管理端那一个**:续签把旧证改 `superseded`
   (`Store.cs:242`)、`SweepStaleProvisioning`(`:203`)、`SweepStaleRenewalCandidates`(`:279`)
   都会,将来还会有新的。「每个入口都记得通知一次」不是设计,是一份会漏的清单。

⇒ 改成**两侧各自复查**,谁也不依赖谁把消息送到。代价:网关侧最坏多吐 1 秒
(而副机那一侧**已经被 Edge 掐了**,所以用户看不见这 1 秒)。

**顺带省掉的**:新路由 `/v1/lan/revoke`、新档位词(`test_local_only_registry.py:247`
钉着分级词表封闭 `{public-minimal, authenticated}`)、以及一条必须做访问控制的新入口
(LAN 设备可经 Edge 代理打到它 ⇒ 互相掐流的 DoS)。

**★ 请协调层裁定**:若仍要那条推送(为把网关侧从 ~1s 压到 ~ms),说一声,我按成对契约补上。
本车道认为不值:用户可感知的那一侧已经是 0 延迟。

### 3.3 中止之后副机收到什么

```
event: error
data: {"error":{"type":"lan_device_revoked","message":"本设备已被【主机】解除授权,这次回答被中途停下 —— 它**没有说完**,…"}}
```

* `type` 两侧**同一个常量字符串**,并有断言去读**对方源码**核对(不是各写一遍);
* 故意含 `revoked` 子串 —— 客户端 `HubClient.LooksRevoked`(`HubClient.cs:710`)按这个子串判"被解除";
* 信封 `{error:{type,message}}` 跟着**真正的消费者** `ChatClient.ParseError` 走,
  与 gpu/sync 那两条推送流的平铺 `{type,message}` **有意不同**,已在两侧注释里写明;
* 话里明说「**没有说完**」+「下一步去主机上重新批准」——
  副机上没有管理端,这是那台机器上唯一能看到的说明。
* **并且掐死连接**(§1 那条补充):不掐的话今天的客户端会把半截答案当成完整答案。

## 4. 任务 2:那条「有意的」注释怎么处置

**技术上能只放行 candidate、挡住 revoked**(`Store.FindByFingerprint` 分得出
candidate / revoked / superseded)。**但不该做**,理由不是麻烦 ——
**它会把今天唯一说对了话的那条路弄坏**:

| | 今天 | 改成握手就拒之后 |
|---|---|---|
| 已吊销副机发起请求 | 握手成功 → `:1584` → **401 `lan_device_unknown`** | 一次 **TLS 失败** |
| 客户端归因 | `LooksRevoked` 命中 | `TlsFailure.Classify` → `_ => null`(`HubClient.cs:794`「判不出来就别猜」)|
| 界面说 | **「本设备已被主机解除,需要重新配对」** | **「连不上」** |

而「连不上」会把人送去查防火墙、改拨号地址、最后**重新配对** ——
**而重新配对会删掉本机私钥**,把一个本可以被主机重新批准的身份亲手销毁。

⇒ **裁定:保持放行,不在 TLS 层查成员表**;把注释补全,写明代价
(「已吊销的也握得上手,靠 `:1584` 每请求复查 + `LiveStreams` 兜住」)与上面这条理由。
留了一句给将来:真要在握手层挡,前提是客户端先有一条能把「握手被拒 = 已被解除」说对的归因
—— 那是 `20-client-win` 的活,不在本车道。

## 5. 判据:红测与「判据能不能为假」

### 5.1 红测(逐条**真的**摘掉跑过)

| 摘掉什么 | 结果 |
|---|---|
| Edge:`live.AbortAll(f)` | **红 1 条** —— `实测 643ms < 200ms` 失败(周期复查兜住了,但延迟肉眼可见) |

| 网关:`gen()` 里的复查 | **红 3 条** —— 流吐满 20/20 块,一帧 error 都没有 |

### 5.2 判据**为什么不是「下一次请求被 401」**

那一半在 V32 之前**本来就成立**。所以判据逐条钉的是:

* **前置**:吊销前这条流真的在流(收到过帧)· 吊销时它还没结束 ——
  少了这两条,「流结束了」可能只是它压根没起来,那样的判据**恒真**;
* **提前结束**:结束于 447ms,而上游跑满要 10000ms —— 把「被掐断」与「跑完了」分开;
* **是异常不是干净流末**:`cleanEnd=False, ex=IOException` —— 这一条钉的是 `ctx.Abort()`,
  它防的是「半截答案冒充完整答案」;
* **两条中止路分开钉**:`< 200ms` 只有登记表做得到(周期复查最快也要几百毫秒),
  否则「把登记表整个摘掉」判据照样绿 —— 那样的判据**测不出登记表在不在**;
* **反向**:放回 active 之后同一条路恢复 200 / 没被吊销的流吐满且**没有**那一帧 ——
  否则全部断言可以靠"这条路一直是断的"变绿;
* **生产复查周期单独钉**(`0 < 值 < 2s`):测试里把它压到 0 才测得动,
  不单独钉的话有人改成 60 秒,上面每一条照样绿。

### 5.3 两处**红过一次**的判据(记一笔,红得对)

1. 「那一帧里有给人看的那句话」按**原始字节**找中文 ⇒ 红。
   根因:`JsonSerializer` 默认把非 ASCII 转义成 `\uXXXX`,而网关侧 `ensure_ascii=False` 不转义。
   ⇒ 判据改成钉**解析出来的形状**(消费者读的是那个),两侧字节不同、解析结果相同。
2. 网关侧那条断言消息写死「只吐了 N 块就停了」,红的时候 N 恰好等于总数,
   打印出「只吐了 20 块就停了,没有跑满 20 块」。⇒ 消息改成两种结果下都读得通。
   一条**红时说不清自己为什么红**的断言,会让人去改一个没坏的东西。
