## 1. ★★ 三条更正(推翻此前记载,含我自己两小时前说错的一条)

### 1.1 `sink` 是**真缺**的,不是已有物改个名

**此前的理解(错的)**:`unseal_for_prompt(t, *, backend: Backend)` 里 `backend.egress` 已经
实现了 D39 要的 `sink` 语义,所以 D39 「有一半已经做掉了」。

**实际**:**这是两根轴。**

| | 说的是什么 | 谁在管 |
|---|---|---|
| `Backend.egress` | **请求发给哪个模型** | `tainted.py:331`(已实现) |
| D39 的 `sink` | **答案最终发到哪儿** | **没有任何代码有这个概念** |

**具体失效路径**(这条必须写下来,否则还会有人重复这个误判):

```
Signal/WhatsApp 桥  → 调用别名 assistant.fast(egress=false,本地 llama-server)
                    → unseal_for_prompt 干净放行(backend.egress 为假)
                    → 记忆正文进 prompt
                    → 模型复述
                    → 答案顺着通道出去
```

全程 `tainted.py:331` 那道闸**一次都没被触发**。⇒ D39 与 PLAN P3d 字面要的那个
**必填 `sink` 参数,是真的还没有**。

### 1.2 `channel-relay` 档位**造不出来**

`classify_caller`(`gateway.py:384-398`)只能返回五个值:
`remote-unauthenticated` / `denied-account` / `lan-edge` / `trusted-local` / `unregistered-local`。

`channel-relay` 只存在于:注释(`:377`、`:556`)· 一个测试的 monkeypatch(`test_gateway_e1.py:133`)·
记忆模块的枚举(`tainted.py:222`)。

⇒ **今天真接一个桥上来,它落 `unregistered-local`** —— 而那个档位按 D30「降档不断连」的裁定
**照样能走 chat、照样拿流式**,并且与"一个没人登记的普通账户"**不可区分**。

★ 附带发现:网关的档位词表(裸字符串)与 `tainted.CallerTier` 是**两个不同的集合**,
没有映射函数,也没有断言要求 `classify_caller` 的每个返回值都能落到某个 `CallerTier`。

### 1.3 响应扫描器**永远守不住记忆**,不得声称它守得住

「外联通道只允许 S0」「最小披露」是**什么进了 prompt** 的性质。
一条记忆被模型**复述**之后,没有任何正则特征 —— 扫描器认不出来。

**真正的结构性强制已经写在 PLAN §4.6.3**:**出境 sink 的会话不该挂载 `memory.search`**。

⇒ **方向 B 的正确定位:凭证线 + 审计线的第二道防线。**
**不得**在任何文档里把它写成「L5 的代码对应物」——那会造成一个假的安全感,
而假的安全感正是本项目固定审查视角里最贵的那种缺陷。

## 2. ★ 两条实测约束(我复测过,不是转述)

### 2.1 扫整个响应体 = **100% 全拦**

```
chatcmpl-ujOeHwdFcAefAZhnM6Jy8c1rihtYlKNx  ->  ['high_entropy']  blocked=True
整个响应体(含该 id)                        ->  ['high_entropy']  blocked=True
只扫 choices[].message.content              ->  []               blocked=False
```

OpenAI 响应的 `id` 是 32 位随机串,**单独就够触发高熵检测**。

⇒ **闸门只能扫"生成内容",不能扫协议信封。** 而"只扫 content"是 **denylist 形状**
(新增一个上游字段默认不扫)—— 所以**必须配一条反向断言**:明确登记哪些字段算"答案",
新增字段默认落被扫一侧或**拒绝启动**。这条不写,方向 B 一上来就带着本项目最恨的那个形状。

★ 更狠的后果:naive 实现会让**每一条回答都被拦**,而当值的人多半会去"修"它 ——
**修法几乎必然是把闸门调松**。这就是为什么这条要写在决议里,而不是留给实现者现场发现。

### 2.2 扫原始 SSE 字节 = **对转义内容瞎**

```
明文卡号                          -> ['card_pan']  blocked=True
全角卡号(解码后)                 -> ['card_pan']  blocked=True
全角卡号(\uXXXX 转义,SSE 帧形态) -> []           blocked=False   ← 漏
```

`e1_detector.normalize()` 折全角、折中文数字,**但不处理 `\uXXXX`** ——
而 `json.dumps` 默认 `ensure_ascii=True`,那正是模型输出到达时的形态。

⇒ **必须先 JSON 解码再扫。** 扫原始帧的闸门**看着在工作,实际漏**。

★ **澄清(一度误判,已更正)**:这条**不是**请求侧的活洞。请求 body 先被 `request.json()` 解码,
E1 拿到的是已解码文本,照样抓到。**它只在方向 B 新写的"扫原始帧"代码里才成立。**

## 3. 用户裁定(2026-08-04)

| # | 裁定 | 依据 |
|---|---|---|
| 1 | **出境 sink 不走流式,发一整段** | 已发出的 chunk 收不回;闸门要能拦,前提是内容还在手里 |
| 2 | **PC 端(局域网客户端)照旧流式** | 它在受控设备集内,不是出境 sink;今天零影响 |
| 3 | **向手机发送要限制回复长度** | 聊天软件有单条消息长度上限 |

**对第 3 条的落法(本包主张,待确认)**:
- 上限**长在通道契约上**(`ChannelCapabilities`,挨着 `operator_can_read_content`),
  **不是常量、不是配置文件** —— 与 D39「不靠配置、不靠文案、不靠权限表」同一条;
- **缺字段 fail-closed**:照 `load_registry` 的形状**拒绝启动**,绝不默认"不限";
- **两层**:请求侧按上限换算 `max_tokens`(**省事,不是保证**)+ 闸门侧强制裁剪(**保证**)。
  只做第一层等于"叫模型少说点",那是请求不是约束;
- **顺序写死**:`完整回答 → 闸门看全文判过/拦 → (放行了才)按上限裁剪/分条`。
  **不得**变成"前 N 字扫着干净就先发" —— 那是部分泄漏;
- **截断不静默**:裁了必须说,并给补救路径;
- **定位**:闸门 = 安全;限长 = 体验与通道兼容。**两件事不许混**。

★ 一条重要澄清:**「不给流式」≠「必须一条巨长消息」**。闸门看完整段之后,
按段落拆成几条发是自由的 —— 关键性质是**闸门在任何东西离开之前看到了全文**。

## 4. 设计评审结果:三路都不能直接开工

| 设计 | 分 | would_ship | 最强反对 |
|---|---|---|---|
| `sink-typed` | **45**/60 | ✅ | 「无绕过」在它自己改的函数里就不成立:闸门插在 happy path,而 502/503/回显三条邻居路径未设防 |
| `minimal-hook` | 43/60 | ❌ | 闸门按 OS 账户判 sink,而**未登记账户落放行侧** —— D30 刚从 `classify_caller` 铲掉的形状,在新轴上又长一遍;**而桥恰恰就是个新账户** |
| `streaming-first` | 35/60 | ❌ | 其核心断言是**假断言**:它在两个目标 sink 上会 100% 全拦(即 §2.1),而测试用的是简化信封,照不出来 |

**共同必修项**(任何一路开工前都要先解决):
1. sink 解析之后的**每一条** return 都要覆盖,不能只管 happy path;
2. `stream` 是**调用方控制的**(`gateway.py:667`)—— 只在非流式分支设闸,桥设 `stream:true` 即绕过
   ⇒ **必须能强制 `stream=False`**(正对应 §3 裁定 1);
3. 账户轴的默认必须翻到 fail-closed 侧(见 §6 待裁 1);
4. `operator_can_read_content` 必须真的进入闸门判据 —— 否则 Signal(D39:**不算出境**)
   与 WhatsApp(**算出境**)会被一视同仁,那是 D39 的正确性失败。

## 6. 待裁(不得默认)

1. **`unregistered-local` 是出境 sink 还是本地 sink?**
   今天当本地、给全量 chat。fail-closed 的答案是**降为出境 sink**,
   但那会改变本机上**每一个**未登记账户的行为(含机主可能的第二账户 `Alle`)。
   ⇒ **必须显式裁定,不能靠默认。**
2. **`unseal_for_prompt` 要不要真的加 `sink` 参数**,还是 sink 只留在网关?
   迁移成本有界(约 10 个调用点,**全在测试里**),所以争的是**不变式该放在哪一层**,不是成本。
3. **拦下时调用方收到什么**:D38 固定模板 / `content_filter` 轮次 / 硬错误?
4. **「答案」的字段边界**:只算 `choices[].message.content`,还是也算 `tool_calls.function.arguments`、
   `reasoning_content`?(§2.1 决定了不能全扫,所以这个边界必须显式登记 + 反向断言。)
5. **方向 B 到底解锁了哪几条线**:STATE 声称它解锁三条(P3d / Hermes H2 / 桌宠)。
   但 Hermes H2 要防的是**不可信抓取文本回流进 loop**,那是**另一个问题**,
   凭证扫描器解决不了。⇒ **「一次解锁三处」这个说法需要复核**,可能只解锁一条半。

## 7. ★ 系统性问题:没有 CI,断言只有人记得跑才会红

`.githooks/pre-commit` 只 grep 绝对路径。`90-ops/` 下**没有任何东西**会跑网关或记忆的测试。

⇒ 一条没人跑的断言,**按本项目自己的标准就是假断言**。
方向 B 会新增一批安全断言,而它们出生时就处在这个状态。

**主张:把"一键跑全部套件"作为方向 B 的前置交付,而不是之后再补。**
(今天已顺手实证:11 个网关测试文件可以用一个循环跑完并汇总,251 PASS / 0 FAIL ——
说明这件事的成本很低,缺的只是有人把它固化下来。)
