## 1. 任务 1 · 自配对在开机自动起栈这条路上不可达

### 1.1 复核:链条逐环量过(★ 协调层没量的那一环在这里)

```
App.xaml.cs:414          decision.MayStartStack ⇒ HostSetup.EnsureStackAsync()   ← 起栈唯一入口
HostSetup.cs:448           → EnsureEdgeAsync()
HostSetup.cs:502             → Arguments = "run"
lan-edge/Program.cs:28       "run" => await Run()
lan-edge/Program.cs:545        Edge.Build(new EdgeConfig(idDir, secDir, "http://127.0.0.1:8080", 8443))
                               ^^^ 位置参数到 ListenPort 为止 —— **AdminPort 没传**
lan-edge/Program.cs:1206     record EdgeConfig(..., int AdminPort = 0, ...)      ← 默认 0
lan-edge/Program.cs:1286     if (cfg.AdminPort > 0) k.Listen(IPAddress.Loopback, cfg.AdminPort);
                               ^^^ 前件为假 ⇒ **8442 一次都没绑**
```

对照:`RunLan()`(:236)在 :283-285 显式写 `const int AdminPort = 8442;` 并传进去。
⇒ **管理面只在 `run-lan` 那条路上存在。** `HubAdmin.cs:75-79` 的注释其实早就写着
「`run-lan` 用 8442」—— 这份知识在仓库里,只是起栈那一行没有用上。

于是客户端侧:

```
DevicesView.cs:167  admin.ProbeAsync(...)                → 连不上 8442
DevicesView.cs:169  LastProbe != Ok && HostToolsDir()!=null → HostRole.HostHubDown
DevicesView.cs:142-143  case HostHubDown: 只 Add(HubDownCard())
DevicesView.cs:792  SelfPairAsync 的**唯一**调用点在 HostSelfCard() 里
DevicesView.cs:139  而 HostSelfCard() 只在 case HostRole.Host 下渲染
⇒ SelfPairAsync 结构上永不触发。
```

**用户 2026-08-07 的裁定「主机上的客户端也需要自配对」,在这条路上今天做不到。**

### 1.2 ★ 转述漏掉的第二道闸(只补管理面是不通的)

`Run()` 建 EdgeConfig 时也没传 `Bind` ⇒ :1269 `k.Listen(cfg.Bind ?? IPAddress.Loopback, 8443)`
⇒ **业务口只在回环上**。而 `SelfPairAsync` 拿 dial 靠 `DiscoverEdgeDialsAsync`
(`HubAdmin.cs:529`),它 `foreach (var ip in LocalIPv4())`,而 `LocalIPv4()`(:597)
在 :606 **明确跳过回环网卡**。

⇒ 就算把 `AdminPort: 8442` 补进 `Run()`,自配对也只会往前挪一格,停在
`dials.Count == 0` 那句「本机就是主机…但本机当前的网卡地址上都没人在 8443 上听」。

**两道闸,补一道不通。** 这就是为什么修法不是「给 `Run()` 补个 AdminPort」。

### 1.3 ★ 修法与理由:改用 `run-lan <ip>` —— 并且这**不**违反 D48

任务书写「直接改成 `run-lan` 会把管理面推上局域网,那会违反 D48」。**量过之后:不会。**

- D48 管的是**管理面**。`run-lan` 里管理面走的是 `Program.cs:1287`
  `k.Listen(IPAddress.Loopback, cfg.AdminPort)` —— **回环是写死的**,没有任何参数能把它挪走;
  外加 :1370-1373 的 `IsAdmin()` 双保险(既查端口、又查远端必须是回环)。
  `run-lan` 放上网卡的是**业务口 8443**,而那本来就是它该在的地方(mTLS,副机就靠它连)。
- **「绑上」≠「够得着」**。防火墙那一步(`EnsureFirewallAsync`)本车道一行没碰。
  规则不在时 Windows 默认入站阻止让 8443 对局域网**仍然不可达** ——
  这正是 `lan-edge` 自己在 `RunLan` 上方(:233-235)写的那句话。
  真正把门打开的仍然是用户点的那次系统授权框。
- **实测**(本机,2026-08-07):不加任何规则,把一个监听绑到网卡地址 192.168.178.61 上,
  再从本机连它 —— **连得通**。⇒ 本机客户端够得着自己的业务口,而局域网够不着。
  这正是自配对需要的那个形状。
  (★ 诚实标注:本机已存在 `LocalAI-LAN-Edge` 规则,但它是**按程序**授权的,
  与实验里那个 PowerShell 监听、那个端口都无关,所以这次观测仍然成立。)
- 顺带把 §0-B 那个洞一起堵上:`run-lan` 传 `OpenPairingWindowOnStart: false`。
  自配对不受影响 —— `SelfPairAsync` 自己开一个 **1 分钟**的窗口,用完就关。

### 1.4 ★ 绑哪个地址:问内核,不猜(`PickBindIp`)

`run-lan` 要一个 IP。**不许随手挑**:挑错会把一个连不上的地址写进配对档案,
那比"没起来"难查得多。三档:

1. 问内核按路由表选出的出网源地址(UDP `Connect` 到 `192.0.2.1`,RFC 5737 文档保留地址
   —— **不发任何包**,只做一次源地址选择)。必须落在 `LocalIPv4List()` 里才采信。
2. 拿不到(纯隔离网段没有默认路由)且只有一张网卡 ⇒ 用它。
3. 多个候选而路由表没答案 ⇒ **停在这一步**,如实报出候选清单,让用户去「设备」页选网卡。

**★ 明确不做的事:选不出来时【不退回 `run`】。** 退回去会"成功",
而那个成功正是这次要消灭的东西。

**实测本机**:两张网卡(`192.168.56.1` VirtualBox host-only、`192.168.178.61` 真 LAN),
`PickBindIp` 选出 **192.168.178.61** —— 与当前真在跑的中枢绑的地址**一致**。
★ 值得记一笔:一个「只有一张网卡才用」的简单规则在这台机器上**会失败**(有两张),
而路由表那一问答对了。

### 1.5 ★ 判据本身也是错的:`EdgeUpAsync` 探了一个不承重的口

原 `EdgeUpAsync` 探 `127.0.0.1:8443`。而 `run` 模式下那个口**确实开着** ⇒
起栈报「已起并探到 8443」,界面一路绿灯 —— 可客户端接下来要用的两样东西一样都没有。
**「起栈成功」与「客户端根本用不了」长得一模一样。**

⇒ 判据改成探**回环管理面**(`127.0.0.1:AdminPort`)。它在两种模式下都只绑回环,
它答话 = 角色判得出来 = 自配对够得着 —— 那才是我们需要它回答的问题。

### 1.6 验收(实测,2026-08-07)

本机当时**正跑着**一个 `run-lan` 模式的中枢(PID 15664:8442 回环 + 8443@192.168.178.61)
—— 那正是本次修改会产生的形状。**没有动它**(不杀用户在跑的中枢),直接对它量两道闸:

| 闸 | 判据 | 实测 |
|---|---|---|
| ① | `GET http://127.0.0.1:8442/admin/ping` | `200` · `{"ok":true,"hubId":"d1218f2f-…","pairingWindowOpen":false,"serverCert":{…}}` —— 字段与 `ParsePing` 期望一致 ⇒ `LastProbe = Ok` ⇒ **`HostRole.Host`**(不是 `HostHubDown`)⇒ 渲染 `HostSelfCard` ⇒ **`SelfPairAsync` 被调用** |
| ② | 逐张网卡探 8443(与 `DiscoverEdgeDialsAsync` 同口径,跳过回环) | 网卡 `192.168.56.1`、`192.168.178.61`;应答的只有 `192.168.178.61` ⇒ **`dials.Count == 1`** ⇒ 过 dials 闸,继续走开窗 → enroll → 自批准 |

⇒ **自配对真的走得到,不停在 `HubDownCard`。**

**★ 诚实标注没做的部分**:没有做「杀掉中枢 → 冷启动客户端 GUI → 肉眼看它自己跑完」
那一遍。理由:那要停掉用户正在用的中枢,而且我这边的进程是**提权**的
(TPM/CNG 用户密钥绑定铸造时的完整性等级 —— 由我拉起 lan-edge 可能撞出 exit 3,
那是环境噪音不是本次改动的性质)。上面两道闸是这条链上**仅有的**两个会挡住它的地方,
两道都实测过了;其余(开窗 → enroll → 自批准)是既有的、已被断言覆盖的路径。

### 1.7 钉住(断言,含红测)

客户端自检新增 4 条,**全部红测过**(把两处改回改动前的形状 ⇒ 4 条同时红):

- **行为**:管理口上有人听 ⇒ `EdgeUpAsync` 说起来了;把它停掉、别的口照样听着 ⇒ 说没起来。
  (★ 端口**先绑住再读号**,不许"读一个空闲号→放掉→再绑回去" ——
  那中间有一段谁都能抢走的窗口,**实测撞过一次假红**,已改成确定性写法,连跑 3 遍绿。)
- **行为**:`PickBindIp` 要么给出一个**本机真有**的网卡地址,要么说得出为什么没有;
  **绝不能返回回环**(那是 §1.2 那道闸)。
- **结构**:`EnsureEdgeAsync` 里必须有 `"run-lan "`,且那个光秃秃的 `Arguments = "run"` 不许再出现;
  且必须有 `RedirectStandardInput = true`(§4.1 那条 —— 换成 `run-lan` 之后**才**承重)。
  ★ 如实标注这是**结构判据**:要变成行为判据就得在自检里真起一个中枢(要身份、要证书、要端口),
  那不是自检该做的事。

> ### ★★ 这里踩了一个坑,记下来
> 结构判据第一版写成 `Assert(slice is not null && …)`。在仓库里跑是绿的
> (源码就在旁边),而 `build-client.ps1` 的**「发布产物原位自检」**那一趟
> ——出厂产物旁边没有源码 ——`TryReadSource` 返回 null ⇒ **三条同时红,而且挡住了出包**。
> 本文件其它源码判据用的都是 `var src = TryReadSource(...); if (src is not null) { … }`
> (读不到就**跳过**,不判红),我没跟上那个形状。已改齐。
> ⇒ **教训**:源码判据有两种运行环境(仓库 / 出厂产物),写的时候要两种都想到。
> 那条「源码根在旁边时不得有读不到的」的元断言管的是**另一件事**(源码根在却读不到),
> 它不会替你兜住"源码根不在"。

### 2.4 钉住(断言,含红测)

### 2.5 ★★★ 波及面:`test_gpu_broker.py` 里有四处踩在旧行为上(**这条差点漏掉**)

改完 `gpu_policy.py` 之后 `test_gpu_policy.py` 是绿的,而**门禁红在另一个文件**上

### 2.6 ★★★ 一个必须写下来的副作用:B6 那道闸今天**够不着了**

`gpu_intended` 的判定顺序是 ① `read` 档 → ② 按 `components` 解出动作再判
→ ③ **带了 `permitted_on_demand` 才判 B6 那道闸**。副机现在在 ② 就被拦住,
根本走不到 ③。而档位表里**只有 `trusted-local` 有 `change_resident`,它同时也有
`permit_on_demand`** ⇒ **今天没有任何档位能走到 B6 那道闸。**

**不删它**:它从"唯一那道闸"降级成**纵深防御的第二层**。哪天有人加一个
「能改驻留、但不能签按需授权」的新档位,它会立刻重新承重。
⇒ 但断言要跟着改:B6 那条只钉【工具】维 + 【动作被点名】,
**不再钉死是哪一个动作** —— 钉死就是把"今天恰好在哪一层拒的"焊进断言里(第 9 条坑)。

## 4. 顺带那条(审计 B 级):起栈进程的输出没有落点 —— **做了**

原打算只捡退出码(见 §4.2),但在动手时发现:**不重定向 stdin 会出真事故**,
而一旦要重定向 stdin,重定向 stdout/stderr 就是顺路的,于是整条都做了。

### 4.1 ★★ 先说那个差点踩进去的坑:`run` 没有 REPL,`run-lan` 有

`Run()`(:540)是 `await app.RunAsync()`,**没有命令台**。而 `RunLan` 末尾有一个
`list / approve / open / quit` 的 REPL,它 `Console.ReadLine()` 读到 null 就 `break`
⇒ **中枢打完「已监听」当场退出**(Program.cs 里那段注释写着 2026-08-04 实测撞过)。
中枢那边为此加了「`Console.IsInputRedirected` ⇒ 不进 REPL,安静地一直跑」,
而**那句判据只有在调用方真的重定向了 stdin 时才为真**。

⇒ 把 `run` 换成 `run-lan` 而不补 `RedirectStandardInput`,换来的会是一个
「起来了、几秒后自己没了」的中枢 —— 比原来的病更难查。**已补。**

### 4.2 落点

`RedirectStandardOutput/Error` + 一个 `StreamWriter` 抽干管道,写进
`%TEMP%\localai-edge.log` —— **与 `Views/DevicesView.StartEdgeAsync` 同一个文件**
(两条起栈路径写两个日志的话,人找错文件会得出"它什么都没说"的结论)。
`Process` 存进静态字段:管道一旦重定向就必须有人一直抽,不抽,子进程写满
约 4 KiB 缓冲就卡死;把 Process 留住,读取回调才活着。
日志**写不了不算起栈失败** —— 中枢已经起来了,别因为记不了账就说它没起。

另外把退出码也捡回来了(`ExitNote`):`lan-edge` 已经把「没身份 / 用法错 /
密钥打不开 / 端口被占」编进 1/2/3/4,那份信号原来被整个丢掉。
**没登记的码如实说不认识** —— 给一句自信而错误的原因比不给还坏。

### 4.3 ★ 这套做法自带的一个风险,如实记

客户端退出时管道读端关闭,中枢再往 stdout 写会拿到 broken pipe。
`RunLan` 起来之后只在证书轮换(一天一跳)和有新配对请求时才写,窗口很小;
而且这**正是 `DevicesView` 今天已经在跑的做法**(逐字对齐,不引入第三套口径)。
真要根治得让中枢自己写文件、或套一层 `cmd /s /c "… >> log 2>&1"`(文件句柄与
客户端生命周期无关)—— 后者多一个进程,且 `Process.Start` 返回的就不再是 Edge 本身,
将来任何「Edge 还活着吗」的判断都会问错对象。**留给专门一次改动。**
