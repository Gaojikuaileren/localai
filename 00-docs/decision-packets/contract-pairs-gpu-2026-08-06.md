## 2. ★★★ 三处在还债过程中被当场抓出来的缺陷

### 2.1 `LeaseKeeper` 的 `generation` 有个默认值 0 —— 一次解析失败会**稳定伪装成「中枢忙」**

```csharp
// 原文
gen = d.RootElement.TryGetProperty("generation", out var g) ? g.GetInt64() : 0;
```

读不到就悄悄用 **0**。而 0 几乎必然与中枢的世代号对不上 ⇒ 每次申请租约都回
**409 `generation_conflict`**,客户端把它记成「申请租约被拒(409)」。

★ **两件事的下一步完全相反**:
读不出 `generation` 要去**对契约**;409 要去**重取快照再试**。
而 409 的字面意思是「你看到的状态已经不是最新的了(别处刚改过)」——
**一个指向别处的假理由**。照它去查,会去查中枢的并发,而那里什么都没有。

⇒ 改成 `TryParseGeneration`(**无默认值**,类型也要对:`"42"` 与 `42` 是两回事),
失败时给一条**理由完全不同**的消息,并明写「别去重试:重试每次都会得到同一个 409」。
★ 这就是任务书说的「断言要能把两者分开」的落点。

### 2.2 SSE 的 `error` 帧被当成快照解析 —— 中枢把原因说了,客户端翻译成了一句猜测

服务端那半写着「推送流崩了要**说出来**,不能静默断开」,发的是
`event: error` + `{"type","message"}`。而客户端**只看 `data:`**:那一帧拿去 `TryParseSnapshot`
必然失败 ⇒ 被记成「中枢发来的帧读不懂(客户端与中枢版本可能对不上)」。

★ 不是没收到,是**收到了却读错了它的种类**;而错的那句话会把人支去对版本。
⇒ 客户端现在记住 `event:` 那一行,`error` 帧走单独路径,理由用**中枢给的那一句**。
★ 中枢没说清楚时返回 null 并显示「(它没说原因)」—— **不替它编一个**。

### 2.3 `HubGpu.ParseOutcome` 的注释与代码**说反了**

注释写着「解析不出来**不能**当成成功」,而代码在 200 时**恰恰当成了成功**。
照着注释写断言,当场变红。

**代码是对的,注释错了。** 真正的规则是两句,而且第二句**依赖服务端那一半**:
① 响应体读不懂 ⇒ HTTP 状态是唯一还可信的东西;
② 而信它之所以安全,是因为服务端钉死了「事务没成 **不得回 200**」。

★ 这正是成对断言的意义:**客户端这条回落的正确性来自另一侧的约束**,
单看这一侧永远说不清它对不对。⇒ 注释已更正并写明它依赖哪一侧;
断言拆成两条(非 200 且读不懂 ⇒ 不 Ok + 可分辨的码;200 且读不懂 ⇒ 仍按成功算,并写明为什么)。

## 6. 一处**方法**上的记账:SSE 不能用 TestClient 读

第一版把 `CONTRACT:gpu.events.frame` 的服务端半边写成
`with _c.stream("GET", "/v1/gpu/events") …` 读第一帧就 `break` ——
**整个套件挂住,120 秒后被超时杀掉**。

根因:那条流**永不结束**。退出 `with` 时要关连接,而服务端那个生成器正 `await` 在
`wait_for_change` 上,TestClient 的 portal 等它收尾 —— 两边互相等。

★ 与 `ASSERTION-PITFALLS` 第 6 条**同源但不是同一条**:
那条说的是**跨连接**推送(两个 TestClient 各起一个事件循环);这条是**单连接的无限流**。

⇒ 改成直接驱动 `gateway.gpu_events` 那个**真的**异步生成器,只 `__anext__` 一次。
它仍然在测真实现(第一帧在 `is_disconnected()` 之前就 yield 出来,不需要任何连接语义)。
★ 建议把这条补进 `ASSERTION-PITFALLS` 第 6 条作为第二种形态 —— **本车道没改那份文档**(中央四文档)。
