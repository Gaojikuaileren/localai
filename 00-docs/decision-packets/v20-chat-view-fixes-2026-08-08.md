## ① 流式增量整块重建会话面板 —— 用户实测「每次生成都先跳到顶端再拉回底部」

### 根因(两个,是**两件事**)

`SendCurrent()` 的 `onTick` 接的是 `BuildConversation`,而它 `_conv.Content = BuildConvPanel(…)`
——**每来一段增量就把整块面板换掉**。于是:

1. **偏移归零**:新面板里的 `ScrollViewer` 是另一个对象,偏移天生是 0;
2. **每个 token 重建 N 个气泡**:一条 200 条消息的热层会话,每个 token 重建 200 个气泡
   外加一个新 `TextBox`(还要把焦点还回去)。会话越长越卡,与用户描述一致。

★ 而"归零"能被**看见**,还有第三层原因,它自己就值一条 WPF 坑(已记为 WPF-PITFALLS 第 14 条):
`DockWithInput` 把 `ScrollToEnd()` 排进 `DispatcherPriority.Loaded`,而
**`Loaded`(6) 比 `Render`(7) 更低** ⇒ "偏移还是 0"的那一帧**真的会被画出去**,
下一帧才跳到底。排到 `Loaded` 本是为了等布局算完 —— 代价恰恰是多画一帧。

### 裁定 ①.1 流式增量走「只改那一条正文」的快路径

判据是**结构变了没有**:
* 只是某条消息的正文在长 → 只改那一条的 `Text`,一个面板都不换;
* 新增/删除消息 · 换会话 · 跨过折叠阈值(要长出「展开全部」按钮)→ 照旧整块重建。

★ 「拿不准就整块重建」是**有意的偏向**:快路径的正确性判据是
**它画出来的东西与整块重建一模一样**,做不到就别走。
★ `Bubble()` 对流式那一条**即使正文还是空的也建控件** —— 否则第一段增量到达时
要长出一个 `TextBox` = 结构变了 = 重建,第一帧照旧闪一下。

### 裁定 ①.2 定位改成**同步**的,而且不贴底就**不拽人**

* 挂上 `_conv.Content` 之后在**同一次调用内** `UpdateLayout()` 再定位 —— 不留那一帧;
* 重建之前用户**没贴在底**(他滚上去看前文)⇒ 把偏移**还回原处**,不要 `ScrollToEnd`。
  ★ 这是顺带修掉的第二个缺陷:原先无条件 `ScrollToEnd`,生成期间往上翻会被每帧拽回去
  —— 等于生成期间根本没法看前文。

### 验收(**能为假**,不是人眼判据)

`client --selftest` 里造一条 60 条消息的真会话、真排版、走 `ChatCenter` 的流式原语
喂 40 段增量、走 `ChatView.OnStreamTick()` 这个**生产入口**,读
`ScrollViewer.VerticalOffset` 本身:

| 断言 | 内容 |
|---|---|
| 全程偏移 > 0 | 40 帧一次都没有归零 |
| 40/40 走快路径 | 退回重建的帧就是重建 N 个气泡的帧 |
| 偏移随内容变长 | 一直贴着底,不是停在旧的底上 |
| 开流那一下退回重建 | 多了一条消息就是结构变了,快路径不许硬撑 |
| 连重建那一次也不归零 | 同步定位 |
| 滚上去之后十段增量不被拽回 | 停在 30px,十段后仍在 30px |

★★ **红测(ASSERTION-PITFALLS 第 14 条要求的那次自查)已经跑过**,而且结果与预期**不一样**:

* 快路径恒返回 false ⇒ **只红 1 条**(那条"40/40"),偏移断言**依然绿** ——
  因为同步定位独立地保住了偏移;
* 定位改回 `BeginInvoke(Loaded)` ⇒ 红 2 条,报 `最小 0,0px`。

⇒ **两个缺陷是两件事,各自需要各自的断言。** 只写"偏移不归零"就收工的话,
性能那一半会一直是绿的、一直是坏的。这一格已回填进 ASSERTION-PITFALLS 第 14 条。

### 诚实边界

自检里**没有跑消息循环**,所以排在 `Loaded` 的东西不会执行。
这恰好使判据**比真机更严**:真机上"归零 → 拉回底"两帧都发生,自检里只留下归零那一帧
—— 而归零本身就是缺陷。

## ② `NoteIntent` 静默吞掉一切 —— 意图即起失败时用户什么都看不到

### 查实:静默有**两层**,第二层更坏

1. `catch { }` —— 抛异常整条吞掉;
2. ★★ **`LastIntent` 一个读者都没有**。它自己的文档注释写着
   「界面据此显示"正在为你启动…"或那句"要先授权"」—— **那句话是假的**,全仓零引用。
3. ★★★ 而抛异常时连 `LastIntent` 都不写 ⇒ 它会停在**上一次的成功**上。
   **一个过期的成功比一个空值糟得多**:任何读它的人都会显示"好着呢"。

⇒ 结果:中枢**明确说过**的「这个模型还没被授权按需装载」,客户端一个字都不显示。
用户唯一能察觉的时刻是按了发送、等很久、然后收到一句**归错因**的"后端没起"(即 ③)。

### 裁定 ②.1 保留「不掀翻输入框」,但**失败必须有落点**

* 意图仍然即发即忘、仍然不阻塞输入 —— 这条一个字没改;
* 失败**写成一条它自己的失败码**(新增 `intent_unreachable`:与 `LOAD_FAILED` 有意分开
  —— 那一种是中枢试过了起不来,这一种是**这句话根本没送出去**);
* 落点 = **输入框上方那一行**。★ 位置的理由:意图的触发点就是**打字**,
  所以人此刻正看着输入框;而弹窗会打断打字,那恰恰是"不许掀翻输入框"要防的事。

### 裁定 ②.2 新增 `IntentChanged` 事件,**只在说法真的变了时**响

★ 接 `Gpu.Changed` 是错的:它跟着显存快照每秒一帧,拿它当刷新信号会把输入框
每秒重建一次(打字当场被打断)。
★★ 而且**同一句话不重复广播**:意图每 20 秒可能来一次,每次都弹等于**训练人忽略它**
(D85 第 5 条 —— 与"每轮重复印同一条预算提示"同一个失败模式)。

### 裁定 ②.3 没配对 / 主机不在线时**不画这一行**

输入框上方已经各有一句在说这两件事。同一屏两句话讲一件事,会让人以为出了两个问题。

### 副作用(一处必要的连带修改)

`App.Gpu` 原来是 `null!` + 在 `OnStartup` 里赋值。它的构造是 `_hub = hub` 一句、
完全惰性(真去连中枢的 `Gpu.Start()` 仍在 `OnStartup`),**本来就没有理由等到 OnStartup**。
而那个 `null!` 不是没有代价的:任何在 `OnStartup` 之前碰到 `Gpu` 的代码都会 NRE ——
本条接提示行时**当场撞上**(自检里 `ChatView` 一构造就炸)。
⇒ 改成在构造函数里建(与 `History` 同一手法),`Vram.Hub = Gpu` 仍留在 `OnStartup`。

## ③ `ChatClient.cs` 那句 `start-stack` 文案 —— 过期,而且**给错原因**

### 查实(不是推断)

* `/v1/chat/completions` **不做按需装载**:解析别名就直接转发给 `backend`,
  连不上 → `httpx.RequestError` → 503 `backend_unavailable`;
* 真正会把模型起起来的是 `/v1/gpu/intent`,而它的失败**已经分得很细**:
  `NOT_PERMITTED`(机主还没勾「允许按需装载」)· `GATE`(闸拦住 = 装不下)·
  `LOADER_ABSENT` · `LOAD_FAILED`,以及 `ALREADY_RESIDENT` + `plane:"loading"`(正在装);
* ★ 客户端**本来就有**一个解析得懂它的 `IntentOutcome.Advice` —— 缺的只是**去问一次**。

⇒ **用户猜的那一种是对的**:最可能的原因就是「没在组件面板勾过按需 / 授权集合是空的」。

### ★★★ 而那句建议今天会把人引向一个**被明令禁止**的动作

D101 裁定② 原文:自动起栈「只起 gateway 与 lan-edge,**绝不起 llama-server**:
按需装载(S14/S16-b)已经落地,静态起会和 transient 平面打架」。
而 `90-ops/start-stack.ps1` **恰恰会**静态起 `llama-server`。

> ⇒ 照着那句文案做,等于亲手制造一个与 transient 平面打架的后端。
> 「给错原因比不给更坏」是本项目自己的判词(ChatCenter 里那条 2026-08-05 审计),而它正在犯。

### ★★ 更值得记的一格:**护栏在替这句错话作保**

自检里配着 `Assert(S11Adv("backend_unavailable").Contains("start-stack"))`。
它不是漏掉了这件事 —— **它在主动阻止这件事被改**:谁去改那句文案,门禁当场判红。
⇒ 已记为 **ASSERTION-PITFALLS 第 16 条**(护栏可以把一句错话钉在原地),
并给出正解:断言别去钉一句话里的具体建议,钉"分得开";
外部专名(脚本名/端口/路径)出现在断言里 = 它在替一个会烂掉的事实作保。

### 裁定 ③.1 `ChatOutcome.Advice` **只说事实,不点原因**

改成:「中枢在,但模型后端没有应答。★ 这一句说不出是哪一种 ——
没授权按需装载 / 正在装载中 / 显存装不下 / 后端进程自己的问题,四种的下一步完全不同。」

★ 说不出就**承认说不出**,并列出可能,不挑一个当结论。

### 裁定 ③.2 真原因由 `ChatClient.BackendUnavailableAdvice(IntentOutcome?)` 分因

失败时**再问一次中枢**(`ChatCenter.SendAndAskAsync` 新增 `probeBackend` 委托,
由 `ChatView` 传 `Gpu.RequestIntentAsync("assistant.fast")`)。走的是与「意图即起」/「再开」
**完全同一条端点** —— 恢复不是新语义,它就是"我现在又要用它了"。
★ 顺带的好处:这次追问本身就可能把模型装上,于是那句话变成"**再发一次**就行"。

| 中枢的回答 | 说给用户的下一步 |
|---|---|
| `NOT_PERMITTED` | 去**主机**的「系统 › 模型」勾一次『允许按需装载』 |
| `GATE` | 原样用闸给的理由(它自己写好了该怎么办) |
| `plane == "loading"` | **正在装载,不是失败** —— 等几秒,不用改任何设置 |
| `OK`(这次追问装上了) | **再发一次**就有回答了 |
| 在跑,而后端仍不应答 | 才是「后端进程本身」那一种 · 去看 `upstream_problem.jsonl` · ★ **不要**用 start-stack 静态起它 |
| 追问自己也失败 | **承认追问失败**,不退回猜一个原因 |

★ 抽成**纯静态函数**,I/O 留在调用方 —— 自检才喂得进每一种形状。
★ 红测:退回一句写死的话 ⇒ **红 7 条**。

## ④ 客户端三处只读 `committed`,看不见 transient 平面(用户 2026-08-08 实机)

### 判据拄 **Broker 自己的语义**,不是照用户的话写

`gpu_broker.py` 算显存闸时写的是
`loaded = list(self._committed) + list(self._transient_resident)`;
空闲收割保留的也是这两者的并集。⇒ 「此刻显存里真的装着什么」= **两个集合的并**。

★ 那条「两个字段永不合并」的纪律(`HubGpuSnapshot` 第 37 行)**没有被违反**:
它禁的是**在界面上把两层说成一层**(会让用户以为自己勾过它)。
而"上下文窗口有多大"、"显存占了多少"是**纯事实问题**,与谁勾过它无关。
⇒ **数字合并,措辞分开**;快照上那两个字段照旧分开。

### 裁定 ④.1 并集只有**一处**实现:`TokenBudget.ResidentOf(HubGpuSnapshot?)`

三个调用点(算窗口 / 发请求 / 显存条)各写一遍的话,漂的那天只有一处会被发现。

### 裁定 ④.2 三处都改

1. `TokenBudget.WindowFrom` 的参数从 `committed` 改名 `residentComponents`,
   `Plan` 的措辞从「当前驻留的组件」改成「**此刻装着的**组件」——
   D90 之后"驻留"这个词专指 `committed`;
2. `ChatView.SendCurrent` 传 `TokenBudget.ResidentOf(Gpu.Snapshot)` 而不是 `Snapshot?.Committed`
   ——★ 这一格**不只是显示问题**:窗口退回 8192 兜底值 ⇒ **真的少带历史**,回答质量跟着掉;
3. `VramMonitor` 的模型段算两层的并;`VramSnapshot` 新增 `TransientGiB`(其中按需那部分)。

### 裁定 ④.3 措辞:有按需成分就**单独说出来**

* 横条:`模型 6.8(含按需 5.3) + 桌面 1.5 / 24.0 GiB`;
* 提示框逐行分开:「你勾的常驻 1.5 GiB」/「按需装载(空闲会自动卸)5.3 GiB」。

★ 「已启用」= 他在组件面板上勾过的;按需装上的**不是**。合成一句就是把 D90 裁定③
那个亏(D24「cap」)搬过来。

### 验收(能为假)

只有按需装载时窗口读出真值 **8192 而不是兜底估算**(`isGuess == false`);
两层都空时**仍然**如实说"读不到、按最小估";两层都有时取**最小**;同一组件出现在两个集合里不算两遍。
★ 红测:`ResidentOf` 退回只看 committed ⇒ **红 2 条**。

### ★ 没做到、如实说

用户报的「左下角**不再**说『暂无』」这一格,自检里断言的是**算法**
(模型段算两层的并 · 有按需时单独报),**不是真机上那一行字**。
真机验证要一台装着模型的主机,worktree 里没有。⇒ 这一格**没有端到端验过**。

## ⑤ markdown 没渲染 —— 用户实测 `**"Come for dinner tomorrow."**` 原样显示星号

### 裁定 ⑤.1 新增 `MarkdownLite`(纯解析)+ `MarkdownText`(渲染),**两个文件**

★ 分开是为了让判据能为假:记号认得对不对是"纯文本进、结构出"的问题,
自检可以逐种记号喂进来对答案;而"画出来好不好看"没法自动断言。
混在一个 WPF 方法里,**能测的那一半也就测不了了**。

范围**有意窄**:`**` `__` `*` `_` `` ` `` `~~` `[](…)` · 标题 · 列表(有序/无序) ·
引用 · 分隔线 · 围栏代码块。表格/脚注/内联 HTML **不认**(认一半的表格比不认更难读)。

### 裁定 ⑤.2 ★★★ 不认的东西**原样保留**,绝不吞掉

配不上对的记号、未闭合的反引号、词里的下划线(`vram_budget_toml` —— 这个仓库里到处都是)、
`2 * 3` 这种乘法,**一律原样**。
> **一个"半吞半留"的解析器会把模型说过的字悄悄弄丢,而那比原样显示星号坏得多。**

### 裁定 ⑤.3 渲染用 `RichTextBox`(而不是 `TextBlock`)

消息正文能**拖选 + Ctrl+C** 是它存在的唯一理由。WPF 的 `TextBlock` 没有选择功能,
换成它等于用"能看粗体"换掉"能复制" —— 净亏。
★ 新增 `PlainRichTextBox` 样式,与 `PlainTextBox` **逐条同构**(不吃滚轮 + 退出 Tab 序):
两者会在同一屏并排出现,有一条不一样用户就会看到两种气泡。
★★ 不吃滚轮必须显式做:`RichTextBox` 自带一个 `ScrollViewer`,而它就住在会话区那个
`ScrollViewer` 里面(嵌套滚动 = 滚轮落在气泡上时整屏不动)。

### 裁定 ⑤.4 三条边界

| 不渲染 | 理由 |
|---|---|
| 用户自己发的消息 | 他打了什么就该看到什么。吃掉他输入的星号 = 界面告白"你发出去的是粗体",而发给模型的是原文 |
| 正在流式接收的那条 | 半截的 `**` 没配对,会在"还是星号 / 忽然变粗"之间跳一整段;而且富文本重排比改一行 `Text` 贵得多(①的快路径正是靠"只改 Text")。说完之后那次重建自然会渲染 |
| 一个记号都没有的 | 绝大多数消息如此,套富文本是白花钱 |

★ 折叠(`CollapseLines`)与渲染**互不影响**:折叠决定"显示哪几行",渲染决定"这几行怎么画"。
绑在一起写过一版,结果是"超过 30 行的回答连记号也不渲染" —— 而**长回答记号最多**。

### 裁定 ⑤.5 链接**不做成能点的**

这段文字是**模型生成的**,带可激活的超链接等于**让模型决定打开哪个网站**。
⇒ 只标下划线 + 地址进 `ToolTip`,让人自己看清再决定。

### 裁定 ⑤.6 ★ 顺带核出来的第二处:**客户端自己的文案里就有 `**`**

自检里那条「界面文案里不允许出现字面 `**`」只扫了**四个视图文件**;
而真正把星号画给用户看的是**系统说明气泡**(`ChatOutcome.Advice` / `IntentOutcome.Advice`
里都有 `**主机**`、`**之前**`)。
⇒ 与其在每处文案里迁就渲染能力,不如让**纯文本落点主动剃掉记号**:
`MarkdownLite.ToPlainText()`,用在系统说明气泡与 ② 那行提示上。

★ 红测:`ParseInline` 退回不解析 ⇒ **红 14 条**。
