### 2.1 先把「被测对象」定位准 —— 这是整个判断的地基

承重问题是:「放开的口子会不会恰好就是被测对象?」
要回答它,必须先分清**隔离住在哪几层**,因为它们**不是同一层**:

| 层 | 是什么 | 谁在验它 | **在 459 里吗?** |
|---|---|---|---|
| **A · OS 身份**<br>(谁能连上) | `pg_ident` + `pg_hba`:SSPI 绑 Windows SID,只映 `ai-mem` | `verify-isolation.ps1` ⑤ **反向全表断言** | ❌ **不在**。属另算的**账户隔离套件 16 条** |
| **B · PG 角色权限**<br>(连上之后能干嘛) | `roles.sql`:`ai_mem_remote` 对基表 REVOKE ALL,只 GRANT 视图 | `verify.sql` C 段 · S9 ⑦ · `verify-isolation.ps1` ④ | ✅ 部分在(S9 ⑦) |
| **C · 类型层**<br>(正文出不出得了门) | `tainted.py` 的 `CallerTier` / `egress` | `test_tainted` · S4 ②③ | ✅ 在 |
| **D · 视图投影** | `v_memory_nons2` 不含 S2 | S4 ④ · S9 ⑦ | ✅ 在 |

### 2.2 ★★ 对协调层那条承重判据的更正

> 协调层:「那 459 条里有一部分正是在验**非授权账户连不上记忆库**这件事
> (S4 隐私三层 + 账户隔离 · S9 恢复库上安全性质仍成立)。」

**这个担心的方向是对的,但归属搞错了 —— 而归属决定了结论。**

逐条读过 S4 与 S9 的实际断言之后:

- **S4 ②③**(`test_s4_acceptance.py:110-135`)验的是 **C 层**:
  `unseal_for_client(..., caller=CallerTier.LAN_DEVICE)` 必须抛。
  **纯进程内,和谁连的库毫无关系。**
- **S4 ④**(`:138-148`)验的是 **D 层**:从当前连接查 `v_memory_nons2`,
  断言 S2 地址不在里面。这是**视图定义**的性质,不是连接身份的性质。
- **S9 ⑦**(`test_s9_drill.py:192-205`)验的是 **B 层**:
  `SET ROLE ai_mem_remote; SELECT ... FROM mem.l3_fact` 期望 permission denied。
  `SET ROLE` 之后按目标角色鉴权,**同样与发起连接的 OS 身份无关**。

⇒ **459 条里没有任何一条在验「非授权 OS 账户连不上记忆库」。**
那条性质的看守是 `verify-isolation.ps1` ⑤,它**不在 459 里**,是另算的 16 条。

这个更正的作用是**双向**的,两边都要说:

1. **它让 (a) 成为可能**:以 ai-mem 身份跑那 10 个套件,A 层原样不动,
   B/C/D 三层照常被验 —— 判据一条都不受影响。
2. **它让 P2「加一条 pg_ident 映射」变得比协调层担心的还糟**:
   那条路不是「可能污染某几条判据」,而是**当场把 A 层的唯一看守打红**。
   `verify-isolation.ps1:170-172` 的注释逐字写着这个动作:

   > 「往 pg_ident.conf 追加一行 `mem <任意账户> mem_rw`,记忆库对那个账户全开,
   > 而全套断言没有一条会红 …… 这正是本项目最恨的形状:看着有防护、实际没有。」

   那条反向全表断言**就是为了抓这个动作写的**。走 P2 = 亲手制造它写来防的事故。

### 3.3 脚本里承重的几条(都是这个仓库自己踩出来的)

- **判据只认 ASCII 且锚定到汇总行**。汇总行长 `=== 25 PASS · 0 FAIL · 1 SKIP ===`,
  cp936 下中文与 `·` 全成乱码而 `===`/`PASS`/`FAIL`/数字完好。
  非锚定的 `(\d+)\s*FAIL` 会匹配到正文里任意「数字+FAIL」——run-tests.ps1 被一个
  HTTP 状态码骗出过 `FAIL=422`(真实是 2)。
- **「退出码 0 + 没有汇总行」一律算没跑起来**,绝不当通过。理由见 §4.1。
- **`$ErrorActionPreference='Continue'`**:`'Stop'` 会把 native 命令的每行 stderr 包成
  NativeCommandError ⇒ 优雅降级分支变成死代码。`verify-isolation.ps1` 2026-08-03 实测栽过。
- **反向全表**:扫到的每个 `test_*.py` 都必须落到 A 档或 B 档;
  落不上判红。**反向也查**:登记了却在磁盘上不存在的,同样判红。
- **worktree 守卫**:B 档在 worktree 里**直接拒跑**并说明原因 ——
  实测 ai-mem 对**主树** `10-core\memory` 有 `ReadAndExecute` 显式 ACE,
  对 `.claude\worktrees\...` 副本**没有任何 ACE**。
  脚本同时写明:**别为此去给 worktree 授权**,那等于给记忆库代码开一个新的可读副本。
- **前置/后置隔离对账**:B 档跑前跑后各取一次 `pg_ident.conf` / `pg_hba.conf` 的 SHA256,
  并各跑一次 `verify-isolation.ps1`。**对不上就判红并宣布本次结果不可信** ——
  「跑完没动隔离」是被**证明**的,不是被**承诺**的。

## 4. 跑不了但必须报告的发现(★ 只报不修 —— P3d 车道)

### 4.1 ★★ 9 个活库套件在连不上库时 `sys.exit(0)` —— 手工跑会得到假绿

`test_s1/s2/s3/s4/s5/s6/s7/s8/s9` 顶层都是这个形状:

```python
try:
    conn = repo.connect()
except Exception as ex:
    print(f"  跳过:连不上 PG({type(ex).__name__})")
    sys.exit(0)          # ← 退出码 0
```

实测(我的身份,全部连不上):

| 套件 | 退出码 | 有汇总行? |
|---|---|---|
| s1 / s2 / s3 / s4 / s5 / s6 / s7 / s8 / s9 | **0** | ❌ 无 |
| `test_s3_repo.py` | 1 | ❌ 无(裸 traceback,连 `except` 都没有) |

**危害方向**:`run-tests.ps1` **抓得住**(它认汇总行,没有汇总行就判「没跑起来」)。
但门禁**从来不跑这 10 个**,而 Reason 恰恰是「必须**手动**跑」——
手动跑的人看的是退出码,而退出码说**成功**。
即:**这条假绿正好埋在唯一被指定的那条使用路径上。**

交付脚本对此的处理:判据只认汇总行,「退出码 0 + 无汇总行」一律判「没跑起来」并列进覆盖账。
但**根子在套件里**,应由 P3d 车道改成 `sys.exit(2)` 或打一行汇总。

### 4.2 `test_s3_repo.py` 连降级分支都没有

其余 9 个至少打了一行「跳过」。它直接抛 `repo.RepoError` 裸 traceback。
不是安全问题,但它是这一批里唯一一个**跑不了时长得和「跑坏了」一样**的。

### 4.3 tainted 套件 64 → 75:S15 改的断言今天第一次真被执行

见 §1.4。审计原话是那些改动「只过了 py_compile,没有实跑过」。
**现在跑过了,绿。** 这条可以从「未验证」名单上划掉。

### 4.4 门禁 Reason 的作用域缺陷

`run-tests.ps1` 的 `$RULES` 粒度是**目录**,承载不了「同目录下不同套件代价不同」。
建议(不属本车道,列给协调层):把 A 档四个套件登记成 `Runnable=$true`,
或给运行器加 `-Memory` 开关(`AUDIT-2026-08-05-full.md` 的修法 1 就是这个意思)。
★ 但注意:**它们要用记忆 venv 的解释器,不是系统 python**(系统 python 没有 psycopg)。
venv 路径按 `install-embedding.ps1:28` 的既有惯例从 `models` 根导出即可,
**不需要往 paths.toml 加新键**。
