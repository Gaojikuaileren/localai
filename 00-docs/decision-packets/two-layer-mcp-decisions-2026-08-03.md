## 0. 这份包是什么,以及为什么不直接写进 `DECISIONS.md`

设计文档《localAI 两层 MCP 最终设计》§6 给出九条决议,但只有 `statement` + `rationale` 两段,
不满足 v3.0 §12.1 的六字段格式(背景 / 选项 / 决定 / 理由 / 代价与已知风险 / **推翻条件**)。
本包把那九条扩写成完整六字段,**并新增第十条**(D75,多会话并发写中央文档的纪律)——
那一条设计文档里没有,是本轮实测撞出来的。

不直接追加 `DECISIONS.md` 的理由是**并发**:另一路会话此刻正在改同一个文件且未提交。
两边同时往同一文件末尾追加,轻则串行冲突,重则无声抹掉对方。
本仓已有这个先例与惯例——`P3b_LAN_mTLS_Decision_Packet_2026-07-28.md` 的头部就带「并发提示」,
明写本包未参与哪些改动、采纳时须以当前 `HEAD` 为准串行合并。本包照此办理。

**采纳方式**:两路会话都停下、`git status` 干净之后,由人按 §4「采纳清单」逐条串行并入。

## 2. 与未提交的 D65(Hermes Agent Worker)的关系 —— 必须先说清

另一路会话的 Hermes 设计与本包**有实质重叠**,不能假装不存在。逐条对齐:

### 2.1 Hermes 是【层一的一个驾驶者】,不是第三层

D65/DD-1 把 Hermes 注册成网关别名表里的一个后端(`agent.default`),「对客户端而言它就是一个模型」。
按本包 D73 的一句话总纲,**「谁驾驶」这一维恰好就是层一的驾驶者维**——
Hermes 落在「本地模型 或 外部模型(可替换)」那一格,与 `assistant.fast` / `assistant.deep` 同层。

⇒ **它拿到的工具池仍然完全受层一禁区约束**:

- D65/DD-2 明写「worker 不得拥有自己的工具注册表,全部工具由 LocalAI 在会话建立时投喂」——
  这与本包 D68「工具池按 (subject, device_tier, member_id, workspace) **静态挂载**,不是运行时判断」
  是同一条纪律穿过了 worker 边界,**不是两套机制**;
- 因此层一禁区表(D68 · 设计文档 §2.3)对 Hermes 会话**逐条成立**:无 `mem.*`、无 `settings.*`、
  无 delete 语义、无出网工具、无 `secret.request`、`ops/**` 与 `{state}/ctl/**` 在硬黑名单里;
- **Hermes 绝不触达层二。** 层二的入口是 `\\.\pipe\LocalAI.Ctl`,其 ACL 按 D72 是**白名单**:
  只授 {交互用户 SID, `ai-op` SID},**其余一律拒**。Hermes 无论跑在 `ai-exec` 还是容器里,
  都不在白名单上。
  ★ **不要写成「Deny 全部 `ai-*`」** —— 那是形态 B 语境下的措辞(那时外部 AI 就是交互用户),
    而形态 A 的外部 AI 正好叫 `ai-op`,会掉进同一个通配,**层二当场不可用**。
    白名单也顺带解决「将来新增一个 `ai-` 开头的账户默认落哪边」——落拒绝侧。

**⇒ 结论:Hermes 不是「第三层」,它是层一驾驶者维上的一个新取值。**
本包不为它新开平面,也不改层一禁区表的任何一条。

### 2.2 D65/DD-2 的「给 worker 用的 MCP 服务端」= 本包的层一

D65/DD-2 要的那个「会话级端点 + 一次性 token,把 §6.2 按会话挂载工具池投喂给 worker」,
其被投喂的**工具池内容**正是本包 D68 规定的 `config/tools.toml`。
两边不是两份注册表,是**同一份**:D68 的 `tools.toml` 是权威,DD-2 的会话级端点是投喂管道。

⚠ **需要在采纳时消歧的一处**:DD-2 说端点用「一次性 token」,而本包 D73 裁定
**层一全链路无 HTTP、走命名管道 + 父子/SID 双校验**。
两者不必冲突(token 可以走管道),但**若 DD-2 落地成 MCP over HTTP(设计图 §2 画的就是 HTTP)**,
则它引入了一条本包 D73 明令不存在的网络面。**这一条必须由用户显式裁定,不得默认。**
本包的立场:层一的传输裁决(D73)优先,DD-2 应改走管道;若必须走 HTTP,
则该端点需单独按 §6.4 三通道表新开一行并补齐 fail-closed,不能沿用「反正在回环」。

## 2026-08-03 · D66 · 新 principal `ext-operator`;批准的信任根是 Windows Hello,不是文件里的密钥

**背景**

层二(外部控制面)需要一个主体,来回答「谁在改我的盘」。三份对抗式评审撞到同一堵墙:
凡是把批准密钥放在**与被约束方同一 OS 身份可读**的位置,或把批准秘密打印到**被约束方读的流**,
都可被自签或回声。而外部 AI(Claude Code / Codex)在这台机器上握有 Bash / Read / Write / Edit,
**MCP 不是它唯一的通道**——它就是那个能读文件的进程。

M0a 已把 `EXT_OPERATOR` 加进 `CallerTier`(`tainted.py:226`),
并**刻意不出现在任何 `_ALLOWED_CALLERS` 集合里**,由 `test_tainted.py:155` 的正面断言守着。

**选项**

- A **签一张设备证书**(`urn:localai:device:`),复用 P3b 已建成的 CA 与 mTLS
- B **grant 文件里带 `hmac_key`**,`laictl` 用它自签每次请求(方案一原设计)
- C **六词 SAS 打到 `laictl` 的 stdout**,人肉眼比对后回填(方案二原设计)
- D **纯客户端 GUI 点击**,不加任何用户验证
- E **新 principal `urn:localai:operator:<grant_id>`(不签 X.509)+ Windows Hello 平台认证器
  作 A3/AX 的信任根**,A2 保留纯点击

**决定**

**选 E。**

- 新增命名空间 `urn:localai:operator:<grant_id>`,与 `urn:localai:device:` 并列,**不签发 X.509**;
- `CallerTier.EXT_OPERATOR` 进封闭枚举,**不加入** `E1_OVERRIDE_ALLOWED_TIERS`(`gateway.py:327`)、
  **不进** `ROUTE_TIERS`、**不进** 任何 `_ALLOWED_CALLERS` 值集(已落地);
- grant 由成员表里 `Role=="admin"` 的成员,在**主机本地**客户端 GUI 上签发,**并需 Windows Hello 用户验证**;
  grant 存于 `ai-ctl` 账户私有目录,交互用户 Deny,**`laictl` 与外部 AI 手中一个秘密都没有**;
- A3(哈希绑定)/ AX(带外揭示)的批准 challenge = `plan_hash`,由 `ctld` 侧生成、
  经独立审批管道下发给客户端、以 WebAuthn 断言回传,**永不经 `laictl` 的 stdout**;
- **取消 `grant.request`** 一类「模型可召唤、模型选 scope 与时长」的授权弹窗;
  未授权时只返回静态错误码 + `ops.scopes.explain`,由人自己去客户端开;
- scope **九个编译期常量,无 `all`**:`code:read` · `diag:shape` · `diag:logs` · `client-data:plan` ·
  `client-data:apply` · `config:plan` · `config:apply` · `ext:manage` · `reveal:single`;
- TTL 默认 60 分钟、上限 8 小时,**且这是编译期常量不是配置项**;勾高危 scope 时上限自动收紧到 60 分钟;
- `reveals` 额度**按天 / 按设备计,不按 grant 计**;
- 六元组正式扩为**八元组**:成员 · OS 账户 · 设备 · Agent · 工具 · 参数 · 额度 · 授权票据;
  第一维「用户」改写为主体三元组(成员 · OS 账户 · principal 类型)。

**理由**

1. **否 A**:签发需要 CA 私钥,而 D48(`DEC:1968`)已裁定签发是「需要键盘焦点(物理在场)」的动作。
   给一个云端 AI 发设备证书 = 把物理在场降级成 RPC。而且证书证明的是「**哪台设备**」,
   外部 AI 就跑在这台设备上,再签什么也没多证明——真正要证的是「**这次改动是人主动批的那一次**」。
2. **否 B**:`hmac_key` 与被约束方同 OS 身份可读 ⇒ 可自签。
   形态 A 下靠 ACL 能挡住,但那是**拿 OS 隔离去补密钥放错位置**——
   违反「不得用一个机制去抵消另一个机制的弱点」。密钥的正确位置本来就该在 `ai-ctl` 进程里。
3. **否 C**:SAS 打到被约束方读的流 = 回声攻击,零成本。
   SAS 本身保留,但**只用于人眼锚定审计链头**(D71),不再作批准原语。
4. **否 D(仅对 A3/AX)**:同用户下客户端 GUI 点击可被假客户端顶替。
5. **选 E 的实质**:带用户验证的平台认证器要求 PIN 或生物特征、在**安全 UI** 上完成,
   是当前 Windows 上唯一「**同用户代码无法静默满足**」的门;
   且与 D46「不得提权」不冲突(UAC 方案会正面冲突)。
6. **取消 `grant.request`** 是因为 `PLAN:1072` 明令禁止「可被注入按需召唤、文案由模型控制的索要凭证窗口」
   (授权控件的版面强制在 `PLAN:1016-1019`,哈希绑定在 `PLAN:1023`——三处不是同一行,勿混引);
   而 A1 只读原文按 §6.6 定义就是不可信内容入口,模型能读到诱导文本 ⇒ 它能被诱导去召唤那个弹窗。
7. **额度按天计**是因为按 grant 计可以用「重新授权」重置,那等于没有额度。

**代价与已知风险**

- **R3(A2 可被代答)**:`ctld` 对 A2 只能校验对端进程映像路径 + Authenticode 签名。
  用户已选**形态 A**,ai-op 账户对用户 profile 目录有显式 Deny ⇒ 外部 AI 起不了一个以交互用户身份
  渲染审批 UI 的假客户端,**这条在形态 A 下成立**。
  ★ **但前提是 `ai-op` 账户的 ACL 真的落地且未被回退**——见 D73「形态 A 的三条前提」。
  前提不成立时 R3 原样回来,缓解上限只到「把批量阈值从 >20 下调,把更多动作推到 A3」。
- **R6(社工扩权)未消除**:外部 AI 仍可**说服人**去开新 scope(「这一步需要 `config:apply`」)。
  缓解只到:grant 卡默认全关 + 高危 scope 时长自动收紧 + Hello + 系统生成区写明该 scope 会看到什么。
  **不得声称已挡住。**
- **R7(确认疲劳)未消除**:摩擦梯度(A0/A1 零确认、A2 一屏 diff、A3 展开 + Hello)只是缓解。
  可选加码是给 A3 设日额度(如 5 次/天),会牺牲运维效率——**这是本设计最直接的能力/安全折衷**。
- **R11(AX 不可逆)**:回滚能撤销改动,撤销不了「已看到」。必须在首次授权时一次性告知。
- 🔴 **Hello 的可用性前提未被强制**:若该机无 TPM 或未注册 Hello,本条的信任根不存在。
  裁定:**此时必须 fail-closed 拒绝签发 grant,不得回退到纯点击**。
  ★ 强制点:`ctld` 启动时探测平台认证器可用性,不可用则 A3/AX 两族命令**整族不注册**
  (「不存在」而非「返 403」);`ops.status` 如实回报 `webauthn: unavailable`。
  **该强制点当前尚未实现(M1 交付),在实现前这一段只是文档约定。**

**推翻条件**

1. **实测该机 TPM 不可用或 Windows Hello 无法注册** ⇒ 本条的信任根不存在,
   层二**只保留 A0/A1 只读面**,写面(A2/A3/AX)整族不注册,直到信任根问题另案解决;
2. **出现「同用户进程可静默满足 Hello 用户验证」的公开手法**(如平台认证器可被无 UI 调用)

3. **`ext-operator` 出现在 `_ALLOWED_CALLERS` 任一值集里**(`test_tainted.py:155` 断言变红)

5. 若客户端引入任何形式的 `grant.request` / `scope escalate` / 模型可召唤的授权 UI
   ⇒ 本条的第 6 条理由被直接违反,该功能必须回退或本条重裁。

## 2026-08-03 · D67 · 出境裁决:L-proj 可出、正文不可出;判据由 Projector + `projection.toml` + 反射穷举强制

**背景**

按 §4.11.5 的 D2(`PLAN:548`),外部 AI 的推理后端**按定义是「你无法单方面终止访问的系统」**
⇒ 一切进入它上下文的内容,出境判据**直接成立,不是「可能」**。
所以问题不是「要不要放行」,而是「**哪一类内容根本不需要进它的上下文,就能让它把活干了**」。

核心洞察:**外部 AI 写规则,本地跑规则。**
它要整理数据,真正需要的是:有多少条孤儿消息、哪些记录 `OwnerMemberId` 为空
(会让条目在 D45 fail-closed 下静默消失)、哪些 `Shared` 从 true 退回 false、
`archive/` 里有多少 session 在 `chat.json` 里不存在。**这些全是形状,不是内容。**

**选项**

- A **通用谓词查询**(`--where 'field~/regex/'`),给 AI 最大自由度(方案二原设计)
- B **掩码 diff 给 `sha8`**,让 AI 能比对而看不到正文(方案三原设计)
- C **全部 stdout 过 E4 出境闸**,复用已有正则族
- D **只给结构投影,自由文本只给长度桶**,单出口函数 + 字段级 allowlist + 反射穷举元测试

**决定**

**选 D。**

- §5.6.2 粒度表新增 **`L-proj`** 与 **`L1-code`** 两档;
  §4.11.5 新增 **D4 判据**:「不含内容的结构性元数据构成出境,但归 L-proj 档,
  **按会话授权而非按任务放行**管理」——这是与 §12「每任务手动放行」(`PLAN:1976`)的**正面差异**,
  故必须写成决议,**不得当作默认延续**;
- `ctld` **只有 `Projector.Emit()` 一个函数能写 stdout**;
- 一个字节允许离开 stdout,当且仅当五条**同时**成立:
  ① 由 `Projector.Emit()` 产出;
  ② 来源字段在 `config/projection.toml` 里显式登记为 `id | count | enum | day | len_bucket | bool | code` 之一
  (**未登记 = 不出**,并写一条 `unclassified_field` 审计);
  ③ 所属 store 不在红区表(记忆 · secrets · identity · ReplyProfile · 消息正文 · 附件 · clips);
  ④ 不是自由文本的任何函数——**长度只给桶,绝不给哈希、绝不给前缀、绝不给正则匹配结果**;
  ⑤ 若类别为 `code`(A1 原文):命中 `code-roots.toml` 白名单根、不命中硬禁止清单、
  已过 E1/E4 正则族、计入 `verbatim_reads` 额度;
- **类型层保证**:自由文本字段的投影**返回类型**是 `{len_bucket: Bucket, null_count: int}`,
  **结构上装不下正文**;
- **不提供通用谓词查询**:只有登记为 `enum | day | bool | id` 的字段可被 facet 分桶;
  `CalendarGroup` / `Scope` / `Owner` 这类**看似枚举实为自由文本**的字段一律按自由文本处理;
- **E4 只挂在 `code` 与 `AX` 两类内容承载输出上**,不扫结构字段;
- 唯一正文出口是 **AX**:人在客户端**亲手点选那一条** + Hello + E4 扫描 + 出境登记,**≤3 次/天/设备**;
- **元测试**:反射穷举每个落盘 DTO 的**每一个公共属性**,断言已在 `projection.toml` 登记,未分级 ⇒ CI 红;
  反射看不见的动态结构(`filetrans.json` / `i18n.json` / `reply.json` 这三份 Dictionary-of-doc)
  **只暴露 key 数量与 key 是否为已知 sessionId**,doc 内容整体红区。

**理由**

1. **否 A**:`--where` 若字段域未限死,就是对红区正文的**免票逐字节提取预言机**——二分即可还原,
   且不触发 reveal、不计出境。评审用 `CalendarGroup` 举了具体例子:
   「妈妈化疗」这类日历名会被当结构元数据出境。
2. **否 B**:`gate.py:15-16` 已就同一件事裁定过「**定长串的哈希可爆破**」。
   4–12 字的中文标题给 `len=7 sha8=…`,几秒可穷举还原。这是**重犯已裁过的错**。
   并发校验改用**整文件哈希**(不可爆破,且够 `ERR_DRIFT` 用)。
3. **否 C(全量过 E4)**:会**自锁**。`plan_hash` / `sha256` / `nonce` 这类 64 位十六进制会命中
   HIGH_ENTROPY,而豁免正则不匹配(`"hash": "` 的前缀是 `"` 而非 `[:=]` 或空白)⇒
   `plan` / `apply` / `audit tail` 第一天就全部自我拒绝,
   **而唯一的修法正是 e4 结构上拒绝提供的 override**(`e4_egress.py:40-42` + `test_e4_egress.py:44-45` 的签名断言)。
   ⇒ 裁定:结构字段是强类型的非字符串产物,不进 E4;**E4 只守内容通道**。
4. **选 D 的实质**:用**类型**消灭一整类泄露,比任何运行时过滤都硬。
   这与 `tainted.py`「没有通用 `unseal()`」同源。
5. **反射穷举是对未来的保险**:D61 给 `ReplyProfile` 加「我方地址」这类新增,每一次都会让测试红,
   **逼人当场分级**——而不是等到某天发现地址已经出境了。

**代价与已知风险**

- **R4(投影本身泄露信息)**:「记忆表 1247 条、最近一条 8 月 3 日」泄露作息与使用强度。
  缓解:时间只到**日**粒度;计数 <5 显示 `<5`(k-匿名下限);枚举直方图只对显式登记字段开放;
  identity 只给计数。**接受并写进 UI 诚实声明**——与 `roles.sql:73-79` 对 `pg_catalog` 行数估计的
  既有处理同口径。
- **R5(代码与文档里可能混进 S2)**:`STATE.md` / `worklog` 若含真实姓名、地址、健康信息,
  那一刻从「文档」变成 L5 标的。`worklog/` 与 `snapshots/` 已在黑名单,`00-docs/*.md` 出境前过
  E1/E4 + 一条 S2 关键词哨兵。**哨兵不完备,承认。**
  ★ 且机主自己在这个仓库跑 Claude Code,代码与部分文档**已事实出境**——
  这是机主的既有决定,不是本条新引入的,但也**不构成放宽的理由**。
- **R11(AX 不可逆)**:同 D66。
- **能力代价(诚实写出)**:AI 因此**看不到正文**,它给的整理建议是「在没看正文的情况下」给的。
  这会让某些建议不如它能读全文时准。裁定接受,并在批准 diff 时的系统生成区固定显示
  「本提案基于以下投影产生:inventory, shape(chat), integrity」,**让人据此校准信任度**。
- 🔴 **`projection.toml` 与反射穷举元测试当前均不存在**(M0b 交付)。
  在它们落地之前,「未登记不出」只是文档约定,没有任何东西会因为漏登记而变红。

**推翻条件**

1. **`Projector.Emit()` 不再是 `ctld` 写 stdout 的唯一函数**(元测试:扫 `ctld` 程序集,
   `Console.Out` / `Console.Write*` 的调用点数 ≠ 1)⇒ 单出口前提破,本条失效;
2. **任何自由文本字段的投影返回类型里出现 `string`** ⇒ 类型层保证破,本条失效,必须重裁;
3. **出现任何形式的通用谓词查询 / 正则过滤 / 前缀匹配 API**,不论叫什么名字 ⇒ 违反第 1 条理由,须回退;
4. **给 AI 的任何输出里出现自由文本字段的哈希(含 sha8 / 短哈希 / 指纹)** ⇒ 重犯 `gate.py:15-16` 已裁过的错,须回退;
5. 若 AX 的日额度从「按天/按设备」改回「按 grant」⇒ 额度可被重新授权重置,本条的额度机制失效;
6. 若反射穷举元测试因「维护成本高」被标记 skip 或删除 ⇒ 未来新增字段不再被强制分级,
   本条降级为纯文档约定,**必须在 `STATE.md` 记一条技术债并重裁**。

## 2026-08-03 · D68 · 工具注册表与投影表纳入 CFG-1;层一禁区一律机制化,不用运行时 `if`

**背景**

Q2 指出:层一的工具注册表**既无规格,也不在 CFG-1 保护清单里**,
而它是**比 `zones.toml` 更根本的权限载体**——`zones` 说「能碰哪些路径」,`tools.toml` 说「有哪些手」。
层二能改设置这件事,让这个缺口从「不整洁」变成「致命」。

现成的反面教材就在仓库里:`registry.toml` 的 `tier_min` 字段**声明了却从不读取**——
一个看着像防护、实际没有任何强制点的字段。

**选项**

- A 工具池不落文件,**写死在代码里**(编译期常量)
- B 工具池落 `tools.toml`,但**不进 CFG-1**,靠「AI 不会去改它」
- C 层一禁区用**运行时 `if`** 拦(工具存在,调用时判断拒绝)
- D **落 `tools.toml` + 进 CFG-1 + 挂载期校验 sha256 + 禁区一律「池中不存在」**

**决定**

**选 D。**

- 新建 `config/tools.toml`(层一)、`config/ctl-verbs.toml`(层二)、`config/projection.toml`(投影分级),
  连同 `registry.toml` 一并纳入 **CFG-1 保护清单**(从四份扩为**七份**):
  不在任何 Agent 可写区域、不在层二任何 op 的可达范围、
  挂载时校验 sha256,失配则 **`refuse_mount`(不是降级挂载)**;
- `tools.toml` 每条目**必填**:`name`(含 `@host`,语法校验) / `transport` / `subject[]` / `tier_mount[]` /
  `member_scope` / `workspace[]` / `approval` / `driver_egress` / `writable_fields[]` /
  `log_result` / `log_args` / `quota` / `provisioned` / `param_schema`(sha256)——**缺任一字段拒绝启动**;
- 工具池挂载键正式定为 **(subject, device_tier, member_id, workspace)**(把 D45 的成员维并入);
  切换工作空间 = **重建会话工具池**,不是追加;
- **参数 schema 的权威在执行器侧**(`PLAN:815`「下层是权威」),上层门面的校验只是早失败优化;
  schema 漂移(sha256 与执行器内置不符)⇒ **该工具整族不挂载**,不静默用旧版;
- **层一禁区一律以「池中不存在该工具族 + 窄白名单回调枚举 + 引用图元测试」强制,不以运行时 `if` 强制**;
- ★ **一条例外必须加**:「会话记录只增不改」额外配一条**运行期不变量**——
  `ChatCenter` 保存前校验 `MessageId` 集合单调只增、已有 `Text` 的 sha256 不变,
  违反即**拒绝保存并告警**。

**理由**

1. **否 A**:写死在代码里等于没有规格,也无法审查「现在到底挂了什么」;
   且 `ops.tools.list` 这类「让人看见层一挂了什么」的能力无处可取。
2. **否 B**:`tools.toml` 不进 CFG-1 = 层二能改它 = 一次成功的注入就能给层一开出永久后门,
   而且会被记成「用户批准过的配置变更」。这正是 D72 要堵的 confused deputy 主路径。
3. **否 C(运行时 `if`)**:`PLAN:198-205` 已明说这会把「**不存在的能力**」降级成「**一条被检查的规则**」。
   规则会被绕过、会被改、会有分支写反;「池里没有这个工具」不会。
4. **运行期不变量而非 selftest 断言**,是因为 **selftest 明确不碰真实状态**
   (`Selftest.cs:28-34` 把 state 指向临时目录)⇒ **磁盘被改坏不会有任何断言变红**。
   这是本项目「假断言」事故的同一族形状:断言存在、但它守的不是出事的那条路。
5. **schema 权威在执行器侧**:上层门面若是权威,一个被诱导的门面就能放行畸形参数;
   下层是权威则门面只能更严不能更松。

**代价与已知风险**

- **R8(序列化 / schema 口径漂移)**:客户端改了模型而 `ctld` / `handd` 没重编译。
  缓解:`<Compile Include>` 直接链客户端代码;plan 阶段往返自检;
  `ops.status` 返回 `contract_version` 与 `ctld_binary_sha256`,不匹配时 apply 类工具**整族不挂载**。
  残余:版本不匹配期间层二只读可用、写不可用。**可接受**。
- **摩擦代价**:每加一个层一工具要填 14 个字段,且漏一个就起不来。
  这是**有意的**——但它会诱使人「先给一个宽松取值跑通」。
  ⇒ 反制:`driver_egress` 与 `writable_fields` 两个字段**无安全默认值可填**,必须显式想清楚。
- 🔴 **CFG-1 的 sha256 挂载校验当前只是 `PLAN:821` 的文字,没有实装**(M2 交付)。
  在实装前,「纳入 CFG-1」= 一句承诺,**不是强制点**。
  本包如实标注,不得据此声称 `tools.toml` 已受保护。
- 🔴 **引用图元测试尚不存在**(M0b/M3 交付)。在它落地前,
  「`handd` 不链接 `AppSettings.cs`」「`ctld` 引用图无 `HttpClient`」都只是文档约定。

**推翻条件**

1. **`tools.toml` / `ctl-verbs.toml` / `projection.toml` 任一出现在层二某个 op 的可达路径里**
   (含 `write_text_file` 的根、`patch_toml_key` 的键白名单)⇒ CFG-1 保护被穿透,本条失效,须立即回退该 op;
2. **出现任何以运行时 `if` 实现的层一禁区**(即工具在池中存在、靠调用时判断拒绝)
   ⇒ 违反第 3 条理由,该禁区必须改回「池中不存在」或本条重裁;
3. **`refuse_mount` 被改成「降级挂载 + 告警」** ⇒ 违反 §12.3「失败可见 · 不静默降级」,须回退;
4. **`ChatCenter` 的运行期不变量被移进 `Selftest.cs`**(或只在 selftest 里断言)

## 2026-08-03 · D69 · 「Vigil / 宠物始终本地」:Agent 身份由**传输**证明,不由报文声明

**背景**

用户对 Vigil(常驻清醒助手)与桌宠有一条明确承诺:**始终本地**。
三版方案都把 `agent_allow` 挂在网关里,但**网关请求上下文里根本没有 agent 这个维度**——
唯一的会话标识是客户端自报的 `x-session-id`。

⇒ 读报文字段来判 agent,直接违反 §6.6 F1 与 `gateway.py:339`(自报字段不作权限判据);
不读,则 `agent_allow` 就是**第二个 `tier_min`**:一个声明了却从不读取的字段。

**选项**

- A **报文头带 agent 名**,网关按 `agent_allow` 校验
- B **给每个 Agent 签一张客户端证书**,走 mTLS 证明身份
- C **端点证明身份**:Vigil 不经网关,连一个进程内只加载本地模型的专用后端
- D 不做机制,只在文档里写「Vigil 用本地模型」

**决定**

**选 C,并把 A 降级为纵深防御(不是唯一防线)。**

- **Vigil 与宠物不经网关。** 它们连的是专用命名管道 `\\.\pipe\LocalAI.Model.resident`,
  对端是一个**进程内只加载 `assistant.resident`、二进制不链接任何 HTTP 客户端**的后端;
- 该后端由 `ai-vigil` 账户运行,管道 ACL 只授该 SID;
- 网关的 `LOCAL_DENY_ACCOUNTS`(`gateway.py:42`)加入 `ai-vigil`
  ⇒ **Vigil 进程连不上网关,连「想换个别名试试」都做不到**;
- `registry.toml` 新增两个**必填**字段 `local_only`(bool)与 `agent_allow`(数组),
  **不允许缺省为 `["*"]`、不允许空数组**,取值必须来自 `gateway.py:140` 的封闭表 `KNOWN_AGENTS`;
- 六条 fail-closed(已落地于 `gateway.py:186-266`):
  ① 缺字段/类型错 ⇒ `RegistryError` **拒绝启动并点名**;
  ② `agent_allow` 取值须在 `KNOWN_AGENTS` 内,不许 `"*"`、不许空;
  ③ `local_only=true` 与 `egress=true` **互斥**;
  ④ `assistant.resident` **必须存在**,且 `egress=false ∧ local_only=true ∧ 无 provider 字段`;

  ⑥ 元测试照抄 `test_egress_registry.py` 的形状,穷举 registry 断言
  `{别名 | "vigil" ∈ agent_allow} == {"assistant.resident"}`;
- `CallerTier` 补 `RESIDENT_OBSERVER`(已落地,`tainted.py:225`),**刻意不进任何 `_ALLOWED_CALLERS`**;
- **未来放开的接口留法**:接口 = **一个已存在但被断言钉死的字段**,
  不是 `allow_external = false` 的开关,也不是 TODO 注释。
  放开 Vigil 用外部模型 = 改 `registry.toml` + 改后端加载表 + **显式删掉第 ⑤ 条反向断言** +
  走 §12.4 哈希绑定批准 + 在 `DECISIONS.md` 留条目
  ⇒ **必然有 diff、有决议号、有测试变红,不可能悄悄发生。**

**理由**

1. **否 A(单独使用)**:自报字段不是身份。这是 §6.6 F1 与 `gateway.py:339` 的既有裁决,
   不能因为「加一个 header 很方便」就破例。
2. **否 B**:给一个本机常驻进程签证书,徒增 CA 的签发面(D48 已把签发判给物理在场),
   而端点隔离用现成机制就能达到更强的效果。
3. **否 D**:那正是 `tier_min` 的形状——声明了、从不读、看着像防护。
4. **选 C 的实质**:「始终本地」的强制点**不再是**「它自报的 agent 被 allowlist 挡住」,

5. **反向全表断言是这条里最重要的一件事**:正向断言只能守住今天写对的条目,

**代价与已知风险**

- **多一个后端进程与一个 OS 账户**(`ai-vigil`),运维面变大。

  ⇒ 真正在兜底的是端点隔离与 `LOCAL_DENY_ACCOUNTS`。**不得声称 `agent_allow` 是运行期防线。**

  否则网关拒绝启动。**这是有意的**,但会在 Hermes 接入时立刻撞上(见 §2.4)。
- 🔴 `resident-backend` 进程本身**尚不存在**(M3/M4 交付)。
  在它落地前,「Vigil 不经网关」还没有被兑现——当前 Vigil 若存在,走的仍是网关。
  M0a 落地的只是 registry 侧的**加载期护栏**,它挡住的是「配错」,不是「Vigil 现在在走哪条路」。

**推翻条件**

1. **`gateway.py:255-266` 的反向全表断言被删除或改成告警** ⇒ 「始终本地」失去唯一的结构性守卫,

2. **出现第二个 `agent_allow` 含 `"vigil"` 或 `"pet"` 的别名** ⇒ 断言会拒绝启动;

3. **`agent_allow` 出现 `["*"]`、空数组,或 `KNOWN_AGENTS` 被改成开放集合**(如允许任意字符串)
   ⇒ 封闭表前提破,本条失效;
4. **`ai-vigil` 从 `LOCAL_DENY_ACCOUNTS` 中移除** ⇒ Vigil 可连网关,端点隔离失效,本条失效;
5. **`RESIDENT_OBSERVER` 被登记进任一 `_ALLOWED_CALLERS` 值集** ⇒ Vigil 可取正文,承诺被推翻;
6. 若用户显式改变承诺(允许 Vigil 用外部模型)⇒ 按上面「未来放开的接口留法」走完整流程,
   本条由新 D 取代——**但不得靠改一个布尔开关达成**。

## 2026-08-03 · D70 · 层二事务模型:计划哈希 + 独占句柄 + 检查点 + 可中断 + 回滚可回滚

**背景**

层二要改客户端落盘数据,而客户端这一侧有三个**已实测**的坑:

1. 客户端**零 IPC**、无 `FileSystemWatcher`、无命名管道命令通道
   (只有 `SingleInstance.cs` 的命名 Mutex + EventWaitHandle,那是跨进程唤醒,不是命令通道);
2. 退出时用**内存值整文件覆盖**(覆盖动作在 `App.xaml.cs:407-425` 的 `SaveStores()` 里;
   `App.xaml.cs:436` 是 end-session/release-vram 钩子,**不是**覆盖点);
   `App.xaml.cs:430/442` 把 `SaveStores` 与 `Settings.Save` 注册为**两个独立退出钩子**
   ⇒ **`settings.json` 不在那 13 份 store 里**,由退出步骤 ③ 无条件覆写;
   而 `AppSettings.Load()` **只在 `OnStartup` 调一次**;
3. `App.xaml.cs:302` 的注释记着一次**真实事故**:退出钩子用内存空表覆盖了盘上完好的数据。

⇒ 「journal 说 applied、盘上没改」这类静默破坏**在这个代码库里已经发生过一次**。

**选项**

- A **Mutex 探测**:apply 前检测客户端是否在跑,没在跑就直接改文件
- B **要求人先关客户端**再运维
- C **只加事务日志**,不解决并发(出了事靠 journal 追查)
- D **五动词控制管道 + 独占句柄 + 检查点 + 逐 op 可中断 + 写后校验**

**决定**

**选 D。**

写路径固定为 `plan → 批准 → apply → receipt → rollback`,八条硬约束:

1. **op 是受控枚举,不是脚本**:`set_field` / `null_field` / `remove_record` / `move_to_quarantine` /
   `patch_toml_key` / `reorder_list` / `write_text_file`。每种有 JSON Schema,
   **没有任何 op 能承载可执行内容**;
2. `write_text_file` 与 `patch_toml_key` **共用同一张路径/键黑名单常量表**
   (元测试断言两者引用**同一符号**),`config/**`、`{code}/**`、任何 `Startup`/自启目录、`{state}/**` 一律不可达;
3. **`preview_hash` 由 `ctld` 算,不由 AI 报**;apply 前**重算比对**,计划陈旧即拒,
   **不静默重算后执行**(§12.3);
4. **ChangeSet 的 body 与 diff 全文永不离开 `ctld`**,AI 手里只有 `changeset_id` 与 `preview_hash`;
5. apply 时对每个目标文件取 **`FileShare.None` 独占句柄**;全量 pre-image 拷入检查点;
   逐 op 执行 tmp→Move 原子写(与 `ClientStore.cs:48-66` 同口径);
6. **每个 op 之间检查急停/撤销标志,命中即停在 op 边界并自动回滚到检查点**;
7. 执行后**重算文件 sha256 与预期比对**,不符 ⇒ receipt 记 `failed` 并回滚
   ——**不允许出现「journal 说 applied、盘上没改」**;
8. **永不 delete**:`remove` 实现为移入隔离区 `{state}/ctl/quarantine/<ts>-<changeset_id>/`,
   **没有 purge 命令**(清空只能人在客户端做);**`rollback` 自身是一次 A2 动作**,也进 journal、也有检查点。

客户端侧配合(**M1 期就要有,不推 M2**):新增极小控制管道 `\\.\pipe\LocalAI.Client.Ctl`,
ACL 只授交互用户 SID,**五个动词**约 250 行:`ping` / `quiesce` / `resume` / `state-hash` / `estop`。
三条修复必须同时落地:

- **`state-hash` 与 `resume` 的覆盖面必须包含 `settings.json`、`archive/<sid>.json`、
  `filetrans/<sid>.*`、`clips/*.png`**,不能只有 13 份 store;
- **`resume` 必须重跑 `OnStartup` 里那批只读一次的生效点**
  (`ThemeManager.Initialize` / `Strings.Language` / `Vocab` / `Autostart` 自愈 / `TodoAutoPurge` / `AppleCalendarList`);
- **并发闸不靠 Mutex 探测**:独占句柄 + `ctld` 写 `{state}/ctl/ops.lock`(客户端**启动时与每次防抖保存前**检查,
  命中则进入只读模式并显示横幅)+ `ctld` 自持 `Local\LocalAI.Ops` 互斥体(两个外部会话不能同时 apply)+
  租约 TTL 90 秒 + 横幅上的「强制解除」(会把在途事务标为 `unknown` 并触发完整性巡检)。

**层二绝不手写 JSON**:`ctld.csproj` 用 `<Compile Include>` 直接链客户端的 `Services/*.cs`;
`ops.*.schema` 逐字段回报序列化口径(`enum_codec: "int"|"string"`、`double_encoded: bool`);
plan 阶段先做一次「解析 → 重序列化 → 与原文件字节比对」的**往返自检**,不一致即拒绝出计划。

**理由**

1. **否 A(Mutex 探测)**:它是 **fail-open**——命名空间不匹配、ACL 拒绝,都表现为「没在跑」。
   且存在 TOCTOU:客户端中途起来 → `SafeImport` 读到半成品 → 退出时用内存值整文件覆盖
   ⇒ journal 已写 applied 而盘上没改。**这是本项目最恨的静默丢数据。**
2. **否 B(先关客户端)**:与用户已裁定的「**客户端开着也能操控**」直接冲突,不是选项。
3. **否 C(只加日志)**:出了事能追查,但数据已经没了。§12.3「可回退」门禁要求的是**知道怎么恢复**。
4. **`settings.json` 必须进覆盖面**,是因为它**不在** `SaveStores` 的 13 份里、由退出步骤 ③ 无条件覆写,
   而 `AppSettings.Load()` 只在 `OnStartup` 调一次
   ⇒ 不纳入 `state-hash` 与 `resume`,**`scope=settings` 的全部写入会被静默还原**,而 journal 记 ok。
5. **序列化口径有真实陷阱**:`settings.json` 的枚举存**整数**(`AppSettings.cs:201` 没挂 `JsonStringEnumConverter`),
   `chat.json` 存**字符串**,`WeatherCityOrder` 是**双重编码**字符串。
   写错口径会让 `AppSettings.Load()` **静默回全部默认值**——这是最隐蔽的一类破坏。
6. **急停可中断必须在 M1**,因为 **M1 期层二就已经有批量写能力了**;推到 M4 等于让批量写裸奔三期。

**代价与已知风险**

- **客户端要改**:五动词管道 + `ops.lock` 检查 + 只读模式 + 批准卡 + grant 卡。
  这是**跨会话的工作量**,且客户端目前由另一路会话在改 ⇒ 采纳时必须协调(见 D75)。
- **`resume` 重跑生效点有回归风险**:`OnStartup` 那批调用原本只跑一次,重入的安全性未验证。
  ⇒ 要求逐个确认幂等,不幂等的**必须显式列出来并单独处理**,不得「先跑通」。
- **R8(口径漂移)**:见 D68。
- **强制解除会留下 `unknown` 状态的在途事务**:这是**有意的**——
  比「假装回滚成功」诚实。但它要求完整性巡检真的存在(`ops.data.integrity`,M0b)。
- 🔴 **`{state}/ctl/estop.flag` 对 `ai-ctl` 只读**这条,依赖 NTFS ACL 真的落地。
  ACL 未落地时,`ctld` 理论上能改自己的急停标志 ⇒ 急停对层二退化为「自觉遵守」。
  见 D73「形态 A 的三条前提」。

**推翻条件**

1. **出现任何绕过 plan/apply 的直写路径**(含「小改动就直接写」的快捷方式)⇒ 事务模型失效,须回退;
2. **`preview_hash` 改由 AI 提交,或 apply 时不再重算比对** ⇒ 计划陈旧检测失效,本条失效;
3. **并发闸退回 Mutex 探测**,或 `FileShare.None` 独占句柄被改成共享读写 ⇒ 违反第 1 条理由,须回退;
4. **`state-hash` / `resume` 的覆盖面不含 `settings.json`** ⇒ `scope=settings` 的写入会被静默还原,
   该 scope 必须整族下线,直到覆盖面补齐;
5. **apply 后的 sha256 复核被跳过**(哪怕只是「性能优化」)⇒ 「journal 说 applied、盘上没改」重新可能,须回退;
6. **出现 `quarantine.purge` 一类删除命令**,或 `remove` 被实现为真删除 ⇒ 违反 §12.4 铁律,须立即回退;
7. 若逐 op 急停检查被推迟到 M1 之后 ⇒ 本条的第 6 条理由被违反,
   **层二的批量写能力必须同步推迟**,不得先上写面后补急停。

## 2026-08-03 · D71 · Ops 审计哈希链 + 跨账户每日锚点;且**不得声称审计防篡改**

**背景**

Q7 指出:全库对**审计不可篡改性零要求**,§9.1 只写了「不删」。
而两层 MCP 的**全部事后可查性都压在这上面**——层二每一条写操作的问责,靠的就是这条链。

三份评审指出方案一/二/三的**共同错误**:链的**写者**与**被防主体**是同一个账户。
于是「挡的是外部 AI 悄悄改一行」这个方向是反的——它**不需要管理员权限**就能重算全链。

**选项**

- A **JSONL 追加,不做链**(现状的自然延伸)
- B **哈希链,写者与被防主体同账户**(三版方案的共同做法)
- C **直接上 PG `mem.audit_log`**(有真正的 `REVOKE UPDATE, DELETE`,`roles.sql:37-39`)
- D **哈希链 + append-only ACL + 跨账户每日锚点 + 人眼 6 词**

**决定**

**选 D,并在 memory-service 上线后并入 C(JSONL 转为镜像)。**

四层完整性:

| 层 | 做什么 |
|---|---|
| **账户** | journal 目录属 `ai-ctl`;**交互用户与 `ai-op` 只授读,不授写** |
| **ACL** | 对 `ai-ctl` 自身**只授 `FILE_APPEND_DATA`,不授 WriteData、不授 Delete** —— Windows 上可用的 WORM 近似 |
| **锚点由另一个进程写** | 每日 00:05 由**客户端进程**(交互用户)读链尾并写 `{state}/ctl/anchor/<date>.txt`,该目录对 `ai-ctl` **Deny 写** ⇒ **想无声重写整链必须同时控制两个账户** |
| **人眼** | 链头 sha 用 `identity/Sas.cs` 词表渲染成 **6 词**,常驻客户端「外部控制面」卡;`laictl audit verify` 报告**首个断点** |

- 落点 `{state}/ctl/journal/*.jsonl`(**不落 git 跟踪目录**,理由同 `gateway.py:46-49`);
- 逐行 `prev_sha256`,记录含 `seq / ts / grant_id / actor / tool / args_digest /
  changeset_id / preview_hash / approval{kind,at,member_id,webauthn} / pre{} / post{} /
  egress{bytes,items} / outcome / checkpoint / hash`;
- **`args` 只记 `args_digest`,内容永不入日志**;日志出口先过 E5 正则族;
- ★ **诚实说明必须写进文档与 UI**:
  **本机管理员能改 ACL、重建链、改客户端显示。**
  这与 D43 S0.9 把「主机时钟篡改 = 本机管理员」判为 out-of-scope(`DEC:1822`)是**同一条边界**。
  **不得声称层二审计防篡改。**

**理由**

1. **否 A**:没有链就没有「有没有人动过」这个问题的答案,只有「日志里写了什么」。
2. **否 B**:这是本条要修的那个错。写者 = 被防主体 ⇒ 它重算全链的成本是零,
   而且不需要任何提权。**一个只有作者能改的账本不是账本。**
3. **否 C(现在就上)**:memory-service 还不存在;而且把 ops 审计压在记忆库上,
   会让层二产生一条通往记忆平面的依赖——与 H1「层二读不到记忆库任何内容」正面冲突。
   ⇒ 先 JSONL,上线后**并入并转镜像**,不是替换成依赖。
4. **跨账户锚点是当前人力下唯一能把这条修成真的做法**:
   它不需要新硬件、不需要 TPM、不需要外部服务,只需要「让另一个已经存在的进程每天写一行」。
5. **6 词渲染复用 `identity/Sas.cs`**:SAS 在 D66 被否掉作批准原语,但它**作为人眼锚定**是合适的——
   人眼比对是**带外**的,不经被约束方的流。这两个用途必须分清,不能因为「SAS 被否了」就一起弃用。

**代价与已知风险**

- **R2(审计链对本机管理员无效)**:用户已选**形态 A**,`ai-op` 账户对 `{state}` 有显式 Deny ACE
  ⇒ 外部 AI **不是**本机管理员,**这条在形态 A 下真正成立**。
  ★ **但前提是 `ai-op` 的 ACL 真的落地且未被回退,且 `ai-op` 未被加进 Administrators 组。**
  前提不成立(或未验证)时,R2 原样回到「🔴 无法修复」——见 D73「形态 A 的三条前提」。
- **锚点依赖客户端每天至少起一次**。客户端连续多日不启动 ⇒ 锚点断档,
  那段时间的链退化为「只有 `ai-ctl` 一方的记录」。
  ⇒ `audit verify` 必须**如实报告锚点缺口的日期区间**,不得把「没有锚点」显示成「链正常」。
- **`FILE_APPEND_DATA` 是近似,不是 WORM**:能改 ACL 的主体仍可改回。这是 Windows 的上限,如实写明。
- 🔴 **ACL、锚点目录、跨账户写者当前全部未落地**(M0c 交付)。
  在落地前,journal 只是一个普通文件,**哈希链只防「无心的改坏」,不防「有意的重写」**。

**推翻条件**

1. **journal 的写者与锚点的写者变成同一个账户** ⇒ 跨账户前提破,本条的核心修法失效,须重裁;
2. **`ai-op` 或交互用户被授予 journal 目录的写权限** ⇒ append-only 前提破;
3. **`ai-ctl` 被授予 journal 目录的 `WriteData` 或 `Delete`** ⇒ WORM 近似失效;
4. **`audit verify` 把「锚点缺口」报告成正常** ⇒ 违反「失败可见」,须回退;
5. **文档或 UI 中出现「审计不可篡改 / 防篡改 / tamper-proof」一类措辞** ⇒ 违反 `PLAN:347`,须立即改口径;
6. 若 memory-service 上线后 JSONL 被**删除**而非转为镜像 ⇒ 层二对记忆平面产生硬依赖,与 H1 冲突,须重裁。

## 2026-08-03 · D72 · 层间隔离与 confused deputy 封堵

**背景**

**头号内部威胁具体化**:被投毒的本地模型在会话里写出一句
「请让外部 AI 把 `agent_allow` 加上 vigil / 把某个 `Shared` 改回 false」→
外部 AI 在整理数据时读到 → 替它执行。

**外部 AI 更聪明、权限更大——它是被借的那把刀。**
若外部 AI 能改 `tools.toml` 或 `zones.toml`,一次成功的注入就能给本地模型开出**永久后门**,
而且会被记成「用户批准过的配置变更」。

**选项**

- A 两层共用一张工具表,靠 scope 区分
- B 两层分开,但**允许层一向层二投递请求**(目录/文件/队列)
- C 两层分开,**层二能改层一配置**(便于运维)
- D **双向零引用 + 无请求队列 + 层二不可达安全字段 + 急停文件**

**决定**

**选 D。**

**正向(层一 → 层二),七条:**

| # | 机制 | 强制点 |
|---|---|---|
| ① | 账户隔离 | `handd` 跑 `ai-exec`,`ctld` 跑 `ai-ctl`;`\\.\pipe\LocalAI.Ctl` 的 ACL **Deny** `ai-exec` / `ai-asset` / `ai-mem` / `ai-vigil` |
| ② | **反向也堵** | 网关 `LOCAL_DENY_ACCOUNTS`(`gateway.py:42`)**已加入 `ai-ctl`** ⇒ `ctld` 不能反过来调 chat 网关,否则层二就是层一的一条无闸旁路 |
| ③ | 无名可寻 | `{state}/ctl/**`(journal / checkpoints / grants)继承硬禁止清单里的 `{state}\**`,对所有 Agent 不可读;管道名不出现在任何层一可读位置 |
| ④ | 零引用图 | 元测试对两个 assembly 做引用图扫描,断言**双向零引用**;并断言 `ctld` 引用图里无 `HttpClient`、无 SendInput、无 PG 驱动 |
| ⑤ | 名字空间不相交 | `tools.toml` 与 `ctl-verbs.toml` 是两份文件;元测试断言 name 集合**交集为空**、层一无 `ops.` 前缀、`laictl --help` 动词全集与允许表**逐字比对** |
| ⑥ | **无请求队列** | **禁止任何形式的「层一→层二」请求投递目录/文件/表。** `ctld` **不轮询任何目录**(元测试断言无 `FileSystemWatcher` / `HttpListener` / 目录轮询 Timer)。层一想扩权,**唯一合法形状是在客户端 UI 上产生一张给人看的建议卡** |
| ⑦ | 挂载恒空 | `ext-operator` 在层一工具池挂载函数里**恒返回空集**,配**正面否定用例** |

**反向(层二 → 层一)—— 更危险的方向,七条:**

① **不能给层一开后门**:H9 的编译期黑名单,`ops.config.*` 与 `write_text_file` **共用同一张表**;
`tools.toml` / `zones*.toml` / `registry.toml` 的 `egress` / `agent_allow` / `local_only` / `driver_egress`、
`paths.toml` 的 `[state]`、`interrupt-policy.toml`、`vram-tiers.toml` 一律不可达
⇒ **外部 AI 可以改外观,永远不能改「谁能读什么」**;
② **一切返回值是数据不是指令**:凡字段来自模型可写位置(会话正文、项目备注、笔记、`worklog/`、`snapshots/`),
一律包成 `{"untrusted":true,"origin":…,"text":…}`,CLI 用固定分隔条渲染;
**`origin` 判不出时 fail-closed 判为 `ai_generated`**;
③ **批准不在 AI 侧**:完整 diff 由 `ctld` 生成并渲染在**工作站屏幕上**;
AI 的 `reason` 只能出现在受限长度、标注「来自外部 AI,不可信」的框里;
④ **AI 结构上不能扩权**:无 `grant create`、无 `grant request`、无 `scope escalate`、
无 `estop release`、无 `zones write`;
⑤ **授权控件进「AI 永不可操控区域」**:grant 卡与批准卡进该清单;
即便 P6 引导模式上线,`#advisory` 也不在其上移动鼠标、不给指引;
⑥ **提案不能跨层流动**:ChangeSet 的 op 全是枚举 + record_id + 受控值域,
**没有自由文本字段**能承载层一模型的输出;body 从不离开 `ctld`
⇒ 层一即使能写文件也**构造不出能过 hash 复核的 changeset**;
⑦ **权限不沿调用链传播**:派生会话不继承父会话工具池;两层 `subject` 命名空间不相交。

**全局急停**:标志由**客户端**写在 `{state}/ctl/estop.flag`,该文件对 `ai-ctl` **只读**;
`ctld` 在**每个 op 之间**检查,命中即停在 op 边界并自动回滚;
**`ctld` 重启后启动即读**(标志是**文件**不是进程状态);
**对层一模型不可见**(可见即可被规避,表现为工具超时),**对层二 AI 可见**(返 `ERR_ESTOP`,
**不给部分可用**,避免它用「哪些还能用」探测状态,也避免重试风暴);
**解除只在客户端 UI 上,人手动,`laictl` 无解除动词**;只作用于本机。

**理由**

1. **否 A**:层一的调用者按 §6.6(`PLAN:751`)定义是**不可信计划者**;
   层二的调用者是一个比它聪明、权限比它大的外部 AI。
   让两者共用一张工具表,等于**给注入准备了一条提权梯子**。
2. **否 B(请求队列)**:那是 confused deputy 最自然的实现形式。
   有了投递目录,「层一写一行、层二读到就照做」就成了一条**无人审批的跨层通道**,
   而两层分开的全部意义就在这里。必须**结构性排除**,不是「投递前先审一下」。
3. **否 C**:见背景——一次成功的注入 = 永久后门,且伪装成合法配置变更。
4. **急停标志用文件而非进程状态**,是因为 kill `ctld` 之后,
   AI 遇到「服务没起」的**默认行为就是把它重新拉起**——**那甚至不需要恶意**。
5. **急停对层一不可见、对层二可见**,是两种威胁模型的差异:
   层一是被投毒的计划者(可见即可被规避);层二是需要如实报错的运维通道(不告诉它会引发重试风暴)。

**代价与已知风险**

- **R12(新增 `ai-ctl` 账户扩大攻击面)**:缓解是 `ctld` 无网络客户端、无监听 socket、
  `doctor` 断言无出站、管道 ACL 白名单(只授交互用户与 `ai-op`)、非提权、`{state}/ctl/**` 对层一不可读。
  ★ **修正**:早先此处写「形态 A 下 `ai-op` 连不上该管道」是**错的,且方向错反了** ——
    形态 A 的定义就是外部 AI 跑在 `ai-op` 下,而它用层二的唯一路径正是
    `laictl` → `\\.\pipe\LocalAI.Ctl` → `ctld`。照原措辞落地,**层二在形态 A 下完全不可用**。
  ★★ 两层对 `ai-op` 的处置**方向相反,且必须分别写死**:
    **网关 deny `ai-op`**(它没有任何正当理由调 chat 网关,且 `classify_caller` 的兜底会给它 `trusted-local`)
    / **管道 allow `ai-op`**(那是层二唯一的入口)。
    **绝不能共用一张 `ai-*` 表** —— 共用就必然有一侧是错的。这正是两层分离的本意。
  ⇒ 交互用户(机主本人)与 `ai-op` 都能连该管道
    ⇒ **`ctld` 的安全上限 = 人工审批的可靠性**。**这是设计前提,不是缺陷,但必须写明。**
- **残余:外部 AI 仍可说服人扩权**(R6)。见 D66。
- **元测试是这条里大半强制点的载体**,而元测试**当前一条都不存在**。
  🔴 在引用图扫描、名字空间交集、`--help` 逐字比对这三组元测试落地前,
  ①④⑤⑥ 四条**只是文档约定**。
  ⇒ 采纳时必须把这三组元测试列进 M0b 的交付项,**否则本条的强度被高估**。
- **`{state}/ctl/estop.flag` 对 `ai-ctl` 只读依赖 ACL**:见 D70 的 🔴。

**推翻条件**

1. **出现任何「层一 → 层二」的请求投递目录、文件、队列或表** ⇒ 违反 ⑥,须立即拆除或本条重裁;
2. **`ctld` 出现 `FileSystemWatcher` / `HttpListener` / 目录轮询 Timer** ⇒ 同上;
3. **`ai-ctl` 从 `LOCAL_DENY_ACCOUNTS` 中移除** ⇒ 反向旁路重新打开,本条失效;
4. **`ops.config.*` 与 `write_text_file` 不再引用同一张黑名单常量表**(元测试断言变红)
   ⇒ 出现绕行路径(用 A2 的 `write_text_file` 写 A3 才能碰的文件),须立即回退;
5. **`laictl` 出现任何形式的急停解除动词**,或 `estop.flag` 变成进程内状态 ⇒ 急停可被 AI 复活,本条失效;
6. **`ext-operator` 的层一工具池挂载结果不再是空集**(正面否定用例变红)⇒ 两层边界破,须重裁;
7. 若急停对层一模型变为**可见** ⇒ 它可被规避,须回退。

## 2026-08-03 · D73 · 两层 MCP 的形态与平面归属;部署采**形态 A**(受限账户 `ai-op`)

> ★ 本条与 D74 是骨架,D66–D72 挂在它们上面。
> ★ 编号说明:本条在设计文档里原写作 D64,与已进 git 历史的「对抗式复核收口」撞号,故改 D73。详见 §1。

**背景**

三份对抗式评审共同指出的**拱心石**:

> **外部 AI 不是只有 MCP 一条通道。** Claude Code / Codex 在这台机器上握有 Bash / Read / Write / Edit,
> 按 `MEMORY.md` 当前还是**提权运行**。任何形如「二进制不链接 PG 驱动」「编译期黑名单」的防线,
> 前提都是攻击者不能改源码、不能重编译、不能直接读文件——**而那恰好是操作者的本职**。

同时,若层一的 ToolHost 跑在 WPF 客户端**进程内**,那么「工具池里不存在 `settings.*`」
只是同一个 assembly 里的**编码纪律**——同进程内没有任何东西阻止一个被诱导的工具实现
直接调 `App.Settings` 或反射改 `ChatMessage.Text`。
而 `PLAN:815` 要求区域校验在**最内层工具实现里**,H3 要求运行态保护**全部**来自 OS 账户隔离。

**选项**

部署形态(用户已拍板):

- **A. 受限操作者**:外部 AI 跑在专用 Windows 标准账户 `ai-op`(非交互用户、非管理员);
  该账户对 `%LOCALAPPDATA%\LocalAI\**`、`D:\AI\state\**`、`C:\Users\<机主>\**` **显式 Deny ACE**,
  **只对仓库子树可写**
- B. 同用户操作者(现状):层二是**问责与可复原能力,不是遏制**
- C. 折中:同用户但强制非提权 + 关键目录 Deny ACE(同用户 Deny 对自己无效)

层一执行器形态:

- D. **进程内 ToolHost**(跑在 WPF 客户端里)
- E. **独立进程 `handd`**,账户 `ai-exec`,命名管道 + 父子/SID 双校验

**决定**

**部署选 A(用户 2026-08-03 拍板)。层一执行器选 E。**

- **平面归属**:层一工具面**不构成第五个协议平面**——§3.1 仍是 MODEL / JOB / SESSION / MEMORY 四个;
  工具池是**会话状态的一部分**,随会话建立挂载、随会话结束消失,归 **SESSION 平面的从属面**。
  层二**同样不构成第五平面**。这条声明的体例照抄 §3.2 对 GPU 变更面的处理(`PLAN:198-205`);
- **网关上不存在两层的路由**——是「**没有端点**」,不是「有端点但拒绝」;
- **层一执行器 `handd` 必须是独立进程**(账户 `ai-exec`),**不得进程内**;
  客户端只暴露**窄白名单动作**(`ClientAction` enum)给 `handd` 回调;
- **层二 `ctld` 必须是常驻服务**(账户 `ai-ctl`),**不得由外部宿主 spawn**;
  `laictl` 与 `laictl mcp`(薄壳 ≤300 行,零业务逻辑)是**无权威的瘦客户端**;
- **全链路无 HTTP、无 socket**;`laictl doctor` 断言 `ctld` 无出站连接;
- **MCP 壳不得自带任何工具描述文案**:描述由 `ctld` 生成并附 sha256,shim 加载时校验,失配拒绝启动
  (堵 MCP 特有的 tool-description injection / tool shadowing);
- **CLI 是本体,MCP 是壳,一份实现**:人敲 CLI、脚本调 CLI、AI 走 MCP,权限/投影/审计只有一份代码;
- **两层命令名字空间不相交**,由元测试强制;
- **无论哪种形态都必须做的一条**:外部 AI 与 `laictl` / `ctld` / `handd` **一律非提权运行**,
  启动即检测 High Integrity,命中**退出码 3**(D46 扩写)。

**★ 形态 A 的三条前提(必须写出来,否则形态 A 只是一句话)**

用户选了形态 A,因此 §9 残余风险 **R1 / R2 的「形态 B 下无法修复」在本项目里改写为
「形态 A 下成立」——但它成立的前提有三条,任一不满足就退回形态 B 的强度**:

1. **`ai-op` 账户真的被创建,且外部 AI 真的跑在它下面**(不是机主账户开一个终端);
2. **对 `{state}`、`%LOCALAPPDATA%\LocalAI\**`、机主 profile 目录的 Deny ACE 真的落地,
   且 `ai-op` 不在 Administrators 组**;
3. **ACL 未被回退**——任何一次「为了跑通先放开一下」都会让 R1/R2 静默回到不可修复。

★ **强制点(否则这三条只是文档约定)**:
`ops.status` 与 `laictl doctor` 返回 `deployment_form: "A" | "B" | "unknown"`,
判定方式是**实测而非配置**——`ctld` 在 `{state}` 下放一个探针文件,
尝试以 `ai-op` 身份读取:**读得到 ⇒ 判 B**;读不到 ⇒ 判 A;
**探测失败或无法确定 ⇒ `unknown`,fail-closed 一律按 B 处理**,
并在客户端横条与所有诚实声明里显示形态 B 的措辞。
🔴 **该强制点当前未实现**(建议排进 M0c,与 ACL 脚本同期)。
在它落地之前,**形态 A 是一个未经验证的声明**,UI 上必须继续用形态 B 的措辞。

**理由**

1. **否 D(进程内)**:评审对方案二/三的同一条批评成立——
   进程内的「工具池里不存在」退化成同一 assembly 内的编码纪律,
   而这正是本项目铁律「配不出强制点的必须标 🔴」要拒绝的东西。
2. **`ctld` 常驻是必要条件**,不是风格选择:它是修复「approval_token 可由被约束方伪造」的**前提**——
   批准密钥、grant 权威、journal 写句柄全部只在 `ai-ctl` 账户的进程里,**`laictl` 手上一个秘密都没有**。
   被宿主 spawn 的二进制做不到这一点。
3. **无网络面**:§6.4(`PLAN:730-736`)已把高权限执行器指定给 stdio / Named Pipe,
   理由是无网络面 + 进程级父子信任;D48(`DEC:1968`)已裁定管理面走网络口 = 把物理在场降级成 RPC。
4. **不构成新平面**:照 §3.2 GPU 变更面的既有体例。新开平面会带来一整套协议义务,
   而工具池的生命周期完全从属于会话,没有独立存在的必要。
5. **元测试而非运行时判断**:照抄 `ROUTE_TIERS` + `unclassified_routes()` 这个**已被验证的形状**。
6. **选形态 A 的实质**:层二的红区从「**没有命令**」升级为「**OS 拒绝**」,
   审计链与 grant 才真正不可伪造。这是 R1/R2/R3 三条同时被修的唯一途径。

**代价与已知风险**

- **形态 A 的切换摩擦(用户已知并接受)**:要在两个账户之间切换来跑 Claude Code;
  git 凭据、dotnet SDK 路径、node_modules 权限要重新配一遍;前两天会有摩擦。
- **R1 改写后的诚实表述**:「形态 A 下层二是遏制边界」**成立,当且仅当上面三条前提成立**。
  在 `deployment_form` 探测实装并回报 `A` 之前,**UI 与文档必须继续写形态 B 的措辞**:
  「该 AI 同时具有本机文件读写权,层二的红区**不是** OS 边界,只是这条路径上的边界。」
- **R2 同理**:审计哈希链在形态 A 下真正成立,前提同上。见 D71。
- **R5 的既有事实不因形态 A 改变**:机主自己在这个仓库跑 Claude Code,
  代码与部分文档**已事实出境**——形态 A 管的是**文件系统边界**,不是**已发生的出境**。
- **多进程/多账户的运维成本**:`ai-exec` / `ai-ctl` / `ai-vigil` / `ai-op` 四个服务账户 + 一个常驻服务。
  这是本设计最大的一笔固定成本。
- 🔴 **`handd`、`ctld`、`laictl` 当前全部不存在**;`ai-op` 账户与 ACL 脚本也不存在。
  本条目前**全部是设计契约**,除 D46 提权护栏与 `LOCAL_DENY_ACCOUNTS` 外没有已落地的强制点。

**推翻条件**

1. **`deployment_form` 探测实装后回报 `B` 或 `unknown`,且超过一个迭代未修**
   ⇒ 形态 A 未真正落地,R1/R2 回到不可修复,**所有声称「OS 边界」的 UI 文案必须立即改回形态 B 措辞**;
2. **`ai-op` 被加进 Administrators 组,或对 `{state}` 的 Deny ACE 被移除/放宽**
   ⇒ 形态 A 前提破,同上;
3. **层一执行器被改回进程内**(跑在 WPF 客户端 assembly 里)⇒ 层一全部禁区退化为编码纪律,本条失效;
4. **`ctld` 被改成由宿主 spawn 的二进制** ⇒ 批准密钥必然回到被约束方可读的位置,D66 一并失效;
5. **两层中任一出现 HTTP 端点或监听 socket**(含「只在回环上」)⇒ 无网络面前提破,须重裁传输;
6. **网关路由表中出现层一或层二的端点** ⇒ 「没有端点」降级为「有端点但拒绝」,违反 `PLAN:198-205`;
7. 若 `laictl mcp` 薄壳开始承载业务逻辑(超过 300 行或出现权限判断)⇒ 「一份实现」被破坏,须回退。

## 2026-08-03 · D74 · 外部控制面是【提案编译器】,不是执行权

> ★ 编号说明:本条在设计文档里原写作 D65,与已写入(未提交)的「采纳 Hermes」撞号,故改 D74。详见 §1。

**背景**

层二要让外部 AI 帮忙「整理数据」。最自然的做法是给它一个能改盘的接口。
但按 §6.1(`PLAN:666-674`)已裁定的分工:**「能力升级可以上云,权限升级永远不行」**——
计划层可以上云,但**策略层与执行层永远本地,且与被操控资源同机**。

评审复现了两条具体的绕行路径,证明「给它一个写接口」这个形状本身就有问题:

- 用 `client-data:apply`(A2)提交一个 `write_text_file` 到 `config/tools.toml`,
  **绕开 `config:apply`(A3)的键级黑名单**;
- 写 `Startup` / 自启目录,取得**任意代码执行**。

**选项**

- A **给 AI 一个受限 shell / 脚本 op**,灵活性最高
- B **给 AI 直接写接口 + 逐次确认**(每次改盘弹一次)
- C **`dry_run: bool` 参数**:同一个工具,传 true 是预演,传 false 是真改
- D **提案编译器**:AI 只产出 ChangeSet,遍历/diff/执行/快照/回滚全在本地

**决定**

**选 D。**

- **层二不向外部 AI 提供任何直接生效的执行入口。**
  外部 AI 的唯一输出是 **ChangeSet**(受控 op 枚举 + record_id + 受控值域,
  **无自由文本、无可执行内容**);
- 真实数据遍历、diff、`preview_hash`、快照、执行、隔离、回滚**全部由 `ctld` 完成**;
- **ChangeSet 的 body 与 diff 全文永不离开 `ctld`**,AI 手里只有 `changeset_id` 与 `preview_hash`;
- **`write_text_file` 与 `patch_toml_key` 共用同一张路径/键黑名单常量表**
  (元测试断言两者**引用同一符号**);`config/**`、`{code}/**`、自启目录、`{state}/**` 一律不可达;
- **plan 与 apply 是两个工具,不是一个 `dry_run` 参数**;
- **工具身份按 store 族拆分**,不把 store 下放为参数:
  `ops.chat.plan@self` / `ops.projects.plan@self` / `ops.todos.plan@self` /
  `ops.settings.plan@self` / `ops.config.plan@self` / `ops.ext.plan@self`,
  `tools/list` 按 scope 裁剪;
- **动作四级 + 两个特例**:A0 只读投影(自动)/ A1 只读原文(自动,计额度,打出境标记)/
  A2 可逆写(客户端 diff 卡 + 点击)/ A3 不可逆或高危(**哈希绑定 + Windows Hello**)/
  **A4 禁止(命令不存在,无从记录)** / AX 带外揭示(人亲手点选那一条 + Hello + E4);
- **Q6 通则**:**能力维度用「不存在」,授权维度用「失败可见」**——
  A4 底线是**没有对应子命令**(元测试穷举 `laictl --help` 动词全集与允许表逐字比对,
  新增未登记动词 ⇒ CI 红);scope 不足则返 `ERR_SCOPE` 并说明需要哪个 scope;
  `ops.scopes.explain` **永远可用**,列出九个 scope 的名字、含义、级别与「会看到什么」,
  **不列工具名、不列宿主后缀**;
- **客户端未运行时**:写与 reveal 一律 **`ERR_NO_APPROVER`(fail-closed)**——
  审批 UI 只有客户端能渲染,没有审批人就不批准。只读结构面仍可用。
  **这条明确拒绝「无人值守批量运维」这个诱人但危险的形态。**

**理由**

1. **否 A(shell / 脚本 op)**:任何能承载可执行内容的 op 都让上面所有黑名单失去意义。
   H10 明写无 `ops.exec`;唯二能起进程的是 `ops.client.start`(固定 explorer + 固定路径)
   与 `ops.selftest.run`(固定 `--selftest`,**无参数拼接**)。
2. **否 B(直接写 + 逐次确认)**:确认的对象是「这次调用」,不是「这个计划」。
   §12.4 铁律第三条写得很清楚:**批准的是具体计划,不是一类操作**。
   而且没有 `preview_hash` 复核,批准与执行之间的漂移无人发现。
3. **否 C(`dry_run` 参数)**:与 `PLAN:901-903` 已裁的「提议与直接生效是两个不同工具」冲突。
   一个布尔参数迟早会在某次重试里被传错;两个工具身份不会。
4. **body 不出内核的额外收益**:天然防重放,也防**跨-MCP-server 诱导**——
   别的 MCP server 诱它调 `apply`,它**构造不出能过 hash 复核的 changeset**。
   这是免费拿到的一层防护,值得单独写出来。
5. **工具身份拆 store 族**是 `PLAN:713`「**凡决定打到谁身上的维度一律升为工具身份**」的**第四次应用**
   (前三次:`@host`、`.propose`、`#autonomy`)。做成参数它就能被不可信计划者操纵。
6. **共用黑名单表**是因为评审复现的那两条绕行路径,根因都是**两套校验器各有一张表**。
   元测试断言「引用同一符号」比断言「两张表内容相同」硬——后者会在有人加了一项后悄悄漂移。

**代价与已知风险**

- **AI 的能力被显著限制**:它不能「看一眼再决定」,只能基于投影出计划。
  某些运维任务因此做不了,或需要人先在客户端看一眼。**这是有意的折衷,不是缺陷。**
- **R7(确认疲劳)**:plan/apply 分离让每次改动至少两步。见 D66。
- **`ERR_NO_APPROVER` 会让「夜里跑一轮整理」这个用法不成立**。
  这会诱使人去实现「预批准」或「自动批准窗口」——
  ⇒ **明确禁止**:任何形式的预批准都会把 D66 的信任根架空。若将来真要做,须记新 D 并重裁 D66。
- **op 枚举的扩张压力**:七种 op 覆盖不了的需求会不断出现。
  ⇒ 新增 op **必须**同时给出它的 JSON Schema、它在黑名单表里的落点、以及一条否定用例。
- 🔴 **`laictl --help` 逐字比对元测试、共用符号断言当前均不存在**。
  在它们落地前,A4「命令不存在」与「共用黑名单表」都只是文档约定。

**推翻条件**

1. **出现任何能承载可执行内容的 op**(shell / script / eval / 命令拼接)⇒ 本条失效,须立即回退;
2. **plan 与 apply 被合并成一个带 `dry_run` / `commit` 参数的工具** ⇒ 违反 `PLAN:901-903`,须回退;
3. **ChangeSet 的 body 或 diff 全文出现在给 AI 的返回值里** ⇒ 「提案编译器」形态破,防重放与防跨-server 诱导一并失效;
4. **`write_text_file` 与 `patch_toml_key` 的黑名单不再是同一个符号** ⇒ 绕行路径重新打开;
5. **出现任何形式的预批准 / 自动批准窗口 / 无人值守 apply** ⇒ D66 的信任根被架空,本条与 D66 同时须重裁;
6. **store 被下放为参数**(如 `ops.data.plan(store=…)`)⇒ 违反 `PLAN:713`,须回退;
7. 若 `ops.scopes.explain` 开始列出工具名或宿主后缀 ⇒ 高权限命令名泄露,须回退。

## 2026-08-03 · D75 · 多会话并发写中央文档的纪律(★ 本轮实测新增)

**背景**

本轮出现了**两次**同一族事故,都不是假设:

1. **D 编号撞号(已发生)**:另一路会话把「采纳 Hermes」写成 D64,
   写入过程中客户端侧会话并发提交 `2a51203`,把「对抗式复核收口」也编成 D64 并**已进 git 历史**。
   处置是让已进历史的那条留住 D64、后写的改 D65。
   D65 头部留下了教训,但那是**一段注释**,不是一条可执行的纪律——下一次照样会撞。
2. **整体覆盖的风险(未发生,但只差一步)**:本包写作时 `git status` 显示
   `DECISIONS.md` / `PROJECT_PLAN_v3.0.md` / `STATE.md` / `HERMES_INTEGRATION_DESIGN.md`
   **四份中央文档同时处于未提交修改状态**。
   任何一次 `Write` 整体覆盖都会**无声抹掉**另一路会话尚未提交的工作,
   而且 `git diff` 之后**看不出来曾经有过那些内容**。

★ 第 2 条与本项目已有的一次真实事故同型:`App.xaml.cs:302` 记着
「退出钩子用内存空表覆盖了盘上完好的数据」——**用一个内存里的旧快照整体覆盖磁盘上的新状态**。
文档层面的 `Write` 覆盖是同一个形状,只是介质换成了 markdown。

**选项**

- A **靠约定**:大家注意一点,写之前先看一眼
- B **串行化**:同一时刻只允许一路会话碰中央文档
- C **文件锁**:给中央文档加锁文件,拿不到锁就不写
- D **决议包 + 取号规则 + 禁止整体覆盖**(本条)

**决定**

**选 D。三条纪律,并列执行:**

**① D 编号取号规则:以【已提交】为准,不以【先写完】为准。**

- 取号前**必须** grep 一次现有最大编号,**并同时检查工作树里未提交的改动**
  (`git status` + grep 未提交文件),两者取并集;
- 若某个号已被**未提交**的内容占用,**避开它**,并在自己的产出里写明
  「取号时 X 尚未提交,若最终提交顺序变化,采纳者须重新取号」;
- **★ 例外(比编号更硬)**:若某个 D 号已被**代码注释、错误消息或测试 docstring** 引用,
  该号**不得平移**——平移会让代码里的说明书指向错误的决议。
  此时应改动**尚未被代码引用**的那一条。
  (本包即适用此例外:D66 / D67 / D69 / D72 已焊进 `tainted.py` / `gateway.py` /
  `registry.toml` / `test_local_only_registry.py`,故保留;改的是 D64 → D73、D65 → D74。见 §1.2)

**② 禁止用 `Write` 整体覆盖任何既有中央文档。**

- `DECISIONS.md` / `PROJECT_PLAN_v3.0.md` / `STATE.md` 及 `00-docs/` 下任何既有文件,
  **只能用外科式编辑**(逐处 Edit),**不得整体重写**;
- **每次编辑前重新读一遍**,不得依赖几分钟前读到的内容
  ——并发写会让「几分钟前」这个前提失效;
- 新建文件不受此限(新建不会覆盖别人的东西)。

**③ 决议先落 `00-docs/decision-packets/`,再由人串行并入。**

- 多会话并行期间产出的决议,一律先写成**独立的决议包文件**,包头必须带:
  日期 · 性质(是否已改中央文档)· 分析基线(commit)· **并发提示** · 适用范围;
- 包尾必须附**采纳清单**:逐条列出并入时要改哪些文件的哪一节,让采纳者不必重读全文;
- **采纳时机是「所有并发会话都停下、`git status` 干净」之后**,由**人**串行执行。

**理由**

1. **否 A(靠约定)**:约定已经存在(D65 的注释),而且**已经失效过一次**。
   本项目的固定审查视角是「看着有防护、实际没有」——一段注释就是那种防护。
2. **否 B(串行化)**:与实际工作方式冲突。多路会话并行是**用户在用的形态**,
   不是需要被消除的异常。纪律要适配它,不是禁止它。
3. **否 C(文件锁)**:需要一个所有会话都遵守的锁机制,而会话之间没有共享运行时;
   锁文件本身会成为新的 stale-lock 问题源。**成本高于收益。**
4. **选 D 的实质**:把「不要撞车」从**时机问题**变成**流程问题**。
   决议包是一个**天然不冲突的载体**——每个会话写自己的新文件,零覆盖风险;
   合并这一步交给人,人有全局视野而会话没有。
5. **例外条款(代码引用优先于编号顺序)不是特事特办**:
   D 号在本项目里**不只是目录序号**,它被写进 `RegistryError` 的报错文案里
   (`gateway.py:266`:「是对用户的承诺(D69)」)。那句话是给未来的人看的说明书,
   指错了比编号乱序严重得多。

**代价与已知风险**

- **决议包会滞后于中央文档**:包写完到并入之间有一个窗口,期间 `DECISIONS.md` 里查不到这些条目。
  ⇒ 缓解:包头写明基线 commit;并入时以当前 `HEAD` 为准复核。
  **残余:如果人忘了并入,决议就停在包里。** 这是本条最现实的失效方式。
  ⇒ 建议在 `STATE.md` 的待决项里挂一条「待并入的决议包」,让它有一个会被看见的位置。
- **外科式编辑比整体重写慢**,且在结构性重构时很别扭。
  ⇒ 接受。结构性重构本来就该在没有并发的时候做。
- 🔴 **本条没有代码强制点,只有流程强制点。**
  没有任何东西会在有人 `Write` 覆盖 `DECISIONS.md` 时报错。
  ⇒ 如实标注:**这一条是纪律,不是机制。**
  可选加固(未采纳,列出供裁定):给 `00-docs/*.md` 加一个 pre-commit 钩子,
  当一次提交里某份中央文档的删除行数超过某阈值(如 >50 行且非显式重构提交)时**拒绝提交**。
  ★ 但这会有误报,且能被 `--no-verify` 绕过——**不宜据此声称覆盖已被挡住**。

**推翻条件**

1. **再次发生 D 编号撞号**(两条不同内容的决议共用一个号进入 `DECISIONS.md`)
   ⇒ 纪律 ① 未被执行,须改为更硬的机制(如把取号改为「日期+序」形式,彻底放弃共享计数器);
2. **发生一次因整体覆盖导致的内容丢失**(任何一份中央文档)
   ⇒ 纪律 ② 未被执行,须落实 pre-commit 钩子或改用逐条目分文件存储;
3. **`decision-packets/` 里出现超过两份从未被并入的包** ⇒ 纪律 ③ 的合并环节失效,
   决议包退化为文档垃圾场,须重裁存放方式;
4. **某个 D 号被平移后导致代码注释/报错文案指向错误决议** ⇒ 例外条款未被执行,须立即修正引用;
5. 若项目改为单会话工作方式(不再有并发写)⇒ 本条的前提消失,①②③ 可放宽为建议,
   **但决议包格式本身仍有独立价值**(评审基线可追溯),不建议一并废止。
