## 2. 中心论点复核:成立,而且论据比协调层给的更硬

协调层的原话:

> 记忆(D45/D52)与模型本来就只在主机。用户对通用客户端的定位是「只是读取和跨网络发送」。
> ⇒ 共享的会话/待办是今天唯一一个不遵守这条的东西 —— 它有多副本。

**【静态阅读】复核结论:成立。** 而且真正的论据不是"对齐原则",是**这一条**:

> D52 自己写着一条硬边界:
> 「**即使会话"只在本机",每次提问的上下文仍要送到主机**才能算出答案 ——
>   区别是主机不落盘、算完即弃。」(`DECISIONS.md:2186-2187`)

⇒ 也就是说,**共享会话的正文本来就必然经过主机**。今天多出来的不是"送不送",
而是"**副机要不要再自己存一份、并且以它为准往回推**"。
把这一份去掉,去掉的是**权威性**,不是可达性。这比"和记忆对齐"是更强的理由。

★ 而副本那一份**今天确实落在副机磁盘上**【静态阅读】:
共享会话与消息进 `ClientStore.ChatPath`(`chat.json`),家庭待办进 `ClientStore.TodosPath`
(`todos.json`)—— `Services/ClientStore.cs:26,28`。这不是缓存,它是**渲染源**:
界面读的是 `ChatCenter` / `TodoCenter` 的内存表,而它们从这两个文件加载。

## 3. 第 1 条 · 真损失有多大

### 3.1 今天主机不可达时,副机**看得到什么 / 改得了什么**(逐条,【静态阅读】)

| 东西 | 今天看得到? | 今天改得了? | 落点 |
|---|---|---|---|
| 共享会话列表 + 已拉到的全部消息 | ✅ 完整 | ✅ 改标题、再说一句 | `ChatCenter._sessions` / `._messages` ← `chat.json` |
| 家庭待办 | ✅ 完整 | ✅ 新建 / 改 / 勾选 / 删 | `TodoCenter._items` ← `todos.json` |
| 把本机会话**提升为共享** | — | ✅ **本地即刻标 `Shared=true`** | `ChatCenter.ShareSession:223` |
| 对方在断线期间的改动 | ❌ | — | — |
| AI 回答 | ❌ | — | 硬约束,D52 已写 |

**补推那条链的形状**【静态阅读】:改动进 `SyncClient._pending`(**纯内存**),
`FlushAsync` 失败就留着;而**即使进程重启把 `_pending` 丢光**,
`ReconcileAsync` 会在每次连上时把 `FullSet()`(= `Todos.SharedSnapshot()` +
`Chat.SharedSnapshot()`)**整份重推一遍** —— 自愈靠的是**本机那份持久副本**,不是队列。
⇒ 拿掉副本,补推这条链**没有可推的东西了**,它不是"退休",是**失去了主语**。

### 3.2 ★★ 新模型下这一列**全部**变成 ❌ —— 而最坏的不是"看不到"

**最坏的是「看到一半」。** 待办列表是**混合**的:个人待办在本机、家庭待办在主机。
主机不可达时,这张列表不会变空,它会**少掉一部分** ——
而一张少掉一部分的列表,和一张"本来就只有这些"的列表**长得一模一样**。

> 这正是本项目反复防的那一类。而今天它**不存在**,是本改向**新引进来的**。
> ⇒ 必须有一条判据钉住:**没有一份新鲜快照时,界面不得渲染一个空/短的共享列表**,
>   要说出来。这条在 §6.3 展开。

### 3.3 ★ 缓解建议(缓存最后一次读到的 + 标「可能已过期」)—— **成立,但要改一个字**

**成立。** 而且它便宜:那正是今天的代码**减掉写路径**。

**但它让「主机单副本」这个说法不再准确。** 拓扑的正确名字是:

> **主机单【权威】副本 + 副机【只读】缓存**

这个区别是承重的,不是措辞:**缓存与副本的差别不在于存不存,在于会不会回写。**
不写清楚,下一个人会很自然地在缓存上长出"离线也能改,连上再推"—— 那就是补推回来了。

**代价,逐条:**

1. **私人正文仍然落在副机磁盘上。** 与今天相比不是回归(今天就落着),
   但与"主机单副本"的字面承诺**对不上** ⇒ 决议里要写成缓存,不要写成"只在主机";
2. ★★ **缓存显示出来的时候,控件必须整块置灰,并写明为什么。**
   一份标着「可能已过期」却还能勾选的待办列表,比空白更坏:人勾了,什么也没发生。
   这条不是新规矩 —— `admin-app-lifecycle-2026-08-07.md` §1.2 与 D99 裁定④ 已经立过
   (「置灰但不说原因,和骗人是一回事;而给一个**错的**原因比不给更坏」);
3. **不设时间过期。** 到期就清空 = 列表自己悄悄变短,又回到 §3.2 那个形状。
   ⇒ 永不过期,但**永远带着取到的绝对时刻**(「读于 08-08 14:32」),让人自己判断。
   ★ 这与天气那条「缓存 + updated_at + stale,无假实时」是同一条口径(D45 裁定 5);
4. **缓存要有一条"它是从哪一代来的"** —— 存 `generation`。否则重新连上之后没有办法
   判断手上这份比中枢老多少,只能整份丢掉重拉(那也可以,但要写明是有意的)。

### 3.4 ★ 一条**缓存救不回来**的,而且它和 D52 补充正面撞上

今天副机在主机不可达时,**可以往共享会话里再说一句**,消息记在本机,连上补推。
D52 补充明写这是**有意保护的**:

> 「★ 允许照常发送并本地记录(**人常常就是想先把事记下来**),但绝不让人以为 AI 正在思考。」

新模型下共享会话的正文只有主机一份 ⇒ 副机**没有可写的落点**。
⇒ **本改向与 D52 补充这一句直接冲突**,不能装作没看见。

**建议的解法(★ 待用户裁):对「往共享会话追加一条消息」这一个动作保留排队,其余一律不排。**

理由不是"网开一面",是**这个写在数学上和别的不一样**:
追加是一次**带新 id 的插入**,不是对共享字段的更新 ⇒ 它**天然可交换**,
两台机器各插一条不会互相覆盖,也不需要冲突处理。而"改标题""勾选待办""删除"
全都是对同一个 id 的更新,那才是分叉的来源。

★ 如果用户不接受这个例外,那就是**如实告诉人「主机不在线时这个会话不能再往下说」**,
并把 D52 补充那句一并改掉。**两条路都行,但不能一边留着那句话一边做不到。**

## 4. 第 2 条 · 「即使来自副机」= 一次跨机写

### 4.1 今天的形状:**恰恰是被禁止的那一种**【静态阅读】

`ChatCenter.ShareSession`(`:223-233`):

```
_sessions[i] = _sessions[i] with { Shared = true };   // ← 先标
PushSession(_sessions[i]);                            // ← 再排队
PushWholeSession(sessionId);
Changed?.Invoke();
return true;                                          // ← 不管推没推上去,都回 true
```

而确认框里**白纸黑字承诺**了这件事(`Views/ChatView.cs:709`):

> 「★ 主机不在线时会先排队,连上后自动补推(界面上会显示「未同步」)。」

并且有**两条断言钉着这句话**(`Selftest.cs:4558`、`:4898`:「★★ 并说清主机不在线时会排队、
界面会显示「未同步」」)。

⇒ 「本地标了共享而主机没收到」今天**不是缺陷,是写在确认框里的设计**。
本改向要推翻的正是它,而推翻它**会让那两条断言变红** —— 这是本改向在客户端最实的一处代价。

### 4.2 ★ 建议:主机不在线时 **不允许发起共享**(诚实),不排队

三条理由,**第二条最硬**:

1. **排队就是补推。** 为一个调用点留着整套队列机制,正是本仓已经记过的那种腐烂形状
   (STATE 里租约五种 kind 中三种**生产调用方 = 0**);
2. ★★ **共享【不可收回】(D52 规则 B)。** 一个不可撤销的动作,不该在结局未知的时候发起。
   这条比拓扑本身更有力,而且它是项目**自己的**规矩,不是本包新立的;
3. **代价不对称。** 拒绝的代价:会话仍在本机、按钮还在、什么都没丢。
   排队的代价:人以为共享好了、去告诉对方看,而对面什么都没有。
   ⇒ 按 D101 裁定① 的方向,拿不准往"不做"那边倒。

**具体形状:**
- 提升按钮在主机不可达时**置灰 + 写明原因**,不是点了才弹失败框(点了才知道 = 又一次"看着好了");
- `ShareSession` 从「先标后推」改成「**先写后标**」:`await` 一次真写,服务端 200 才置 `Shared=true`;
- 确认框那句「会先排队、连上后自动补推」**删掉**,换成「要主机在线」。

### 4.3 ★ 协调层没提到的一格:**降级共享**

`TodoCenter.Update:152-165` 记着一条**明写待裁**的事:一条家庭待办被改成个人时,
中枢那份**还在**,只是记进 `DowngradedWhileShared` 列表。

新模型下这件事**换了形状,而且更清楚了**:家庭待办本来就只在主机 ⇒
「改成个人」= **从主机删掉它 + 在本机新建一条个人的**。那是一次两台机器上都看得见的动作
⇒ 必须和删共享会话同级地确认(D52 规则 C)。
⇒ 建议把这条**一并裁掉**,别让它继续挂着 —— 本改向正好给了它一个落点。

### 5.1 ★★ 墓碑有两个用途,**只有一个**退休 —— 协调层完全没提

`sync_store.in_scope` 里的 `deleted` 记录今天承着两件事:

1. **防复活**(离线副本回灌把对方删掉的东西推回来)⇒ **退休**,因为没有副本了;
2. **在增量帧里表达"这条没了"** ⇒ **留着**。
   `snapshot(since_rev=N)` 发的是**增量**,而一条被真正删掉的记录在增量里
   **表现为"什么都没有"** —— 副机永远不会知道它没了,除非重拉全量。

⇒ 这两个用途今天**缠在同一个 `deleted` 字段上**。裁掉哪个必须说清,
否则下一个人会把整条删掉,而**删除就再也传不出去了** —— 那正是 2026-08-05 用户实测报的
「删除时还是没法同步删除」,**兜了一圈回到原点**。

★ 顺带:如果采纳 §6.4 的建议(帧永远发**当前可见全集**),用途 ② 也跟着消失,
墓碑可以整条退休。**那是一次真正的简化,而不是删一个字段。**

## 6. 第 4 条 · `/v1/sync/snapshot` 怎么重写

### 6.1 建议:**线上形状一个字节都不改。变的是客户端拿它干什么**

三条理由:

1. **语义变了不等于形状变了。** 今天的响应体 `{generation, since_rev, data, counts}`
   恰好就是"这台机器现在该看到的全部共享数据"—— 正是新模型要的东西;
2. V15 刚把服务端半边**加深过**(从顶层键集合加到 `since_rev==0` · `generation` 是数字 ·
   三个集合一个不少 · 每条带 `id` 与 `rev`)—— **那几层正好是新模型下消费者真正要读的那几层**。
   改形状等于白扔这一轮;
3. **改形状要付欠债。** `CONTRACT:sync.snapshot` 今天是 `paired`,总欠债 `1/30`,
   而收工要求是欠债不许涨。改形状要两边一起动。

### 6.2 ★★★ 那条成对断言还成不成立?—— **服务端半边成立;客户端半边【今天就不成立】**

【静态阅读,V15 §6 已明写移交,main 上至今未做】

- **服务端半边**:成立,而且更该在;
- **客户端半边**:`Selftest.cs` 里 `CONTRACT:sync.snapshot` 钉的是 `FrameContinues(0, 0)`
  —— 那是**断层判据**,不是"一份真的快照体能被解析出来"。
- **`90-ops/gate/check_contract_pairs.py` 里那条 `note` 今天是错的**(实读 `:187-192`):
  它仍然写着「用途**不是**重连对齐……而是丢一帧之后的补全量」,而 V15 起它已经是上线/重连的对齐路径。

⇒ ★★ **在新模型下,这从「钉错了」升级成【硬前置】。**
副机屏幕上的每一个字都从这条路来,而**客户端能不能把它解析出来,客户端那半边一条断言都没有**。

> 顺序反了的话,改拓扑那天没有任何东西守着这条唯一的读路径。

### 6.3 ★★ 必须**新增**的两条判据(不是契约形状,是判据)

1. **「空」与「没拿到」必须长得不一样。**
   今天 `data.sessions == []` 有两个来源:真没有共享会话 / 拉失败。
   今天不咬人(界面读本地副本);新模型下它**直接决定屏幕上是不是一片空白**。
   ⇒ 要一条断言钉住:**没有一份新鲜快照时,界面不渲染空列表,而是说出来**。
   ★ 客户端今天已经有那个标记(`_needFullPull` + `StatusLine()` 那行 V15 加的字),
     但它现在只是**一行状态字**;新模型下它要变成**渲染的前件**。
2. **`counts` 从"顺带"变成"承重"。**
   `counts[k] == len(data[k])` **只在 `since_rev=0` 时成立**;增量帧下 `counts` 报的是
   可见总数、`data` 是增量 ⇒ 两者对不上。今天没人踩(客户端不看 counts),
   新模型下如果有人拿它当"我该显示几条",就会显示一个和列表对不上的数字。
   ⇒ 要么把这条写进契约注释,要么**让增量帧不带 counts**。

### 6.4 ★ 一条可选的真简化:**帧永远发当前可见全集**

如果采纳,`snapshot()` 不再有 `since_rev` 增量语义,每帧就是"你现在该看到的全部"。

- **换掉的**:断层检测(`FrameContinues`)· 补全量的三个触发点 · 墓碑用途 ②
  —— 一整族"丢一帧就永远补不回来"的缺陷**结构上消失**;
- **代价**:每帧 O(n) 序列化。家庭数据量(几百条)下是常数级噪声
  —— 与 V15 §5 记的那条代价同量级,但**换掉的是一整族缺陷**;
- ★ **不建议在本改向里顺手做** —— 它动的是 `CONTRACT:sync.events.frame` 的语义,
  该单独一条决议。**写在这里是为了让它有个位置,不是为了现在做。**

## 8. 第 7 条 · 「同步/聊天走回环」—— 协调层这句**不对**

> 协调层:「共享数据归主机存 ⇒ 主机写自己的存储 ⇒ 天然回环,自动解决。」

**【静态阅读】核实结论:不对。这句把两件不相干的事接在了一起。**

### 8.1 走不走回环,由**客户端的路由判据**定,与数据存在哪儿无关

`HubClient.BusinessRoute()`(`:332`)→ `DecideBusinessTarget(isHostMachine, pairedDial,
loopbackPort, demotedWhy)` —— 一个**纯函数**,四个入参里**没有一个**和存储拓扑有关。

### 8.2 `SyncClient` 三处调用点,每一处都要显式改

【静态阅读】今天三处走的都是 `_hub.TryDial()` 拿到的**配对拨号地址**(= lan-edge 的 mTLS 业务口):

| 调用点 | 今天 |
|---|---|
| `FlushAsync:300` | `Transport.Send(_hub.Profile, ep, POST, "/v1/sync/push", …)` |
| `PullFullAsync:641` | `Transport.Send(_hub.Profile, ep, GET, "/v1/sync/snapshot", …)` |
| `RunAsync:414` | `Transport.OpenStream(_hub.Profile, ep, "/v1/sync/events…", …)` |

⇒ 改拓扑**不会**让这三行变成 `SendBusinessAsync` / `OpenBusinessStreamAsync`。

### 8.3 而且「共享数据归主机存」**今天就已经成立**

`sync_store.py` 的 `{state}/shared/` 就在主机上,单写者,所有写经 `put()`。
本改向改的是「**副机还留不留一份**」——那和主机客户端走哪条 socket **没有因果关系**。

### 8.4 ★ 聊天面与同步面分开说(协调层要求的)

- **聊天面**:`ChatClient.StreamAsync` 走 `Transport.OpenStream(hub.Profile, ep,
  "/v1/chat/completions", …)` —— 同样是 lan-edge。它打的是**模型**,一个字节都不碰 `sync_store`。
  ⇒ **本改向对它零影响。** 它要不要走回环是一件**完全独立**的事。
  ★ V13 已评估过「今天不咬人」,本包**没有独立复核**聊天面的档位表 —— 如实标未核。
- **同步面**:见上。要走回环是**三处逐点改** + 一次归因裁定(V15 §11.4 移交那条)。

### 8.5 ★★ 一条本包独立抓到的:归因判据**今天就是错的**,而新模型下它会全面暴露

`SyncClient.Absorb:574-587` 把"被另一台改过"判成:

```
if (dev.Length > 0 && !dev.Equals(Environment.MachineName, …)) → 记进 _conflicts
```

**判词是"被另一台改过",判据是"不是我写的"。** 这两件事不一样:
对方**正常共享**过来的每一条都"不是我写的",但它们**没有被覆盖**。

⇒ 今天不咬人,因为 §5.2 已证明 `_conflicts` **根本没有界面消费者**。
⇒ **新模型下副机看到的每一条都来自主机 ⇒ 这张表会包含【全部记录】。**
   哪天有人把它接上界面,满屏都是「这条被另一台改过」。

★ 而它还与 V15 §11.4 那条移交叠在一起:主机客户端一旦改走回环,
它的同步身份从机器名变成 `local` ⇒ **主机会把自己写的记录判成"别人写的"**。

**⇒ 建议合并处置:把判据换成服务端已经给的那个** ——
`put()` 的响应里有 `superseded` / `superseded_from`,`sync_store` 还有 `superseded_for()`。
用"服务端说它被覆盖了"当判据,**判词与判据就对上了**,而且归因改名那件事**顺带变得无害**。
