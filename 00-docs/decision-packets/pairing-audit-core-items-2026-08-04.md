## 1. ★ 回环管理面 8442 没有任何来源校验(blocker)

**位置** `10-core/lan-edge/Program.cs` 的 `IsAdmin` 与 `/admin/*` 全部路由。

**问题** 现在的门禁是「请求来自管理端口 + 回环地址」。而**能连回环的不止"坐在主机前的人"**:

- 浏览器里的一个网页(`fetch('http://127.0.0.1:8442/admin/pairing/window', {method:'POST', ...})`);
- 同机的沙箱应用、另一个用户会话;
- DNS rebinding。

⇒ 文档里那句「按 D37/D48,**结构上**只有坐在主机前的人能批准/吊销」**不成立**。
这不是"暂时还没加 CSRF",是**门禁模型选错了判据** —— 和今天客户端侧连栽四次的
「检查代理指标而不是它真正关心的事实」是同一个形状。

★ **在令牌落地之前,这句断言要先从文档与界面里撤掉或改写。** 错误的安全声称比没有声称更坏。

**改法**
1. Edge 启动时往 `{state}/secrets/admin-token` 写 32 字节随机串(ACL 仅当前用户);
   `/admin/*` 全部要求 `X-LocalAI-Admin: <token>` 头。
   ★ 自定义头**跨源发不出去**(预检必失败),rebinding 也读不到文件 —— 一招同时封死三条路径。
2. 保险:带了 `Origin` 头、或 `Sec-Fetch-Site != same-origin`、或 `Host` 不在
   `{127.0.0.1:8442, localhost:8442, [::1]:8442}` 里的,一律 **404**(与现有"连存在性都不暴露"一致)。

**客户端侧已就绪**:`HubAdmin` 已经会在令牌文件存在时带上这个头
(`LOCALAI_ADMIN_TOKEN_FILE` 或 `{LOCALAI_STATE_DIR}/secrets/admin-token`);
文件不存在就不带 —— 所以 core 落地前后都能用,不用同步发版。

**★ 顺序**:这条**要先于**所有围绕 HubAdmin 的界面改动落,否则会返工三次。

## 2. 匿名 enroll 没有速率/来源限制(high)

**位置** `10-core/identity/Pairing.cs`(`MaxPending = 8`、`Enroll` 只查窗口与全局总数)、
`10-core/lan-edge/Program.cs` 的 `/pair/enroll`(匿名)。

**问题** 窗口开着时,局域网上任何人发 8 条 enroll 就把待批准队列占满,真正要配的机器进不来。
`MaxPending` 是**全局**配额,一个来源可以饿死所有人。

**改法** `Enroll` 收下 remote IP,按来源限流:同一 IP 最多 2 条 pending、每分钟最多 3 次,
超了回 **429**;`MaxPending` 从全局配额改成「每来源配额 + 全局硬顶」。

★ 客户端侧已经把"自动弹框"改掉了(待批准的只进列表,由人主动点某一条才弹)——
那是**缓解**,不是修复:队列照样能被占满。

## 3. `displayName` 服务端不限长(medium)

**位置** `10-core/identity/Pairing.cs` 的 `Enroll`(`DisplayName = displayName` 原样存)。

**改法** 砍到 **64 字符**并剔除控制字符/换行。自报字段本来就只作显示,不该有长度自由。

★ 客户端侧已自保(截断 48 字 + 剔控制字符 + 确认框加 MaxHeight/滚动),
但**服务端这一刀是根治** —— 别的消费者(主机控制台)不该各写一遍。

## 4. `provisioning` 条目要能被认出来(medium,配合客户端)

**位置** `/admin/devices` 的投影。

**问题** 「批准了但对方没来领证」的半截条目混在已配对列表里,看起来像配好了。
两边截止时间不一致时会稳定产生这种幽灵(客户端侧已对齐,但网断、进程被杀仍会留下)。

**改法** `/admin/devices` 已经带 `status`,客户端会照它标注 —— 但请确认:
① `status` 对这类条目确实是 `provisioning`;② 有没有清理它们的路径(过期自动清?还是只能手动 revoke?)。
如果没有清理路径,请加一条:超过 N 分钟没领证的 provisioning 自动作废。

## 6. ★ 一条必须按顺序的依赖(容易被忽略)

修「绑定地址」、以及提权护栏落地,都会让一部分用户的主机**换 IP 或重铸身份** ——
那正好踩中「链校验失败被判成证书过期」那一条,界面会加粗告诉他们"不需要重新配对",
而重新配对是唯一出路。

**客户端侧已经先改掉了那句文案**(`8ff76be`:拆出 `HubIdentityChanged`)。
所以顺序上现在是安全的 —— 但如果 core 先发、客户端后发,这个坑会重新打开。
**发版时客户端不能落后于中枢。**
