# 项目方案书审计 — v2.0

> 审计对象:`PROJECT_PLAN_v2.md` v2.0(2026-07-26),对照 `PROJECT_PLAN_v1.md` v1.0
> 审计日期:2026-07-26
> 审计性质:**文档审计**,不是代码或系统审计——本项目尚未执行任何安装或部署
> 结论:方案整体成立,定位转向有说服力。**发现 4 项严重、7 项重要、3 项事实修正、10 项建议补充。**
> 其中 S1(无备份方案)与 S2(安全设计被静默删除)会造成不可逆后果,建议在 P0 开工前处理。

---

## 0. 总评

v2.0 相对 v1.0 的三个判断是对的:

1. **把记忆提为核心**——这是"私人助理"与"聊天软件"的真实分界,且双轨检索的论证(向量答不出"我妹妹叫什么")击中了要害。
2. **资产减重**——砍掉本地 Flux FP8 与生成式 3D,把重点从"跑重型模型"移到"模型管家 + 提示词转译",这个转向识别出了真正的痛点(现有 16.92GB 全是人像向,与游戏资产无关)。
3. **投资只预留接口**——"现在建表否则后期是重构"的论证是对的。

问题不在方向,在**收窄范围时把护栏一起收掉了**,以及**把未实测的假设写成了确定数字**。

## 1. 严重发现

### S1 · 全项目没有备份与灾难恢复方案

**问题**:整套系统跑在一台机器上。文档对记忆库做了加密(§4.6)、进 GC 白名单(§7.3)、"备份分级"(§4.6 一行),但**从未定义备份方案**:目标介质、频率、是否异地、保留代数、恢复演练。

**为什么这是最严重的一条**:五类数据里,

| 数据 | 丢失后果 |
|---|---|
| 代码 | git 有,可恢复 |
| 模型 | 可重新下载(§5.3 甚至专门记录"重获成本") |
| 产物 | Asset Spec 可复现重放(v1 §5.2 明确论证过) |
| 缓存 | 设计上就可随时清空 |
| **记忆** | **不可重建。没有任何来源可以重放。** |

项目把最不可重建的数据识别为"最敏感",然后只针对**泄露**做了设计,没有针对**丢失**做设计。而对个人系统而言,硬盘故障、误删、加密卷损坏的发生概率远高于定向窃取。

**另一半**:§12 已决"记忆库走 BitLocker VHDX"。**BitLocker 恢复密钥一旦丢失,记忆库永久不可读**——这是比泄露更可能发生的失效模式,文档未提恢复密钥的保管方案。

**建议**:
- P0 增加一项:定义 `STATE` 根(尤其记忆库)的备份策略,并在 P3 记忆系统上线**之前**跑通一次恢复演练
- 恢复密钥离线保管(纸质 / 独立介质),不与被加密数据同盘
- 备份本身也要加密(否则备份成为绕过加密卷的后门)

### S2 · v1 的安全设计被静默删除,但对应的高风险功能照做不误

**问题**:v2 删掉了 v1 的整个 §6(安全与权限),只在架构图里保留"六元组强制"一行注释。但 v2 的 P6 **原样保留**了文件整理、浏览器执行器、游戏自动化这三项 v1 定级为"高风险"的功能。

**净效果:风险没有降低,描述并约束风险的章节没有了。**

具体丢失的、执行时最要紧的内容:

| v1 中的内容 | 为什么不能丢 |
|---|---|
| 浏览器执行器**独立 profile 的禁止清单**:邮箱 / 银行 / IBKR / 密码管理器 / 个人浏览器会话默认不可见 | 这是"独立 profile"四个字的**全部实质**。只写"独立 profile"不写清单,执行时等于没有约束 |
| 文件整理的**隐藏目录清单**:`.meine` / `.UE5.5` / `.git` / `.localAI` 默认不可见 | 这几个目录正好是这台机器上最不能被自动整理器碰的 |
| 事务化文件操作链:精确清单 → **哈希绑定批准** → 执行前复核哈希 → 隔离区(永不 delete)→ 尽力回滚 | v2 P6 只剩"清单 → 哈希绑定批准 → 隔离区 → 回滚"一行任务,机制细节没了 |
| **参数级**权限校验的说明:"同一个写文件工具,路径参数决定它是安全还是灾难" | 六元组里最难实现也最关键的一维,只剩一个词 |
| 威胁模型:模型是**不可信计划者**(计划本身要被审查,而非只审查执行者身份)、资产导演 Agent 独立工具池与记忆域 | v2 只在风险清册留了"提示词注入 高"一行,失去了应对方法 |
| 日志隐私三层规则:永远记录元数据 / 默认不记录对话正文与语音转写 / 按需开启加密短 TTL | v2 说记忆"不进日志",但没说日志本身记什么。**这与记忆隐私是同一个问题的两面** |
| 游戏自动化:**VLM 仅负责未知状态诊断,不得自行猜坐标继续操作** | v2 P6 保留了"VLM 仅诊断"但丢了这条禁令的表述 |

**建议**:把 v1 §6.3–6.5 的表格原样并入 v2,作为新的 §6「安全与权限」。这不是重写,是**恢复**。

### S3 · 文档引用悖论与幽灵依赖

**问题一(自相矛盾)**:
- v2 §7.3 写:"GC 策略见 v1 §5.2"
- v2 附录写:"v1.0 ⋯ **已被本文档取代**"

一份被宣布作废的文档,同时是现行 GC 策略的唯一来源。执行时无法判断该不该按 v1 §5.2 做,以及 v1 其余部分是否也仍然有效。

**问题二(幽灵依赖)**:
v2 附录写:"v0.4(GPT 编制):节点循环协议 · 记录协议 · 首轮门禁 · 审批规则 — **继续有效**"。

但 v0.4 **不在 `00-docs/` 目录里**(当前目录只有 v1、v2 两份),其内容也从未在 v1 或 v2 中展开。这意味着:

- 一套被声明为"继续有效"的执行协议,任何执行者(包括你自己三个月后、以及任何 AI 助手)都**无法读取,因而无法遵守**
- P0 要建 `00-docs/STATE.md`,而 STATE.md 的格式据称由 v0.4 的"记录协议"定义 —— **P0 第一项任务就卡在幽灵依赖上**

**建议**:
- 把 v1 §5.2(GC 与三池)、§6(安全)的原文**内联**进 v2,然后 v1 才能真正归档
- 把 v0.4 的四条协议原文并入 v2 附录;若 v0.4 已遗失,则重新写一遍(篇幅不大,但必须存在)
- 确立规则:**现行文档不引用已作废文档**

### S4 · P5 与 P7 存在排期倒置

**问题**:
- **P5**(语音 v1)的任务包含"**全局热键**按住说话"
- **P7**(Windows App)才做 Tauri 壳,而 §4.3(v1)/§10(v2) 都明确:P1–P4 期间界面是 **Open WebUI 的 PWA**

**PWA 无法注册系统级全局热键。** 浏览器安全模型不允许网页在失焦时捕获键盘。所以 P5 的这项任务在 P5 的技术栈下**不可实现**。

**三个出路(选一个写进文档)**:
1. 把 Tauri 壳的**最小版本**(仅托盘 + 全局热键 + 转发)提前到 P5,完整壳仍在 P7
2. P5 的热键降级为"**应用内**快捷键",全局热键明确推迟到 P7
3. P5 用一个独立的极小常驻程序(AutoHotkey / 一个 Rust 小工具)先顶上,P7 再收编

**推荐第 1 个**:因为 P5 的验收标准是"随口一句可正确进入 L2/L3",而"随口"的前提正是不用先切窗口——降级为应用内快捷键会让 P5 的验收失去意义。

## 2. 重要发现

### M1 · P1 实测没有"可接受阈值",测完无法据以决策

P1 验收写的是"产出实测表"。但**表不是决策**。如果 30B-A3B 混合放置实测只有 8 tok/s、首 token 12 秒,是接受、换 14B dense、还是放弃 `deep` 模式?文档没有规则。

**建议**:P1 开测**之前**,先为每一项写下可接受阈值(哪怕是拍脑袋的),例如:

| 项 | 可接受 | 不可接受时的动作 |
|---|---|---|
| `daily` 首 token 延迟 | < 1.5s | 降上下文 / 换更小模型 |
| 语音端到端延迟 | < 800ms(半双工) | 换 ASR 实现 |
| `deep` tok/s | > 15 | 放弃 30B-A3B,改 14B dense |
| `daily` 常驻显存 | < 13.5GB | 砍小 VLM |

否则 P1 只是把"不实测就冻结"换成了"实测了但仍然靠感觉决定"。

---

### M2 · 投资"现在建表"只给了表名,没给字段 Schema

§6 的核心论证是:"**后期迁移数据远难于现在建表**"。这个论证成立——但它成立的前提是**字段也定好了**。

文档只列了五个表名(提案 / 批准票据 / 幂等账本 / 对账记录 / 法规快照)加一个"分池字段"。表名不构成 Schema:后期若发现账本缺了"成交时间戳时区""对手方""费用明细拆分",照样是迁移而非填空。

**建议**:P2 建表时,至少把**账本表**的字段定到可下单粒度(即使全部为空)。其余四表可以只建骨架。理由:账本是唯一有法定保存义务、且最难回填的表。

---

### M3 · 记忆系统缺评测方法,P3 与 P9 的验收无法判定

- **P3 验收**:"能正确回答『我妹妹叫什么』与『上次聊的灯光问题』"——**两个例句不是验收标准**。通过率是多少?抽样多大?
- **P9**:"长期使用后的记忆质量评估与调优"——评估什么指标?没有定义。

**建议**:P3 内建一个**记忆 eval 集**(问题 → 期望答案 → 期望来源),随使用逐步扩充,并定义四个指标:

| 指标 | 含义 |
|---|---|
| 召回率 | 该记得的记住了 |
| 精确率 | 检索出来的确实相关 |
| **误记率** | 记住了错的事实(最危险) |
| **溯源完整率** | 每条记忆都能展开到原始对话(§4.5 已定为信任前提) |

---

### M4 · P2 缺 embedding / rerank 服务,而 P3 依赖它

P3 双轨检索需要 bge-m3 + rerank(§4.2 明确写了)。但 P2 的任务清单里只有 llama.cpp + LiteLLM + PostgreSQL + Qdrant + Open WebUI,**没有部署 embedding / rerank 服务**这一项。

v1 §3.3 有 `embedding.default` / `rerank.default` 别名并注明"跑 CPU,省 2.4GB 显存",v2 的能力别名表把它们保留了,但推进纲领没有对应任务。

**建议**:P2 增加一项"embedding / rerank 服务(CPU)+ 别名注册"。

---

### M5 · P2–P3 期间没有 GPU Broker,缺 OOM 过渡方案

GPU Broker 在 **P4**。但 P2 就要跑 llama.cpp,P3 还要叠加 embedding + Qdrant + 可能的 rerank。这段时间靠什么防止显存打架?

**建议**:P2 增加一条最小措施——**显式串行加载 + 一个手动模式开关**(一个脚本或一个环境变量即可),并在 P4 被正式 Broker 取代。写进文档比默认"到时候再说"可靠。

---

### M6 · 显存数字把未实测的假设写成了确定值,且上下文预算整节丢失

**问题一**:§7.1 的 `deep` 模式写"驱逐小 VLM,加载 30B-A3B 混合 → ~15.3GB"。但 30B-A3B 的 Q4 权重远超 16GB,必然依赖 CPU offload。表里的 15.3GB 只是 GPU 侧驻留部分,**offload 比例与由此产生的速度代价没有出现在文档任何位置**。这与项目自己的原则("不实测就冻结,等于把假设冻进地基")相冲突。

**问题二(更严重)**:v1 §5.3「上下文预算」**整节被删除,且未进 Backlog**。丢失的内容包括:

- KV cache 表(8K→0.6GB / 32K→2.3GB / 128K→9GB)。v2 的 `daily` 模式写"8B Q4@**16K**",但 16K 的 KV 占多少,全文没有
- **Prefill 延迟**约束:32K 上下文首 token 4–10 秒,语音模式不可接受,必须开 prompt cache / prefix 复用
- **有效上下文 < 标称上下文**:长上下文中段检索准确率显著下降
- **截图 token 消耗**:一张 2560×1440 截图在常见 VLM 中是 1500–4000 tokens,10 步 GUI 循环仅截图就 20–40K

最后一条尤其不该丢:v2 的范围决议里保留了"电脑操控,优先 UIA 树"这个**结论**,却删掉了支撑它的**数字**(UIA 树同一窗口通常只需 200–800 tokens)。结论没有理由支撑,后来的自己会怀疑它。

**建议**:恢复 v1 §5.3 为 v2 的一节;`deep` 模式标注"含 CPU offload,比例与速度待 P1 实测"。

---

### M7 · 出境闸门"逐次确认"与 nano-banana 的迭代式交互冲突

§5.2 定的规则是:"闸门在提交前明示将发送什么,**由你逐次确认**"。

但 nano-banana 的价值恰恰在于**迭代式编辑**(§5.1:"角色一致性好,迭代修改自然")——一张概念图往往要改十几轮。**逐次确认会把这个交互毁掉**;而放宽成"会话级授权"又会放大风险窗口。文档没有处理这个张力。

同时,Q3 已决"月度上限可手动调整、显示累计",但**超限时的行为未定义**:硬停?自动降级到本地 ComfyUI?仅告警?

**建议**:
- 定义**两级授权**:会话级(概念阶段,一次授权覆盖本次迭代会话,会话结束自动失效)+ 逐次确认(涉及项目专有素材时强制)
- 判定依据用已有的分轨规则(§5.2):概念阶段 vs 生产阶段
- 明确超限行为,建议"硬停 + 提示可手动提额",而不是静默继续计费

## 3. 事实与口径修正

### F1 · "15.7GB" 口径混淆,会导致 P0 第四项任务找不到目标

这是从 v1 继承下来的一处确凿缺陷:

- v1 §1 写:已有资产 **Juggernaut-XL-v9 / ControlNet-union+openpose / InstantID / inswapper(15.7GB,在 C:)**,需迁出系统盘
- v1 P0 与 **v2 P0 都写**:"**HF 缓存**自 C: 迁至 `D:\AI\cache\hf`(**15.7GB**)"

同一个数字,一处指"模型资产",一处指"HF 缓存"——这是两类完全不同的东西(前者不能删只能搬,后者可随时清空重建)。

更关键的是:v2 §2 的扫描显示 **ComfyUI 的 16.92GB 模型已经在 `D:\ComfyUI`**,且构成(controlnet 7.0 / checkpoints 6.62 / instantid 1.57 / insightface 0.91)与 v1 所说"在 C: 的那批"高度重合。

**很可能的真相**:那批模型早已在 D:,v1 的记录是错的,v2 原样继承了错误的 P0 任务。

**建议**:P0 执行前先做一次实测确认:
- `C:` 上到底还有什么(`%USERPROFILE%\.cache\huggingface` 实际占用)
- 如果 HF 缓存实际远小于 15.7GB,把 P0 那一项改为"迁移 HF 缓存(实测大小)",并单独确认 v1 提到的那批模型现在在哪

**不确认就执行,会在 P0 第一天卡住。**

---

### F2 · "ASR + TTS 合并省一个 CUDA context(~0.4GB)"是待验证的假设,不是结论

§7.1 把它列为"源自实测认知"的优化。但**能否合并取决于两者是否同框架**:若 ASR 走 faster-whisper(CTranslate2 后端)、TTS 走 PyTorch,塞进同一进程不一定省显存,还可能出现 CUDA 上下文或依赖冲突。

而 P5 的第一项任务就是"ASR + TTS **合并单进程**"——把一个未验证的假设写成了实作指令。

**建议**:P1 增加"验证 ASR/TTS 是否可合并同进程"一项;P5 的任务改为"ASR + TTS(可合并则合并)"。

---

### F3 · 对税法要求"记录法规快照",对云 API 条款却没有同等要求

文档对德国税务规则的处理很谨慎:"记录法规快照;由 Steuerberater 确认"(v2 §6 / v1 §7.2)。

但 §12 已决"nano-banana 必须用付费层——免费层数据可能被用于改进产品"这一条,**同样依赖一份会变的第三方条款**,却没有快照要求。Google 的模型与条款迭代频繁,`nano-banana` 这类模型代号本身就说明它处于快速演进阶段。

**建议**:启用 nano-banana 时,把当时的 Gemini API 数据使用条款存一份快照到 `00-docs/`,并列入定期复核(与 §9 Backlog 复核同频)。

| **A8** | **记忆的多端并发写入预留** | 项目对投资模块要求"现在就建表,否则后期是重构",但对记忆的多端写入(B1 iOS / B6 第二台 PC)没有同等前瞻。这是一处**不对称**——记忆的数据模型比交易表更难迁移 |
| **A9** | **P8 定义一个 v1 冻结点** | §10 注明 P8"没有终点"。无终点的阶段无法判断项目是否完成。建议定一个可判定的冻结点(例如"端到端产出 10 个可用于 UE5 的资产"),之后再进入持续迭代 |
