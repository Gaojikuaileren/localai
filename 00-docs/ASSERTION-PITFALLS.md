# 写断言时反复踩的坑 — 写下来是为了不再犯

> 用户要求(2026-08-04):**同一个陷阱踩了三次以上就要记下,防止以后再踩。**
> 这份是 [WPF-PITFALLS.md](WPF-PITFALLS.md) 的姊妹篇 —— 那份收界面的坑,这份收
> **断言与测试方法本身**的坑。两者都跨语言:Python 侧与 C# 侧同一个坑各踩各的。
>
> 收录标准:**在这个项目里真的踩过、而且不止一次**。
> 每条写清:症状 / 为什么 / 正确写法 / **有没有护栏**(没有护栏的条目等于没记)。
>
> ★ 排序按【已踩次数】,不按写下来的顺序。

## 1. ★★★ 断言撞在「解释它已经被删了」的那句注释上 —— 已踩 9 次(2026-08-04~05)

**症状**
写一条「某某东西必须已经不在了」的反向断言,它**在真的删干净之后仍然红**。
或者反过来:写「某处不得出现 X」,而 X 恰好出现在**说明为什么不能有 X** 的注释里。

**实际踩到的七次**(2026-08-04 ~ 08-05)

| # | 断言想说的 | 撞上的东西 |
|---|---|---|
| 1 | `_notify_locked` 里不得跨 `await` | 该函数**注释里**那句「`Event.set()` 非阻塞…不违反锁内不得跨 await」 |
| 2 | `set_power` 不得写 `_intended` | 该函数**注释里**那句「`self._intended` 一个字都不动」——**它正是在说明"不碰"** |
| 3 | 网关某处不得出现 `Body()` | 说明为何不用 `Body()` 的注释 |
| 4 | 不得出现 `e4_egress` | 同上 |
| 5 | `ModelsView` / `ModelCatalog` 里不得再有 `ModelCatalog.All` / `chat.8b` | 我刚写下的、**解释这套词汇为什么被删**的那段注释 |
| 6 | `test_error_disclosure.py` 自带一份去注释器 | 那份实现的 **docstring 里就写着「★ 必须这么做」** —— 它自己就是一次 |
| 7 | 统计「GPU 面还剩几处散落的 `classify_caller` 比较」 | **我自己刚写下的那段注释**里引用了那行代码 |
| 8 | 「代码里不再有『装载器尚未实现』」(2026-08-05 审计) | **这条断言自己的消息字符串** —— `code_only` 去注释但**保留字符串字面量**,针写成字面量就成了它自己要找的东西 |
| 9 | 假防护扫描器找恒真断言 / 环境依赖 | 注释里**引用**被删掉的 `check(..., True)`;`test_no_proxy.py` **docstring 里**那句「本该只走 127.0.0.1:8080 回环」(那个文件一个连接都不发) |

**★ 第 8 次带出的写法(推荐)**:针**拼出来**,别写成字面量 ——
`_needle = "装载器" + "尚未实现"`。这样守卫能连**自己所在的文件**一起扫,
不必靠"跳过本文件"开一个后门(那是 fail-open:守卫从此不查自己)。
C# 侧同款:`("AI 模型" + "尚未接入", …)`,并把断言消息里的那句话改成 `$"…{needle}…"` 插值。

**★ 第 9 次带出的判据(推荐)**:**散文不是代码**。
本仓的习惯正是"删掉之后把原文留在注释里说明为什么删" ——
照字面搜,这些**最负责任的写法**全都成了嫌疑。
⇒ 扫描类工具一律先算出注释与三引号块的位置,落在里面的匹配不报
(`90-ops/debug/scan_fake.py` 的 `prose_spans` / `is_prose`,且**两个方向都钉了**:
散文里的必须排除,真代码里的必须仍然抓到)。

**为什么会这样**
反向断言天然要求「源码里找不到这个词」,而**一段负责任的删除必然会在注释里提到被删的东西**——
不提,后人就不知道这里为什么空着、以及不许再加回来。
⇒ 越是写得清楚的代码,越容易把这类断言弄红。

**正确写法:去注释再判。收紧判据,不是删断言。**

- **C#**:用 `Selftest.CodeOnly(src)` —— 它同时剥掉注释**与字符串字面量**
  (不剥字符串的话,`Assert(x.Contains("Foo"))` 这行代码本身会让「不得出现 Foo」恒假)。
- **Python**:用 `_nodoc(fn)` —— 先去 `"""docstring"""` 再去 `# 注释`。

```python
def _nodoc(fn):
    return re.sub(r"#.*", "", re.sub(r'"""(?:.|\n)*?"""', "", inspect.getsource(fn)))
```

**★ 绝对不许的两种"修法"**
1. 把断言删掉 —— 那正是这条坑最想诱你做的事;
2. **把注释改写成绕开断言的样子**(比如把 `_intended` 写成 `_int ended`)——
   那让注释为了迁就测试而说不清话,是把代价转嫁给下一个读代码的人。

**护栏**
`CodeOnly` / `assert_helpers.code_only` 已就位,并有一条反向全表断言「没有测试文件自己再写一份去注释器」。
**新写任何「源码里不得出现 X」的判据,一律先过它们** —— ★ 第 7 次说明这条也适用于**临时的统计命令**,不只是断言:我用 `grep -c` 数残留时,数进了自己刚写的注释。

## 2. ★★★ 破坏性 git 命令冲掉未提交的活 —— 已踩 2 次(2026-08-04 当天)

**症状**
`git reset --hard` / `git checkout -- <file>` 用来撤销一次**临时改动**,
连带把**同一文件里未提交的真活**一起冲掉。

**实际踩到的两次**
- `git reset --hard HEAD~1` —— 冲掉封存的自配对三个文件(从 scratchpad 备份恢复,逐字节核对过);
- `git checkout -- test_gpu_broker.py` —— 冲掉**未提交的 250 行 S8 测试**(按上下文重建并复绿)。

**为什么会这样**
红测/试验的套路是「改一下 → 跑 → 还原」。还原时手最顺的就是 git ——
但 git 的还原目标是**已提交的版本**,而不是"我刚才那一下之前的样子"。
一旦文件里压着未提交内容,这两者就不是一回事。

**正确写法**

```bash
cp target.py /tmp/target.bak     # 先备份
# ...改、跑...
cp /tmp/target.bak target.py     # 用备份还原
```

**规矩:临时改动一律用文件备份还原;绝不在有未提交内容的文件上用 `git checkout` / `git reset`。**
真要用 git 还原,先 `git status --porcelain` 确认那个文件是干净的。

**护栏**
今天没有自动护栏,只有这条规矩。★ 值得考虑加一个 pre-command 检查,但目前靠纪律。

## 3. ★★★ 跑的不是刚改的那个产物 —— 已踩 3 次(2026-08-04~05)· **已装护栏**

**症状**
改了代码,测试结果却像没改;或者改了之后测试**数量**变了而不只是结果变了。

**实际踩到的三次**
- **增量构建跳过**:`Copy-Item` 还原备份时把文件时间戳设成了**更早**,
  `dotnet build` 判定"没变"直接跳过 ⇒ 跑的是上一次那个被改坏的二进制,报了一片假红。
  修法:`dotnet build --no-incremental`。
- **Debug / Release 是两个 TFM**:客户端自检在 `bin/Debug/net9.0-windows` 下跑出
  **1471** 条,在 CI 用的 `bin/Release/net9.0-windows10.0.19041.0/win-x64` 下跑出 **1755** 条。
  差了 284 条 —— 拿 Debug 的结果去对 CI 的基线,会得出完全错误的结论。

- **★★★ 第 3 次(2026-08-05 审计):门禁自己就在跑旧产物。**
  `run-tests.ps1 -Full` 的客户端半边直接执行**已有的 exe**,从不重编。
  我改了 `Selftest.cs`、净增 3 条断言,门禁照报 `client --selftest PASS=1852 FAIL=0`
  —— 与改动前**一模一样**。那 1852 条是**上一次出包时**的源码跑出来的,
  而这行输出读起来像是"当前源码通过了"。
  ⇒ 改坏客户端源码但不出包,门禁会**一直是绿的**。这是 P4 全程都存在的一个假绿。

**判据:先看总数,再看红绿。**
断言**总数**变了而你没有增删断言 ⇒ **一定是跑错了产物或漏跑了段落**,先查这个,别去查结果。
★ 第 3 次正是被这条判据抓到的:数字**没有**按预期变,而不是变红了。
**反过来同样成立:你增删了断言而总数没动 ⇒ 你跑的不是刚改的那个东西。**

- **★★ 第 4 次(2026-08-05 傍晚):`dotnet build -c Release` 不带 `-r win-x64`,
  根本不更新被测的那个产物。**
  改了 `Selftest.cs`、`dotnet build -c Release --no-incremental` 报「0 个错误 / 1.78 秒」,
  而 `bin\Release\net9.0-windows10.0.19041.0\win-x64\localai-client.dll` 的时间戳**纹丝不动** ——
  它编的是另一个 TFM(`net9.0-windows`),而门禁和手跑自检用的都是 win-x64 那个。
  ⇒ 我对着一条**上一版**的断言消息查了三轮,以为是判据写错了;真相是那份修改根本没编进去。
  ★ 判据同上:**断言总数没按预期变** —— 加了一条断言而 `PASS+FAIL` 的总数不变,就是它。

**正确写法**
- 要和 CI 对齐,就用 CI 那条命令:`powershell -ExecutionPolicy Bypass -File 90-ops\run-tests.ps1 -Full`;
- 单独跑客户端自检,用 **Release/win-x64** 那个 exe,不用 Debug 的;
- 手工构建一律带 `--no-incremental` **和 `-r win-x64`** —— 少了 RID 就是在编另一个产物;
- ★ 改完立刻**比时间戳**:`(Get-Item ...\win-x64\localai-client.dll).LastWriteTime`
  必须晚于你刚改的那个 `.cs`。这一步比读构建输出可靠 —— 构建输出会说"成功"。

**护栏(2026-08-05 落地)**
`run-tests.ps1` 在跑客户端自检前**比时间戳**:任何 `*.cs`/`*.xaml` 比 exe 新,
就把它记成「没跑起来」并**拒绝执行**,门禁不过。
★ 关键是**不跑**而不是"跑了再警告":跑出来的那个绿数字比不跑更有害。
★ 不在门禁里强制重编,是因为单文件发布要几分钟,会把门禁拖成没人跑的东西 ——
  拦住假绿不需要重编,只需要让"旧产物"和"通过"长得不一样。
★ 两个方向都实测过:产物新 ⇒ 照常跑出 1854 条;把 exe 时间戳回拨 3 天 ⇒ 门禁拒绝跑并判未过。

## 3b. ★★★ 守卫只盖住了它自称范围的一部分 —— 已踩 4 次(2026-08-05 审计一次性抓出)

**症状**
断言的**判词**说的是"每一个 / 凡是 / 全仓",而它的**判据**是一份手写名单或一条写死的路径。
名单里没有的那些**静默跳过**,测试全绿 —— 而漏掉的永远是**新加的那个**,
也就是最没被审视过的那个。

**实际踩到的四次(全部由 2026-08-05 的全项目审计抓出)**

| # | 判词说的 | 判据实际盖住的 | 后果 |
|---|---|---|---|
| 1 | 「模型已接入,那句『AI 模型尚未接入』必须删掉」 | 只读 `Views/ChatView.cs` | 那句话正躺在 `Services/ChatCenter.cs` |
| 2 | 「不得再用笼统的『中枢尚未接入』」 | 只读 `Views/ChatView.cs` | 那句话正躺在 `Views/ProjectUi.cs` |
| 3 | 「**每个**公开操作都收 caller 参数」 | 手写 7 个名字,而 `panel` 有 **11** 个 | 漏掉的 4 个里含 `mark_confidential_episode` —— 它自己的注释点名说漏了向量迁移就是 §4.11.4 破防 |
| 4 | 「GPU 路由都不自己比档位、都走 `gpu_guard`」 | 手写 `_gpu_fns` 元组 | 新增 GPU 路由忘了加进来就整条跳过 |

**为什么**
写守卫的那一刻,你眼里只有**你正在改的那个文件**。
判词是照着**意图**写的("这类话到处都不许有"),判据是照着**手边**写的("我现在看的这个文件")。
两者当天是一致的 —— 因为当天那句话确实只在那一个文件里。
**它在你搬动代码的那一天才开始说谎,而那天没有任何东西会红。**

**正确写法:判据的范围必须由**判词**决定,不是由你手边的文件决定。**
- 说"全仓"就**枚举全仓**:`TryReadAllSources()`(C#)/ `sources()`(Python),不写死路径;
- 说"每一个"就**从模块导出名单**,不手写:
  `sorted(n.name for n in tree.body if isinstance(n, ast.FunctionDef) and not n.name.startswith("_"))`;
- 手写名单只能用作**期望值**(反向全表:`set(实际) == EXPECTED`),不能用作**遍历源**。
  两者的区别就是"新增一项会红"和"新增一项被跳过"。

**护栏**
① 客户端:文案类守卫改成 `TryReadAllSources()` 全仓扫描,并配元断言"确实读到了 ≥20 个文件";
② `test_s5_acceptance.py` 的面板操作名单改成 AST 导出 + `_EXPECTED_OPS` 反向全表;
③ `test_gpu_policy.py` 的 `_gpu_fns` 配了元断言,与 `app.routes` 实际路由对拍;
④ **一般规则**:凡是判词里出现「每个 / 所有 / 凡是 / 全仓」,判据里就不许出现写死的文件名或手写的名字列表。

## 3c. ★★ 查文案却用了会剥掉字符串的去注释器 ⇒ 恒真 —— 已踩 2 次(2026-08-05)

**症状**
`Assert(!CodeOnly(src).Contains("某句界面文案"))` —— **它永远不会红**。
`CodeOnly` 会把**每一个字符串字面量整个换成 `""`**(见其实现),
而界面文案**只可能出现在字符串里**。⇒ 判据在找一个它已经亲手删掉的东西。

**实际踩到的两次**
1. 2026-08-05 白天:S12 一批文案断言误用 `CodeOnly`,其中「不得出现 X」那条**恒绿**。
   当场发现并拆成 `CodeOnly`(查代码结构)/ `NoComments`(查文案)两个工具。
2. 同日审计:`Selftest.cs` 里**还剩一条**没改到 ——
   `Assert(!CodeOnly(cv3).Contains("AI 模型尚未接入"), …)`。
   ★ 它的来历才是最该记住的:**它本身就是为了修一句谎言而写的**,
   上面还留着一整段"⇒ 反过来钉:那句话必须【不在了】"的说明 ——
   动机对、措辞诚恳、**而修法是空的**。

**判据(一句话)**
> 查**代码结构**用剥字符串的;查**文案**用只去注释的。用反了,方向是**恒真**那一边。

**护栏**
新写的全仓文案守卫用 `NoComments`,并且它**第一次跑就把上面第 2 条的针抓了出来** ——
这是这条护栏成立的直接证据,不是推断。

## 4. ★★ 判据比想判的东西宽 —— 已踩 3 次(2026-08-04 当天)

**症状**
断言红了,但代码是对的;或者更糟 —— 断言绿着,而它其实什么都没在判。

**实际踩到的三次**
1. `self._state ==`(比较)被 `self._state\s*=` 匹配到 —— **前者是后者的前缀**。
   修法:`=[^=]`,把赋值与比较分开。
2. 锁作用域正则 `async with self._lock:(.*?)(?=\n    def )` **一路捕到下一个方法定义**。
   S8 之前每个锁块恰好是方法最后一段所以看着对;`apply_intended` 里锁块后面还有
   【缩进已退回去】的代码,被误算进锁内 ⇒ 三条全红。
   修法:按**缩进**取块,只收缩进更深的行。
3. 跨文档对拍时,peak 列里有 `~~11.0~~ → **8.14**` 这种"旧值划掉→新值"写法,
   正则取到了**箭头前**那个已作废的估算值 ⇒ 两条假红。修法:取 `→` 之后的那个数。

**★ 最要紧的一条推论:判据太宽会静默变成【零断言】。**
如果提取器一条都匹配不上,`for` 循环一次都不跑,里面那几条检查会**静默消失**——
测试仍然全绿,而它已经什么都不管了。**那是本项目最恨的假断言。**

**正确写法:给每个"提取 + 循环"的断言配一条元断言。**

```python
check("★★ 提取器没有静默失灵(块数 == 源码里的出现次数)",
      len(_bodies) == src.count("async with self._lock:") and len(_bodies) > 0)
```

**护栏**
已在 `test_gpu_broker.py` 第 8 组落地。**凡是"先提取再循环判"的断言,都要配这条元断言。**

## 5. ★★★ 会随环境漂移的断言 —— 已踩 2 次(第 2 次尤其刺眼)

**症状**
门禁判红,红的却是**与本次改动无关**的一条;换个时间跑又绿了。

**实际那一次**
`test_vram_gate.py` 第 13 节把 CLI 打到**实机 NVML**。当晚桌面吃到 7.5 GiB,
闸如实拒绝 ⇒ 退出码 1 ⇒ 两条断言无辜变红,挡下了一次无关的提交。
**这条从写下那天起就是会漂的**,只是此前显存一直够。
更刺眼的是:那个文件**开头第 4 行**自己就写着「动态闸统一注入固定的 free 值,
不依赖真实 GPU 状态(否则测试结果随桌面占用漂移)」——**它违反的是自己声明的纪律**。

**为什么代价大**
不是"偶尔红一下"那么轻。**它训练人去用 `--no-verify`** ——
而本项目已被这个模式咬过一次:D24 里 `-Force` 一路跳过三道闸,显存闸整整一天没生效过。

**正确写法**
把外部量**注入**,不要去读真实环境:

- 进程内:直接换掉那个读数函数(`vram_gate.nvml_free_gib = lambda: 14.65`);
- 跨进程:用 `-c` 引导脚本先注入再调 `main()`;
- ★ **不要给生产代码加 `--free` 之类的旁路开关** —— 那种开关迟早被用来绕闸;
- ★ 补一条元断言,钉住注入**确实生效**(输出里的值必须正好是注入值),
  否则这一节会悄悄退回打实机,又变成随机红/随机绿。

**★ 一条走过的弯路,省得下一个人再走**:
Windows 上想用「PATH 里放一个桩 `nvidia-smi.cmd`」来伪造 —— **不成立**。
`CreateProcess` **不执行 `.cmd`**,`nvidia-smi` 仍然解析到 System32 里的真 exe。

### ★★★ 第 2 次(2026-08-05):**它整天是绿的,恰恰因为产品还不能用**

`test_gateway_e1.py` / `test_lan_edge_policy.py` 里有 11 条断言写成 `status_code == 503`。
文件开头的 docstring 把理由写得明明白白:

> 「**无后端时** chat 转发会 ConnectError → 503,正好证明「E1 放行了」。」

判据是「E1 有没有放行」,而 503 只是个**顺手拿来的信号** —— 它成立的前提是
**后端没起**。那天晚上模型第一次真的接进来、`llama-server` 起在 18081 之后,
这些 503 全变成 200,两个套件当场红/崩(还带 `Event loop is closed` 的收尾噪声,
让退出码变成 1,运行器报「应该跑却没有汇总行」)。

**为什么这一次比第 1 次更值得记:**
第 1 次(显存闸)是桌面占用波动弄红的 —— 那是"环境有噪声"。
这一次是**功能终于能用了**弄红的。它把「产品还没做好」焊进了判据里。

> **⇒ 判据:一条断言若会因为「功能终于能用了」而变红,它测的就不是它自称在测的东西。**

**修法**(与显存闸同款,注入而非读环境):

```python
class _AlwaysUnreachable:          # 只在测试里存在,生产的 _client 一个字没改
    def build_request(self, *a, **k): raise httpx.ConnectError("注入:上游恒定不可达")
    async def send(self, *a, **k):    raise httpx.ConnectError("注入:上游恒定不可达")
    async def post(self, *a, **k):    raise httpx.ConnectError("注入:上游恒定不可达")
gateway._client = _AlwaysUnreachable()
assert not isinstance(gateway._client, httpx.AsyncClient), "上游注入没生效"   # ★ 元断言
```

于是 503 依然精确表示「E1 放行了、转发被尝试了」,**而与谁在跑无关**。

**★ 自查一遍的办法**:把栈起起来(`start-stack.ps1`)再跑一次全套。
凡是"只在系统没跑起来时才绿"的断言,那一刻会全部现形。

## 6. ★★ 用 TestClient 测"跨连接的实时推送" —— 已踩 1 次,但差点得出相反结论

**症状**
SSE 订阅收得到首帧,但**永远收不到 update**。看起来像"推送机制没做对"。

**实际那一次**(2026-08-05,同步面 SSE)
测法是:一个线程用 `TestClient` 订阅 `/v1/sync/events`,另一个 `TestClient` 发 push。
`_sync_notify()` 里 `event.set()` 叫不醒订阅者 ⇒ 收不到 update。

**为什么**
**每个 `TestClient` 各起一个事件循环。** `asyncio.Event` 不是跨循环安全的 ——
在 A 循环里 `set()`,B 循环里 `wait()` 的那个协程不会被唤醒。
而生产里 uvicorn **只有一个**事件循环,push 和 SSE 都在它上面,机制是对的。

> **⇒ 差点得出的错误结论:"推送设计有问题"。实际是【测法】制造的假象。**
> 这比测不出问题更危险 —— 它会诱你去改一段本来正确的代码。

**正确写法**
凡是判据涉及**两条连接之间的实时交互**(推送、通知、租约互斥、并发抢占),
**必须走真 HTTP**打到一个真的服务进程上,不能用两个 TestClient。
进程内 TestClient 只适合测**单条请求**的输入输出。

★ 实测数据留在这儿当基准:真 HTTP 下 push → 收到 update 是 **24 ms**。

## ★ 护栏(2026-08-07 加)—— 把那个"每次都靠肉眼发现"的判据交给机器

**八次里,每一次抓到它的都是同一句话**:
> 「我只加了 N 行,而 `git` 报了 M insertions / K deletions,K ≠ 0」

—— 而八次都是**人肉看出来的**。⇒ 做成 `.githooks/pre-commit` 的第 ③ 段。

**判据(精确,不是启发式)**:

```
churn = (git 数的 增+删) − (内容层去掉 \r 之后 diff 数的 增+删)
```

- 只改了行尾的一行:git 记 1 删 + 1 增 = 2,内容层记 0 ⇒ churn **+2**
- 真改了内容的一行:两边都记 2 ⇒ churn **0**
- 纯追加的一行:两边都记 1 ⇒ churn **0**

⇒ **churn > 0 的那一半,就是被静默改掉的行尾。** `churn ≥ 2` 判红并点名文件与行数。

**★ 落地前在真实历史上对拍过,两个方向都验**:

| 提交 | churn | |
|---|---|---|
| `78e01d5` / `0b042cc` / `f9af80b` | 3154 / 3918 / 764 | **全部会被拦** |
| `b38464a`(5 个文件)· `104e3d8`(3 个文件) | **全部 = 0** | **一个都不误报** |

★★ **"不误报"和"能报"一样承重** —— 钩子自己的注释警告过:
一个动不动就拦人的钩子,会让人养成 `--no-verify` 的习惯,那等于没有钩子。

**★ 放行口是窄的**:`LOCALAI_ALLOW_EOL_CHANGE=1 git commit …`。
真要整体改行尾(例如有意规范化一份文件)是合法的,但必须是**一次有意的动作**,
而且它会在终端上留一行明说。
⇒ **不要用 `--no-verify`** —— 那会把绝对路径检查和自检门禁**一起**关掉。

**已红测(2026-08-07,亲手制造)**:
- ① 把一份 CRLF 文件整体转 LF ⇒ 当场拒绝,并打印
  「有 15 行**只有行尾被改了** · 文件里的 `\r` 数 15 → 0」;
- ② 同一状态下带 `LOCALAI_ALLOW_EOL_CHANGE=1` ⇒ 放行,并打印那是一次有意的改写;
- ③ 还原后做一次**正常追加**(`+2/-0`)⇒ **不误报**,`exit 0`。
- 靶文件已逐字节还原(SHA 与 HEAD 一致)。

★ **churn < 0 不判红**:那说明 git 与 `diff` 的配对算法不同,
**看不懂的东西不许当成证据** —— 那会变成一条时不时假红的护栏,而假红的护栏很快就没人看。

**★★ 修好之后它又犯了一次 —— 这次不是 heredoc,是 Edit 工具。**
往同一份 worklog 里再加一段时用的是精确串替换(也就是本条推荐的写法),
`git diff --stat` 的删除数又从 60 跳到 180 —— **恰好是那 121 行**。
判据:**行尾统一的文件怎么改都安全;行尾混合的文件,任何整体重写都会把它统一掉**,
而"整体重写"包括你以为只动了一行的那些工具。

**⇒ 真正靠得住的不是"用哪个工具",是那条判据本身:**
> 提交前看 `git diff --stat`。**删除行数**尤其要对得上 ——
> 新增可以是你写的,**删除不会凭空多出来**。
> 两次都是它抓到的,而两次我用的工具不一样。

## 9. ★★★ 判据问的是「我是什么身份」,而不是「我做不做得到」 —— 已踩 3 次

**症状**
一道闸 / 一句文案,真正关心的是**某件事做不做得成**,而它实际检查的是一个**代理指标**
(我属于哪个组 / 我在哪个阶段 / 那个东西该在哪儿)。
代理指标与事实**大多数时候一致**,所以它看起来能用 —— 直到遇上两者分家的那台机器,
而那时它给出的**理由是假的**,人会照着假理由去改一个没坏的东西。

**实际踩到的三次**

| # | 真正关心的事实 | 它实际问的 | 分家的时候 |
|---|---|---|---|
| 1 | **这把密钥打不打得开** | 「我是不是管理员」(`IsInRole`) | UAC 关闭(`EnableLUA=0`)的机器上,该判据对管理员账户**恒为真**,于是把一台**完全健康**的机器判成不能用,理由(「密钥集不存在」)**是假的** —— 密钥就在那儿,打得开 |
| 2 | **这台是不是主机** | 「探测失败了吗」 | 探测失败有很多原因(防火墙、端口没起、地址写错),把其中任何一种读成"不是主机"都会指错方向 |
| 3 | **两个东西的先后顺序** | `IndexOf(a) < IndexOf(b)` | `b` 被删掉时 `IndexOf` 返回 **-1**,断言以**一个假理由**失败(报"顺序错了",真相是"根本没有 b") |

> 前两次的记录见 `decision-packets/integrity-guard-asks-wrong-question-2026-08-03.md`
> —— 那份包的标题就是这条坑的名字。

**★ 第 3 种今天(2026-08-06)又踩了一次**,而且是**同一天踩了两遍**:
- 一次在 `VramBar` 的顺序判据上:拿**整个文件**比 `ShowUnavailable` 与 `UpdateRing` 的位置,
  比到的却是 `UpdateRing` 的**方法定义**(它写在前面)⇒ 报"顺序错了"而代码是对的;
- 一次在 `HubGpu` 的时间戳顺序上,同款。
⇒ 说明这条**不会因为被记下来就自动消失** —— 它每次都伪装成一个具体的小 bug。

**为什么它特别难发现**
代理指标**通常是对的**。它不像恒真断言那样"从不变红" ——
它平时表现完美,只在那一台特殊的机器 / 那一次删除之后翻脸。
⇒ 你不会在写它的那天发现,而发现它的那天,它给的理由会**把你引向别处**。

**正确写法**

1. **先问真问题,再谈代理。**
   ```csharp
   // ✗ if (IsElevated()) 拒绝;
   // ✓ if (!KeyUsable(out var why)) 拒绝,理由就是 why;
   //   代理指标只用来**丰富理由**,不用来做判定:
   //   打不开【而且】当前是管理员 ⇒ 多半是身份在普通用户下铸的
   ```
2. **顺序判据:先各自 `Contains`,再比位置;而且把范围缩到该比的那一段。**
   ```csharp
   Assert(src.Contains(A) && src.Contains(B), "两处都在(位置判据的前提)");
   var body = src[src.IndexOf("void Update(")..];      // ★ 只在该比的那段里比
   Assert(body.IndexOf(A) < body.IndexOf(B), "…");
   ```
3. **判据失败时给出的理由,必须是它真的验过的那件事。**
   闸说"密钥集不存在",那就必须真的去开过一次密钥;没开过就不许这么说。

**护栏**
- `lan-edge` 与客户端的提权护栏都已改成"先试着打开密钥"(见该文件 `CaKeyUsable` 上方那段);
- 顺序判据的两条纪律已写进 `test_gpu_broker.py` / `Selftest.cs` 的相关注释旁;
- ★ **但这条没有自动护栏** —— 它不是一种语法形状,是一种**提问方式**。
  唯一可靠的检查是人:**写下任何一道闸时,问一句"我拒绝的理由,我真的验过吗?"**

## 8. ★★ 判据依赖了**非 ASCII 字符**,换个终端就失灵 —— 已踩 3 次

**症状**
同一个脚本,在你的终端里好好的,在**门禁/钩子**里失灵 —— 而且失灵的方式通常是**静默**的。

**实际踩到的三次**
1. PowerShell 5.1 把无 BOM 的 UTF-8 当 ANSI 读 ⇒ 脚本里的中文变成乱码。
2. **S0(踩了 5 天才发现)**:`vram_gate` 的**唯一生产集成**在干净的 cp936 PowerShell 里,
   连**通过**的路径也会在 `print(preview(...))` 抛 `UnicodeEncodeError`
   (判定符是 `✓` U+2713,GBK 里没有)⇒ stdout 为空、退出码 1,
   而 `start-stack.ps1` 只看退出码 ⇒ 打印「拒绝启动」。
   ★ 那 38 条断言全绿也没发现它 —— 它们是**进程内**跑的,坏的是**跨进程**那条唯一的生产路径。
3. **2026-08-05 提交时**:我给门禁新加的那段用 `·`(U+00B7)当分隔符去匹配汇总行
   (`=== 调试工具自检:40 PASS · 0 FAIL ===`)。我的终端里好好的;
   而 pre-commit 钩子是从 git bash 起的、控制台码页是 cp936 ⇒ 中文与 `·` 全成乱码,
   正则匹配不上 ⇒ 门禁报「**没跑起来**」并拒绝提交。

**为什么它一直复发**
你**只在一个环境里试过**。而门禁/钩子/计划任务跑的是另一个环境,
它们恰恰是"没人盯着"的那些环境 —— 于是失灵的时候也没人看见。

**正确写法**
- **解析用的判据只认 ASCII**:`===` / `PASS` / `FAIL` / 数字乱码之后**依然完好**,
  中文和符号不是。人看的输出爱怎么写怎么写,**机器读的那几个字符必须是 ASCII**。
- 并且**锚定到汇总行**(`^\s*===`),不在整段输出里乱找 ——
  `run-tests.ps1` 自己栽过一次:非锚定的 `(\d+)\s*FAIL` 匹配到了某行里的 HTTP 状态码。
- 给 PowerShell 读的文件写成 **UTF-8 with BOM**;`Set-Content`/`Add-Content`
  默认是系统 ANSI 码页,要显式 `-Encoding utf8`。
- Python 脚本一律 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")`。

**护栏**
`run-tests.ps1` 的「**没有汇总行 = 没跑起来,绝不当作通过**」这条纪律 ——
第 3 次就是它抓到的。**它不是在检查断言的结果,是在检查"这东西到底跑没跑"**,
而那正是本条坑唯一能被自动抓住的地方。

## 10. ★★★ 分派表「先到先得」,排错位置的条目**静默失效** —— 已踩 1 次 · 险些第 2 次(2026-08-06)· **已装护栏**

**症状**
一张「谁归谁管」的表(规则表 / 路由表 / 匹配链 / `case` 链),用的是**首个匹配胜出**。
于是一条**更具体**的条目,只要排在**更宽泛**的那条**后面**,就永远轮不到它 ——
而这件事**不报错、不告警、不抛异常**。表照样加载,程序照样跑完,退出码照样是 0。

> **「改了、看起来改了、其实没生效。」**
> 这比崩溃恶劣得多:崩溃会逼你去看,静默失效只会让你以为已经修好了。

**★ 真踩到的那次(而且踩了很久)**

`run-tests.ps1` 的 `$RULES` 里有一条:

```powershell
@{ Dir = '10-core\memory'; Tier = 'manual'; Runnable = $false
   Reason = '连的是【真实】记忆库,pg_ident 只映射 ai-mem —— 结构上跑不了' }
```

这条**理由是对的**:那个目录下 13 个套件确实连真库、确实跑不了。
但 `10-core\memory\test_tainted.py` **不连数据库** —— 它验的是密封/解封与档位允许表,纯逻辑。
它被目录规则**整条连坐**成 `manual`,于是:

> **那 75 条断言,从写下的那天起就没有任何人跑过。**
> 而覆盖账里它躺在「已裁定不自动跑 + 写明理由」那一栏 —— **看起来是被认真处置过的**。

★ 这正是本仓第一戒律的形状:**没人跑的断言就是假断言**。
它甚至比"忘了写断言"更难发现 —— 忘了写会留下空白,而这里留下的是**一条写得很好的理由**。

**★ 险些的第 2 次:修它的时候**

把文件级例外加进 `$RULES` 时,如果排在 `'10-core\memory'` **后面**,
`Get-Rule` 的首个匹配胜出会让目录规则先命中 ⇒ **例外永不生效**,而且:
· 不报错 · 不告警 · `-ListOnly` **照样把它显示成 `manual`**
⇒ 那 75 条断言继续没人跑,**而门禁看起来一切正常,提交也照过**。

**为什么它特别难发现**
其它静默失效至少还有个"什么都没发生"的迹象。这一条不是 ——
**它有输出、有分类、有理由,只是分错了。** 你去看 `-ListOnly`,它会明明白白告诉你
"这个文件是 manual",而那句话是**表在如实汇报它自己的错误状态**,不是在报警。

**同族(不同表,同一个形状)**
`scan_fake.py` 的盘符正则写死了 `D:`,而这个项目在 **E:** 上
⇒ 扫描器**一条都没匹配到**,输出「未发现问题」。零命中与全清白在终端上长得一模一样。
> ⇒ 凡是「匹配式」的东西,都要问一句:**它今天到底命中了几条?零命中是不是也算通过?**

**正确写法**

1. **具体的排在宽泛的前面**,并在表头把这条顺序语义**写成注释**——
   因为下一个来加规则的人不会知道 `foreach + return` 意味着先到先得。
2. **★★ 给顺序本身加一条断言**,而且**用真实的表 + 真实的查找函数**去问一个具体问题:
   ```powershell
   $__hit = Get-Rule (Join-Path $repo '10-core\memory\test_tainted.py')
   if (-not $__hit -or -not $__hit.Runnable -or $__hit.Tier -ne 'fast') { …红… ; exit 1 }
   ```
   ★ **不要另建一份模型来验** —— 另建的话它验的是那份模型,不是这个脚本。
3. **失败信息要说出它【实际】命中了哪条**(`命中的是 '10-core\memory'(Tier=manual)`)。
   只说"顺序错了"会让人去猜;说出命中的那条,人一眼就知道该把谁挪到谁前面。
4. **零命中要判红**,不要判绿(同族那条的教训)。

**护栏 · 已装**
`90-ops/run-tests.ps1` 顺序护栏(在 `$RULES` 与 `Get-Rule` 之后、扫盘之前),**判红即 `exit 1`**。

## 11. ★★ 源码判据有【两种运行环境】,写的时候要两种都想到 —— 已踩 1 次(2026-08-07)

**症状**
客户端自检会跑**两趟**:① 在仓库里(源码就在旁边);
② **出厂产物原位**(`build-client.ps1` 的第 `[2]` 步,产物旁边**没有源码**)。

一条源码判据写成

```csharp
Assert(Slice(src, "…") is not null && …, "…");     // ✗
```

在①**绿**、在②**红** —— 而②那一趟是**出包前的闸**。
⇒ **一条本意是护栏的断言把出包挡住了,理由还与它自称在守的那件事无关。**

**为什么它特别容易写出来**
写的时候你在仓库里,①永远绿 —— 你**根本碰不到**那个会红的环境,
直到出包那一刻才第一次遇见它。而那时报出来的红长得像"某个接线坏了",
人会去查那个接线,而不是去想"我现在站在哪一趟里"。

**正确形状**(本文件既有判据都是这个)

```csharp
var src = TryReadSource(f);
if (src is not null) { …Assert… }      // ✓ 读不到就【跳过】,不是判红
```

★★ 那条「**源码根在旁边时不得有读不到的**」的元断言(见第 10 条那轮加的)管的是**另一件事** ——
「源码根**在**、却有某个文件读不到」(= 路径写错了)。
**它不会替你兜住"源码根不在"这一趟**,两件事别混。

**判据**
> 写任何读源码的断言之前问一句:**这条在"旁边没有源码"的那一趟里会怎样?**
> 答案必须是「跳过」,不是「红」。要它在那一趟也有效,就得换成**运行时问得出来**的判据
> (枚举成员用 `Enum.GetNames`、界面词用 `Strings.Get`、措辞直接调那个属性)——
> 那类判据**比查源码文本更强**:测的是行为,不是那串字写在哪个文件里。

## 12. ★★★ 断言全绿,而核心功能在真机上开不起来 —— 已踩 1 次(2026-08-07 实机场次)

**症状**

> **4197 条断言全绿、门禁通过、出包通过 —— 而两台真 PC 上,
> 「意图即起」不起模型,组件「确定」在【任何设备上】都按不下去。**

**为什么全绿**

没有**一条**断言走「**主机客户端的真实连接路径**」。
权限那一层的测试里,**档位(tier)是直接构造的** —— 测试自己说"我是 `trusted-local`"、
"我是 `lan-device`",然后验那个档位下的行为对不对。**每一条都对。**

而真机上决定档位的是**另一件事**:客户端连的是回环还是网卡 → 有没有证书指纹 →
`resolve_lan_principal` 封不封顶。**那一段从来没有被任何断言走过。**

⇒ 于是「主机客户端属于哪个档位」这个**承重前提**,
在整套测试里**是被假设的,不是被测出来的**。当那个假设在 08-07 被一次起栈参数改动
(`run` → `run-lan`)悄悄推翻时,**没有任何东西会红**。

**★ 它和第 3 条(「跑的不是刚改的那个产物」)是同族**

| | 第 3 条 | 本条 |
|---|---|---|
| 测得对不对 | 对 | 对 |
| 测的是不是**会真的跑的那个** | **不是**(跑的是上一次出包的产物) | **不是**(测的是构造出来的档位,不是真实连接路径解出来的档位) |

> **两条的共同点:判据本身没错,错在它测的那个东西不是最终会跑的那个东西。**

★★ 更要紧的一条:**其中一个缺口(`permit_on_demand` 没给 `lan-device`)在 08-06 就存在了**,
而它一直被"主机客户端走回环所以是 `trusted-local`"这个**巧合**遮着。
⇒ **一条被巧合遮住的缺口,和一条不存在的缺口,在门禁上长得一模一样。**

**正确写法**

1. **端到端至少一条**:让一个**真的带证书指纹**的请求走完整条 `resolve_lan_principal` →
   档位 → 动作判定,断言它解出来的档位**就是**你以为的那个。
   ⇒ 档位不许再由测试自己声明,要**由那条路解出来**。
2. **对每一个"只有 X 能做"的动作,反问一句:今天有没有设备真的是 X?**
   本次的病灶正是这句话的反面 —— 面板写着「只能在主机上改」,
   而**没有任何设备满足"主机"这个条件**。
   ⇒ 判据形状:`assert 存在某个真实可达的身份能通过这道闸`(**存在性**,不只是"该拒的都拒了")。
3. ★ 一道闸只钉了"该拒的拒掉",没钉"该放的放得过去",**就是一条随时会变成恒拒的闸** ——
   与第 5 条那类恒真/恒假判据同源,只是方向相反。

**护栏**
★ **2026-08-08(V13)装上了** —— 本条写下时是「今天没有装」，现在两条都有了:

1. **端到端那条**：`test_gpu_policy.py` 第 9 节**不再 monkeypatch `classify_caller`**，
   替身只打在「操作系统说这个 socket 属于谁」上，回环判据 → allowlist 查表 →
   `gpu_principal` → 档位表 → HTTP 层**全部真跑**；客户端那半边真开一个监听冒充回环网关，
   让生产代码路径（`HubGpu.ApplyAsync` / `RequestIntentAsync`）真发一次请求看它落在哪儿。
2. **存在性那条**：「回环 + allowlist 账户 + 无指纹 ⇒ `trusted-local` ⇒ `/v1/gpu/intended`
   **不是** 401/403」—— **确实存在一个真实可达的身份能通过这道闸**。
   反向同时钉住：只多一个证书指纹 ⇒ 403/tool（副机仍然改不动）。

★★ 而**为什么**当初会写成「档位直接构造」，是另一条独立的坑 —— 见下面第 13 条。
两条不要合并：本条说的是**症状**（全绿而真机开不起来），第 13 条说的是**机制**
（替身打在了判据本身上）。只记症状的话，下一次换个判据函数还会再来一遍。

## 13. ★★★★ 替身打在【判据本身】上 ⇒ 那条判定链一条断言都没有 —— 已踩 **2 次**(2026-08-06 ~ 08-07)

> ★ 这是上面**第 12 条的机制**。第 12 条记的是症状（全绿而真机开不起来），
> 本条记的是它是**怎么做到全绿**的 —— 两条分开，因为只堵症状堵不住下一次。

**症状**

2026-08-07 实机:**4197 条断言全绿**,而主机上组件面板点「确定」直接吃
「这台设备不能做这个操作」;敲字不起模型。核心功能开不起来,门禁一点反应都没有。

**为什么**

`test_gpu_policy.py` 的探针把**判据函数整个换掉**:

```python
gateway.classify_caller = lambda r, t=tier: t      # ← tier 是【直接构造】的
```

于是「档位表判得对不对」被测得极透(87 条),而
**「主机客户端实际会走到哪一档」从头到尾没有一条断言问过**。
客户端那一侧同样:它测了解析器、测了文案,**从没测过拨号去了哪儿**。

⇒ 两侧各自自洽,**中间那根线谁也没看**。这与审计 A1(6 条 A 级里占 4 条)
是同一个形状,只是那次缝在"响应体形状"上,这次缝在"身份是怎么解出来的"上。

★ 第 1 次(2026-08-06,审计 B3):GPU 面 holder 用客户端自报值、同步面用服务端解析,
两套各自有测试、各自全绿 —— 直到 `/v1/session/end` 横跨两者才炸。

**正确写法**

> **替身只许打在「这个进程结构上拿不到的那一件事」上,不许打在判据上。**

本例里结构上拿不到的只有一件:**操作系统说这个 socket 属于谁**
(合成请求没有真 socket)。所以替身只换 `caller_identity.account_from_request`,
而回环判据 → allowlist 查表 → `gpu_principal` → 档位表 → HTTP 层**全部真跑**:

```python
gateway.caller_identity.account_from_request = lambda req: ("HOST\Zori Ma", "Zori Ma")
# classify_caller / gpu_principal 一个都不碰
with TestClient(gateway.app, client=("127.0.0.1", 5555)) as c:
    r = c.post("/v1/gpu/intended", json={...})     # 401/403 ⇒ 红
```

客户端那一半同款:**真开一个监听冒充回环网关**,让生产代码路径
(`HubGpu.ApplyAsync` / `RequestIntentAsync`)真发一次请求,看它**落在哪儿** ——
而不是去 grep 源码里有没有 `127.0.0.1`。

**自查的一句话**

> 写完替身问一句:**我换掉的这个东西,在真机上是谁负责答的?**
> 如果答案是"我们自己的代码",那就换错地方了 —— 你把要测的那段删掉了。

**有没有护栏**

有一半,而且如实说清是哪一半:

* ✅ 这两条断言**互为成对**(服务端问"这条连接给哪一档",客户端问"这次请求发去哪条连接"),
  且**都验过能为假**:把主机那一支改回走网卡 ⇒ 客户端 5 条红;
  给 `lan-device` 加回 `change_resident` ⇒ 服务端 4 条红。
* ✅ **判据的输入是怎么来的,也被钉住了**(2026-08-08 对抗式复核补的,见下)。
* ❌ **没有**一条元断言去数"还有多少条判定链是被 monkeypatch 掉的"。
  今天靠的是人去翻探针。⇒ 下一次同形状的缺陷仍然可能溜过去。

### ★★★★ 同一天、同一次改动里,这个坑**又踩了一次**(第 2 次,2026-08-08)

修完上面那条之后,新断言测的是「给它 `isHost=true`,它会打到哪儿」——
而 `isHost` 是**自检自己喂进去的**。全仓唯一的生产写入点是 `App.xaml.cs` 里那一行
`Hub.NoteRole(decision.Role.IsHost, …)`。

⇒ **把那一行删掉、或挪到 `Gpu.Start()` 之后,20 多条新断言一条都不红**,
而出厂客户端在主机上会走回旧路,点「确定」照旧被拒。
**缝只是从「档位怎么解出来」挪到了「角色怎么喂进去」——形状一模一样。**

**判据升级成一句更狠的自查**

> 写完一条断言,问:**我喂给它的输入,在真机上是谁喂的?那个"谁"有没有被钉住?**
> 一路问到**生产入口**为止。中间任何一环没有断言,整条链就都不算被测过。

**修法**(如实标成结构判据 —— 要变成行为判据就得真跑一遍 `App.OnStartup` 的后台分流):
钉「那一行在不在」**加上**「它在 `Gpu.Start()` / `Lease.Start()` / 起栈**之前**」。
实测反证:删掉 ⇒ 3 条红;挪到起流之后 ⇒ 2 条红。

★ 而写这条断言时**当场踩了本文件第 1 条的第 10 次**:
我在 `App.xaml.cs` 的注释里写了「必须在 `Gpu.Start()` 之前」,`IndexOf` 先命中了那句**注释**,
断言判红而代码是对的。⇒ 先 `Body()` 去掉注释再比位置。
**一条钉顺序的断言,必须在去注释后的正文上算位置。**

## 14. ★★★ 扫源码的判据对「这个按钮点下去到底做没做事」**什么都不会说** —— 已踩 1 次(2026-08-08 · V18 红测当场量出来)

**症状**

一个 UI 承诺(「托盘右键 → 关闭」**真的**会关掉它)配了四条断言。
把那个点击处理**整个换成空实现**之后:

| 断言 | 它问的是什么 | 换成空实现之后 |
|---|---|---|
| `4c-2` 菜单项在 | 源码里有没有这一项 | **照样绿** |
| `4c-3` 文案是「关闭」 | 源码里那串字是什么 | **照样绿** |
| `4c-4` / `4c-6` 行为判据 | 点下去之后**发生了什么** | **红** |

> **⇒ 一个功能被彻底掏空,而两条断言毫无反应 —— 它们从头到尾问的都不是这件事。**

**为什么**

扫源码的判据问的是「**那串字写在哪个文件里**」,不是「**那个动作会不会发生**」。
两者在功能好着的时候**永远一致** —— 所以它看起来能用。
它们分家的那一天,正是实现被改坏的那一天,而**那一天恰恰是你最需要它说话的时候**。

★ 与第 9 条同族(判据问的是「我是什么身份」而不是「我做不做得到」)、
与第 12 条同族(判据测的不是最终会跑的那个东西)。
**三条的共同形状:判据问了一个【相关】的问题,而不是【那个】问题。**

**正确写法**

1. 凡是「点了之后会发生 X」这类承诺,判据必须**真的触发那个入口**并观察后果 ——
   哪怕只能观察到一个替身(标志位、回调计数、状态迁移),也比读源码强;
2. **源码判据只能当补充,不能当唯一。** 它擅长的是「这一段被删掉了没有」
   (第 1 条那种反向钉),不擅长「这一段做的事对不对」;
3. ★★ 界面这一层常常**没法**在自检里真跑(无桌面环境 / 会动到用户真在用的进程)——
   那就**如实写成"没验到"并说清为什么**,不要拿一条扫源码的判据顶上去充数。
   **少一条诚实的判据,好过多一条假的。**

**★ 判据升级成一句自查(这条最省事,而且当场就能做)**

> **把那段实现整个换成空的,再跑一遍 —— 你的判据里有几条会红?**
> 一条都不红 ⇒ 你钉住的是**文本**,不是**行为**。

★ 这次就是这么量出来的:V18 亲手把点击处理换成空实现,四条里**只有两条**红。
**不是推理出来的,是跑出来的** —— 而这类问题**只能**这么发现:
一条从不变红的断言,和一条钉住了正确性质的断言,在绿色的终端里长得一模一样。

**护栏**

★ **今天没有装** —— 本条是第 1 次,按本仓门槛(三次)先记形状。
但上面那句自查**成本极低**:任何一条 UI 承诺的判据写完,把实现清空跑一次就知道了。
⇒ 下一个写 UI 断言的人请顺手做一次,别等它踩满三次。

**★★ 2026-08-08 · V20 照办了(这条自查的第一次实际执行)**

V20 五条改动,每条都把实现掏空跑了一遍。**七次红测,结果逐条记在这里** ——
因为其中两条的红法与写断言时的预期**不一样**,而那正是自查的价值:

| 掏空什么 | 红了几条 | 说明 |
|---|---|---|
| 流式快路径恒返回 false | **1** | 只有"40 段全走快路径"红 |
| 定位改回 `BeginInvoke(Loaded)` | **2** | 两条偏移断言红,报 `最小 0,0px` |
| `NoteIntent` 退回 `catch { }` | 2 | |
| 去掉"说法没变就不广播" | 2 | |

## 15. ★★★★ **临时测量工具本身没被验过** —— 已踩 **7 次**(2026-08-08 一天之内)

写断言的时候我们很小心。而**用来检查断言的那个临时脚本、那条 grep、那个退出码**,
往往是随手写的 —— 然后我们**拿它的输出当事实**。

> **它比被测的东西更不可靠,而它说话的口气一模一样。**

### 已经踩到的 7 次(全部 2026-08-08)

| # | 临时工具 | 它说的 | 真相 |
|---|---|---|---|
| 1 | `grep -c $'\r'` 数行尾 | 一个数字 | 数错了 —— 行尾护栏那次误报就是拿它"自证"的 |
| 2 | `cmd \| grep; echo $?` 读退出码 | `0` | 读到的是 **grep** 的退出码,不是 cmd 的 |
| 3 | grep 出「八步 0/8」 | 那八步没跑 | **跑了,8/8** —— `Invoke-GateSelftest` 只在失败时 dump 输出 |
| 4 | 红测脚本 print 一个 `⇒` | (崩了) | 控制台码页 cp936,`UnicodeEncodeError` 当场炸在第 3 个红测中途,**留下一个没清理的 ghost 工程** |
| 5 | 红测脚本的多行锚点 | "锚点找不到" | 锚点用 `\n` 拼,而那个文件是 **CRLF** —— 一条都匹配不上 |
| 6 | 红测脚本的另一个锚点 | "替换没生效" | 拿一串 `═` 制表符当锚点,长度差一个字符 |
| 7 | 我**新写的那条断言**自己 | 绿 | 它读的是**原始源码**,而旁边一句注释里有同样的字 —— 被自己的注释喂饱了(同第 1 条,第 11 次) |

★ 第 4 次尤其难看:脚本炸了以后留下的那个 ghost 工程,是**被测的那条护栏**抓出来的。
  **护栏比测护栏的脚本可靠。**

### 判据

> 写完一个临时测量工具,**第 0 步**:在**不改任何东西**的情况下跑一遍,
> 要求它给出一个**你已经知道的答案**。给不出来,后面所有结论都不算数。

具体三条,缺一不可:

1. **先跑基线**。红测脚本的第一步永远是「什么都没改 ⇒ 必须绿」。
   基线就是红的,那后面每一个"它红了"都可能只是基线那条红,**证明不了任何东西**。
2. **每一处替换/锚点都要 `assert` 命中**。
   `text.replace(old, new)` 在 `old` 不存在时**不报错、不改动、静静返回原文** ——
   于是"改完还是绿"被读成"判据没盖住",而真相是**根本没改**。
   ⇒ `assert old in text, "锚点找不到 —— 测量工具坏了,不是被测的东西绿了"`。
   ★ 那句错误消息的措辞是判据的一部分:它要挡住的正是"顺手把期望值改宽"这个动作。
3. **输出通道也要先验**:`sys.stdout.reconfigure(encoding="utf-8")`(cp936,见第 8 条)、
   `\r\n` 与 `\n`(见第 7 条)、退出码到底是谁的。
   ★ 这三样都不是"细节" —— 它们**决定你看到的那行字是不是真的**。

### ★★★ 推论:工具与被测者**不一致**时,先分清是谁错了

2026-08-08 有一次:红测说「删掉这条锚点,门禁必须红」,**而门禁是绿的**。

两种解释,代价天差地别:
* 「我的期望写错了」⇒ 顺手把红测改成期望绿,**收工**;
* 「门禁真的漏了」⇒ 去查。

查下去发现是后者:门禁的锚点计数用**裸子串** `.count()`,
而 `CONTRACT:cert.admin.ping` 是 `CONTRACT:cert.admin.ping.servercert` 的**前缀** ——
父契约那一半被整个删掉,子形状那几行还在,`.count()` 照样 ≥ 1。
**那条承重判据「0 次 = 这一半被删了」结构上永远不会红**,已经这样躺了不知道多久。

> **一个"没有按预期红"的红测,是**证据**,不是**噪音**。
> 在把期望值改宽之前,必须先证明被测的那一侧是对的。**

★ 这一条与第 3b 条互补:3b 说「守卫只盖住了它自称范围的一部分」,
这一条说「**发现守卫有漏洞的那个瞬间,最容易被顺手抹掉**」。

## 16. ★★★ 护栏可以**把一句错话钉在原地** —— 已踩 1 次(2026-08-08 · V20 查实)

**症状**

`ChatOutcome.Advice` 里 `backend_unavailable` 那一句写着
「目前后端要在主机上**手动启动**:跑 `90-ops\start-stack.ps1`」。
而自检里配着一条断言:

```csharp
Assert(S11Adv("backend_unavailable").Contains("start-stack"),
       "★★ 后端没起要说清【怎么起】,而不是只说连不上");
```

查实之后,那句话有两层错:

1. **过期**:它是「按需装载」落地**之前**的话;
2. ★ **它给的建议今天会把人引向一个被明令禁止的动作** ——
   D101 裁定② 原文:自动起栈「只起 gateway 与 lan-edge,**绝不起 llama-server**:
   按需装载已经落地,静态起会和 transient 平面打架」;
   而 `start-stack.ps1` **恰恰会**静态起 `llama-server`。

**⇒ 那条断言不是漏掉了这件事,它是在主动阻止这件事被改。**
谁去改那句文案,门禁就当场判红。

**为什么**

断言写的时候文案是对的,于是「文案里有 `start-stack`」与「文案说得对」重合。
分家发生在**别处**:D101 改了栈的启动规矩,而这句文案与它没有任何机械联系。
★ 与第 14 条同族但**方向相反**:第 14 条是判据**说不出**实现坏了;
本条是判据**替一句错话作了保**。前者是沉默,后者是背书 —— 后者更难发现,
因为绿色终端里它看起来正是"这件事有人管"。

**正确写法**

1. ★ 断言**别去钉一句话里的具体建议**。钉判据、钉结构、钉"分得开",不钉措辞:
   - 好:「七种失败七种说法」(`Distinct().Count() == n`)——它不关心每句说的是什么;
   - 坏:「这一句里要有 `start-stack`」——它把一个**会过期的事实**冻进了门禁。
2. 凡是断言里出现**外部世界的专名**(脚本名 / 端口 / 路径 / 命令),问一句:
   **「这个东西改了名或改了规矩,这条断言会告诉我吗?」**
   答案是"不会"⇒ 它钉的是一句会烂掉的话。
3. ★ 反过来用它:文案里凡是**给具体操作建议**的,配一条**反向**断言
   (「这句话里**不许**出现 X」),X 是已经被裁定禁止的那个动作。
   V20 现在钉的就是这一条:`Assert(!S11Adv("backend_unavailable").Contains("start-stack"))`。

**护栏**

本条第 1 次,按门槛先记形状。但有一句当场能做的自查:

> **翻一遍你的断言,哪几条里写着一个外部专名?那几条正在替它作保。**

## 17. ★★★ 落盘的字节与你看到的文本不是一回事 —— 已踩 3 次(2026-08-08 夜,一夜之内)

**症状**

用脚本生成/修改文本时,字符串里的 `\a` `\b` `\f` `\v` 被当成**转义**,
`dist\admin` 落盘成 `dist<BEL>dmin` —— 一个**不可见**的 0x07。

> 终端上它长得像**少打了一个字**(`distdmin`),而磁盘上那儿躺着一个控制字节。

**一夜之内三次(全是同一个 `\a`)**

| # | 在哪 | 怎么发现的 |
|---|---|---|
| 1 | V18 决议包并入时写的抬头 | 提交前**碰巧**数了一遍控制字符 |
| 2 | 未了项总表的生成脚本(**未加引号**的 heredoc,`$` 与反引号被 shell 先展开) | **当场炸掉** —— 反而是三次里最好发现的一次 |
| 3 | 通宵收工便条 | 又是**碰巧**数了一遍,**3 个 BEL** |

**为什么它特别阴**

1. **看不出来** —— 编辑器与终端把 0x07 显示成"什么都没有";
2. **Edit 的串替换也匹配不上** —— 你按屏幕上看到的 `distdmin` 去替换,匹配不到,
   因为磁盘上是 `dist` + 0x07 + `dmin`。**只能按字节改**;
3. ★★ 三次里抓到它的都是**同一个人肉动作**:落盘后数一遍控制字符。
   **而"碰巧数了一遍"不是判据。**

**正确写法**

- 写含 Windows 路径的文本:**用原始字符串** `r'...'`,或干脆 `chr(92)` 拼出来。
  ★ 别指望"我记得把反斜杠写成双份" —— 三次里有两次我确实写了双份,
    而 `\\a` 在**外层 shell** 那道又被吃掉一层;
- **heredoc 一律用带引号的** `<<'PY'`,靠环境变量传参数。
  不加引号时 shell 会先展开 `$` 与反引号,**而那一层你根本没在看**;
- ★ **落盘之后按字节验**,不看渲染:

```python
b = io.open(p, 'rb').read()
print(sorted(x for x in set(b) if x < 9 or 13 < x < 32))   # 必须是 []
```

**护栏 · 已装(2026-08-09)**

`.githooks/pre-commit` 第 ⑤ 段:**暂存的文本文件里不得出现 `\t` `\n` `\r` 之外的 C0 控制字符**。
二进制文件按 `numstat 是不是 -` 跳过。**没有放行口**,而这是有意的 ——
「我确实要在文档里放一个裸 BEL」不是一个真实需求。

**★★★ 而这条护栏的第一版是个空壳,是红测把它抓出来的**

第一版用「内容里有没有 NUL」判二进制:

```sh
if git show ":$f" | grep -q "$(printf '\000')"; then continue; fi    # ✗
```

`$(printf '\000')` 在命令替换里**带不出 NUL**(bash 直接丢弃并警告)⇒ 模式变成**空串**
⇒ `grep -q ""` **匹配一切** ⇒ **每个文件都被当成二进制跳过,护栏恒绿**。
造一个带 BEL 的文件提交,**照过**。

> ★ 记住这个形状:**一条"跳过二进制"的分支写错方向,整条护栏就变成恒绿** ——
> 而恒绿的护栏与没有护栏,在终端上长得一模一样(第 10 条同族)。
> ⇒ 改用第 ③ 段已经验过的那套(`numstat` 对二进制报 `-`)。

**已红测(三个方向,2026-08-09)**:
带 BEL 的文件 ⇒ **exit 1、HEAD 没前进** · 同一文件改成正常反斜杠 ⇒ **放行** ·
**真二进制文件 ⇒ 不误拦**(★ 第三个方向是必须的:第一版的 bug 就在那条分支上)。

### ★★★★ 第 4 次 —— 就在**警告这件事的那句话内部**,而护栏抓到的第一个提交是**引入它自己的那一个**

写上面那条护栏的帮助文案时,我要说的是「真有需要就把它写成 `\a` 的**转义文本**,
而不是落一个裸字节」——**而我把那个 `\a` 写成了一个真的 BEL。**

于是:**第一次带着这条护栏去提交,它拒绝的就是引入它自己的那次提交**,
理由是 `.githooks/pre-commit` 里有 1 个不可见控制字符。

> ★ 这是这条护栏能拿到的**最强红测证据** —— 它不是我造一个靶子喂给它,
> 是它在**真实的一次提交**里抓到了**我本人、在同一分钟、在同一句话里**又犯的同一个错。

★★ 而它也说明了为什么"记得写双份反斜杠"这条纪律靠不住:
**四次里我每一次都知道这个坑,第四次是在写它的说明书时踩的。**
⇒ 判据不能是"记得",只能是**落盘后有人去数**。现在数的是机器。
