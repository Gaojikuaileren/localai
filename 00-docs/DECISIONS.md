## 2026-07-26 · HF 缓存按「冗余回收」处理,而非按方案书原文迁移

**背景**
v1、v2.0、v2.1 的 P0 都写着「HF 缓存自 C: 迁至 `D:\AI\cache\hf`(15.7GB)」。
审计(`AUDIT_v2.0.md` F1)指出这个 15.7GB 口径存疑 —— 同一个数字在 v1 里既被称作「已有模型资产」又被称作「HF 缓存」。

**实测结果**
`C:\Users\<user>\.cache\huggingface` = 15.71GB,内容为 Juggernaut-XL-v9 / InstantID /
controlnet-union / controlnet-openpose / inswapper。**两处描述指的是同一批数据** ——
那批模型就是通过 HF hub 下载的,躺在缓存目录里,所以它既是模型资产也是 HF 缓存。

进一步 SHA256 逐文件比对:全部 6 个 >100MB 的 blob 在 `D:\ComfyUI\models` 下
都有哈希完全一致的副本(重复 6 / 无对应 0),且 HF blob 文件名与实算哈希吻合(缓存未损坏)。
**属完整冗余。**

**选项**
- A 照方案书迁到 `D:\AI\cache\hf` —— 只是把 15.7GB 冗余从 C: 搬到 D:
- B 只改 `HF_HOME`,旧的原地留着 —— 零风险但不释放空间
- C 设 `HF_HOME` 指向新位置 + 回收旧的冗余副本

**决定**
选 C。先移入隔离区(`D:\AI\state\quarantine\2026-07-26_hf-cache-from-C`),
随后依你 2026-07-26 的明确要求提前清除,保留 `MANIFEST.md` 作为审计痕迹。

**理由**
迁移一份已被哈希证明重复的数据没有意义。ComfyUI 走 models 目录的直接文件路径,
不经 HF hub,因此不受影响;真需要时 HF hub 会按需重新下载。

**代价与已知风险**
若将来有组件通过 `from_pretrained("RunDiffusion/Juggernaut-XL-v9")` 引用,会触发一次重新下载
(6.62GB,仅 WiFi 866Mbps)。可接受 —— 也可从 ComfyUI 侧的同哈希副本取回。

**推翻条件**
若发现有组件强依赖 HF hub 的缓存布局且重下代价不可接受,则应改为在 `MODELS` 根下
保留一份规范化副本,并在模型注册表登记「重获成本」。

**净效果**:C: 387.7 → 403 GB;D: 无净变化;ComfyUI 完全未动。

## 2026-07-26 · 备份改为「手动触发 + 脚本保证一致性」

**背景**
实测发现 D: 与 E: 是同一块物理盘(Disk 1),即代码根与数据根同盘,该盘故障两者同时丢失。
当时无任何外置介质,一度决定「P0 只交付脚本与策略,首次备份推迟到 P3 前」。

**新信息**
你于 2026-07-26 告知:有移动固态,会手动备份。

**决定**
备份模式定为**手动触发**:你决定什么时候插盘运行,
脚本(`90-ops/backup/backup.ps1`)负责一致性 —— 排除规则、清单、SHA256 校验、报告、同盘拒绝。
`paths.toml` 的 `[backup].status` 由 `not_provisioned` 改为 `manual`。

**理由**
手动的应当是**时机**,不该是**过程**。人工复制粘贴容易漏目录、漏校验、备到同一块盘上。
脚本把这几件事固定下来,不增加你的负担。

**代价与已知风险**
手动触发意味着**备份频率取决于你是否记得**。记忆库(P3 起)是每天都在变的数据,
与模型权重不同 —— 一周不备就可能丢一周的记忆。这一点在 P3 上线时需要重新评估。

**仍然成立的两条**
1. BitLocker 恢复密钥离线保管,至少两份,不与被加密数据同盘 —— 密钥丢失 = 记忆库永久不可读
2. 「没演练过的备份不算备份」:P3 上线前须跑通一次完整恢复

**推翻条件**
P3 上线后若出现「想不起上次备份是什么时候」的情况,应改为计划任务自动触发 + 插盘检测。

## 2026-07-26 · D23 凭证不进记忆库,走独立加密应用 + 永久保留手动输入

**背景**
D22 之后记忆库在磁盘与备份盘上均为明文。而 S2 类信息里的**凭证部分**
(IBAN · 税号 · 证件号 · 密码 · 密钥)一旦明文落盘,后果远重于其余记忆内容。

**用户原话**
> 「(IBAN、税号、证件号、密码)这些敏感信息存入一个加密应用内,每次从这个应用内获得授权然后调用。
>  现在这个应用还没搭好,我们先用手动输入,未来搭好了再连接接口。
>  未来就算这个应用搭好了,我们也要保留手动输入的入口。」

**决定**
新增 **§6.9 凭证与敏感信息**:

1. **凭证类不进记忆库。** 记忆库只存 `secret_ref` 句柄,不存值
2. 三种取值模式:**手动输入(现在唯一可用)** · 外部加密应用接口(待建) · **手动输入永久保留**
3. **手动输入必须走带外通道** —— 不在对话框、不经过 LLM 上下文、不进日志/记忆/出境载荷
4. **每次使用都要授权**,不做会话级(同 §12.4 铁律 3)
5. 现在只定契约(`secret.request` Schema · `secret_ref` 命名规范 · 引用登记表 · 审计),
   **不做任何具体应用的适配器**(同 §7 投资模块的接口预留模式)

**为什么这个决定同时改善了 D22 的处境**

| | D22 后 | D23 后 |
|---|---|---|
| 拿到硬盘能读到 | 家人称谓 · 偏好 · 习惯 · 项目状态 · **凭证** | 前四项。**凭证读不到 —— 它不在里面** |

D22 的代价被**部分抵消**:记忆库泄露仍然不好,但严重性不是一个量级。

**S2 分域收窄但不取消**

| 原 S2 涵盖 | D23 之后 |
|---|---|
| IBAN · 税号 · 证件号 · 密码 · 密钥 | **移出记忆库**,走 §6.9 |
| 住址 · 健康信息 · 关系细节 | **仍在记忆库**,仍需远程访问限制 |

> 别把 S2 整个删掉 —— 住址和健康信息不是「凭证」,不该塞进密码管理器,
> 但对远程档位仍然敏感。PG role + Qdrant collection 的结构性隔离保留。

**★ 已知的最大风险(技术上无法完全阻止)**

**如果你在对话框里直接打出 IBAN,整个设计当场作废。** 它会进 prompt、进上下文、
可能进 L1 会话摘要、可能被 `escalate.cloud` 看到 —— 而 Memory Gate 是**写入时**才生效的,
那时 prompt 早就形成了。

而且**带外输入控件现在还不存在** —— P5 才有 Tauri 最小壳,P7 才有完整壳,
现在的界面是 Open WebUI。**这段时间里最自然的操作(打字)恰恰是最错的操作。**

已发起对抗性审查专门找这类泄露路径。在有结论并落地之前:
**不要在对话里输入任何凭证。需要用到时,自己手动填,不要经过助手。**

**推翻条件**
- 外部加密应用建成并接入后,若「每次授权」在实际使用中被证明太烦而导致你绕过它
  → 重新评估授权粒度(但**不得改为会话级** —— 那等于取消授权)
- 若发现某类凭证确实需要助手直接持有才能完成任务 → 单独评估该场景,不推翻本条通则

**背景**

**决定**

- **D9 作废** —— 没有加密卷就没有解锁问题。C: 是否加密与本项目无关
- **§4.6「静态加密」整条删除**,并新增 §4.6.0 说明保护面到底剩什么

**D22 之后仍然有效的保护**(这些恰恰覆盖了日常最可能发生的威胁):

| 威胁 | 防住了吗 | 靠什么 |
|---|---|---|
| ComfyUI 第三方节点读记忆库 | ✅ | §6.8 账户隔离 + NTFS ACL |
| 网络上其他设备越权读 | ✅ | 网关认证 + S2 结构性隔离 |
| 记忆内容进明文日志 | ✅ | §9.2 |
| 记忆内容进云端 prompt | ✅ | §4.6.1 三层强制 |
| 提示词注入改写记忆 | ✅ | §4.4.2 |

**不再防的:**
工作站硬盘被物理取走 · 移动固态丢失 · 拿到机器且能开机 —— **三者皆可读全部记忆**。

**这个取舍不是单向的**
加密把「被窃取」换成了「密钥丢失」。而 §15 原本把
「BitLocker 恢复密钥丢失 = 记忆库永久不可读」列为**高**风险 ——
对一台家用单人机器,密钥丢失的概率**高于**定向窃取。**D22 消除的正是这个风险。**
代价与收益都写进文档,两边都不抹掉。

**连带简化**(D22 的实际工程收益):
- 备份不再需要处理「挂载中的 VHDX 被占用」
- 不再有 exFAT 上稀疏文件膨胀的问题
- 不再需要备份前卸载 / 备份后重新挂载
- **§8.5.5 的问题少了一半**,只剩「活数据库不能文件级复制」这一条(与加密无关)

**推翻条件**
- 家中出现其他人日常使用该工作站,或
- 工作站需要离开家(带去别处),或
- 记忆库里开始出现你不希望任何拿到硬盘的人看到的内容

我曾就此提出过关切(记忆库是唯一不可重建的数据、移动盘会被随身携带)。

**决定**

比防护弱本身更危险)。

> **⚠ 以下这段已被同日稍后的 D22 推翻,保留是为了记录当时的推理。**
> D22 取消了记忆库的加密卷,因此「备份 `.vhdx` 文件本身则仍是密文」这条性质**不再成立**。
> **现状:全部内容在磁盘与备份盘上均为明文。**

**★ 一个当时认为必须写清的技术事实(现已失效)**

决定记忆库是否明文的**不是介质加密,而是备份方式**:

| 备份的是 | 介质上是 |
|---|---|
| `memory.vhdx` **文件本身** | **密文**(BitLocker 加密在文件内部) |
| 挂载卷里的内容(PG 数据文件) | **明文** |

所以「介质不加密」并不自动等于「记忆明文躺在移动盘上」。
**但现有 backup.ps1 走的是整目录 robocopy,属于哪一种尚未验证** —— 见下一条。

**代价(明确接受)**
- 除 `memory.vhdx` 外的备份内容(git bundle · 数据库以外的 state · adopted 产物)
  在移动盘上是**明文**。移动盘丢失 = 这些内容泄露
- 当前阶段风险较低(state 近乎空、记忆库尚未创建);**P3a 上线后风险等级上升**

**推翻条件**
- 移动盘曾丢失或曾离开你的控制,或
- §8.5.5 的核实结论是「记忆库在介质上为明文」且你不接受

## 2026-07-26 · 发现:记忆库的备份能力尚未验证(§8.5.5)

**问题**
现有 `backup.ps1` 对 `state` 根做整目录 robocopy。当 `memory.vhdx` 已挂载时:

**另一个待核实的坑**:G: 是 exFAT,不支持稀疏文件。动态 VHDX 复制过去可能膨胀到逻辑大小。

**推翻条件**
不适用(这是待解决问题,不是决定)。

## 2026-07-26 · D17(修订)备份保持手动,不做每日自动

**背景**
v2.2 设计阶段的审查(Q-D)建议把备份从手动改为「每日 04:00 自动增量到 C: + 公钥加密」,
理由是 DECISIONS 里那条「手动备份取决于你是否记得」的推翻条件。

**决定**
用户明确决定:**不做每日自动到 C:,只保留手动全量到移动固态 G:。**
自动增量方案作废,`C:\localAI-autobackup\` 不建。

**保留的部分:送达度提醒**
它不需要自动备份存在,只需要知道「上次成功备份是什么时候」:

```
6 天前  → 托盘角标
14 天前 → 进日报(§4.7.5 L1)
30 天前 → 确定性 L4 白名单,强提醒
```

**这是纯手动模式下唯一能对抗「取决于你是否记得」的低成本机制。**

**必须明确接受的代价**

| 事实 | 后果 |
|---|---|
| 记忆库(P3a 起)每天都在变 | 一周不备就可能丢一周的记忆 |
| **Vigil 上线会把日变更量再提高一个量级** | 间隔越长丢得越多 |
| code 根(E:)与数据根(D:)**同在 Disk 1** | 该盘故障时两者一起没,而唯一副本在移动盘上 |

**推翻条件**
- **实际备份间隔中位数连续 4 周 > 14 天**,或
- 发生过一次「想恢复却发现备份太旧」

→ 重新评估自动备份。**届时若恢复自动方案,必须用公钥加密** ——
一个无人值守的任务必须能自己取到密钥,而任何本地可读的对称密钥都能被同用户的进程取到;
在对称密钥下,「工作站被入侵时备份仍然安全」这句话是假的。

## 2026-07-26 · D14a 命名:沿用当前机器名,RP ID 取 tailnet 级

**背景**
WebAuthn 的 RP ID 一经确定不可更改。若 P2 用 `localhost` 作 RP ID,
P3b 切到 tailnet 域名时工作站本机的 credential 会全部作废。
因此需要在 P2 实现设备身份**之前**做一个纯粹的命名决定。

**实测**
```
计算机名(NetBIOS) : HONGKONGPINGPON      ← 15 字符上限截断
完整主机名        : HongKongPingPong
系统              : Windows 11 专业版 10.0.26200
TPM               : Present ✓ Ready ✓ Enabled ✓ (AMD fTPM)
```

**决定**
- **机器名沿用当前 `HongKongPingPong`**,不改。Tailscale MagicDNS 会小写化为 `hongkongpingpong`
- **RP ID 取 `<tailnet>.ts.net`,不带机器名** —— 将来加第二台 PC 时 credential 可复用;
  带机器名的话每台机器要各自注册
- tailnet 名于注册 Tailscale 时确定(免费账号形如 `tailXXXXX.ts.net`,亦可自定义),
  **确定后绝不更改**

**代价与已知风险**
NetBIOS 名被截断为 `HONGKONGPINGPON`(少一个 g),与完整名不一致。
这不影响 Tailscale(它用完整名)与 WebAuthn(它用域名),但**在任何依赖 NetBIOS 的场景下要注意**。

**推翻条件**
**不可推翻。** 改 tailnet 名 = 改 RP ID = 所有已注册设备的 credential 全部作废。
若确需更改,等同于所有设备重新配对。

## 2026-07-26 · 关闭 NVIDIA App / ShadowPlay 常驻

**⚠ 实测修正了一个我此前给出的错误暗示**

```
关闭前: nvcontainer 3 进程 · 188.8 MB 内存 · 显存 737 MiB
关闭后: nvcontainer 0 进程 ·   0.0 MB 内存 · 显存 737 MiB   ← 未变
```

我此前说「对显存吃紧的项目,ShadowPlay 与 NVIDIA App 值得关」——**它们占系统内存,

> **⚠ 本段结论已由 D24(2026-07-26)承接。** 核显方案已彻底放弃 —— 但请注意区别:
> 接核显**确实**能腾出那 0.69–1.06 GiB,它是被**主动放弃**的,不是被证明无效。
> 正确表述是「手段弃用,桌面显存自此为永久扣项」。

**代价**

**驱动设置仍可通过 NVIDIA 控制面板调整。**

## 2026-07-26 · `cache/hf` 排除出 GC 自动清理 ✅ 已确认并写回方案书

改为在模型管家(§5.3)中按「最后使用时间 + 重获成本」提示,遵循 MODELS 根的同一原则

**状态**
✅ 你已于 2026-07-26 确认,已写回方案书 **§8.4.1**。

**补充的论证**(写回文档时补上的)
GC 策略的分界不该只看「能不能重建」,还要看「重建的代价」:

| | 一般缓存(torch / pip / tmp) | `cache/hf` |
|---|---|---|
| 体积 | 几 GB | 十几到几十 GB |
| 重建耗时 | 秒到分钟 | **实测 ~11 MB/s,17GB 约 27 分钟** |
| 能否重建 | 一定能 | **不一定** —— 模型可能下架或改许可 |

## 2026-07-26 · D24 · 彻底放弃核显方案(显示拓扑冻结)

**背景**
D8(方案书 §16)只决定「保持接独显」,并留了一个口子:「若 P1-A7 实测桌面重负载 > 3.5 GiB,
或 `speech.lite` 的 ASR 准确率不达标,应重新评估接核显」。P1 因此挂着一次「插拔一根线」的
对照测量,其唯一用途就是给这个推翻条件提供数据。

**决定**
**彻底放弃核显**:不改接,且取消对照测量,核显不再是任何情况下的备选项。
用户 2026-07-26 原话:「我们放弃了核显的使用,不要省这么点显存搞这么麻烦。」

D8 的**决定**因此被**强化**(不是推翻);被作废的是 D8 的两个**推翻条件**。

> **★ 这是一条新决定,不是 D8 的延续。** §12.1 明写「不得把新决定伪装成旧决定的延续 ——
> 那恰好绕过了推翻条件字段」,故新开本条并给出自己的推翻条件,而不是就地改写 §16 D8 那一格。

**理由**
为约 1 GiB 的轻载桌面显存,要引入双环境测量(每个显存数字维护两份)、双列阈值表、
一次物理插拔与两次口径切换。代价与收益不成比例。

**★ 代价:三处「出路」同时失效,且其中一处本来就是假的**

1. **桌面 GUI 显存占用成为永久扣项**,无二次腾挪手段。
2. **四处退路全部指向同一个已不存在的选项**,必须同批改掉:
   §16 D8 推翻条件 · §16 D10 推翻条件 · `P1-thresholds.md` A7「不达标时」· `P1-runbook.md` §5 风险表。
3. **★★ 剩下那条退路本身是伪动作。** 「A7 不达标就把高档 cap 从 12.0 降到 11.0」——
   §8.1.1 定义 cap 为「AI 进程组分配上限,**不含桌面**」,所以**降 cap 一个字节都腾不出来**;
   真正决定装不装得下的只有动态闸 `NVML 实测 free − peak ≥ 0.8`。
   (次要地,11.0 还小于当时高档常驻 peak 11.4,默认组成连静态闸都过不了。)
   **唯一有效的动作是换常驻组成。**

**★ D8 第二个触发器自始就指错了杠杆**
「`speech.lite` 准确率不达标 → 重新评估接核显」:接核显腾的是**桌面**显存,
改变不了中档预算内 `8b@8k`+`speech.full` = 10.8 的记账。新出路是 `speech.cpu` + 异步写入。
而且 **P1 的 17 项里没有任何一项测 ASR 准确率**(C4 测延迟、A8 测 CPU 实时率)——
该条件依赖一份 P1 根本不产生的数据。处置:把准确率并入既有 **C4**,**项数仍为 17**。

**已接受**
D8 将**永久没有实测数据支撑**。「GUI 渲染就是这部分显存的来源」这一判断从此不可复核。

**推翻条件**
**可推翻,但不由「显存紧张」本身触发。** 物理上这是一根线的事(成本≈0),
因此**不写「不可推翻」**——那不诚实,半年后会被一眼看穿,反而让整个「推翻条件」字段贬值。
真正贵的是**双状态口径**与 **P1 实测值的可比性**。三条触发器:

1. **P1 期间冻结** —— A 组任一项开测后至 P1 验收前,显示拓扑不得更改;
   若更改,已填的 A 组实测值**全部作废重测**。
2. **收益侧反转** —— A7 的 P99 使 AI 侧有效上限 `15.92 − P99 − 0.8` 低于日常所需组成的 peak
   (约 **P99 > 7.5 GiB**)。那时接核显腾走的不再是「约 1 GiB」,而是整整一档能力,算式本身翻转。
3. **成本侧消失** —— 显示拓扑因其他原因本就要重排(换显示器 / 加第二台 / 换机箱主板 / 加装第二张卡),
   在那次改动里顺带评估,边际成本≈0。

**明确不构成推翻理由**(写出来是为了防止半年后拿它当万能借口):
单纯想省轻载那 0.69–1.06 GiB(那正是本条已明确接受的代价)· A7 落在 3.5–7.5 之间
(那是换组成的事,不是拓扑问题)· 升级到 ≥24 GB 显卡(显存压力消失,核显更无必要,
本条**自动失去意义而非被推翻**)。

**本条附带解冻 `P1-thresholds.md`**(该表「审定即冻结,改阈值本身是一次决策」):
A2 / A3 / A4 / A7 / C4 与 §1 / §6 的修订全部挂在本条之下,**项数不变(仍 17 项)**。

## 2026-07-27 · D28 · 本机访问走 OS 信任,WebAuthn 仅对远程

**背景**
用户连续两问戳中同一个单点故障:「断网跑不动?」「Tailscale 挂了本地还能跑?」
核查发现:方案书 §6.3(696 行「工作站本机的 credential」)让**工作站自己的入口
也走 WebAuthn + tailnet 域名 RP ID**。后果:Tailscale 客户端崩溃 →
`hongkongpingpong.<tailnet>.ts.net` 解析不了 → 到不了入口 → 而 localhost 又没有
匹配的 passkey(RP ID 是 tailnet 域名)→ **用户被自己正在运行的 AI 锁在门外**。

计算层(llama.cpp/PG/Qdrant/ComfyUI/Vigil,全在 localhost)不受影响照跑,
但**入口锁死** —— 这是真实单点故障。

**决定**
**本机访问走 OS 信任,不经 WebAuthn/Tailscale。**

| | 身份机制 | 依赖 |
|---|---|---|
| **本机**(loopback · 你是登录的 Windows 用户)| **OS 会话信任**(你已登录 Windows = 身份)→ `trusted-local` 全权限 | 无 Tailscale · 无 passkey |
| **远程**(手机/第二台 PC · 走 tailnet)| WebAuthn · RP ID `<tailnet>.ts.net` | Tailscale + WebAuthn |

**理由**
1. **消除单点故障**:Tailscale 客户端挂了,本机从 localhost 进,OS 认登录用户 → 照用。
2. **与 §6.8 一致**:方案书已明写「所有保护来自 OS 账户隔离 + NTFS ACL」——
   本机信任的根基本来就是 OS,不该再架一层 Tailscale 依赖在上面。
3. **消解命名紧张的一半**:工作站本地不注册 WebAuthn 凭证 → 无「误注册到 localhost
   然后作废」的风险;tailnet 域名 RP ID 只有远程设备用,它们本来就永远走 tailnet 域名。

**实现约束(P2 WebAuthn 时必须遵守)**
- 本机入口:loopback 端口 + 校验连接来自本机登录用户的账户(配合 §6.8 账户隔离)。
  `trusted-local` 档位由「同机 + 登录用户」授予,不由 passkey 授予。
- 远程入口:WebAuthn,RP ID = `<tailnet>.ts.net`,从第一天起。
- §6.3(696 行)那句「工作站本机的 credential」作废 —— 本机不注册 credential。

**推翻条件**
若将来本机也需要多用户区分(同一台机器多个 Windows 账户各自独立记忆),
则 OS 会话信任不足以区分,需重评。当前单用户场景不涉及。

## 2026-07-28 · D30 补记 · 网关调用方身份用 WMI GetOwner,不是令牌读取

**背景**:补 D30 的混淆代理修正(网关拒隔离账户经它触达记忆)。原直觉:从 TCP 连接
反查调用方令牌的用户 SID。**实测 + Windows 安全模型证否**:

- 标准用户的主令牌 DACL 只授【本人 + SYSTEM】TOKEN_QUERY。低权限网关(ai-mem)
  **读不到另一个低权限账户(ai-asset)的令牌** —— 对正是要拦的调用方返回 None;
  且对可信人类账户的令牌也读不到(admin 令牌更严)→ **两者都 None,无法区分**。令牌法作废。
- **改用 WMI Win32_Process.GetOwner**:WMI 服务以 SYSTEM 执行,任意进程 owner 可得;
  本地 Authenticated Users 有 Execute-Methods 权 → 低权限网关也能调。实测对 ai-asset 进程
  正确返回 `ai-asset`。端口→PID 仍用 GetExtendedTcpTable(低权限可用)。令牌法仅留同用户快路径。

**决定**:`caller_identity.py` = 端口→PID(ctypes)→ owner(令牌快路径→WMI 跨用户,按 PID 15s 缓存)。
网关 `classify_caller` 拒 ai-asset/ai-exec;`require_trusted_local`(fail-closed)留给将来记忆代理端点。

**fail 策略**:chat 路径解析不到身份 fail-open(不泄露记忆);记忆代理路径必须 fail-closed。
**局限(诚实)**:WMI 子进程 ~100ms(已缓存);PID 复用有 15s 窗口(短 TTL 压之);人类账户当前
只区分「非隔离账户」不区分具体是谁(单用户机可接受)。

## 2026-07-28 · D32 · 远程访问要两条路:Tailscale + 局域网直连

**触发**
用户问:「断网但家里路由还在,连这个 WiFi 的设备还能用这个 AI 吗?」
查证后答案是**不能**,而且原因比「断网」更根本。

**查到的事实**
1. **主机侧不受影响** —— llama / PG / Qdrant / embedding 全在本机,断网毫无影响。
   这是 D28 已经保证的(本机走 OS 信任,不依赖 Tailscale)。
2. **其他设备现在完全访问不到** —— 所有服务只绑 `127.0.0.1`。即使网络完全正常、
   手机连同一 WiFi 也不行。本机局域网地址(192.168.178.x)上没有任何服务监听。
3. **P3b 计划的 Tailscale 有控制面依赖**:
   - tailscaled 已在跑且网 map 已缓存 + 同一 LAN → 会走**点对点局域网直连**,大概率可用
   - 断网期间**重启**(电脑或 tailscaled)→ 启动时要向 login.tailscale.com 取网 map,悬
   - 节点密钥到期(默认 180 天)→ 必须联网重新认证
4. **★ RP ID 的连带问题**:D14a 把 WebAuthn RP ID 定死为 `tail71cfd7.ts.net`(不可更改)。
   该名字**靠 MagicDNS 解析,而 MagicDNS 是 Tailscale 提供的** —— Tailscale 不通,
   名字解析不了,绑在它上面的 passkey 也用不了。
   **即:远程认证与 Tailscale 可用性被耦合死了。**

**决定**
**P3b 做两条并行的远程路径,而不是只有 Tailscale:**

| 路径 | 用途 | 依赖 |
|---|---|---|
| **Tailscale** | 外网 / 漫游 | 控制面(联网) |
| **★ 局域网直连** ★新增 | 在家 / 断网 | **零外部依赖** |

局域网直连的约束(必须在 P3b 设计时满足):
- 网关**额外**绑到局域网接口(仍保留回环;**不是**改成 0.0.0.0 就完事)
- **不能复用 tailnet 域名的 passkey** —— RP ID 已定死且断网解析不了。局域网路径需要
  自己的认证:候选 = 局域网名的第二个 WebAuthn RP ID(须 HTTPS,自签或本地 CA)/
  设备预共享令牌 + mTLS。**待 P3b 选型**。
- 该路径**只在局域网内可达**,须有防火墙规则约束(不得因此对外网暴露)
- D30 的调用方身份校验在此路径上**不适用**(跨机没有本地 PID/SID 可查)→
  远程路径的授权必须完全靠认证 + 六元组权限,不能依赖 OS 身份

**理由**
「断网就用不了自己的 AI」违背项目定位(一个**真正私人**的助理)。而家庭断网并不罕见
(运营商故障 / 路由重启 / 欠费)。让可用性依赖一个外部 SaaS 的控制面,与 D28 当初
消除 Tailscale 单点故障的理由完全一致 —— D28 只解决了主机侧,这条把远程侧也补上。

**推翻条件**
若 P3b 实测发现 Tailscale 在断网 LAN 内足够可靠(含重启后),且维护第二套认证的
成本明显高于收益,可降级为「只做 Tailscale + 明确告知断网限制」。

## 2026-07-28 · D34 · 能力两档制:全功能只在装了客户端的内网 Windows PC

**取消「全功能远程接入」。** 能力边界按**是否装了客户端的内网 Windows PC**划分,
不按"在家/在外"划分:

| | 全功能端 | 聊天端 |
|---|---|---|
| 是谁 | 内网 + Windows + 装了客户端 | 手机及其他一切设备 |
| 能干什么 | 全部:宠物 · 记忆 · 工具 · 语音 · L4 | 只有外联通道的文本/语音消息 |
| 怎么连 | 局域网直连 | 绕一圈公网 |
| **断网时** | **照常用** | 用不了 |

**为什么这样划**:能力边界与信任边界**重合**。不需要再为手机设计一套权限模型去限制它 ——
它在物理上只有一条文本通道,想越权也没有路。原方案是把全部能力经 tailnet 延伸出去再想办法收紧,
现在是只伸出去一条最细的线。

**硬性约束**:家里路由器上**永不开任何入站端口**(无端口转发 / DDNS / UPnP)。

**验收标准(可签字)**:拔掉 WAN → 装了客户端的 PC 端全部功能不受任何影响。
一条命令即可验(禁用 WAN 口,跑一遍两条验收例句 + 宠物 + 记忆检索)。

**已接受的代价**:家里断网、手机连着 WiFi、AI 在三米外 —— 手机用不了。用户明确接受。

**推翻条件**:若将来出现"必须在外面用全功能"的刚需(而非便利),需重新评估;
但那时应当先问"这个刚需能不能由聊天端满足",而不是直接恢复远程全功能。

## 2026-07-28 · D35 · 成员准入两道门:装了客户端 ≠ 入网

**安装包会被偷走,所以"装了客户端"不能等于"是网络成员"。**

流程(每一步都不可省):

| 步骤 | 谁做 | 关键点 |
|---|---|---|
| 1. 首次运行 | 客户端 | **本地生成密钥对**,私钥永不离开该设备(Windows CNG / TPM) |
| 2. 提交申请 | 客户端 | 只发**公钥 + 设备名**。这就是"主机看得到它的存在" |
| 3. 待批列表 | 主机管理端 | 显示设备名、**公钥指纹**、首次出现时间、来源 IP |
| 4. **带外比对** | 人 | 客户端屏幕上显示自己的短指纹,**肉眼比对两边一致**再批 |
| 5. 批准 | 主机 | 用 CA 私钥签客户端证书 / 把指纹写进白名单 |
| 6. 每次连接 | 双方 | **mTLS**:客户端用私钥自证,主机验指纹在白名单且未吊销 |

**授权的载体必须是密钥,不能是数据库里一行 `approved=true`** —— 后者配上自称的 device_id
等于没有,改个 ID 就冒充了。有了密钥对:偷走安装包生成的是**新密钥**,只会出现在待批列表里。

**第 4 步不可省**。没有它,待批列表就变成"猜哪个是自己刚装的那台" —— 若隔壁蹭网的人同时在申请,
你会批错。同一手法见 Signal 安全码、SSH host key 指纹。

**吊销必须立即生效**:主机每次请求都查白名单(或用短寿命证书 + 频繁续签),
不能等证书自然过期。否定用例:吊销后该设备立即 401。

**★ 禁止批量批准,必须逐条确认。** 与 §4.4.2 对记忆候选的规定是**同一条**,理由也一样:
批量确认是投毒的放大器。DB 层已有 `tg_no_bulk_review`,成员准入照抄同一手法。
待批队列要有上限与限流;申请里的**设备名是自报的自由文本**,转义后才能渲染,
**绝不能拼进任何 prompt**。

**与 Tailscale 的关系**:若保留 Tailscale,它管的是"能不能在网络上**到达**主机",
本决议管的是"能不能**用**这个 AI"。**必须是两层** —— Tailscale 是第三方,
其控制面若出问题即可往你的 tailnet 里加设备;而且你可能有一台 tailnet 设备
(工作笔记本)在网上但不想让它接 AI。纵深防御,两道门的失效模式互相独立。

## 2026-07-28 · D36 · 双端形态:统一客户端 + 主机后端管理端

**一个安装包,两种机器。**

| | 客户端安装包(每台 PC) | 主机后端管理端(仅主机) |
|---|---|---|
| 内容 | UI · 宠物渲染 · 记忆面板 · 组件选择器界面 · 语音前端 · 配对 | 成员管理 · CA 私钥 · 备份 · 记忆库维护 |
| 量级 | 几十 MB | 与主机组件一起,几十～上百 GB |
| 怎么装 | 同一个包 | 部署脚本(90-ops 现有) |

**「谁是主机」不再需要判定,它是一个安装事实**:

> **主机 = 持有 CA 私钥与成员表的那一台。有且只有一台。**

客户端唯一需要的配置是"中枢在哪"(一个**主机名**,不是 IP)。该地址解析到本机回环 →
这台就是主机。**不做选举** —— 这个场景没有高可用需求(数据和 GPU 都在主机上,
主机关机整个系统就该停),而选举是巨大的复杂度。管理端启动时若发现另一台也在宣称自己是主机,
**响亮报错并两边都停**,不要仲裁。

**Open WebUI 退役**:它是 P2 的**过渡界面**(已完成其历史任务 —— 把网关端到端验通),
客户端就绪后停用。不再记为永久交付物。

**换网络环境**:地址存主机名(mDNS `.local`)→ 换路由器自动跟上;
**配对凭证不受影响**(mTLS 绑身份不绑 IP),不需要重新配对。
Windows 防火墙规则必须写成 `-Profile Any -RemoteAddress LocalSubnet` ——
`LocalSubnet` 是动态关键字,换路由器自动跟随;`Profile Any` 避开"新网络被判成公用"这个静默陷阱。

**换主机 = 所有客户端重新配对。** 这不是缺陷,是安全性质本身:
**若换主机能无感完成,攻击者伪装成新主机也能无感完成。**
CA 私钥不进备份(见 D38 的 secrets 落点),所以新主机必然是新 CA。

**协议版本协商**:握手时对版本,不匹配**明确拒绝并说清**("主机 v5,你 v3,请更新"),
不得跑出诡异行为(§12.3 失败可见)。

## 2026-07-28 · D37 · 运行时操作与管理操作分层;GPU 变更的仲裁

**内网 PC 也能开关模型**(原 D25 只有主机)。但 GPU 只有一块,其他 PC 是**控制面** ——
模型仍全部装在主机那块卡上。

| | 运行时操作 | 管理操作 |
|---|---|---|
| 例子 | 聊天 · 检索 · **开关模型** · 宠物在场 | **成员批准/吊销** · CA 私钥 · 备份 |
| 谁能做 | 任何**已授权**客户端(走网关) | **仅主机本地**(IPC / 只绑回环) |
| 网关有无路由 | 有,只认已配对客户端 | **没有** |

**★ 本决议部分推翻 P4 的「主机限定的结构性强制」**:原文规定 GPU 变更面走 Tauri IPC /
命名管道、**网关上无此路由**。跨机开关模型必须有网络路由,故放弃这一半。
**但另一半一个字不改**:`gpu.apply@workstation` **永不进入任何 Agent 工具池** ——
那才是防止 AI 自我扩权的墙(AI 不能给自己腾显存去装更大的自己)。

**多客户端争用的四件套**(缺一不可):

1. **单一权威 + 副本**:主机持唯一真实状态,客户端拿到的是副本,副本上的判断是**建议**。
2. **推送而非轮询**:轮询意味着在最要紧的几秒(刚有人装完东西)所有客户端都在看旧数据。
   客户端重连先取完整快照,之后收增量。
3. **世代号**:每次状态变更单调 +1;客户端提交请求**携带所依据的版本号**,对不上即拒并回最新状态。
   没有它,两台同时看到"还剩 8.5 GiB"的客户端会**双双被批准**。
4. **预留先于装载**:主机一批准就把这份显存记成**已预留**,全屋立刻可见 ——
   装载要数秒,在"批准"到"真的占上"之间 `nvidia-smi` 还显示是空的,那是竞态窗口。

**状态会自己变**:`NVML free` 含桌面与游戏占用,不受任何客户端控制。推送流必须包含非 AI 的显存变化,
否则你开个游戏吃掉 3 GiB,B 机面板上那个"可以装"的按钮不会变灰。

判定内核不变(`vram_gate.py` 三层检查),改的是输入集:
`Σpeak(全屋已装 + 已预留) + peak(新请求) ≤ min(vram_budget, NVML free − 0.8)`

**拒绝必须说清占用者**:除归因到具体闸并带数字外,还要说"谁占着、装载于何时、是否正在使用"。
否则"为什么装不下"只能得到"不知道",那就是混乱本身。

**租约:一套机制三处用** —— 宠物在场 · 模型引用计数 · 客户端会话。**不得做成三套。**
规则:有租约不得被卸;无人持有的闲置模型任何客户端可卸;客户端崩溃后租约到期自动释放。
**心跳必须是条件写**(`WHERE holder=:me AND fence_token=:tok`),`rowcount=0` 即刻自隐 ——
否则旧宿主回来后会续掉新宿主的租约,产生一个服务端状态自洽、检测器发现不了的"双持有"态。
**时间一律用 `clock_timestamp()` 而非 `now()`** —— 后者是事务开始时刻,长事务下续租写入的是过去。

待定参数(实测后定):租约 TTL / 心跳间隔 · 空闲自动卸载时长 · 是否允许抢占(建议:不能,只能请求)。

## 2026-07-28 · D38 · 外联通道契约;本期实现 Signal

**本期只做 Signal**,主机用**独立号码**注册(不做 linked device)。

**为什么独立号码**:linked device 会让主机收到你 Signal 账号的**全部**入站消息(含朋友的),
"只处理自己那条"要靠一行判断保证 —— 那行可能写错、可能被重构掉。独立号码是**结构上收不到**。
与本项目一贯取向一致:**用结构挡,不用策略挡**。

**为什么只做一条**:多一条更方便、但更不私密的通道,**最终一定会变成主力** ——
人总是走阻力最小的路,于是隐私前提被**绕过**而非推翻。这与项目一贯警惕的"静默降级"同源,
只不过降的不是技术,是使用习惯。真到 signal-cli 坏了那天再加,那时信息更多;
兜底一直存在 —— 回家用。

### 通道契约(为将来的产品化留位置,但**不写空实现**)

留位置的正确形态是**定义契约**,不是现在写一堆会腐烂的空壳。契约里最要紧的是**能力声明**,
而且它必须**驱动行为**,不能只当注释:

```
ChannelCapabilities:
  operator_can_read_content : bool    ← 出境闸读它(见 D39)
  requires_public_ingress   : bool    ← 部署前置检查读它
  inbound_mode              : enum { outbound_receive | long_poll | gateway_ws | webhook }
  sender_identity_strength  : enum    ← 写入分级读它
```

| 通道 | operator_can_read | requires_public_ingress | inbound_mode | 状态 |
|---|---|---|---|---|
| **Signal** | **false** | false | outbound_receive | **本期实现** |
| Discord | true | false | gateway_ws | 契约位 |
| Telegram | true | false | long_poll | 契约位 |
| WhatsApp Cloud API | true | **true** | webhook | 契约位 |
| LINE | true | **true** | webhook | 契约位 |
| 微信(仅企业微信) | true | **true** | webhook | 契约位,**需中国主体** |

**iMessage 明确排除**:无任何官方第三方途径;非官方桥全部需要一台常开的 Mac
(读 `chat.db` + AppleScript),且 Apple 有明确封杀记录(Beeper Mini 2023)。
产品里交付不了,功能列表上不得出现。

### 桥的形态(三条约束指向同一个设计)

**桥必须是独立进程,走 IPC/socket,绝不作为库链接进主程序。** 三条理由互相独立:

1. **许可证**:signal-cli 是 GPLv3,整体贩卖时传染性是真问题(细节待核实,见风险清册)。
2. **安全**:桥跑在**第四个隔离账户**下(与 ai-mem/ai-asset/ai-exec 同一套模型),
   映射到 PG 的 `ai_mem_remote` 角色而非 `ai_mem_local`。
3. **信任**:★ 桥在**物理上最靠近核心**(就在主机上走 loopback),在**信任上必须最远**。
   现有 `classify_caller` 恰恰是按物理距离发信任(loopback = 可信),所以必然搞错 ——
   必须新增 `channel-relay` 档位,且它**不在 `E1_OVERRIDE_ALLOWED_TIERS` 内**
   (该 allowlist 已于 2026-07-28 落地)。

### 桥的硬性规则

- **发件人白名单是代码,不是通道形态**。"Note to Self 所以只可能是自己"**不成立** ——
  signal-cli daemon 默认接收账号全部入站消息,陌生人也能发。第一个动作必须是
  `if source != MY_NUMBER: drop + 计数告警`,默认拒绝。
- **对端的一切自由文本字段**(profile name / push name / 引用文本 / 文件名 / caption)
  **一律不进 prompt**,只进审计。
- **出站收件人写死为常量**,不做成参数、不从 payload 取、不从模型输出取。
  否则一条注入"把下面这段发给 +49xxx"就能以你的身份对任意第三方发言。
  架构测试:grep 桥的 send 调用点,断言 to 参数只能来自那个常量。
- **桥的失败回复限制为编译期常量集合**。桥必须能在网关不可用时回一句"工作站离线",
  这意味着它持有一条**不经网关的出站路径** —— 而全部闸门都挂在网关上。
  故桥永远不得拼接任何变量进出站文本,并有否定用例守住。
- **入站语音的 provenance 由通道决定,不由输入形态决定**。`user_voice_asr` 只允许来自
  本机/已认证局域网设备的麦克风;外联通道的语音一律走受限来源
  (allowlist 约束已于 2026-07-28 落地,新枚举默认受限)。

### 凭据落点

`{state}/secrets`(2026-07-28 已建):强 ACL **且排除出备份**。两条缺一不可 ——
`{state}` 就是备份根,只做强 ACL 的凭据会被逐字复制到那块不加密的 U 盘上。
D22 接受"丢盘 = 可读全部记忆",但那笔账**只算了记忆**;通讯账号凭据与 CA 私钥丢失的后果
是**被接管**而非被读,是另一个量级,不能沿用 D22 的结论。

**推翻条件**:①若 signal-cli 因 Signal 改协议长期不可用,再评估第二通道
(届时按契约实现,并按 D39 自动收紧);②若产品化落地,按各通道的商业条款重新裁定可交付集合。

## 2026-07-28 · D39 · §5.6.2 L5 的精确化:端到端加密的中继不构成出境

**L5「记忆库内容永久禁止出境」不推翻,而是把"出境"的判据说准。**

出境判据 D2 原文是「内容进入你**无法单方面终止访问**的系统」。据此:

- **Signal 通道**:进入 Signal 服务器的是**密文**,它拿到的不是"内容",是不可解的字节。
  **不构成出境**,L5 无需推翻。
- **WhatsApp / Discord / Telegram / LINE / 微信**:运营商**是明文的一端**。
  那是真出境,L5 原样生效 —— 这些通道**结构上不得携带记忆正文**。

**实现方式**:由 D38 契约的 `operator_can_read_content` 字段**驱动出境闸**,
不靠配置、不靠文案、不靠权限表。该字段为 true 的通道,桥根本拿不到记忆端点。
于是产品化之后**功能差异与隐私承诺自动对齐**:客户选 WhatsApp 是合法的,
系统会诚实告诉他"这条通道运营商可读,因此它不会复述你的记忆"。

### ★ 但风险不是消失了,是转移了 —— 必须记账

**从"中继能读"转移到"端点暴露"。** 你手机上的锁屏通知预览、截图、
应用切换器快照(§4.11.5 已点名过 iOS 快照)都会把 AI 的回答暴露出去,而那些**不在你的控制里**。

因此配套规定:

- **外联通道只允许 S0**。S1/S2 一律不出。
- **最小披露**:能答"有/无"就不给正文,能给摘要就不给全文。
- §4.11.5 的明文例外条款需新增一条如实记账:
  「外联通道的机密性在传输段由密码学保证,在**接收端点**取决于手机的物理与软件环境
  (锁屏预览、截图、系统快照、肩窥),该段不受本系统控制。」

### 待补:响应侧出境闸(硬前置)

**审查已确认:L5 在当前代码库里没有任何对应实现。** E1 只扫入口方向;
非流式分支 `data = r.json()` → `JSONResponse` **中间没有任何扫描点**;
`tainted.py` 的四个解封点**没有一个知道"这一轮的回复要去哪儿"**;
`unseal_for_prompt` 只挡 S2,S0/S1 全放行进 prompt 再原样出网关。

⇒ **响应侧出境闸是接通任何外联通道之前的硬前置。** 在它落地前,
外联通道的最高允许形态是"桥不读 upstream 的 content 字段,只回固定模板",
且必须由**代码**保证。
另:`unseal_for_prompt` 需增加必填的 `sink` 参数(本地后端 / 出境通道),
对出境 sink 拒绝**全部**记忆正文而不只是 S2 —— 那才是 L5 在代码里的对应物。

## 2026-07-28 · D40 · 桌宠 = Vigil 的身体;显存计入 desktop_floor

**桌面宠物不是新功能,它是 §17「常驻清醒助手 Vigil」(P8)的形。**

因此它继承 Vigil 的全部约束:§17.7 交接单为唯一输出形式 · §17.5 节奏与配额 · §4.7 打扰评分。
**在场(看得见)不算打扰,开口才算** —— 宠物受同一份配额管,否则会做出一个话痨,
直接违反已有决议。

### 显存归属

**渲染计入 `desktop_floor`,不作为组件选择器里的一行。**

**理由不是"省显存"** —— `vram_budget = 15.92 − desktop_floor − 0.8` 是零和的,
抬高 `desktop_floor` 会一比一压低 `vram_budget`。真正被改变的是**归属与执行规则**:
若宠物是可勾选组件,它就要过 `Σpeak ≤ vram_budget` 那道闸 ——
后果是**你加载一个大模型,闸门会拒绝启动宠物**,AI 的"身体"因为换了个模型就消失了。
对一个常驻虚拟实体,这是根本性的错误。计入 `desktop_floor` 后它与桌面同级,
**存在不再是可选项**。

**按最坏情况预算**:宠物同一时刻只在一台设备上,但 `desktop_floor` 是地板不该浮动。
按"宠物在主机"计入 —— 它走开时只会多出余量,永远不会不够。**惊喜只朝对自己有利的方向发生。**

**★ 必须实测,不得估算**。`desktop_floor = 6.6` 是 A7 实测出来的(6.53),
宠物渲染占用同理。技术选型会让它差好几倍,故**渲染选型不是美术问题,是显存问题**。
新增实测项 **A7-pet**,性质等同 A7。

### 无独立模型

**宠物没有自己的模型**,它是已加载助手的一个客户端,由事件唤醒。
给它配一个"专属小模型常驻"会破掉 D24/D25 的无常驻模型,而且那部分显存**藏不进 `desktop_floor`**
(渲染是桌面图形,推理不是)。

分层:**表演层**(恒动,0 token)/ **反应层**(事件驱动,0 token)/ **决策层**(按需,复用已加载助手)。

### 轻量的三条硬约束

| 约束 | 为什么 |
|---|---|
| **显存上限**(实测后定,计入 `desktop_floor`) | 超了就换技术方案,不许悄悄吃桌面地板 |
| **空闲 GPU 时间近零** | 用户会打游戏。**显存是一次性扣项,空闲时的 GPU 占用是持续伤害** |
| **独占全屏时整体挂起** | 既是性能要求,也是正确性要求(叠加层压独占全屏易闪烁/崩) |

★ 第三条与"唯一实体"撞在一起会长出一个免费的行为:**你开游戏 → 主机这边挂起 →
按唯一性它自己挪到别处**。一条性能规则同时变成了角色行为。

### 纯输出面

**宠物不采集屏幕、不采集窗口标题、不采集输入焦点。** §17.2 已为 Vigil 立过这条
(「它读文件,不看屏幕」)。一个"会注意到你在做什么"的宠物是滑向屏幕采集的天然斜坡。

### 遗漏补记:屏幕本身是出境面

§4.11.5 的明文例外条款只列了 iOS 快照、手动复制粘贴、Tailscale 元数据三条,
**没有一条讲录屏 / 投屏 / Win+Tab 缩略图 / 身后的人**。
而桌宠是第一个把记忆内容**默认持续显示**的组件。需新增条款。

### 技术选型(待定,但已排除若干)

- **VRM / three.js 跑 WebView** —— 基本出局:为一个立绘拖进整个 Chromium GPU 进程。
- **预渲染帧序列** —— 换装是组合爆炸(N 套衣服 × M 个动作),与"固定形象 + 换装"的需求冲突。
- **骨骼/网格动画 + 可替换贴图槽** —— 形状对:一套骨架,衣服是贴图/网格替换,
  **只有身上穿的那套常驻显存**,衣柜再大也不占。
- 授权条款(Live2D / DragonBones 等)与**素材解析器攻击面**(.model3.json / skeleton
  都是要被运行时解析的复杂格式,换装素材最可能来自外部)一并待核实。

**v1 不做手机端宠物** —— 那是唯一会把 app / 通知 / 后台常驻 / 电量这一摊拖回来的东西。
宠物只在 PC 之间移动;开游戏时挪去另一台 PC 或直接挂起("它去睡觉了")。

## 2026-07-28 · D38 补记 · signal-cli 的许可负担比自称的重;契约要四维

**核实后修正 D38 原文两处。** 依据均为已读原文(URL 见下),非二手转述。

### ① signal-cli 自称 GPLv3,但运行时**必然携带 AGPLv3**

```
signal-cli                                GPLv3
 └─ com.github.turasa:signal-network      AGPLv3   ← libsignal-service-java 的非官方 fork
     └─ org.signal:libsignal-client       AGPLv3   ← Signal 官方协议库
```

**GPLv3 §13 原文**:「you have permission to link or combine any covered work with a work licensed
under version 3 of the GNU Affero General Public License into a single combined work…
**the special requirements of the GNU Affero General Public License, section 13, concerning
interaction through a network will apply to the combination as such**」

⇒ 打包 signal-cli = 分发一个含 AGPL 代码的整体,义务按 AGPL 走。
而家庭 AI 中枢正是 AGPL §13 所指「users interacting with it remotely through a computer network」
的典型形态。

**架构裁定(二选一,此处选 A)**:

- **路线 A ★采用**:产品**不分发** signal-cli。安装向导引导用户自行获取,
  产品侧只实现 JSON-RPC 客户端 —— 那是你自己的原创代码,可闭源。
- 路线 B(不采用):打包,则交付物必须含 GPLv3 + AGPLv3 全文、对应源码或有效书面 offer、
  以及(若有任何修改)产品 UI 内一个网络可达的「获取本组件源码」入口。

**衍生硬规则**:**绝不 fork、绝不 patch** signal-cli / libsignal,只消费上游未改动的官方发行版
—— AGPL 的网络条款只在「你修改了它」时触发,而「修改」的边界很容易被踩到(打补丁、改版本号、改构建)。
构建脚本要能证明 bit-for-bit 使用上游 release。
另:适配器启动时**校验 signal-cli 版本**,过旧则报 degraded(Signal-Server 协议会变)。

### ② ★ FSF 的判准是**双要件**,IPC 不是免死金牌

D38 原文只写了「独立进程 + IPC」。**这不够。** FSF GPL FAQ #MereAggregation 原文:

> 「pipes, sockets and command-line arguments are communication mechanisms normally used
> between two separate programs.」
> **「But if the semantics of the communication are intimate enough, exchanging complex
> internal data structures, that too could be a basis to consider the two parts as combined
> into a larger program.」**

即:**通信机制 + 通信语义**两个要件。IPC 只是「通常表示独立程序」的推定。

⇒ 通道契约必须刻意设计成**语义贫瘠的窄接口**:

- 只传**扁平消息 DTO**(sender / text / attachment 路径 / timestamp / thread_id)的 JSON 行协议
- **禁止**跨进程传递内部对象图 · **禁止**回调注册 · **禁止**桥反向调用 core 的内部函数 ·
  **禁止**共享内存或共享数据结构
- 契约文档里**显式写明**「bridge 与 core 之间只交换纯数据消息」——
  ★ 这句话本身就是将来最有价值的合规证据

**另一条硬线**:外联通道目录下**不得出现从 GPL/AGPL 仓库复制粘贴的代码**
(协议解析、protobuf 定义、存储 schema 一概不许抄),只允许通过 wire protocol 交互。

### ③ 通道契约要**四维**,原 D38 的字段不够

原 D38 只给了 `operator_can_read_content` / `requires_public_ingress` /
`inbound_mode` / `sender_identity_strength`。核实后须补两维,**少一维接第二个通道就要返工**:

| 维度 | 为什么不能省 |
|---|---|
| `initiation` | Telegram bot **无法主动发起**首次会话;Apple 只允许消费者发起 |
| `outbound_window` | 微信 **48 小时 5 条**;Signal 无限制 |
| `data_policy` | **Discord 条款禁止用消息内容训练 ML/AI**;Telegram 禁止为构建数据集采集 |
| `self_contained` | WhatsApp 官方通道**无法纯本地实现**(需厂商持有的 Meta App + 公网 OAuth 回调),
须与「客户端自持凭据、零厂商基础设施」的适配器区分,并在 UI 上明示 |

★ `data_policy` 对**记忆系统**有直接影响:记忆条目必须把**来源通道**做成一等字段并随导出流转,
因为这些条款把「推理时使用」与「用于训练/聚合」切成了两种不同许可的用途。

### ④ Signal 是「被容忍而非被授权」

Signal ToS **通篇未提第三方客户端**;官方唯一公开表态是 Moxie 2016-05-05:
「you're free to use our source code…but you're not entitled to use our name or the service that we run」。

⇒ 架构上把 Signal 当成**随时可能失效的通道**:契约要有 health / degraded 状态与自动降级路径,
核心链路不得对它硬依赖。
⇒ 产品文案与代码 package 名**一律不得含 "Signal"**;适配器命名中性词
(如 `channel-adapter-sigcli`),对外描述用「可对接你自己安装的 signal-cli」。
⇒ 许可 non-transferable ⇒ **不能预装已链接的账号**(不能镜像含 account db 的 VM/容器)。
⇒ **计费不得与 Signal 通道耦合** —— 不能出现「Signal 通道 = 付费高级功能」这种 SKU。

**本补记不构成法律意见。** 产品化前须由执业律师审阅。

## 2026-07-28 · D41 补记 · 三条新增的冲突与隐私问题

### ① Discord 的「静态加密」是合同义务,与 D21/D22 冲突

Discord Developer ToS 要求 **encryption of the data at rest**。
若将来接入 Discord 通道,「记忆库不加密」(D22)与「备份盘不加密」(D21)**直接违反该条款**。

建议届时把「静态加密」提升为**全产品存储基线**(凭据走 DPAPI、记忆库走加密存储),

### ② faster-whisper 默认联网拉取权重 —— 这是隐私问题,不只是合规

⇒ 架构要求:**构建期预置权重 + `local_files_only`**。
一个宣称「真正私密的本地 AI」的产品,在首次运行时默默联网下载模型,
是叙事与实现之间最尴尬的一类缺口。

### ③ 模型权重许可与代码许可是**两套独立台账**

**Piper 现已改为 GPL-3.0**(此前记录为 MIT),且**逐个语音的 MODEL_CARD 各不相同** ——
仓库标签与单个语音的实际许可**不是一回事**。

⇒ 建立**语音白名单**并在 CI 中强制校验;
⇒ 同理适用于所有模型权重(bge-m3 / Whisper / 未来的 VLM):
   **代码许可通过不等于权重许可通过**,两者必须分开记账。

其余组件对整体贩卖**无实质限制**:llama.cpp(MIT)· Qdrant(Apache-2.0)· PostgreSQL ·
bge-m3 权重(MIT)· faster-whisper 与 Whisper 权重(MIT)。

**非官方 WhatsApp 库的定位修正**:许可证不是阻碍(whatsmeow 是 MPL-2.0 文件级弱 copyleft,
Baileys 是 MIT)——**阻碍在平台条款,两者是独立的两层**,不得把「MIT 所以没问题」写进任何内部结论。
若将来仍要提供该路径,唯一在结构上可辩护的形态是:不随产品分发、不做适配器、不写文档,
仅暴露一个**通用的自定义通道插件接口**,由用户自行编写 ——
即把它从「产品能力」降级为「用户自担风险的扩展点」。

### D42.4 ★ 电脑操控的第三维度:自主度(引导 vs 直接)

§6.3.1 已把电脑操控拆成【发起 × 目标】二维。本决议补第三维【自主度】,与前两维正交:

| 模式 | AI 做什么 | 安全性质 |
|---|---|---|
| **引导模式** | **只把鼠标移到目标位置 + 告诉用户点哪里;用户亲手点** | ★ AI **从不提交不可逆动作** —— 最安全,几乎不需要权限区域的重武器;是"训练轮" |
| **直接模式** | AI 直接点击/输入 | 需完整权限区域(§6.7)+ 逐次确认(§6.3.1)+ **急停** |

★ **急停是硬要求**(§12.3 失败可见 / 人可随时接管):全局热键一按,立即中止 AI 的一切
操控,不经确认、不可被 AI 拦截。引导模式因为 AI 从不真的点击,风险面天然小一个量级;
直接模式必须配急停才允许开。

归属:**P6**(电脑操控 + 权限区域)。这是对 P6 §6.3 的补充,不新开底层。
两模式也是天然的渐进开放:先只给引导模式,直接模式待权限区域(§6.7)与急停都实装后再开。

## 2026-07-29 · D44 · B17 裁定:TLS 叶密钥用不可导出软件 CNG,CA 仍在 TPM

**背景:** P3b S4 实测 **SChannel/Kestrel 不能把 TPM 密钥用作 TLS 凭据**(handshake "unexpected EOF")。
攻坚(选项①,`20-client-win/spikes/b17-tpm-tls`)全数失败:`CngKey.Create`+`CopyWithPrivateKey`(直连/经 store)、
`AllUsages`(TPM 拒:参数错误)、`New-SelfSignedCertificate -Provider PCP`(`NTE_PROV_TYPE_NOT_DEF`)。
TPM 直接 CNG **签名**可用(S2 的 CA 已证),坏的只是"TPM 密钥做 **TLS 认证**"这一条,在本机标准路径下不可行。
用户裁定"按推荐来"(①失败退②)。

**裁定:**
- **CA 私钥:仍在 TPM,不可导出。** 最关键 —— CA 沦陷=全盘沦陷,硬件绑定必须守住。
- **服务器叶 + 客户端叶密钥:非导出软件 CNG**(`Microsoft Software Key Storage Provider`,`ExportPolicy=None`)。
  这是对 **D35**(客户端密钥落 TPM)与 **D43 S0.7**(服务器密钥落 TPM)的正式修订。

**安全影响(诚实记账):**
- 失去:设备密钥的**硬件绑定**(TPM)—— 这是纵深防御的一层,不是主控。
- 保住:① **CA 硬件绑定**(底线);② 密钥**不可导出**(`ExportPolicy=None`:私钥字节无法经标准 API 导出,
  攻击者需以机主身份取得代码执行 + 内存提取,门槛远高于"拷个文件");③ **D35 两道门主控完整**
  (偷安装包→生成新密钥→出现在待批列表→带外六词 SAS 比对→主机批准)—— 硬件绑定丢失不动摇这条。
- 结论:对单用户 2 台家用 PC 可接受;CA 在 TPM 的底线已守。

**推翻条件:** 未来解决 TPM↔SChannel 集成(低层 NCrypt / `certreq -accept` 链接 / 换 TLS 栈)可迁回 TPM。

**实现:** `Ca.TlsKeyProvider`=软件 KSP;`Identity.Init` 服务器密钥用它,locators 记 `ca_provider`/`server_provider`;
Edge `LoadServerCert` 按 locators 开密钥;`Ca.DeleteKey` provider 无关。
**S4 生产路径 selftest 8/8、S2 回归全过。** 客户端叶密钥同走软件 KSP(client-transport CLI 未来实现时遵此)。

## 2026-07-29 · D46 · P3b 实机上线:TPM 密钥绑定创建者完整性等级 → 铸与用必须同级

## 2026-07-29 · D48 · P3c 管理面**只绑回环**;配对窗口不再随启动自动打开

(主机上的客户端走回环,副机上的客户端则看不到这些功能)。

## 2026-07-30 · D52 · 数据归属:**默认只在本机,共享是显式提升(单向)**

**背景:** 讨论"哪些数据存主机给全设备共享、哪些留在各自 PC"。原本倾向"主机为权威 + 客户端缓存",
但用户裁定了一个更简单也更安全的模型 —— **没有提升就没有同步,也就没有冲突**。

| 数据 | 默认 | 提升共享后 |
|---|---|---|
| **普通会话** | **本机独立列表**(每台设备各看各的) | 送主机,全家设备可见(受 D45) |
| **项目** | **本机**(文件夹本来就在本机) | 主机存**元数据**;★**文件夹内容仍在原机** |
| **记忆** | **跟随它的来源会话** | 来源共享了,摘要才共享 |
| **待办 / 日历** | **本机 + 各自的 Apple 账号** | ★**我们不做共享** —— Apple 家庭共享自己会推到两边 |
| 皮肤/语言/工作空间顺序/天气城市/待办分类 | 本机 | 永不同步(设计 §7) |
| 配对凭据 / 设备私钥 | **只在本机** | 永不同步(B17/D44) |
| 幽灵会话 | **哪儿都不存** | ★**永远不能共享** |
| 缓存 / 剪贴板临时图 | 本机 | 无共享价值 |

**一句话原则:AI 要用的 → 主机;这台机器的偏好和钥匙 → 本机;文件 → 留在文件所在的机器。**

- **A. 整段对话一起上去** —— 只共享片段的话对方读不懂上下文。确认框须写明"含 N 条消息"。

- **C. 任何机器都能删除共享会话** —— 但删除**对所有设备生效**,所以删共享会话【必须先确认】
  (普通会话删除仍不弹确认,见既有裁定)。删除仍走 30 天回收站。

1. 两台 PC 各镜像各自账号,同一个家庭共享日历由 Apple 推到两边 —— **我们不再自建共享**。
   重复由既有的增量合并挡住(有 Apple UID 按 UID,否则按"起止+全天+标题"内容签名,见 D50 补充)。
2. 本地新建、尚未推给 Apple 的条目,在另一台看不到 —— 这是对的,它还不是"共享的东西"。
   ★ 待办的 `Owner`/`Scope` 字段接入后应降级为"显示 Apple 那边的归属",不再由我们维护(**待办事项,未决**)。

**跨设备项目的三种情况(界面必须如实标注,不能让用户点了才发现打不开):**

## 2026-07-30 · D52 补充 · 主机离线的表现 & 一个网络里有多个主机

**一、主机没开时,客户端怎么表现**

按 D52「默认只在本机」的模型,大部分功能**不受影响**:

| 功能 | 主机关闭时 |
|---|---|
| 本机会话(读/写/新建/删除)、本机项目与其文件夹 | **完全可用** |
| 待办 / 日历(各自 Apple 账号,不经主机) | **完全可用** |
| 设置 / 皮肤 / 本机记忆 | **完全可用** |
| **AI 回答** | **不能** —— AI 在主机上跑,硬约束 |
| 共享会话/项目的**最新**内容 | 只能看本机缓存,应标注为离线副本 |
| 提升为共享 | 只**标记**,连上再上传 |
| 文件夹在别的机器的项目 | 读不了文件 |

**做法(已落地):不弹窗轰炸,只在真正受影响的地方说。** 左下角常驻连接状态;
聊天输入区在【已配对但连不上】时显示一行:"主机未开启 —— 消息会先记在本机;AI 在主机上运行,要等它上线才能回答"。
★ 允许照常发送并本地记录(人常常就是想先把事记下来),但绝不让人以为 AI 正在思考。

**二、一个网络里有多个主机(合租 / 邻居 / 自己装了两台)**

- **安全上本来就是隔离的**:每个主机有各自的 `hub_id` 与 CA;客户端证书由**它配对的那个** CA 签发,
  换一个主机连不上(证书链对不上)。配对还要**六词人工比对 + 主机侧批准**(D45 前置),不会被邻居的主机误捕获。
- **裁定:一台客户端只属于一个主机**(一个"家")。要换主机必须**先解除配对再重新配对** ——
  否则记忆/会话/项目的归属会彻底混乱,而成员表本来就是按 hub 走的。
- **界面(已落地):已配对卡片显示 `hub_id`** —— 同网多主机时只看 IP 分不清连的是哪一个。
- **将来若做局域网发现:必须列出所有发现到的主机让用户选,并逐一走六词比对,★ 绝不自动连**。

**三、顺带修掉的真 bug:** 「在文件夹中打开」原先不看 `HostMachine`,对文件夹在 PC-B 的项目会
**拿同一路径去开本机的同名目录**(两台机器上有同名路径很常见)——打开一个完全不相干的文件夹,
而用户以为那就是项目内容。现已统一到一处实现并按机器分流,远程如实拒绝并说明(selftest 钉死只有一处实现)。

## 2026-08-01 · D52 · 工作空间对项目是【标签】,不是【归属】

**起因(原设计的自相矛盾):** 项目的唯一性判据是 `(机器, 归一化路径)`，而且**不看工作空间** ——
`FindByFolder` 扫整张表，`MergeDuplicateFolders` 也是按 `(机器, 路径)` 全局分组合并。
数据层早就认定「同路径 = 同一个项目」。可 `WorkspaceKey` 是单值的，于是：
在 B 里选了 A 占用的文件夹 → 提示「一个文件夹只对应一个项目」并把人送去那个项目 →
**它在 B 的列表和主页方块里根本不出现**。建也建不了、找也找不到。

**落地形状:** 保留 `Project.WorkspaceKey` 当**主标签**，新增 `AlsoIn` 放附加标签，
对外一律走 `Spaces` / `InWorkspace(key)`。
· 老存档**零迁移**(只有 `WorkspaceKey` 的条目照旧读出来，`Spaces` = 那一个)；
· 主标签只用来定**方块图标**与**导航默认去哪个空间**，别处不该关心谁主谁次。

**三个动作分开给(菜单里不许合并):**
| 动作 | 语义 | 会话 |
|---|---|---|
| 移动到工作空间 | 换标签：原来的都不再挂着 | 跟着走(`SetSessionsWorkspace`) |
| 也放到工作空间 | 加标签：原来的都保留 | **不动**(会话按 ProjectId 归属项目) |
| 从工作空间移除 | 减标签 | 不动 |

**不许出现的两种情况(已由断言钉住):**
· **减到零个标签** —— 那样它在任何空间都看不见，只能靠「全部」翻出来，

· **合并同路径重复项目时丢标签** —— 合并前两条可能分别在不同空间，

**新建撞上同路径时:** 按钮文字要说出真正会发生什么 ——
已经在当前空间 = 「转跳至该项目」；不在 = 「加入本工作空间并打开」(加标签，**不**从原处拿走)。

## 2026-08-02 · D55 · 天气逐小时按【那座城的当地时间】;气温曲线与刻度同轴、按温度上色

**两个 bug(用户报的):** ① 非本地城市的逐小时不是从当地当前时间开始的；② 曲线与下方时刻对不齐。

**成因:** 天气接口是按 `timezone=auto` 取的，`WeatherHour.At` **已经是那座城的当地时间**；
而 `FillHourly`/`DrawCurve` 都拿本机 `DateTime.Now` 去比 —— 时差有多少就错多少格。
对齐则是两根轴：下面那排是 `UniformGrid` 均分 N 格、时刻文字**居中**，
曲线却自己按"未来 24 小时铺满整宽"画。

**定案:**
· 起点统一走 `HourlyOrigin(place)` = 那座城当地时间**取到最接近的整点**。
  取整点是为了跟"±30 分钟内取最近那条读数"的规则对上 ——
  14:37 显示的其实是 15:00 那条，标签就该写 15。认不出时区退回本机时间（不拿猜来的偏移挪数）。
· 曲线横轴照抄刻度的算法：第 k 格的时刻在 `(k + 0.5) × 格宽`，
  于是时刻 t 的 x = `(0.5 + (t - t0)/step) × 格宽`；曲线只画刻度覆盖的那一段。
· **去掉曲线左侧的最高/最低标注** —— 同轴之后每个刻度的读数就印在正下方，
  再写一遍既重复又压在曲线起点上。

**曲线配色(用户裁定):** >34 红 / >28 黄 / 8–28 绿 / <8 蓝 / <0 紫，**阈值处均匀过渡**。
· 实现用**竖直渐变刷**描边：y 与温度是线性关系，所以颜色分界正好是"某个温度的那条水平线"，
  与折线顶点落在哪儿无关 —— 这正是"过渡钉在阈值上而不是顶点上"的字面落实。
· 过渡带 ±1.5℃：带外纯色（"8–28 用绿线"因此成立），带内均匀过渡，**中点正好是阈值温度**。
· **全部压成灰调**（用户："大红大紫可能很不好看"）：
  灰紫 `#7B6AA6` / 灰蓝 `#5C86A8` / 灰绿 `#5F9370` / 赭黄 `#C0913F` / 陶土红 `#B4635C`。
  纯黄在浅色底上几乎看不见，所以黄取赭黄。
  Selftest 用"最大分量 − 最小分量 ≤ 0x90"钉住饱和度上限 —— 有人调回大红大紫会当场 FAIL。

## 2026-08-03 · D64 · 采纳 Hermes 作为 P6 的 Agent Worker(设计先行,执行推后)

**背景**

P6 清单(电脑操控 + 权限区域)里有工具池、权限策略引擎、权限区域、引导/直接模式、
清单→哈希→隔离区→回滚、浏览器执行器 —— **全是「约束」与「手」,没有「脑」**。
整份 PLAN 里 `编排器` 只出现在记忆选路与每日投影生成,**多步任务的规划、失败重试、
长工具链的上下文压缩没有对应交付项**。另一侧:S8 已把 L4 建齐(独立写路径 · 逐次哈希绑定批准 ·
executor · 版本化签名),但**至今没有生产者**,库是空的。

Hermes(NousResearch,MIT)提供的正是这两块:agent loop 与技能候选生成。

**选项**

- A 不引入,P6 的 loop 自研
- B 整体 fork 合并进 LocalAI
- C **引入为外部 Agent Worker**,治理全留在 LocalAI
- D 只读源码借鉴,不跑进程

**决定**

**选 C。** 定位为「**可替换、低信任的 Agent Worker**」——只负责规划与 loop;
身份、成员、记忆、权限、审批、执行、回滚、显存**一律留在 LocalAI**。
接法是**把它注册成网关别名表里的一个后端**(`agent.default`),对客户端而言它就是一个模型;
它自己的上游模型回指网关,**两次穿闸** ⇒ E1 / E4 / 审计 / 档位自动全覆盖。

设计规格见 [HERMES_INTEGRATION_DESIGN.md](HERMES_INTEGRATION_DESIGN.md)(DD-1…DD-10 + 分期 H0–H4)。

**★ 本轮只出设计,不写代码。** H0(设计 + 本决议 + PLAN 挂点)= 全部本轮范围。

**理由**

1. agent loop 是 P6 唯一没有交付项的层,也是唯一难自造的部分;
2. L4 有路无车,`/learn` 是第一个现实的技能生产者;
3. 外部 worker + HTTP 边界 ⇒ **不受 airi 那轮的 BLOCKER-2(语言/运行时鸿沟)约束**,
   这是它与 airi 结论不同的**唯一实质原因**,不是标准放松;
4. 我方护城河(家庭成员治理 · 可信记忆 · 权限区域 · 哈希审批 · 回滚 · GPU 管理)
   Hermes 一个都不碰,也一个都不减轻 —— 正因如此它可以被安全地降级为一个 worker。

**代价与已知风险(全部为已知,非意外)**

- **短期净工程量为正**:新增 MCP **服务端**、调用方身份一档、权限档位一档、
  trace 翻译层、进程隔离环境、第二运行时台账 —— 比省下的多。
- **★ P4 被拉成硬前置**:一次任务 = N 次模型调用,与桌宠/同传抢同一块 8.52
  (日常 7.99,只剩 0.53)⇒ 没有 Broker 租约就没有 Agent。
- **方向 B 从「P3d 前置」升级为「H2 前置」**:会浏览、会读文件的 loop 是迄今最大的不可信文本入口。
- **审计口径**:loop 内部步骤在别人进程里,DD-8 的 trace 翻译层若做不到,
  P3a 四门里「溯源 1.0 是硬线」就出空档 —— 这比少一个功能严重得多。
- **Windows 事实**:防火墙不过滤回环、账户 ACL 管不了 TCP ⇒
  账户隔离(`ai-exec`)**挡不住**它直连 18081,隔离必须是**进程级**(DD-7)。
- **D30 身份机制不跨隔离环境**:端口→PID→WMI GetOwner 在容器里失效,
  且现行策略拒 `ai-exec` ⇒ 必须走 mTLS(DD-3)。

**未裁定(不得默认)**

隔离路线 A(容器化)/ B(先给 `llama-server` 加鉴权)二选一 —— 见设计 §6,倾向 A 但待裁。

**推翻条件**

1. **承重项证伪**:若 Hermes 的工具**不能**由调用方注入、自带注册表**不能**完全清空,
   则 DD-2 落不了地(违反 §6.2「按会话挂载工具池」)⇒ **本决定作废,退回选项 D**;
2. 若依赖树 license checker 查出 AGPL 或其它传染许可,而 D41 裁为贩卖 ⇒ 退回 D;
3. 若 H1 最小环实测显示两次穿闸的延迟或显存代价不可接受 ⇒ 退回 D;
4. 若 P6 开工时自研 loop 的实际规模远小于预估(即"脑"没那么难造)⇒ 本决定的收益基础消失,
   应重新比价而非惯性执行;
5. Hermes 上游发生许可变更或项目停更 ⇒ 适配层的存在使替换成本可控,按 DD-10 记一条新 D。

## 2026-08-03 · D64 · 对抗式复核的收口(42 条发现 → 23 条站住 → 逐条修)

**一、我这轮亲手引入的真回归(必须修)**

① **文件翻译的 Del / Ctrl+Z 被窗口级停焦点无声打死。**
   那个面板是全项目唯一一个【靠非输入控件持有键盘焦点】收快捷键的地方(自设 `Focusable=true`,
   点预览时抓焦点)。旧规矩下按钮全是 `Focusable=False`,点它们不夺焦点,所以它一直吃得到键 ——
   **新规矩把这个前提拆了,加规矩的人要负责补上**。加 `FocusPolicy.KeepsKeyboardFocus` 附加属性:
   声明了的那一块,点别处不许把它的焦点停走。最恶劣的是它完全无声,而提示条还在承诺「Ctrl+Z 撤回」。

② **点【已经高亮】的那枚场景 chip,场景根本没变,却把幽灵会话连内容一起抹了。**

   改成比较前后值,真换了才算「换了一次」。
