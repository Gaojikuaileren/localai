## 0. 一句话定义

> 一个隐私优先、模型可替换、可扩展到多设备的**本地 AI 中枢**——不是绑定某个模型的聊天软件。
> 一个逻辑入口,MODEL / JOB / SESSION 三个协议平面,两类工具传输,一个 GPU 资源仲裁器,
> 一条独立的 CPU 交易安全链,以及多条严格隔离的权限边界。

## 2. 目录结构决议

### 2.1 对原提案的评审

**原提案**(首层四文件夹):
```
.localAI\
├── 本地调用app
├── 远程端IOS调用
├── 项目记录文档
└── 模型本体          ← "具体的模型和项目都在这里"
```

**方向正确**:按"谁调用谁"分层是清晰的心智模型,客户端与文档分离也对。

**三处必须修正**:

| # | 问题 | 后果 |
|---|---|---|
| **M1** | **服务端没有位置**。网关、编排器、GPU Broker、MCP 工具、数据库、交易链——整个系统的主体不在这四个文件夹的任何一个里 | 会被塞进"模型本体",导致 M2 |
| **M2** | **代码与模型权重同居**。代码几百 MB、经常改、必须 git 管理、必须备份;模型 200–250GB、几乎不变、能重下、绝不能进 git | 换 SSD 要整体搬(与"只改配置就迁移"的目标直接冲突);git 仓库会被误提交的 gguf 撑爆;备份策略无法分离 |
| **M3** | **运行时状态无处安放**。数据库、日志、审批票据、**交易账本**——既不是文档也不是代码也不是模型 | 交易账本有法定保存义务,混在其他目录里无法单独备份和排除 GC |

### 2.2 决议后的结构

**核心原则:代码与数据物理分离,五个逻辑根,换盘只改配置。**

```
E:\.meine\.Proj_Soft\.Proj\.localAI\        ← AI_ROOT(git 管理,~1–2GB,几乎不增长)
│
├── 00-docs\                项目记录文档 · 架构基线 · 决策日志 · STATE.md · worklog
├── 10-core\                ★服务端(原提案缺失)
│   ├── gateway\              统一入口 · 认证 · 限流 · 别名路由 · 设备管理
│   ├── orchestrator\         Agent 编排 · 权限策略引擎 · 审批状态机
│   ├── gpu-broker\           显存租约仲裁 · 模式切换 · 准入控制
│   ├── job-service\          异步任务 · 进度 · 取消 · 产物索引
│   ├── session-service\      全双工语音编排(VAD / 打断 / 流式串联)
│   ├── mcp-tools\            工具服务(按传输方式分 stdio\ 与 http\)
│   └── trade-chain\          风控引擎 · 幂等账本 · Broker Adapter(独立进程)
├── 20-client-win\          本地 Windows App(本机 + 局域网**共用同一个**)
├── 30-client-ios\          iOS App 源码(构建需在 macOS,见 §4.4)
├── 40-integrations\        ComfyUI 工作流模板 · 3D 适配器 · IBKR 适配器 · UE5 导入脚本
├── 90-ops\                 部署脚本 · 配置模板 · 迁移工具 · 存储审计
└── config\
    └── paths.toml          ★唯一路径配置源 — 换盘只改这一个文件

D:\AI\                                       ← 数据区(不进 git,可整体迁移)
├── models\                 AI_MODELS   模型本体(原提案的"模型本体"归位于此)
├── assets\                 AI_ASSETS   生成产物(draft / adopted / exported 三池)
├── state\                  AI_STATE    数据库 · 日志 · 审批票据 · **交易账本**
└── cache\                  AI_CACHE    HF / torch / 临时(可随时清空重建)
```

### 2.3 为什么"模型本体"必须移出项目文件夹

用你自己提出的需求来验证:**"未来买一块专门的固态,要准备好路径迁移"**。

| 方案 | 换 SSD 时要做什么 |
|---|---|
| 模型在项目文件夹里 | 搬 250GB+ 的整个项目,停服,git 工作区跟着动,所有相对路径重新验证 |
| **模型独立成根(本方案)** | **改 `paths.toml` 里两行,重启服务,校验哈希** |

同理适用于产物和缓存——它们各自的增长速度、备份必要性、迁移频率完全不同,绑在一起就只能按最严格的那个处理。

### 2.4 路径契约(强制规则)

1. **禁止任何绝对路径出现在代码里**,pre-commit 钩子 grep 到 `E:\` / `D:\` 即拒绝提交
2. **数据库存 `{root, rel}` 二元组**,不存绝对路径 → 迁移后数据库零改动
3. **第三方工具路径全部收编**:
   ```
   HF_HOME        → %AI_CACHE%\hf
   TORCH_HOME     → %AI_CACHE%\torch
   XDG_CACHE_HOME → WSL2 侧同理
   ComfyUI        → extra_model_paths.yaml 指向 %AI_MODELS%(否则搬 ComfyUI 会连着上百 GB 一起搬)
   ```
4. **迁移必须带校验**:搬完逐文件比对哈希,通过后才切换 `paths.toml`,旧位置保留至下一次备份完成

### 3.4 显存模式(16GB 单卡,含 CUDA context / KV / 缓冲 / 碎片)

| 模式 | 桌面接独显 | 桌面接核显 |
|---|---|---|
| `voice-interactive`(8B@8K + ASR + TTS) | ~13.4GB ⚠️ | **~11.7GB ✅** |
| `deep`(30B-A3B 混合 @32K) | ~15GB ⚠️ | **~14GB ✅** |
| `asset-heavy`(Flux FP8) | ~15.3GB ❌ 易 OOM | **~13.6GB ✅** |
| `mesh-heavy`(3D) | 独占 | 独占 |

> **R2 前置条件:显示器改接主板核显。** 这不是优化项——Flux FP8 在独显驱动桌面时装不下。
> 打游戏时可插回独显,由显式模式切换配合。

**Broker 规则**:
- 按 **NVML 实测空闲显存**发放租约,不按权重表估算
- 每进程 CUDA context(~0.4GB)计入配额
- "小模型优先保温,但重任务到来时可被驱逐"
- 检测到独占全屏游戏 → **拒绝发放新租约并明确告知**(准入控制),**不中断已持有租约的任务**

## 4. ★ 接入层与客户端(重点章节)

### 4.1 一个 App 还是两个?

**Windows 端:一个 App,不做本机版和局域网版之分。**

| 维度 | 说明 |
|---|---|
| 差别仅在连接地址 | 本机 `https://127.0.0.1:8443` / 局域网与远程 `https://ai-box.<tailnet>.ts.net` |
| 权限由服务端判定 | 按**设备密钥**决定档位,客户端无权自我提权 |
| 电脑操控不在 App 里 | 那是独立的 stdio MCP 执行器进程,App 只是前端 |
| 做两个的代价 | 两份代码、两份更新、权限逻辑下放到客户端(等于没有权限逻辑) |

**结论:一个 App + 多个连接 Profile。** iOS 端因平台不同必须单独实现,但**消费完全相同的 API**。

### 4.2 客户端职责边界(两端一致)

客户端**只做**四件事,不含任何业务逻辑:

1. 连接 Profile 管理(本机 / 局域网 / 远程)
2. 设备密钥的安全存储与出示
3. 平台集成(热键 / 托盘 / 通知 / 麦克风 / 屏幕捕获入口 / 生物识别)
4. 渲染前端界面

业务全在服务端 → iOS 与 Windows 复用同一套 API,新增客户端零后端改动。

### 4.3 Windows App

**分两步走:**

| 阶段 | 方案 | 理由 |
|---|---|---|
| P1–P4 | **Open WebUI 的 PWA** | 零开发成本,先验证整条链路 |
| P5+ | **Tauri 壳**(Rust + WebView) | 需要系统集成时才做 |

**为什么是 Tauri 而不是 Electron**:体积 ~10MB vs 150MB+,内存占用低——在一台要精打细算的机器上有实际意义;且 Tauri 可直接嵌 WebView 复用已有前端,渐进迁移。

**Tauri 壳提供的原生能力:**
- 全局热键唤起语音(按住说话 / 免提)
- 系统托盘常驻 + 当前 GPU 模式指示
- 任务完成的系统通知
- 屏幕捕获入口(交由执行器,不在 App 内处理)
- 设备密钥存 **Windows Credential Manager / DPAPI**

### 4.4 ★ iOS App — 身份验证与远程调用

#### 4.4.1 分阶段:PWA 先行,原生后补

| | PWA(Safari 添加到主屏) | 原生 SwiftUI |
|---|---|---|
| 开发成本 | **零** | 需 Mac + Xcode |
| 文本对话 | ✅ | ✅ |
| 按住说话 | ✅ | ✅ |
| **全双工语音(后台/锁屏)** | ❌ **后台被杀,WebRTC 断** | ✅ 后台音频 |
| 推送通知 | 🟡 iOS 16.4+ 且必须"添加到主屏" | ✅ 可靠 |
| Face ID 二次验证 | ❌ | ✅ LocalAuthentication |
| Siri 快捷指令 / 锁屏小组件 | ❌ | ✅ |
| Keychain 密钥保护 | 🟡 弱 | ✅ 带生物识别门禁 |

**决议:P3 用 PWA 打通远程访问,P7 做原生 App 承载全双工语音与审批流。**

#### 4.4.2 四层身份验证

```
第 1 层  网络层   Tailscale 设备授权 — 设备不在 tailnet 内则完全不可达
第 2 层  传输层   TLS(Tailscale 自动签发 *.ts.net 证书,iOS 无需装根证书)
第 3 层  应用层   per-device API key — 每台设备一把,可单独吊销
第 4 层  操作层   Face ID — 解锁密钥 + 高风险操作二次验证
```

**第 2 层的实际价值**:走 Tailscale 就不必在 iPhone 上安装并信任自签根证书——那个流程繁琐,且证书轮换时要重来一遍。

#### 4.4.3 设备注册流程(配对码,不是直接输密钥)

```
1. iPhone 安装 Tailscale,加入 tailnet(你在 Tailscale 后台批准该设备)
2. iPhone 安装 App,首启显示 6 位配对码(有效期 5 分钟,一次性)
3. 你在本机 https://ai.home/admin/ 输入配对码
4. 服务端生成该设备密钥,并记录:设备ID · 名称 · 权限档位 · 创建时间 · 最后使用
5. 密钥写入 iOS Keychain,标记为 "需要生物识别解锁"
6. 后续每次调用携带设备密钥;服务端每次调用记录设备ID用于审计
```

**为什么用配对码而非直接输入密钥**:避免密钥经由剪贴板、截图、聊天记录流转;短期一次性有效;可随时在 admin 单点吊销而不影响其他设备。

#### 4.4.4 权限档位(与权限矩阵对齐)

| 档位 | 适用设备 | 日常问答/语音 | 提交资产任务 | 只读投研 | 文件操作 | 电脑操控 | 交易审批 |
|---|---|---|---|---|---|---|---|
| `trusted-local` | 本机 App | ✅ | ✅ | ✅ | 逐次确认 | 逐次确认 | ✅ Face ID |
| `trusted-lan` | 局域网 PC | ✅ | ✅ | ✅ | 逐次确认 | ❌ | ❌ |
| `mobile-remote` | iPhone | ✅ | ✅ | ✅ | ❌ | ❌ | ✅ Face ID |

**关键**:权限在**服务端按档位挂载工具池**,而非运行时判断。`mobile-remote` 的会话在建立时其工具池里就**不存在**文件写与执行器工具——丢手机的场景下,运行时判断是靠不住的。

#### 4.4.5 ★ iOS 的杀手级用途:移动审批终端

iPhone 最有价值的角色不是"另一个聊天窗口",而是**架构里的审批节点**:

```
家里的 Agent 产出文件整理计划
   → 计划哈希绑定 → 推送到 iPhone
   → 你查看精确清单(源 → 目标,逐条)
   → Face ID 确认 → 服务端校验哈希未变 → 执行
   → 执行回执推送回来
```

同一机制服务于:交易提案审批、长任务完成通知、异常状态告警、高风险操作的第二因子。

这把"人在环路中"从口号变成了可以在外出时依然运转的机制。

#### 4.4.6 网络路径

```
在家:  iPhone ──WiFi──→ tailnet 直连 ──→ ai-box:8443
在外:  iPhone ──蜂窝──→ WireGuard(NAT 穿透)──→ 同一个地址
语音:  iPhone ←──WebRTC / UDP──→ LiveKit(tailnet 内)
```

**MagicDNS 让家里家外使用同一个地址,App 内无需切换配置。**

**端口视图(两种口径,不要混淆):**

| 口径 | 开放情况 |
|---|---|
| **路由器 / 公网** | **0 个端口**。不做任何端口转发 |
| tailnet 内部 | 443/TCP(统一入口) · 7880/TCP(LiveKit 信令) · **7882/UDP**(WebRTC 媒体) · 可选 7881/TCP(ICE 回退) |
| 本机 loopback | llama.cpp · ComfyUI · 3D · Qdrant · PostgreSQL — 全部 bind 127.0.0.1 |

#### 4.4.7 现实约束(必须提前知道)

| 约束 | 说明 | 应对 |
|---|---|---|
| **构建 iOS App 必须有 Mac** | 无合法绕过方式 | Mac mini / 云 Mac / 借用;或推迟到 P7 |
| **Apple Developer $99/年** | 免费账号签名的 App **7 天过期**需重签 | 真机长期使用必须付费账号 |

## 5. 存储与生命周期

### 5.1 容量预算

| 阶段 | 规模 |
|---|---|
| 起步(P0–P4:日常 + 语音) | **~85GB** |
| 全场景就绪(+ 资产 + 3D) | **~210GB** |
| 第一年末(+ 候选区 + 交易 + 一年产物) | **500–700GB** |

**两个最容易被漏算的:**
1. **运行时依赖 55–80GB** — 每个独立 venv 一份完整 PyTorch+CUDA(单份 8–12GB),ComfyUI / 3D / 语音三套栈通常需要不同 torch 版本无法共用;再加 CUDA Toolkit、WSL2 发行版、Docker 镜像
2. **模型候选区** — "新模型不覆盖旧模型 + 保留回滚点"意味着关键别名常驻两份,LLM 部分接近翻倍

**结论**:D: 的 578GB 可支撑至第一年中后期。新盘选 **4TB**(2TB 会在 2–3 年内再次紧张);**无需 PCIe 5.0**,模型加载是大文件顺序读,PCIe 4.0 的 7GB/s 早已不是瓶颈,省下的预算换容量。

### 5.2 分级回收(GC)策略

| 根 | 可自动删 | 策略 |
|---|---|---|
| CODE | ❌ | git 管理,GC 不碰 |
| **STATE** | ❌ | **只归档不删。交易账本进 GC 白名单 + 独立备份链(法定保存义务)** |
| MODELS | 🟡 | **引用计数**,非 LRU:被任何别名(含回滚点)引用即锁定;候选区评测完成且 N 天未晋升 → **提示**清理,不自动删 |
| ASSETS | ✅ | 三池分级,见下 |
| CACHE | ✅ | 纯 LRU/TTL,唯一可静默清理的根 |

**产物三池 — 增长最快部分的核心机制:**

```
draft    未被采纳的候选   → TTL N 天后回收,但永久保留 Asset Spec + seed + workflow 版本(几 KB)
adopted  你标记为要用的   → 永久保留 + 纳入备份
exported 已导入 UE5 的    → 项目内已有一份,此处只留元数据引用
```

> **可复现性把"存储"变成了"缓存"。** 因为 Asset Spec 能原样重放,删掉一张 2MB 草稿图只损失几 KB 的记录。
> 活跃使用下 12GB/月 的草稿增长可因此砍到接近零。

**磁盘水位线(与 GPU Broker 同构的准入控制):**
```
> 75%   仅提示
> 85%   自动清 CACHE 根(安全,可重建)
> 92%   自动回收超过 TTL 的 draft
> 95%   拒绝发放新 JOB 租约(不中断已有任务)
```

**回收器必须遵守与"文件整理"同等的安全规则** —— 它本质上就是一个自动触发的文件整理器,且无人按确认键,故要求更严:永不 `delete` 只移隔离区 → 隔离区再留 M 天 → 每次产出清单与释放报告 → 除 CACHE 外一律先报告后执行。

**第一个月只观察不清理**,用真实数据校准 TTL。

### 5.3 上下文预算

上下文是与显存同级的受管资源,由网关按别名强制,客户端无权自定。

| 上下文 | KV(FP8,8B 级) | 备注 |
|---|---|---|
| 8K | ~0.6GB | 语音模式上限 |
| 32K | ~2.3GB | 深度模式上限 |
| 128K | ~9GB | 本机不可行 |

**三条约束:**
1. **显存** — 见上表
2. **Prefill 延迟** — 32K 上下文首 token 约 4–10 秒,语音模式(目标 <300ms)不可接受。必须开启 prompt cache / prefix 复用
3. **有效上下文 < 标称上下文** — 长上下文中段检索准确率显著下降,装得下也未必该塞满

**隐藏杀手:一张 2560×1440 截图在常见 VLM 中是 1500–4000 tokens。** 10 步 GUI 循环仅截图就 20–40K。这是 UIA 树优先于视觉的第二个理由(第一个是显存):同一窗口的 UIA 树通常只需 200–800 tokens,且更精确。

**应对**:分层记忆(工作窗口 / 滚动摘要 / 向量库)+ RAG 替代长上下文 + Agent 循环用"交接"而非"累积" + 确需超长上下文时走 `escalate.cloud`。

## 6. 安全与权限

### 6.1 核心原则

> **能力升级可以上云,权限升级永远不行。**

```
计划层  ← 可升级到云端 Claude/GPT,输出【结构化提案】
   ↓
策略层  ← 永远本地:权限校验 · 参数校验 · 额度 · 动作预览
   ↓
执行层  ← 永远本地:stdio 执行器
```

云端只接收**脱敏的结构化摘要**,不接收原始截图与文件内容;每次数据出境前明确告知将发送什么。

### 6.2 权限强制

服务端按 **(用户 / 设备 / Agent / 工具 / 参数 / 额度)** 六元组强制。参数级尤其关键——同一个"写文件"工具,路径参数决定它是安全还是灾难。

### 6.3 工具传输分层

| 工具类别 | 传输 | 理由 |
|---|---|---|
| 高权限本机执行器(点击 / 输入 / 文件写 / 进程) | **stdio / Named Pipe** | 无网络面;进程级父子信任;不暴露为网络服务 |
| 低风险只读(搜索 / 行情 / 文档检索) | 认证后的 MCP over HTTP | 需跨设备复用 |
| Broker Adapter | 两者都不用 | 仅接受风控引擎调用 |

### 6.4 四项操控需求的具体设计

| 需求 | 风险 | 技术路线 | 关键约束 |
|---|---|---|---|
| 写文档 | 低 | 只读输入 + 写指定输出目录 | 可较宽松 |
| **操作浏览器** | **高** | Playwright / CDP,**独立 profile** | 邮箱 / 银行 / IBKR / 密码管理器 / 个人浏览器会话**默认不可见**;点击提交类控件逐次确认;网页内容标记为不可信 |
| **整理文件夹** | **高** | 事务化文件操作 | 精确清单 → **哈希绑定批准** → 执行前复核哈希 → 隔离区(永不 delete)→ 尽力回滚;`.meine` / `.UE5.5` / `.git` / `.localAI` 默认不可见 |
| 游戏日常 | 中 | **模板匹配 + OCR + 确定性状态机**为主 | 游戏无 UIA 树;固定 UI 用模板匹配比 VLM 更快更准更省(~0.2GB vs 6GB);**VLM 仅负责未知状态诊断,不得自行猜坐标继续操作**;已有成熟开源方案的建议直接复用,本地 AI 只做调度与汇报 |

> 文件批量操作与带登录态浏览器**同属最高风险等级**,风险类型不同:前者是数据完整性,后者是账户、隐私与外部世界后果。

### 6.5 威胁模型要点

- **模型是不可信计划者**:网页、邮件、文档、参考图元数据均可能携带提示词注入 → 计划本身要被审查,而非只审查执行者身份
- **资产导演 Agent 独立身份**:处理用户上传的参考图(不可信输入),故与日常助手**共用模型别名但不共用工具池与记忆域**
- **日志隐私**:
  ```
  永远记录:元数据(时间/别名/token/延迟/显存/成本/工具名)+ 工具调用参数与结果
  默认不记录:对话正文、语音原始转写
  按需开启:单会话显式开关 + 加密 + 短 TTL
  eval 语料:通过"捐赠本轮到 eval 集"的显式按钮采集,非默认全量抓取
  ```

## 7. 交易安全链

### 7.1 固定链路

```
模型提案(submit_trade_proposal 是唯一出口)
   → CPU 确定性风控引擎(纯 CPU,零显存,独立进程)
   → 批准票据
   → 幂等订单账本
   → Broker Adapter(对模型不可见,凭证走 DPAPI / Credential Manager)
```

**模型永远看不到 IBKR 凭证。** Paper 与 Live 是不同进程、不同凭证、不同权限、不同部署,**不存在自动升级路径**。

### 7.2 德国 / IBKR 的架构约束

> ⚠️ 以下为架构影响分析,非税务或投资建议。德国资本利得规则近年有变动,具体条款须经 Steuerberater 确认。

| # | 约束 | 架构后果 |
|---|---|---|
| 1 | 亏损抵扣仍保留**股票出售亏损的单独抵扣限制**(2024 年税改已取消衍生品/坏账的 2 万欧特殊限制) | 账本**按类别分池记账**,不能只记总盈亏 |
| 2 | 26.375% **不可逐笔机械扣除** — 25% 税率、Soli、免税额(Sparer-Pauschbetrag)、年度净额、FIFO、基金规则、外税抵免、教会税、其他账户共同决定 | 税负计算按**年度净额模型**实现,回测输出税前/税后双口径 |
| 3 | 不可笼统认定"IBKR 完全不扣税" | 先从账户协议 / Statement 确认**实际法律实体**,并逐项记录股息来源国预扣、现金利息预扣等**实际事件** |
| 4 | PRIIPs 影响缺少 KID 的零售投资产品(如许多美国 ETF),**不等于所有美股不可买** | 回测与实盘共享**资格规则**,但各自保存当时的 **universe snapshot**;下单前向 IBKR **重新预检**,禁止永久静态白名单 |
| 5 | 交易时段**不可写死**(美欧夏令时切换日期不同、节假日、提前收市、券商支持时段) | 使用**交易所日历 + IANA 时区** |
| 6 | 税务凭证保存义务 | **交易账本进 GC 白名单,独立备份链** |

### 7.3 Paper → Live 毕业门槛

状态机中这条边在所有门槛置位前**物理不可达**:

| 门槛 | 阈值(占位,需实测校准) |
|---|---|
| paper 交易笔数 | ≥ 200 |
| 市场环境覆盖 | 含上涨段 / 下跌段 / 高波动段 |
| 滑点模型验证 | Shadow 实时 vs Paper 偏差 < X% |
| **税后**夏普 / 最大回撤 | 你能接受的数字,**税后口径** |
| 风控引擎独立测试 | Kill switch · 单笔/单日限额 · 幂等重放全通过 |
| 连续无人工干预运行 | ≥ 30 天 |

**独立常开执行节点或等效独立故障域是 P9 门槛**,不是现在购买设备的前置条件。理由:若做美股短线,交易时段(德国时间傍晚至深夜)与游戏 / 出图时段高度重叠,而这台工作站会因 ComfyUI / 3D / 游戏而显存爆满——风险不来自策略,来自基础设施。
