## 4. ★ 记忆系统(本项目的核心)

### 4.1 五层记忆

| 层 | 内容 | 存续 | 存储 |
|---|---|---|---|
| **L0 工作记忆** | 当前会话上下文窗口 | 易失 | LLM context |
| **L1 会话摘要** | 每轮 / 每会话结束的滚动压缩 | 数天 | PostgreSQL |
| **L2 情节记忆** | 带时间戳的事件:「7月26日你说打算买 4TB 硬盘」 | 长期 | PostgreSQL + Qdrant |
| **L3 语义记忆** | 关于你的**结构化事实**:偏好 / 人际关系 / 进行中的项目 / 习惯 | 长期 | PostgreSQL(结构化) |
| **L4 程序记忆** | 学会的工作流:「整理下载文件夹」= 这几个确定步骤 | 长期 | 版本化 Spec / 脚本 |

### 4.2 ★ 双轨检索 — 最关键的设计决定

> **只做向量 RAG 的记忆系统,会在最需要精确的地方失败。**

| 轨道 | 回答的问题 | 技术 |
|---|---|---|
| 向量检索(Qdrant) | 「**相关的**是什么」— 模糊、联想、上下文 | bge-m3 + rerank |
| 结构化查询(PostgreSQL) | 「**确切**是什么」— 精确事实 | SQL over 实体表 |

「我妹妹叫什么名字」——向量检索会返回一堆「关于妹妹的对话片段」,但答不出名字;这必须走结构化实体查询。反过来「上次我们聊过的那个关于灯光的问题」必须走向量。

**两轨都要,且由编排器根据问题类型选择或并用。**

### 4.3 实体图谱

```
Person      你 / 家人 / 朋友        ── 关系边(称谓 · 亲疏 · 重要日期)
Project     .localAI / UE5 项目 / 投资计划
Device      这台工作站 / 手机 / 未来的第二台 PC
Place       家 / 常去的地方
Thing       设备 / 物品 / 订阅
Event       带时间戳,可关联到以上任意实体
Preference  带置信度与时效性
```

### 4.4 写入把关(Memory Gate)

**不是什么都记。** 每条候选记忆需通过判断:

- 是否是关于用户的**持久**事实(而非一次性任务细节)?
- 是否会影响未来的行为?
- 是否用户明确要求记住?

写入后**必须**满足:
- **用户可见** — 有一个记忆面板可以浏览全部记忆
- **用户可编辑 / 可删除**
- **记录来源** — 哪次对话、什么时间、原文片段

### 4.5 时效、冲突与可解释性

**每条事实携带**:`asserted_at` · `confidence` · `source_ref` · `superseded_by`

**冲突处理**:新事实与旧事实矛盾时**不覆盖**,新增一条并将旧条标记为 superseded,保留完整历史。因为「曾经如此」本身是有价值的信息。

**时效性**:部分事实天然会过期(「我最近在减肥」「我在找工作」)→ 定期 review 提示,由你确认仍然有效或标记结束。

**★ 可解释性是信任的前提**:当助理说「我记得你提过 X」,必须能一键展开看到:**来源对话 · 时间 · 原文片段**。没有可解释性的记忆既不敢信任,也无法纠错。

### 4.6 隐私红线

| 规则 | 说明 |
|---|---|
| 静态加密 | 独立 BitLocker VHDX(`D:\AI\state\memory.vhdx`),与其余 state 分离 |
| **永不出境** | 即使使用 `escalate.cloud`,也**只发送当前任务的脱敏上下文,绝不发送记忆库内容** |
| 备份分级 | 记忆备份与资产备份分离,采用更高保护等级(**具体方案见 §8.5**) |
| 不进日志 | 记忆内容不写入常规运行日志(见 §9.2) |

> **隐私红线同样适用于备份。** 备份必须加密,否则备份就成了绕过加密卷的后门。

### 4.7 克制的主动性

| | 行为 |
|---|---|
| ✅ | 基于时间 / 日历的提醒(**你曾明确让它记的**) |
| ✅ | 状态变化通知(任务完成 · 磁盘水位 · 模型下载完毕) |
| ✅ | 明确承诺的跟进(「下周提醒我买硬盘」) |
| ❌ | 「我觉得你可能想知道」式的主动打扰 |

**原则:只在你曾明确请求过的事情上主动。**

### 4.8 多模态写入通道

随口一句「记一下,下周要交房租」应当直接进入 L2/L3——这要求**语音层与记忆层打通**,也是本版把语音提前并设为常驻的主要理由。

### 4.9 ★ 冷启动、评测与兜底(v2.1 新增)

#### 4.9.1 冷启动

系统上线第一天记忆库是空的。L3(家人 / 偏好 / 进行中的项目)靠日常对话自然积累会很慢,而**头两周的体验决定你会不会继续用它**。

**做法**:P3 提供一次**结构化初始化会话**——助理按实体类型逐项发问(重要的人及称谓、常用设备、进行中的项目、明确的偏好与禁忌),你口述,它写入 L3 并当场展示写了什么、允许你改。一次约 20–30 分钟。

这不是「灌数据」,是把 §4.4 的把关流程**显式跑一遍**,顺便验证记忆面板与溯源能用。

#### 4.9.2 评测集与四项指标

P3 的验收不能只靠两个例句。**建立记忆 eval 集**:每条为 `问题 → 期望答案 → 期望来源`,随使用逐步扩充,分向量轨 / 结构化轨两类。

| 指标 | 含义 | 为什么 |
|---|---|---|
| 召回率 | 该记得的记住了 | 漏记 |
| 精确率 | 检索出来的确实相关 | 噪声 |
| **误记率** | 记住了错的事实 | **最危险** — 错的记忆比没有记忆更糟 |
| **溯源完整率** | 每条记忆都能展开到原始对话 | §4.5 已定为信任前提 |

P9 的「记忆质量评估」即按此四项每季度跑一次。

#### 4.9.3 漏记与误记的兜底

Memory Gate 由 LLM 执行,必然有漏有误。两个兜底:

- **漏记**:你说「你怎么不记得 X」时,助理须能**即时补录**并标注「事后补录 + 补录时间」,而不是只在当前会话里应付过去
- **误记**:你不会主动去翻记忆面板。因此**每周推送一条「本周新记住的事」摘要**(仅标题级,不含正文),扫一眼即可发现离谱的条目

### 4.10 规模增长与多端写入的预留(v2.1 新增)

**规模退化**:L2 情节记忆只增不删(进 GC 白名单)。几年后数十万条,向量检索的信噪比会下降。

- 数据模型现在就带 `last_accessed` 与 `access_count`
- 检索时对久未命中且低置信度的旧条目**降权**(不删除)
- 超过 N 年的 L2 事件可**归档为 L1 级摘要**,原文保留但不进主索引

**多端并发写入**:B1(iOS)与 B6(第二台 PC)都会写记忆。虽然本期单机,但**数据模型现在就要留位**——理由与 §7「投资现在就建表」完全相同,且记忆的数据模型比交易表更难迁移。

预留字段:`origin_device_id` · `write_seq`(单调序号)· `merged_from`。冲突策略沿用 §4.5:**不覆盖,新增并标记 superseded**。

## 5. 资产工作室

### 5.1 事实澄清:nano-banana 不做 3D

> **nano-banana(Google Gemini 2.5 Flash Image)是 2D 图像生成 / 编辑模型,不生成 3D 网格。**

它的强项恰好契合你要的交互:**原生接受参考图 + 指令式编辑**,角色一致性好,迭代修改自然,因此非常适合概念阶段。

**3D 仍需另找出路**,三条路留待 B3:本地 Hunyuan3D / TRELLIS(10–14GB 独占,sm_120 编译需趟)、云端 3D API(另一条出境路径)、Blender 脚本化(0 显存,AI 写 bpy,结果可控可复现)。**本期不做 3D。**

### 5.2 双轨分工

| 阶段 | 走哪条 | 理由 |
|---|---|---|
| **概念图 / 风格探索 / 迭代修改** | ☁ nano-banana | 交互自然,参考图原生支持,不占显存不占磁盘 |
| **批量生产 / 风格锁定 / 精确控制** | ⌂ 本地 ComfyUI | 可复现 · 不花钱 · 不出境 · 已有 ControlNet 基础 |
| **贴图 / PBR / de-light** | ⌂ 本地 ComfyUI | 需要确定性管线 |
| **3D** | ⏸ 本期不做 | §5.1 |

这个划分同时是出境闸门的判定依据(见 §5.6)。

### 5.3 ★ 模型管家(Model Curator)

> **建在已有的 ComfyUI-Manager 之上,不重造下载与安装。**

ComfyUI-Manager 已解决:按名称搜索 · 下载 · 安装 · 更新。**缺的是语义层与治理层**:

```
你的自然语言需求(「我想要能画等距像素风建筑的」)
   ↓ 意图理解(LLM)
结构化检索条件(底模类型 · 风格标签 · 用途 · 许可证要求)
   ↓ 查询 Civitai / HuggingFace API
候选列表 + AI 解读
   「这个是 SDXL 的 LoRA,擅长等距建筑,但许可证禁止商用」
   「这个是 Flux 的,和你现有的 Juggernaut 底模不兼容」
   ↓ 你选择
调用 ComfyUI-Manager 安装 → 校验哈希 → 写入模型注册表
```

**注册表额外记录(ComfyUI-Manager 不记的):**

| 字段 | 用途 |
|---|---|
| 许可证 / 商用条款 | 游戏资产若要商用,许可证链条必须可追溯 |
| 底模兼容性(SDXL / Flux / SD1.5) | 避免装了用不了 |
| 最后使用时间 · 使用次数 | 清理决策依据 |
| 重获成本(下载大小 · 是否仍可获取) | 决定该不该删 |
| 你的评价笔记 | 半年后你不会记得哪个更好用 |

**清理助手**(与 §8.4 联动):「这 12 个 LoRA 三个月未使用,共 3.2GB,建议清理」。**引用计数保护**:仍被任何 Asset Spec 引用的模型不建议删除。**只提示,不自动删。**

### 5.4 ★ 提示词转译器(Prompt Translator)

**你不写硬核 prompt。** Asset Spec 是唯一的人机接触面:

```
中文自然语言 + 参考图
   ↓
Asset Spec(结构化,与目标模型无关)
   ↓ 多目标编译器
   ├→ SDXL prompt        (tag 堆叠 + 权重语法)
   ├→ Flux prompt        (自然语言长句)
   ├→ nano-banana 指令   (指令式编辑描述)
   └→ ComfyUI workflow JSON(模板填槽)
```

不同底模的 prompt 风格差异巨大——手写就意味着换模型要重写全部提示词;**编译器让 Asset Spec 跨模型可移植**。

**反向能力(同样重要)**:贴进别人的 prompt → 解析成 Asset Spec → 逐段解释在做什么 → 存为可复用模板。这是学习与复用的主要途径。

### 5.6 ★ 数据出境闸门(v2.1 重写)

v2.0 定的是「逐次确认」。但 nano-banana 的价值恰恰在于**迭代式编辑**(一张概念图往往要改十几轮),逐次确认会毁掉这个交互;而全面放宽又会放大风险窗口。

**解法:两级授权,判定依据用 §5.2 已有的分轨规则。**

| 级别 | 适用 | 机制 |
|---|---|---|
| **会话级授权** | 概念阶段(公开素材 / 自己的草图) | 一次授权覆盖本次迭代会话;**会话结束自动失效**;会话内实时显示已发送条目与累计费用 |
| **逐次确认** | 涉及项目专有素材;任何生产阶段内容;首次使用某条新路径 | 执行前逐条展示将发送什么 |

**分级粒度(承 v2.0,继续有效):**

| 级 | 允许发送 | 状态 |
|---|---|---|
| L0 | 不启用任何云端路径 | |
| L1 | 仅你手打的问题文本 | |
| **L2** | + 你**显式选中**的内容 | **`escalate.cloud` 锁定在此级(Q2 已决)** |
| L3 | + RAG **自动检索**出的片段 | 需要时手动临时升级 |
| L4 | + 截图与文件原文 | 需逐次确认 |
| **L5** | + 记忆库内容 | **永久禁止(§4.6)** |

**预算(Q3 已决 + 本版补齐超限行为):**

- 月度上限是**设置项,随时可手动调整**,不写死在代码或配置里
- 闸门处实时显示本月累计与剩余额度
- 达上限 **80%** → 告警
- 达 **100%** → **硬停**,并提示「可手动提额」或「改走本地 ComfyUI」。**不静默继续计费**

**条款快照(v2.1 新增)**:启用 nano-banana 时,把当时的 Gemini API 数据使用条款存一份快照至 `00-docs/snapshots/`。理由:项目对德国税法已有「记录法规快照」的做法,对同样会变的第三方 API 条款应当同等对待。列入 §13 Backlog 的定期复核。

## 6. ★ 安全与权限(v2.1 恢复)

> 本章恢复自 v1 §6。v2.0 删除了本章,但 P6 的文件整理、浏览器执行器、游戏自动化三项高风险功能**一项没少**。删掉的不是风险,只是对风险的约束。

### 6.1 核心原则

> **能力升级可以上云,权限升级永远不行。**

```
计划层  ← 可升级到云端,输出【结构化提案】
   ↓
策略层  ← 永远本地:权限校验 · 参数校验 · 额度 · 动作预览
   ↓
执行层  ← 永远本地:stdio 执行器
```

云端只接收**脱敏的结构化摘要**,不接收原始截图与文件内容;每次数据出境前明确告知将发送什么(§5.6)。

### 6.2 权限强制:六元组

服务端按 **(用户 / 设备 / Agent / 工具 / 参数 / 额度)** 六元组强制。

**参数级尤其关键,也最容易被忽略**:同一个「写文件」工具,**路径参数决定它是安全还是灾难**。六元组里如果只实现了前四维,等于没有实现。

权限在**服务端按档位挂载工具池**,而非运行时判断。低权限档位的会话在建立时其工具池里就**不存在**高风险工具——运行时判断在设备丢失的场景下是靠不住的。

### 6.3 权限档位

| 档位 | 适用设备 | 问答/语音 | 资产任务 | 文件操作 | 电脑操控 |
|---|---|---|---|---|---|
| `trusted-local` | 本机 App | ✅ | ✅ | 逐次确认 | 逐次确认 |
| `trusted-lan` | 局域网 PC | ✅ | ✅ | 逐次确认 | ❌ |
| `mobile-remote` | 手机(B1/B2) | ✅ | ✅ | ❌ | ❌ |

`mobile-remote` 本期**定义但不启用**。

### 6.4 工具传输分层

| 工具类别 | 传输 | 理由 |
|---|---|---|
| 高权限本机执行器(点击 / 输入 / 文件写 / 进程) | **stdio / Named Pipe** | 无网络面;进程级父子信任;不暴露为网络服务 |
| 低风险只读(搜索 / 行情 / 文档检索) | 认证后的 MCP over HTTP | 需跨设备复用 |

### 6.5 ★ 四项操控需求的具体设计

> 这张表是 P6 的**执行依据**。v2.0 只保留了任务名,丢了约束——而约束才是实质。

| 需求 | 风险 | 技术路线 | **关键约束(不可省略)** |
|---|---|---|---|
| 写文档 | 低 | 只读输入 + 写指定输出目录 | 可较宽松 |
| **操作浏览器** | **高** | Playwright / CDP,**独立 profile** | **邮箱 / 银行 / IBKR / 密码管理器 / 个人浏览器会话默认不可见**;点击提交类控件逐次确认;网页内容标记为不可信 |
| **整理文件夹** | **高** | 事务化文件操作 | 精确清单 → **哈希绑定批准** → 执行前复核哈希 → **隔离区(永不 delete)** → 尽力回滚;**`.meine` / `.UE5.5` / `.git` / `.localAI` 默认不可见** |
| 游戏日常 | 中 | **模板匹配 + OCR + 确定性状态机**为主 | 游戏无 UIA 树;固定 UI 用模板匹配比 VLM 更快更准更省(~0.2GB vs 6GB);**VLM 仅负责未知状态诊断,不得自行猜坐标继续操作**;已有成熟开源方案的直接复用 |

> 文件批量操作与带登录态浏览器**同属最高风险等级**,风险类型不同:前者是数据完整性,后者是账户、隐私与外部世界后果。

### 6.6 威胁模型

- **模型是不可信计划者**:网页、邮件、文档、参考图元数据均可能携带提示词注入 → **计划本身要被审查,而非只审查执行者身份**
- **资产导演 Agent 独立身份**:处理用户上传的参考图(不可信输入),故与日常助手**共用模型别名但不共用工具池与记忆域**
- **记忆库是最高价值目标**:任何能读记忆的路径都是攻击面。因此记忆检索结果进入 prompt 时须标注来源,且**记忆内容永不参与出境**(§4.6 / §5.6 L5)

## 8. 显存、上下文与存储

### 8.1 显存三模式

| 模式 | 组成 | 桌面接核显 | 桌面接独显 |
|---|---|---|---|
| **`daily`(默认常驻)** | LLM 8B Q4@16K (6.2) + ASR/TTS (4.0) + 小 VLM (2.5) | **~13.0GB ✅** | ~14.7GB ⚠️ |
| `deep`(按需) | 驱逐小 VLM,加载 30B-A3B 混合 | ~15.3GB ⚠️ | ❌ |
| **`asset`(异步出图)** | 驱逐 LLM 与 VLM,**保留语音** + ComfyUI SDXL 栈 (10.4) | **~14.7GB ✅** | ❌ |

> **⚠ v2.1 标注**:`deep` 的 ~15.3GB 只是 **GPU 侧驻留部分**。30B-A3B 的 Q4 权重远超 16GB,**必然依赖 CPU offload**,而 offload 比例与由此产生的速度代价**尚未实测**。
> 本项目自己的原则是「不实测就冻结,等于把假设冻进地基」——因此本表在 P1 完成前**不得作为选型依据**。

**`asset` 模式保留语音是有意的体验设计**:出图是异步 JOB,你提交后会去做别的事,此时仍应能用语音问「好了没」。

**两个优化:**
- **ASR + TTS 合并为单进程** — 省一个 CUDA context(~0.4GB)。**⚠ 但这是假设不是结论**:能否合并取决于两者是否同框架(如 ASR 走 CTranslate2、TTS 走 PyTorch,合并未必省,还可能冲突)。**P1 须验证**,P5 的实作依 P1 结论而定。
- **显示器接主板核显** — 释放约 1.7GB。v2 范围下从「前置条件」降为**强烈建议**,但 `deep` 与 `asset` 仍依赖它才舒适。

**Broker 规则**:
- 按 **NVML 实测空闲显存**发放租约,不按权重表估算
- 每进程 CUDA context(~0.4GB)计入配额
- 「小模型优先保温,但重任务到来时可被驱逐」
- 检测到独占全屏游戏 → **拒绝发放新租约并明确告知**,**不中断已持有租约的任务**

### 8.2 上下文预算(v2.1 恢复)

> 恢复自 v1 §5.3。v2.0 删除了本节,但 `daily` 模式写的是「8B Q4@**16K**」——16K 的 KV 占多少,v2.0 全文没有答案。

上下文是与显存同级的受管资源,由网关按别名强制,客户端无权自定。

| 上下文 | KV(FP8,8B 级) | 备注 |
|---|---|---|
| 8K | ~0.6GB | 语音模式上限 |
| 16K | ~1.2GB | `daily` 默认 |
| 32K | ~2.3GB | 深度模式上限 |
| 128K | ~9GB | 本机不可行 |

**三条约束:**

1. **显存** — 见上表
2. **Prefill 延迟** — 32K 上下文首 token 约 4–10 秒,语音模式(目标 <300ms)不可接受。**必须开启 prompt cache / prefix 复用**
3. **有效上下文 < 标称上下文** — 长上下文中段检索准确率显著下降,装得下也未必该塞满

**隐藏杀手:一张 2560×1440 截图在常见 VLM 中是 1500–4000 tokens。** 10 步 GUI 循环仅截图就 20–40K。

> 这是 §1.1「电脑操控优先 UIA 树」这条决议的**第二个理由**(第一个是显存):同一窗口的 UIA 树通常只需 200–800 tokens,且更精确。
> v2.0 保留了结论却删掉了这个数字——**结论没有理由支撑,后来的自己会怀疑它**。

**应对**:分层记忆(工作窗口 / 滚动摘要 / 向量库)+ RAG 替代长上下文 + Agent 循环用「交接」而非「累积」+ 确需超长上下文时走 `escalate.cloud`。

### 8.4 存储生命周期与 GC(v2.1 恢复)

> 恢复自 v1 §5.2。v2.0 写「GC 策略见 v1 §5.2」,同时宣布 v1「已被本文档取代」——既作废又引用。本版把内容搬进来,该引用悖论就此消除。

**五个逻辑根:**

| 根 | 可自动删 | 策略 |
|---|---|---|
| CODE | ❌ | git 管理,GC 不碰 |
| **STATE** | ❌ | **只归档不删。记忆库与交易账本进 GC 白名单 + 独立备份链** |
| MODELS | 🟡 | **引用计数**,非 LRU:被任何别名或 Asset Spec(含回滚点)引用即锁定;候选区评测完成且 N 天未晋升 → **提示**清理,不自动删 |
| ASSETS | ✅ | 三池分级,见下 |
| CACHE | ✅ | 纯 LRU/TTL,唯一可静默清理的根 —— **但 `cache/hf` 例外,见 §8.4.1** |

#### 8.4.1 `cache/hf` 例外(2026-07-26 决议)

`cache/hf` 语义上属 CACHE 根(内容可重新下载),但**不参与 85% 水位的自动清理**。

**理由**:重获成本与「可重建」不是一回事。

| | 一般缓存(torch / pip / tmp) | `cache/hf` |
|---|---|---|
| 体积 | 通常几 GB | 动辄十几到几十 GB |
| 重建耗时 | 秒到分钟 | **实测下载 ~11 MB/s,17GB 需约 27 分钟** |
| 能否重建 | 一定能 | **不一定** —— 模型可能从 HF 下架或改许可 |

`paths.toml` 中由 `[gc].hf_cache_auto_purge = false` 控制。

**代替做法**:交给 §5.3 的模型管家按「最后使用时间 + 重获成本」提示清理,
遵循 MODELS 根的同一原则 —— **只提示,不自动删**。

> 这条例外的本质:GC 策略的分界不该只看「能不能重建」,还要看「重建的代价」。
> 一个能重建但要花半小时且可能失败的东西,不该被静默删除。

**产物三池:**

```
draft    未被采纳的候选   → TTL N 天后回收,但永久保留 Asset Spec + seed + workflow 版本(几 KB)
adopted  你标记为要用的   → 永久保留 + 纳入备份
exported 已导入 UE5 的    → 项目内已有一份,此处只留元数据引用
```

> **可复现性把「存储」变成了「缓存」。** 因为 Asset Spec 能原样重放,删掉一张 2MB 草稿图只损失几 KB 的记录。

**磁盘水位线(与 GPU Broker 同构的准入控制):**

```
> 75%   仅提示
> 85%   自动清 CACHE 根(安全,可重建)
> 92%   自动回收超过 TTL 的 draft
> 95%   拒绝发放新 JOB 租约(不中断已有任务)
```

**回收器必须遵守与「文件整理」同等的安全规则**——它本质上就是一个自动触发的文件整理器,且**无人按确认键**,故要求更严:

- 永不 `delete`,只移隔离区 → 隔离区再留 M 天
- 每次产出清单与释放报告
- 除 CACHE 外一律先报告后执行
- **备份目录对回收器不可见**(见 §8.5)

**第一个月只观察不清理**,用真实数据校准 TTL。

### 8.5 ★ 备份与灾难恢复(v2.1 新增)

> 这是 v2.0 最大的结构性空白。项目把记忆识别为「最敏感」,然后只针对**泄露**做设计,没有针对**丢失**做任何设计。而对个人系统而言,硬盘故障、误删、加密卷损坏的概率远高于定向窃取。

#### 8.5.1 为什么只有记忆非备不可

| 数据 | 丢失后果 |
|---|---|
| CODE | git 有,可恢复 |
| MODELS | 可重新下载(注册表专门记录「重获成本」) |
| ASSETS · draft/exported | Asset Spec 可复现重放 |
| CACHE | 设计上就可随时清空 |
| **STATE · 记忆库** | **不可重建。没有任何来源可以重放。** |

#### 8.5.2 备份矩阵

| 根 | 备份内容 | 频率 | 介质 | 保留 |
|---|---|---|---|---|
| CODE | git remote(私有) | 每次提交 | 远端 + 本地另一盘 | 全历史 |
| **STATE · 记忆库** | **加密全量 + 增量** | **每日增量 / 每周全量** | 外置盘 + 异地一份(密文) | 30 日增量 + 12 周全量 |
| STATE · 其余(数据库 · 票据 · 日志) | 加密 | 每日 | 外置盘 | 30 日 |
| MODELS | **不备份本体**,备份**清单 + 哈希 + 来源 URL + 许可证** | 每次变更 | 随 CODE 进 git | — |
| ASSETS · adopted | 加密 | 每周 | 外置盘 | 12 周 |
| ASSETS · draft / exported | 不备份(可重放 / 项目内已有) | — | — | — |
| CACHE | 不备份 | — | — | — |

#### 8.5.3 五条铁律

1. **备份必须加密** — 否则备份就是绕过 BitLocker 加密卷的后门
2. **恢复密钥离线保管** — 至少两份,不同物理位置,**绝不与被加密数据同盘**。BitLocker 恢复密钥丢失 = 记忆永久不可读,这比被窃取更可能发生
3. **恢复演练** — **P3 记忆系统上线之前**必须跑通一次完整恢复;此后每季度一次。**没演练过的备份不算备份**
4. **备份不可由助理自身的文件工具触及** — 备份目录进入 §6.5 的「默认不可见」清单,防止一次错误的自动整理连备份一起清掉
5. **备份失败必须告警**(§9.3)— 静默失败的备份比没有备份更危险,因为你以为有

## 9. 可观测性与日志(v2.1 新增)

> v2.0 多处提到「审计」「日志」,但从未定义记什么、存哪、留多久、怎么查。而这与记忆隐私是同一个问题的两面。

### 9.1 三类记录

| 类 | 记什么 | 存哪 | 保留 |
|---|---|---|---|
| **运行日志** | 元数据:时间 · 别名 · token 数 · 延迟 · 显存 · 成本 · 工具名 | `AI_STATE/logs/` | 90 天 |
| **审计日志** | 谁(用户 / 设备)对什么做了什么 · 批准链 · 哈希 · 回执 | PostgreSQL | **不删**(与账本同级) |
| **指标** | 显存水位 · 磁盘水位 · 任务时长 · 失败率 · API 累计花费 | 时序表 | 1 年 |

### 9.2 隐私规则(承 v1 §6.5)

```
永远记录:元数据 + 工具调用参数与结果
默认不记录:对话正文、语音原始转写
永不记录:记忆库内容(§4.6)
按需开启:单会话显式开关 + 加密 + 短 TTL
eval 语料:通过「捐赠本轮到 eval 集」的显式按钮采集,非默认全量抓取
```

### 9.3 告警最小集

- 磁盘水位越线(75 / 85 / 92 / 95%)
- 显存租约被拒绝
- 出境累计费用达月度上限的 **80%** / **100%**
- **备份任务失败**(§8.5 铁律 5)
- 记忆写入失败
- 隔离区即将到期(提醒你确认是否可清)

## 10. 测试策略(v2.1 新增)

> v2.0 全文除「基准测试」外几乎没有测试概念。而本项目里有若干「自动执行且难以撤销」的组件。

| 组件 | 风险 | 最低要求 |
|---|---|---|
| **文件回收器 / GC** | **最高** — **无人按确认键的自动文件整理器** | 单元测试 + **干跑模式(只出清单不动文件)** + 隔离区可恢复性测试;首月只观察不清理 |
| **权限策略引擎** | 高 | 以**否定用例**为主:该拒的必须拒。六元组每一维都要有拒绝用例,尤其**参数级** |
| **记忆系统** | 高 | §4.9.2 的 eval 集;冲突 / superseded 的回归测试 |
| **出境闸门** | 高 | 断言:任何路径下**记忆库内容零外发**;预算硬停生效 |
| GPU Broker | 中 | 并发申请 / 驱逐 / 游戏共存的场景测试 |
| 提示词转译器 | 低 | 快照测试(Asset Spec → 各目标 prompt) |

**原则:凡是「自动执行且难以撤销」的组件,先写否定用例再写功能。**

## 12. 执行协议(v2.1 新撰)

> **为什么有这一章:** v2.0 附录声明 v0.4 的「节点循环协议 · 记录协议 · 首轮门禁 · 审批规则」继续有效,但 **v0.4 不在 `00-docs/` 中**,内容也从未在 v1 / v2 展开。一份读不到的协议无法被遵守;而 P0 的第一批任务(建立 `STATE.md`)直接依赖它。
>
> **本章为 v2.1 重新撰写,不是 v0.4 的复原。** 若 v0.4 原文日后找到,**以本章为准**,并把差异记入决策日志。

### 12.1 记录协议 — 三份文件各司其职

| 文件 | 回答的问题 | 更新时机 |
|---|---|---|
| `00-docs/STATE.md` | **现在在哪** | 每个节点结束;每次中断前 |
| `00-docs/DECISIONS.md` | **为什么这么定** | 每次做出不易反悔的选择 |
| `00-docs/worklog/YYYY-MM.md` | **做了什么、测出什么** | 每次实作或实测 |

**`STATE.md` 固定格式:**

```markdown
# STATE — 本地 AI 中枢
> 更新时间: YYYY-MM-DD HH:MM
> 方案书版本: v2.1

## 当前阶段
P0 · 地基 — 进行中 (3/8)

## 已完成
- P0-1 接 2.5GbE 网线 (2026-07-28)

## 进行中
- P0-3 核实 C: 现存内容 — 已查 HF 缓存,待查 v1 所述模型位置

## 下一步(不超过三项)
1. ...
2. ...

## 阻塞
| 事项 | 阻塞了什么 | 需要什么才能解 |

## 环境事实(变更即更新)
| 项 | 值 | 核实日期 |
```

**`DECISIONS.md` 条目格式:**

```markdown
## YYYY-MM-DD · <一句话的决定>
**背景**:
**选项**:A / B / C
**决定**:
**理由**:
**代价与已知风险**:
**推翻条件**:   ← 什么情况下应当重新考虑这个决定
```

> **「推翻条件」是本格式里最重要的字段。** 半年后你需要知道的不是「当时决定了什么」,而是「这个决定现在还成不成立」。

**worklog 条目**:日期 / 类型(决策 · 实作 · 实测 · 问题)/ 阶段 / 标题 / 正文。与 Artifact 控制台的导出格式一致,可直接粘贴归档。

### 12.2 节点循环协议

每个工作节点(一次坐下来做事)的固定循环:

```
1. 读 STATE.md          确认当前阶段与「下一步」
2. 做一件事             只做「下一步」里的一项
3. 写 worklog           做完立刻记,含实测数字
4. 若产生不易反悔的选择 → 写 DECISIONS.md(含推翻条件)
5. 更新 STATE.md        尤其「下一步」与「阻塞」
6. 若跨阶段            → 对照该阶段验收标准逐条确认
```

> **不更新 `STATE.md` 就不算做完。**
> 项目跨度长(保守估计 6–12 个月)且单人,中断后恢复上下文的唯一凭据就是这三份文件。

### 12.3 首轮门禁

任何一个新组件**第一次实际运行前**,必须先满足:

| 门禁 | 说明 |
|---|---|
| **路径合规** | 不含绝对路径,配置全部来自 `paths.toml` |
| **显存申报** | 声明峰值显存;P4 之后须走 Broker 租约 |
| **失败可见** | 失败时有明确报错,**不静默降级** |
| **可回退** | 知道怎么关掉它、怎么恢复到上一状态 |
| **数据边界** | 明确能读什么、能写什么;涉及出境须过闸门(§5.6) |

### 12.4 审批规则

| 级别 | 适用 | 机制 |
|---|---|---|
| **自动** | 只读、可重放、无外部后果 | 事后可查即可 |
| **逐次确认** | 写文件、点击提交类控件、单次出境 | 执行前展示**精确动作预览** |
| **哈希绑定批准** | 批量文件操作、GC 回收、交易提案 | 计划哈希绑定 → 你批准 → **执行前复核哈希未变** → 执行 → 回执 |

**三条铁律:**

1. **永不 `delete`,只移隔离区**;隔离区保留 M 天后才真正清除
2. **除 CACHE 根外,一律先报告后执行**
3. **批准的是具体计划,不是一类操作** — 「同意整理下载文件夹」不等于「以后都可以整理下载文件夹」

## 17. 术语表

| 术语 | 含义 |
|---|---|
| **五个逻辑根** | CODE / STATE / MODELS / ASSETS / CACHE。备份、GC、迁移策略各不相同,故物理分离 |
| **能力别名** | 客户端使用的稳定名称(如 `assistant.deep`),与背后的真实模型解耦 |
| **租约** | GPU Broker 按 NVML 实测空闲显存发放的显存使用许可,有期限、可被驱逐 |
| **票据** | 审批通过的凭证,绑定计划哈希,执行前须复核 |
| **哈希绑定批准** | 你批准的是**一个具体计划的哈希**;执行前若哈希已变则拒绝执行 |
| **三池** | 产物的 draft(可回收)/ adopted(永久+备份)/ exported(仅留元数据引用) |
| **六元组** | 权限强制的六个维度:用户 / 设备 / Agent / 工具 / **参数** / 额度 |
| **L0–L4** | 记忆的五层:工作 / 会话摘要 / 情节 / 语义 / 程序 |
| **双轨检索** | 向量检索(相关的是什么)+ 结构化查询(确切是什么),由编排器选路 |
| **Memory Gate** | 记忆写入前的把关:是否持久 / 是否影响未来行为 / 是否用户要求 |
| **superseded** | 新事实与旧事实矛盾时,旧条被标记为已被取代,但**保留不删** |
| **Asset Spec** | 结构化的资产描述,与目标模型无关;由编译器翻译成各家 prompt |
| **出境闸门** | 数据离开本机前的确认与记录关口,分 L0–L5 六级粒度 |
| **隔离区** | `delete` 的替代品。所有「删除」实为移入隔离区,保留 M 天 |
| **首轮门禁** | 新组件第一次实际运行前必须满足的五条检查(§12.3) |
| **节点** | 一次坐下来做事的工作单元;每个节点走一遍 §12.2 的循环 |
