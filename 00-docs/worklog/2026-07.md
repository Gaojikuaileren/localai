### [实作] P0-3 接网线 —— 问题在端口不在线材

**过程**:接上网线后 Realtek 2.5GbE 只协商到 **100 Mbps**,比 WiFi 7 的 866Mbps 协商值还低。

先排除本机因素:「连接速度和双工模式」= **自动侦测**,未被锁死;
驱动 1125.27.50.919 (2025-09-19)。但发现一批省电项全开:
`节能乙太网路(EEE)` · `环保节能` · `Gigabit Lite` · `Power Saving Mode`。

**当时的判断是错的。** 我把线材列为第一嫌疑(理由:100 Mbps 只需 2 对线,
1G/2.5G 需 4 对全通,所以 100M 典型对应「只有 2 对可用」),端口问题排在第二。

实际原因是**插错了口** —— 插在蓝色 WAN 口上。开链路监控(0.4 秒采样)后换到 LAN1,
捕捉到完整协商过程:

```
13:29:02  Up             100 Mbps    ← 蓝色 WAN 口
13:30:00  Disconnected               ← 拔线
13:30:03  Up             1 Gbps      ← LAN1
```

**线材完全正常**(能跑 1 Gbps 说明 4 对线全通,至少 Cat5e)。省电项也没动过。

**最终实测**:

| 项 | 值 |
|---|---|
| 链路 | 1 Gbps 全双工 |
| 到网关延迟 | < 1 ms(30 次全部低于 PS 的 1ms 分辨率) |
| 抖动 | 0 |
| 丢包 | 0 / 30 |
| 路由优先级 | 以太网 IfMetric 25 < WLAN 35 ✓ |

方案书接 2.5GbE 的目的是「消除 WiFi 抖动风险」—— **该目的已达成,且与带宽无关**。

### [决策] CUDA Toolkit 选 13.2 —— 匹配未来而非存量

**关键前提**:实测发现 `D:\ComfyUI\venv` 已在跑 **torch 2.11.0+cu128**,
arch list 含 sm_120,`cuda.is_available()=True` —— **而当时系统根本没装 CUDA Toolkit**。
因为 PyTorch 的 wheel 自带完整 CUDA 运行时。

**这改变了问题**:系统 Toolkit 只在**自己编译** CUDA 代码时才需要,不是「让 GPU 能用」的前提。

**选 13.x 而非 12.8 的理由**:
1. PyTorch 已把 cu128 移出构建矩阵,**cu130 是当前 stable default**,cu126 只留给旧驱动。
   项目里新建的所有 venv(P2 embedding/rerank、P5 ASR/TTS)都会装 cu130 —— Toolkit 应匹配未来
2. ComfyUI 的 cu128 环境不受影响(wheel 自带运行时)
3. llama.cpp 不链接 PyTorch,无版本耦合

**选 13.2 而非 winget 的 13.3**:当时驱动 596.36 报告支持上限为 CUDA 13.2,
装更高版本的 toolkit 编译出的东西可能报 driver insufficient。在跑 P1 之前不想动驱动。

### [问题] 四个 Windows PowerShell 5.1 的坑(会再遇到,记下来)

1. **UTF-8 无 BOM 的 `.ps1` 会乱码。** Write 工具产出无 BOM UTF-8,而 PS 5.1 按 ANSI(GBK)
   读脚本 → 中文全乱、语法解析崩溃。**含中文的 `.ps1` 必须存为 UTF-8 with BOM。**
   `backup.ps1` 也有同样问题(此前从未实跑所以没暴露),已一并修复。
   注意:**用 Edit 工具改过之后 BOM 会丢失,需要重新加。**

2. **`& exe 2>&1` 会炸。** PS 5.1 里对原生 exe 做 stderr 重定向会把每行包装成 ErrorRecord
   并令 `$?` 为 false,配合 `$ErrorActionPreference='Stop'` 直接中断脚本。
   `cl.exe` 不带参数正是把版权信息写到 stderr。**解法:把重定向交给 cmd —— `cmd /c "cl 2>&1"`。**

3. **`~` 在 PS 路径里是主目录简写。** 临时目录的 8.3 短名 `ZORIMA~1` 会被误解析,
   `Set-Location` / `Push-Location` 报「path does not exist」。
   **解法:用长路径(`$env:USERPROFILE`)或 `-LiteralPath`。**
   另注:`New-Item` 在 PS 5.1 里**没有** `-LiteralPath` 参数。

4. **`link`/`cl` 不带参数返回非零退出码**,会污染脚本的 `$LASTEXITCODE`。
   dot-source 场景不能用 `exit`,需显式 `$global:LASTEXITCODE = 0`。

### [问题] 恢复演练暴露了 `backup.ps1` 的一个真缺陷:校验清单不可移植

第一次演练时用 `sha256sum -c` 校验,**3/3 全部 MISMATCH**。
用 PowerShell 重新比对则 3/3 通过 —— 说明**数据完好,是清单文件的格式有问题**:

| 问题 | 后果 |
|---|---|
| UTF-8 **BOM** | 第一行的哈希前面多了 BOM 字符 |
| **CRLF** 行尾 | bash 的 `while read` 会把 `\r` 读进路径变量 |
| **反斜杠**路径 | 非 Windows 环境无法解析 |

**为什么这不是小事**:灾难恢复的典型场景就是 Windows 起不来 —— 那时只有
Linux live USB 或 WSL 可用,`sha256sum -c` 是最自然的校验方式。
清单只能被 PowerShell 读,等于**把恢复路径限死在「Windows 还能启动」这个前提上**,
而这恰恰是备份要应对的场景。

**修复**:改为无 BOM · LF · 正斜杠 · 双空格分隔(GNU coreutils 格式)。
`BACKUP-REPORT.md` 同时改为无 BOM,并补齐两套校验命令与四步恢复流程。

**修复后复验**:

```

sha256sum -c → 3 个全 OK,退出码 0
tree 哈希仍与原仓库一致
```

### [决策] 关闭 NVIDIA App / ShadowPlay —— 但结果修正了我的一个错误说法

**做了什么**:

| 对象 | 处置 |
|---|---|
| `NvContainerLocalSystem`(NVIDIA App / ShadowPlay 容器) | 停止 + 启动类型 Disabled |
| `NVIDIA App SelfUpdate` 计划任务 | 禁用(否则更新时会把服务重新拉起) |
| `NVDisplay.ContainerLocalSystem`(**驱动核心**) | **保留 Running/Automatic** |

**回归验证**:`nvidia-smi` 正常 · torch `available=True` · capability `(12,0)` ·
之前编译的 sm_120 kernel 重跑通过。驱动功能零影响。

**⚠ 但收益不是我此前说的那样**:

```
关闭前: nvcontainer 3 进程 · 188.8 MB 内存 · 显存 737 MiB
关闭后: nvcontainer 0 进程 ·   0.0 MB 内存 · 显存 737 MiB   ← 未变
```

我此前在本文件与 STATE.md 里写「对一个显存吃紧的项目,ShadowPlay 与 NVIDIA App
的常驻部分值得评估是否关闭」—— **这个暗示是错的。它们占系统内存,不占显存。**

实测占显存的进程全是 GUI 程序:

```
ShellHost · ApplicationFrameHost · LGHUB · EdgeWebView
RadeonSoftware.exe · AMDRSSrcExt.exe    ← 连 AMD 自己的软件也在独显上渲染
```

**因为显示器接在独显上,所有 GUI 的渲染都落在独显。**

**恢复方法**(若日后要用 ShadowPlay 录游戏):

```powershell
Start-Service -Name NvContainerLocalSystem
Enable-ScheduledTask -TaskName "NVIDIA App SelfUpdate_*"
```

### [实作] 备份保留策略 + 清理两个过时备份集

**起因**:你问 `G:\localAI-backup` 里两个文件能不能删一个。核查发现:

```
1406 与 1408 的 code.bundle 哈希完全相同(6bf977880d8c6de5...,95174 bytes)
两者都只含到 91acdba,而当前 HEAD 已是 01bd153
```

两次备份只隔 2 分钟,仓库未变,所以数据相同;区别只在 1406 的清单有 BOM。

**但更要紧的是两个都已过时** —— 且有个讽刺之处:`01bd153` 正是修复 backup.ps1
清单格式的那次提交,所以**1408 的 bundle 里装的是未修复版本的 backup.ps1**。
真从它恢复,会拿回那个有缺陷的脚本。

**处置**:重跑备份得 `2026-07-26_1418`(含 01bd153 · `sha256sum -c` 全 OK ·
tree 哈希一致 · 恢复出的 backup.ps1 已确认是修复版),然后删掉两个旧集。

**顺带补上脚本缺的功能**:v2.1 §8.5.2 定了「30 日增量 + 12 周全量」的保留策略,
但脚本每跑一次就新建时间戳目录、从不清理。现在每集 105 KB 无所谓,
**但 P3 记忆库进来后(§8.3 估 2–10 GB)会堆积。**

实现遵循 §8.4 的原则 ——**只报告,不自动删**:

- `paths.toml` 新增 `[backup].keep_last = 12`
- 每次备份后报告超出保留数的集及总占用
- 确需清理时用 `-PruneOld`,删除前打印完整清单

理由:备份不是 CACHE 根。§8.4 明确「除 CACHE 外一律先报告后执行」,
而**自动删备份**恰恰是那条规则最该防的事。
