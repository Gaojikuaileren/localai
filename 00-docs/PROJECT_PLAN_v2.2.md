## 4. ★ 记忆系统

### 4.1 五层记忆

| 层 | 内容 | 存续 | 存储 |
|---|---|---|---|
| **L0 工作记忆** | 当前会话上下文窗口 | 易失 | LLM context |
| **L1 会话摘要** | 滚动压缩 | 数天 | PostgreSQL |
| **L2 情节记忆** | 带时间戳的事件 | 长期 | PostgreSQL + Qdrant |
| **L3 语义记忆** | 关于你的结构化事实 | 长期 | PostgreSQL |
| **L4 程序记忆** | 学会的工作流 | 长期 | **版本化 + 签名,见 §4.4.2** |

### 4.2 ★ 双轨检索

> **只做向量 RAG 的记忆系统,会在最需要精确的地方失败。**

| 轨道 | 回答 | 技术 |
|---|---|---|
| 向量检索 | 「**相关的**是什么」 | Qdrant · bge-m3 + rerank |
| 结构化查询 | 「**确切**是什么」 | PostgreSQL · SQL over 实体表 |

「我妹妹叫什么名字」——向量检索返回一堆相关片段但答不出名字,必须走结构化查询。反过来「上次聊的那个灯光问题」必须走向量。**两轨都要,由编排器按问题类型选路。**

### 4.3 实体图谱

`Person`(关系边:称谓 · 亲疏 · 重要日期)· `Project` · `Device` · `Place` · `Thing` · `Event`(带时间戳,可关联任意实体)· `Preference`(带置信度与时效性)

### 4.4 写入把关(Memory Gate)

#### 4.4.1 三问

- 是否是关于用户的**持久**事实?
- 是否会影响未来的行为?
- 是否用户明确要求记住?

写入后**必须**:用户可见 · 可编辑可删除 · **记录来源**。

#### 4.4.2 ★ 置信度只能由服务端可验证的信号产生(v2.2 新增)

> **审查 S1**:客户端自报 `user_explicit` 可铸造 confidence=1.0 的「用户事实」并自动 supersede 真实事实。而 L4 是可执行工作流 —— **这条链直通代码执行**。

Gate 输入必须携带 `provenance`,且 `body` 里的 `user_explicit` 字段**一律忽略**(与 `device_id` 同等对待):

| 来源 | `source_confidence` | 能否自动 supersede |
|---|---|---|
| 记忆面板上的显式点击(带票据) | 1.0 | ✅ |
| 客户端 UI 标记,且该输入经设备密钥签名 | 1.0 | ✅ |
| 助理从对话流推断 | ≤ 0.6 | ❌ |
| `tool_result` / `web_content` / `rag_chunk` 派生 | ≤ 0.4 | ❌ 且强制 `pending` |

`provenance ∈ {user_typed, user_voice_asr, tool_result, rag_chunk, web_content}`,**只有前两类可产生 explicit 候选**。

**`pending_review` 禁止批量确认。** 逐条确认,且「这条将取代哪条现有事实」是主视觉。积压上限 50 条,超限告警并**暂停接受远程候选** —— 积压本身是攻击信号。

> 这是 §6.6「计划本身要被审查」在**写侧**的对应物。

#### 4.4.3 ★ L4 是代码资产,不是记忆的一层(v2.2 新增)

> **审查 S2**:L4 程序记忆是可执行工作流,却与 L2/L3 共用写权限。

1. L4 写入**仅 `trusted-local`**,且**逐次哈希绑定批准**(与 §12.4 对批量文件操作同级)。远程档位的路由表里**不存在 L4 写端点**。
2. L4 条目**版本化并签名**。策略层在消费任何 L4 派生的提案前,校验源条目当前哈希与**你最近批准过的**哈希一致,不一致则拒绝执行。这把 §12.4 的哈希绑定从「提出到执行之间」延长到「**教会到执行之间**」。
3. L4 的 supersede = **需批准的版本升级**。§4.5 的自动裁决对 L4 一律不适用。
4. **远程档位检索默认排除 L4** —— 读工作流步骤对远程问答无价值,却给了攻击者一张可执行面的地图。

### 4.5 时效、冲突与可解释性

每条事实携带 `asserted_at` · `confidence` · `source_ref` · `superseded_by` · **`origin_device_id`** · **`write_seq`**。

**冲突**:新旧矛盾时**不覆盖**,新增一条并将旧条标记 superseded,保留完整历史。
**铁律**:**自动事实不得 supersede 用户事实**。否则任何能把文件写进授权区域的东西都能改写你的记忆。

**时效**:部分事实天然过期 → 定期 review 提示。

**★ 可解释性是信任的前提**:助理说「我记得你提过 X」时,必须能一键展开看到 **来源 · 时间 · 原文片段 · 记录设备**。没有可解释性的记忆既不敢信任,也无法纠错。

### 4.6 ★ 隐私红线(2026-07-26 按 D22 重写)

> **★ 本节最重要的一句:记忆库在磁盘上是明文。**
> 决议 D22 推翻了 D2(BitLocker VHDX),记忆库改为普通文件夹 `D:\AI\state\memory\`。
> 文档不得再声称任何形式的静态加密 —— **声称高于实际的保护,比防护弱本身更危险。**

| 规则 | 状态 |
|---|---|

**仍然有效的(这些恰恰是日常最可能发生的威胁):**

| 威胁 | 防住了吗 | 靠什么 |
|---|---|---|
| ComfyUI 的第三方节点读记忆库 | ✅ | §6.8 账户隔离 + NTFS ACL |

| 提示词注入改写记忆 | ✅ | §4.4.2 置信度只由服务端信号产生 |

| 威胁 | 后果 |
|---|---|
| 工作站硬盘被物理取走 | 全部记忆可读 |

| 拿到机器且能开机 | 同上 |

> **一个诚实的补充:这个取舍不是单向的。**
> 加密把「被窃取」的风险换成了「密钥丢失」的风险,而后者在 §15 风险清册里原本是**高**级
> —— BitLocker 恢复密钥丢失 = 记忆库永久不可读,而这对一台家用单人机器来说,
> **发生概率高于定向窃取**。D22 消除的正是这个风险。
> 代价写在上表,不粉饰;收益也不抹掉。

#### 4.6.1 三层强制(缺一不可)

> **审查 S5**:`no_export` 属性在 `r.text` 这一步就失效了。`r.text` 是 `str`,不是 `MemoryResult` —— **引用链在属性读取那一刻就断了**。而 `ctx = "\n".join(r.text for r in results)` 是 RAG 注入的标准路径,**每次都走这一步**。

| 层 | 做法 |
|---|---|
| **类型层** | `MemoryResult.text` 返回 `TaintedText`(密封,**不实现 `__str__`**,不实现 `Exportable`),只能经 `render_for_prompt(backend)` 取值;`backend.egress == true` 时抛 `MemoryExportViolation` |
| **渲染层** | 出境闸门的**最终**强制点放在**已组装完成的 prompt 字符串**上,不是组装前的类型检查 |
| **存储层** | `CHECK (no_export = true)`;`UPDATE ... SET no_export = false` 在数据库层被拒 |

#### 4.6.2 ★ 必须明文写下的一句话

> **不得声称「记忆零外发」是被证明的。**

`no_export` 作用于对象与已组装文本,**无法阻止你手动复制粘贴**。§10 的断言相应改为两条可验证的:

1. 「不存在任何程序路径使记忆文本进入出境载荷构造器」—— 否定用例须覆盖 **str 拼接 · f-string · 模板渲染 · 日志格式化** 四种取值方式
2. 「重叠检测在记忆 eval 集上的召回率 ≥ X%」—— X 由实测填,不预设

#### 4.6.3 Off 档的结构性保证

> **审查 S6**:Off 档「记忆可查 + 云端推理」若靠 UI 文案与运行时判断,用户看到的提示会与实际发生的事**恰好相反**。

按 §6.2「按会话挂载工具池而非运行时判断」落实:

- 模型别名注册表给每个后端打 `egress: true|false`
- 会话建立时若解析出的生成后端 `egress=true`,**该会话的工具池里根本不挂载 `memory.search`**
- 记忆检索由客户端走**独立的 MEMORY 平面**单独发起,结果只渲染成卡片,**永不回流进 MODEL 平面的请求体**

**「云端基于记忆推理」在会话结构上不可表达**,而不是靠运行时判断或文案。

> Off 档的正确表述是「**记忆可查 + 云端推理**」,**不是**「云端基于记忆推理」。UI 文案必须写清。

### 4.7 ★ 打扰评分(整节替换 v2.1 的「克制的主动性」)

> **本节起因**:用户于 2026-07-26 明确决定**推翻 v2.1 §4.7 放权**。原文「只在你曾明确请求过的事情上主动」与「无时无刻清醒、持续分析」的助手直接冲突。

#### 4.7.1 放权的实际含义

放权不是「随便打扰」,而是**把「能不能主动」从一条禁令,改成一个有阈值、有配额、有反馈的机制**。

原则从「只在你请求过的事上主动」变为:

> **主动性是挣来的。** 新的打扰类型从最低级别起步,靠你的反馈逐步解锁更高级别。

#### 4.7.2 四段流水线与信任边界

```
① 提名  ← Vigil(1.7B CPU)。只填受约束的槽,不给分数
② 校验  ← 确定性代码。claim_class 白名单、证据行号存在性、来源类型
③ 评分  ← 纯确定性公式。Vigil 读不到公式,也读不到自己的得分
④ 投递  ← 配额闸 + 分级路由
```

> **★ 核心难题与解法**:§6.6 说模型是不可信计划者。**如果评分由模型自己给,它就能给自己打高分来打扰你。**
> 解法不是「让模型诚实」,而是**改变模型的任务** —— 它只做分类(属哪类 / 命中哪个既有主题 / 是否新颖 / 是否命中承诺 id),判断留给它读不到的确定性公式。

#### 4.7.3 提名契约(模型只能填槽)

`title` **不是模型自由文本**,由 `claim_class` 固定模板 + `{root,rel}` + 证据行号拼装。
`claim.summary` 上限 **80 字**,必须以模板起头 ——「`{rel}` 在 `{行号}` 附近出现与 `{topic}` 相关的变化」。

> 自由文本越长,注入载荷的携带能力越强。

#### 4.7.4 五维评分与来源封顶

| 维 | 含义 | 权重 |
|---|---|---|
| U 时效性 | 错过就没用了吗 | 0.25 |
| S 后果严重性 | 由 `claim_class` 决定 | 0.30 |
| R 关联度 | 是否命中你曾表达关心的主题 | 0.20 |
| N 新颖性 | 是否重复既有信息 | 0.15 |
| C 置信度 | 证据强度 | 0.10 |

**★ 来源封顶(防操纵的核心):**

| `claim_class` 档 | 开放给 |
|---|---|
| `irreversible_loss` / `financial` / `system_degradation` | **仅 `source=deterministic`**(§4.7.6 白名单与 §9.3 告警器) |
| `self_commitment` 及以下 | `source=model_nominated` **封顶 S=0.40** |

`deadline_src=file` 的 U **上限 0.35**(与 `inferred` 同档)—— 文件里的时间戳正是攻击者最容易控制的东西,「字面出现在 quote 里」只证明它来自那个文件,不证明它是真的。

> **修复后重算注入攻击链**:Base = 100×(0.25×0.35 + 0.30×0.40 + 0 + 0.15×0.30 + 0.10×1.0) = **34.8** → ×0.925 = **32** → **L1 日报**。
> 攻击者能拿到的最好结果是「进日报」,不是「弹通知」。

#### 4.7.5 分级与配额(v1 只开两档)

| 级 | 分数 | 通道 | v1 |
|---|---|---|---|
| L0 | < 20 | 静默记录 | ✅ |
| **L1** | 20–59 | **每日 22:00 日报,每天 3 条** | ✅ |
| L2 | 60–79 | 托盘角标 | ❌ P9 之后 |
| L3 | 80–94 | 系统通知 | ❌ 需解锁 |
| **L4** | ≥ 95 | 强提醒 | ✅ **仅确定性白名单** |

**★ 硬性配额优先于一切分数**:每日主动打扰(L2 及以上)**上限 3 次**。模型再怎么给自己打高分也突破不了。**配额不依赖模型诚实,这是它相对评分公式的根本优势。**

**唯一自适应通道**:同一 `claim_class` 累计 **3 次**你标记「该早点说」→ 解锁 L3。

> **为什么 v1 砍到两档**:完整设计的自适应能力依赖一次 shadow 期末的 2–4 小时人工标注。那次标注不会被完成(单人 · 业余 · 6–12 个月跨度)。不完成则整套退化成一个拍脑袋的固定公式,而 L3 阈值在真实分布下几乎无人能过 —— 你一个月收到 2 条通知,结论是「这功能没上线」,然后关掉常驻助手。

#### 4.7.6 确定性 L4 白名单(不经模型)

磁盘水位越线 · 显存租约被拒 · 出境费用达月度上限 80%/100% · **备份任务失败** · 记忆写入失败 · 隔离区即将到期 · 你曾明确设定的时间提醒。

#### 4.7.7 反馈与可解释性

日报每条两个按钮:**「该早点说」** / **「不用告诉我」**。

每次打扰可展开看到**各维度得分与判定依据** —— 承 §4.5「没有可解释性的东西既不敢信任也无法纠错」。

#### 4.7.8 手动可调

全部参数(阈值 · 配额 · 各维权重 · 日报时间 · 各 `claim_class` 的默认级别)在设置里可手动调整。
**但配置文件位置受 CFG-1 约束** —— 见 §6.7.4。

### 4.8 多模态写入通道

随口一句「记一下,下周要交房租」应直接进入 L2/L3。这要求语音层与记忆层打通,也是本版把语音提前并设为常驻的主要理由。

**选 `speech.cpu` 时语音走 CPU**(§8.1.3)。CPU 语音的定位是**异步的记忆随手写入**,不是对话 ——「记一下,下周三交房租」是 3 秒音频,CPU ASR 实时率 0.3–0.6 意味着 1–2 秒转写,对写记忆完全够用。**文档必须写清这个定位,不要让人以为低档能用语音对话。**

### 4.9 冷启动、评测与兜底

#### 4.9.1 冷启动

P3a 提供一次**结构化初始化会话**:助理按实体类型逐项发问(重要的人及称谓 · 常用设备 · 进行中的项目 · 明确的偏好与禁忌),你口述,它写入 L3 并当场展示、允许你改。一次约 20–30 分钟。

**★ 顺带完成敏感度定级**(§4.11.4 的 S2 标记)。§4.9.1 的初始化会话只跑一次,**错过就没有第二次**。

#### 4.9.2 评测集与四项指标

| 指标 | 含义 |
|---|---|
| 召回率 | 该记得的记住了 |
| 精确率 | 检索出来的确实相关 |
| **误记率** | 记住了错的事实 —— **最危险** |
| **溯源完整率** | 每条记忆都能展开到原始来源 |

**自动记忆(Vigil 派生)单列一组指标**,其误记率风险显著更高。

#### 4.9.3 漏记与误记的兜底

- **漏记**:你说「你怎么不记得 X」时,助理须能**即时补录**并标注「事后补录 + 补录时间」
- **误记**:每周推送一条「本周新记住的事」摘要(仅标题级),扫一眼即可发现离谱条目

### 4.10 规模增长

L2 只增不删(进 GC 白名单)。数据模型带 `last_accessed` 与 `access_count`;检索时对久未命中且低置信度的旧条目**降权**(不删除);超过 N 年的 L2 事件**归档为 L1 级摘要**,原文保留但不进主索引。

### 4.11 ★ 多设备记忆(v2.2 新增)

#### 4.11.1 拓扑:单一权威 + API 访问

记忆库**只有一份**,在工作站的 `D:\AI\state\memory\`(普通文件夹,**不加密** —— D22)。
其他 PC 与手机通过 MEMORY 平面读写。

**不做分布式副本。** 理由:单人使用真并发极少;§4.5 的「不覆盖,新增并标 superseded」在单权威下是几行代码,分布式下是研究课题;多份加密副本 = 密钥管理复杂度爆炸(而「避免密钥管理复杂度爆炸」正是选这个拓扑的理由之一)。

**已接受的后果**(用户 2026-07-26 明确接受):

> **工作站关机 = 所有设备都没有记忆 + 所有机器 AI 失效无法调用。**

本文档**不偷偷改写为「工作站必须常开」**。但失效必须是**可诊断、可预期**的 —— 见 §4.11.6。

#### 4.11.2 写入路径

所有写入都经工作站的 Memory Gate。**客户端无本地队列** —— 无网即明确失败。

> **为什么不做 Outbox**:iOS 的 WebCrypto 不用 Secure Enclave,`extractable:false` 只挡 JS,**密钥材料与密文同在一个 IndexedDB 里**;而 IndexedDB 在 iOS 备份范围内,默认非端到端加密的 iCloud 备份是「你无法单方面终止访问的系统」。按 §4.11.5 的判据,**加密后的 Outbox 仍构成出境**。

**推翻条件**:`mobile-remote` 写入送达率连续 4 周 < 99% → 进 P3.5 按受控规格实现(纯素材 · 非记忆 · 72 小时 · 恢复后逐条确认)。

#### 4.11.3 `write_seq` 与冲突

- `write_seq` **全局单调**,由工作站 PostgreSQL 的 advisory lock 唯一分配。**客户端不参与分配。**
- **时间戳以服务端为准**(客户端时钟不可信)
- 冲突沿用 §4.5:不覆盖,新增并标 superseded
- **自动事实不得 supersede 用户事实**(§4.5 铁律),多设备下「用户事实」的认定见 §4.4.2

`source_ref` 扩展为携带 `origin_device_id` 与设备显示名。**记忆面板必须显示「这条是在哪台设备上记的」** —— 否则 §4.5 的可解释性在多设备下就残缺了。

#### 4.11.4 敏感度分域(两级,不是三级)

| | P3b 实装 | P3.5 启用 |
|---|---|---|
| **S2 机密** | **结构性不可见**,任何远程档位永久不可读,**无提级路径** | 不变 |
| **S0 / S1** | **不区分**。远程档位可读全部非 S2 内容 | 用一个月真实读取日志定边界后启用三级分域 |
| 约束手段 | 读取预算(首月只观察不硬停)+ 逐条全量审计 + **溯源展开需生物识别** | 增加域过滤 |

**为什么 S2 可以第一天就强制而 S0/S1 不行**:S2 的定级是**确定性的**(IBAN / 税号 / 证件号 / 地址模式 / 「密码是」/「恢复密钥」的正则族 + 用户手动标记),不需要 LLM 判断也不需要真实数据校准;量很小,不会造成「手机很傻」;而它恰恰是丢手机场景下伤害最大的部分。S0/S1 的边界**必须靠真实数据**,在没有它之前 fail-closed 会把手机压到不可用。

**结构性隔离,不是运行时过滤:**

```
PostgreSQL:  role ai_mem_local  → 基表全表
             role ai_mem_remote → 只 GRANT SELECT ON v_memory_nons2
Qdrant:      collection mem_main  ← 远程会话唯一持有的句柄
             collection mem_s2    ← local 独有,独立 loopback 端口
```

> 漏了 payload filter 是**沉默的**(返回多余结果,没人报错);漏了 collection 句柄是**响亮的**(直接异常)。§12.3 门禁第三条要的正是后者。

**「我妹妹叫什么」这条 P3 验收例句,必须在手机上也通过。** 否则这条验收是自欺。

#### 4.11.5 ★ 「出境」的精确定义

> **审查 S11**:五份设计给了「境」五个定义。

| # | 判据 | 结论 |
|---|---|---|
| **D1** | 内容离开**你控制的设备集合** | **出境**。禁止 |
| **D2** | 内容进入**你无法单方面终止访问的系统** | **出境**。禁止(涵盖 iCloud 备份、第三方云) |
| **D3** | 内容投递到**你已注册、可吊销、可审计的设备**,且**不落盘** | **不是出境** |

**D3 的三个条件必须同时满足。** 原设计的「已下发内容随之失效」是一个**已知不成立的前提**(下发出去的东西收不回来),用假前提证明「投递不是出境」是边界论证的典型失效形态。改为「**不落盘**」—— 这是可兑现的。

**明文例外条款**:

1. **iOS 应用切换器快照**属于系统行为,PWA 无法阻止。**明文接受为已知风险**,不在「禁止」与「接受」之间摇摆
2. **手动复制粘贴**无法阻止(§4.6.2)
3. **Tailscale 控制平面可见连接元数据**(不含内容),记入 §5.6 的第三方清单

#### 4.11.6 故障分类(§12.3 失败可见)

五种在客户端都表现为「用不了」,但原因与应对完全不同,**必须区分**:

| 故障 | 客户端表现 |
|---|---|
| 工作站关机 / 休眠 | 「工作站未响应 · 上次成功连接 3 小时前」 |
| 服务未起 | 「工作站在线,但记忆服务未启动」 |
| **记忆卷未挂载** | 「记忆库已上锁」+ 解锁指引 |
| 网络断 | 「网络不可达」+ 区分局域网/tailnet/互联网 |
| 工作站在完全 Off 档 | 「AI 已完全关闭」 |

> **诚实限制**:iOS 的 Tailscale 走 NetworkExtension,PWA 的 JS 拿不到 peer 状态。
> **明确合并为一态**:「无法连接 · 上次成功连接 {时间}」。§12.3 要求的是「不要伪装没事」,不是「必须诊断出根因」。

#### 4.11.7 Wake-on-LAN

**不做。** 理由:它把「工作站关机 = 全失效」这条已被接受的约束偷偷改写成「工作站必须能被远程唤醒」,而唤醒路径本身是一个新的、无认证的攻击面。若实际使用中确实频繁受阻,进 P3.5 单独评估。

### 5.6 ★ 数据出境闸门

| 级别 | 适用 | 机制 |
|---|---|---|
| **会话级授权** | 概念阶段(公开素材 / 自己的草图) | 一次授权覆盖本次迭代会话;**会话结束自动失效**;实时显示已发送条目与累计费用 |

#### 5.6.2 分级粒度(L3 已拆)

| 级 | 允许发送 | 状态 |
|---|---|---|
| L0 | 不启用任何云端路径 | Vigil 永久锁定在此级 |
| L1 | 仅你手打的问题文本 | |
| **L2** | + 你**显式选中**的内容 | **`escalate.cloud` 锁定在此级**(D-Q2) |

## 6. ★ 安全与权限

### 6.1 核心原则

> **能力升级可以上云,权限升级永远不行。**

```
计划层  ← 可升级到云端,输出【结构化提案】
   ↓
策略层  ← 永远本地:权限校验 · 参数校验 · 额度 · 动作预览
   ↓
执行层  ← 永远本地:stdio 执行器
```

**★ 「本地」的精确定义**(v2.2 澄清):

> **策略层与执行层必须与被操控的资源同机。**

「永远本地」指的是**相对被操控资源**,不是「每台机器都有一份完整权威」。这与 §4.11 的「记忆单一权威」不矛盾:第二台 PC 对自身的操控需要本机策略层,但它的**记忆**仍走工作站。

### 6.2 权限强制:六元组

服务端按 **(用户 / 设备 / Agent / 工具 / 参数 / 额度)** 强制。

**参数级尤其关键**:同一个「写文件」工具,**路径参数决定它是安全还是灾难**。六元组里如果只实现了前四维,等于没有实现。

权限在**服务端按档位挂载工具池**,而非运行时判断。低权限档位的会话在建立时其工具池里就**不存在**高风险工具。

### 6.3 权限档位

| 档位 | 设备 | 问答/语音 | 资产 | **记忆读** | **记忆写** | 文件操作 | 电脑操控 |
|---|---|---|---|---|---|---|---|
| `trusted-local` | 本机 App | ✅ | ✅ | **全部** | ✅ 含 L4 | 逐次确认 | 逐次确认(**本机**) |
| `trusted-lan` | 局域网 PC | ✅ | ✅ | **非 S2** | ✅ 不含 L4 | 逐次确认 | 逐次确认(**仅自身**) |
| `mobile-remote` | 手机 | ✅ | ✅ | **非 S2** | ✅ 不含 L4 · 无队列 | ❌ | ❌ |
| **`resident-observer`** | Vigil | — | ❌ | **仅 `mem.exists` + 投影** | **仅 `vigil_observations`** | **只读白名单** | ❌ |

#### 6.3.1 ★ 电脑操控是二维的(v2.2 修正)

v2.1 的「电脑操控」一列把两个维度压成了一维。实际是:

| 发起 ＼ 操控 | 工作站 | 局域网 PC | 手机 |
|---|---|---|---|
| **本机 App** | 逐次确认 | ❌ | — |
| **局域网 PC** | ❌ | **逐次确认** | — |
| **手机** | ❌ | ❌ | ❌ |

**对角线 = 本机操控本机;非对角线 = 跨机操控 = 默认禁止。**

跨机必须禁的理由:§6.5 的安全边界(浏览器 profile 禁止清单、文件隐藏清单)都是**按机器**定的;远程发起时你看不到那台机器的屏幕,无法核对动作预览;允许跨机会让「丢一台设备」升级成「丢所有设备」。

**★ 操控目标必须是工具身份的一部分,不能是参数。** `execute@workstation` 与 `execute@lan-pc-2` 是**两个不同的工具**。局域网 PC 的会话工具池里只挂 `execute@self`,**根本不存在** `execute@workstation`。若做成参数,它就能被不可信的计划者操纵。

#### 6.3.2 ★ 设备身份:统一 WebAuthn(v2.2 新增)

> **审查 S12**:原设计写「手机设备密钥存 iOS Keychain(`kSecAccessControlBiometryCurrentSet`)」—— **这是原生 Security.framework 常量,PWA 调不了**。而 B1 已定不做原生 App,所以这条约束永远不会被满足;实际得到的是一个 32 字节长期 bearer 秘密躺在 IndexedDB 里,而文档上写着「生物识别保护」。

- **设备身份 = WebAuthn 平台认证器**,PC 与手机共用同一套实现(Windows 侧走 Windows Hello,私钥由 TPM 保护)
- 服务端**只存公钥与 `credentialId`**,不存任何秘密的哈希
- **不使用长期 bearer 令牌**;短寿命令牌 + `tailscale_node_id` 交叉绑定 + 双层吊销
- **配对码**:8 位 Crockford base32 · **工作站显示 / 新设备输入** · 5 分钟一次性 · 同会话失败 5 次作废 · 全局每分钟 10 次

> **方向比强度更重要**:反方向(新设备显示、工作站输入)下工作站屏幕上只有几个数字;正方向下 admin 面板可以先让你选定设备名与档位,**再完整显示你正在授予什么**。

> **`tailscale_node_id` 绑定的强度必须如实描述**:它防「密钥离机」,**不防「整机沦陷」**。文档不得用它来抵消凭据保护的弱点。

**★ RP ID 必须在 P2 之前定死。** WebAuthn 的 RP ID 一经确定不可更改 —— 若 P2 用 `localhost`,P3b 切到 `ai-box.<tailnet>.ts.net` 时工作站本机的 credential **全部作废**。因此把「定死 tailnet 名与机器名」这个 **0.2 天的命名决定**提到 P2 之前。

### 6.4 工具传输分层

| 类别 | 传输 | 理由 |
|---|---|---|
| 高权限本机执行器 | **stdio / Named Pipe** | 无网络面;进程级父子信任 |
| 低风险只读 | 认证后的 MCP over HTTP | 需跨设备复用 |
| **记忆读写** | **MEMORY 平面(独立)** | §4.6.3 的结构性前提 |

### 6.5 ★ 四项操控需求的具体设计

> 这张表是 P6 的**执行依据**。约束才是实质。

| 需求 | 风险 | 技术路线 | **关键约束** |
|---|---|---|---|
| 写文档 | 低 | 只读输入 + 写指定输出目录 | 可较宽松 |
| **操作浏览器** | **高** | Playwright / CDP,**独立 profile** | **邮箱 / 银行 / IBKR / 密码管理器 / 个人浏览器会话默认不可见**;点击提交类控件逐次确认;网页内容标记为不可信 |
| **整理文件夹** | **高** | 事务化文件操作 | 精确清单 → **哈希绑定批准** → 执行前复核哈希 → **隔离区(永不 delete)** → 尽力回滚;区域约束见 §6.7 |
| 游戏日常 | 中 | **模板匹配 + OCR + 确定性状态机** | 游戏无 UIA 树;固定 UI 用模板匹配更快更准更省(~0.2GB vs 6GB);**VLM 仅负责未知状态诊断,不得自行猜坐标继续操作** |

### 6.6 威胁模型

- **模型是不可信计划者**:网页、邮件、文档、参考图元数据、**授权区域里的文件**均可能携带提示词注入 → **计划本身要被审查**
- **资产导演 Agent 独立身份**:与日常助手共用模型别名但不共用工具池与记忆域
- **Vigil 是持续摄入不可信内容的主体**:它读的文件可能被投毒 → 见 §17.7 的隔离设计
- **记忆库是最高价值目标**:任何能读记忆的路径都是攻击面

### 6.7 ★ 权限区域(v2.2 新增,取代 §6.5 的隐藏清单)

> **本节起因**:用户明确要求「设立一个板块专门告诉 AI 哪些地方是有权限的」。

#### 6.7.1 三条基本裁决

1. **默认拒绝。** 未在白名单内的路径一律不可读。与 §6.2「按会话挂载工具池」同构。
2. **区域是分主体的。** `vigil` / `assistant.main` / `asset_director` 各有各的区域集合,不共享。
3. **黑名单优先于白名单。** 命中硬禁止清单即拒绝,不论白名单怎么写。

#### 6.7.2 数据模型

```toml
[[zone]]
id       = "proj_localai_docs"
subject  = "assistant.main"        # vigil | assistant.main | asset_director
path     = "{code}/00-docs"        # 用 paths.toml 的根变量,不写绝对路径
mode     = "ro"                    # list | ro | rw
recursive = true
purpose  = "项目文档与决策日志"
exclude  = ["**/snapshots/**", "**/worklog/**"]
```

`mode` 三级:`list`(只能看到文件名/大小/时间)· `ro`(可读内容)· `rw`(可写)。

**隔离区继承来源区域的 mode。** 从 `list` 区域移入隔离区的文件,`fs.read_head` 必须拒绝并给出 `origin_mode=list` 的理由 —— 否则隔离区会变成把 list-only 目录的正文搬进可读位置的通道。

#### 6.7.3 Vigil 的区域(最严)

| 路径 | mode | 说明 |
|---|---|---|
| `{code}/00-docs` | **元数据级** | **不给内容**。项目状态经编排器生成的结构化只读投影获取(见 §17.6) |
| `{assets}/draft` | `ro` | 自己产出的草稿 |
| 用户显式添加的工作目录 | `ro` | 默认带编译产物排除模式 |

**Vigil 永久黑名单**:`{code}/**` 的全部内容级读取 · `00-docs/snapshots/**` · `00-docs/worklog/**` · `.git/` · `.githooks/` · `config/` · `{state}/**`

> **为什么 `worklog` 与 `snapshots` 必须黑名单**:前者按定义装工具输出(第三方报错原文),后者按定义装第三方条款原文。**它们是注入载荷最自然的落点**,而 Vigil 会把「项目自身文档」当作高可信来源。

#### 6.7.4 硬禁止清单(`zones.local.toml`,不进 git)

```
%LOCALAPPDATA%\Google\Chrome\User Data\**
%LOCALAPPDATA%\Microsoft\Edge\User Data\**
%APPDATA%\Mozilla\Firefox\**
%USERPROFILE%\.ssh\**
%APPDATA%\Bitwarden\**   %LOCALAPPDATA%\1Password\**   %APPDATA%\KeePass\**
%APPDATA%\Thunderbird\**   %LOCALAPPDATA%\Microsoft\Outlook\**
%USERPROFILE%\.aws\**   %USERPROFILE%\.config\**
**/.env   **/*.key   **/*.pem   **/*.pfx   **/credentials*   **/secrets*
{state}\**                      ← 记忆库、票据、日志
<备份目标盘>\**                  ← §8.5 铁律 4
任何恢复密钥 / 主密码 / 凭证的存放位置
```

> **本清单只写路径模式,不探测本机是否安装了这些软件。** 写一条 `%APPDATA%\Bitwarden\**` 的禁止规则不需要知道 Bitwarden 装没装,而**探测本身就是凭证侦察的行为模式**。

#### 6.7.5 强制点与诚实说明

**强制在工具层**:`fs.read_head` / `fs.stat` 等工具自身校验区域,不信任调用方传入的路径。

> **诚实限制**:在 P6 建立专用 Windows 账户之前,**OS ACL 层是零防护**。工具层就是全部的边界。因此它必须按安全关键代码对待,**否定用例先于功能写**(§10)。

#### 6.7.6 配置文件的保护(CFG-1)

`zones.toml` / `zones.local.toml` / `vram-tiers.toml` / `interrupt-policy.toml` 全部:

- **不在任何 Agent 的可写区域内**(`self_protect` 通配 `config/*.toml`)
- 挂载时校验 `sha256`,不匹配则 `refuse_mount`
- 安全不变式(如出境级别、`counts_as_active_task`)移入 `{state}/policy/`,config 里只留只读镜像用于展示

**否定用例**:以 `assistant.main` 身份写 `config/*.toml` 必须被拒。

#### 6.7.7 变更流程

| 动作 | 审批级(§12.4) |
|---|---|
| 新增 `list` 区域 | 逐次确认 |
| 新增 `ro` 区域 | 逐次确认 + 展示该目录的文件计数与总大小 |
| 新增 `rw` 区域 | **哈希绑定批准** |
| 修改硬禁止清单 | **哈希绑定批准** |

**一键临时区域**:被拒绝时可一键授予「本次会话内只读」,会话结束自动失效。拒绝日志驱动扩权 —— 每周日报汇总「本周被拒最多的 3 个路径」。

> **诚实**:默认拒绝的头两周确实难用。这是白名单模型的固有代价。

### 6.8 ★ 账户隔离(v2.2 新增,从 P3 提前到 P2)

> **审查 S3**:ComfyUI 的第三方节点与记忆服务同一个 Windows 用户,是一条**绕过网关、六元组、预算、审计**的读全库路径。

| 账户 | 跑什么 |
|---|---|
| `ai-mem`(专用低权限服务账户) | PostgreSQL · Qdrant · embedding/rerank · memory-service |
| `ai-asset` | ComfyUI · 浏览器执行器 · 游戏自动化 |

- `D:\AI\state\memory\` 的 **NTFS ACL 拒绝资产侧账户**(继承关闭,显式 ACE)
- PostgreSQL 按 SSPI/SID 限制连接源;Qdrant 前置只认本地 token 的代理
- **任何其他本机连接尝试写审计并触发 §9.3 告警**(目前这类尝试完全静默)

> **★ D22 之后,本节从「第二层」升为「主要保护层」。**
> 运行态与静态的保护**全部**来自 OS 账户隔离 + NTFS ACL + 网关认证 —— 没有加密可以兜底。
> 因此本节的**否定用例必须先于功能写**(§10),与权限区域同级。

### 6.9 ★ 凭证与敏感信息(D23 · 经对抗性审查修订)

#### 6.9.0 ★★ 门禁:本节在 P6 之前整体 `not_provisioned`

> **规范说「手动输入现在唯一可用」,实现说「现在什么都不存在」——
> 这个缝隙里,你面对的唯一入口是对话框,而那恰恰是本节要禁止的动作。**

带外输入控件需要一个**接收方**(执行器),而执行器要到 P6 才存在。因此:

| 阶段 | `secret.request` | 助手的正确行为 |
|---|---|---|
| **P1 – P5** | **工具池里刻意不存在**(照 §3.2 `trade.execute` 的先例) | 遇到需要凭证的步骤:把任务拆到那一步为止,给出**你自己操作的指引**,然后停下。**不接收、不转述、不代填、不建议你发给它** |
| **P6 起** | 上线,`provider=manual` | 见 6.9.5–6.9.7 |

**这不是取消手动输入,这是手动输入在没有接收方时的唯一可能形态。**
§12.3「失败可见,不静默降级」在此的字面要求就是:**能力不存在时明确不提供,而不是降级到对话框。**

**P2 必须先行的两项**(它们保护的正是这个空窗期):**入口凭证检测器**(E1)· **`secret_ref` 登记表建表**。

#### 6.9.1 核心决定

> **凭证类敏感信息不进记忆库。** 记忆库只存引用,不存值。

IBAN · 税号 · 证件号 · 密码 · API key · 恢复密钥 —— 存放在独立加密应用中,每次使用经授权取出。

> **★ 泄露面的准确表述(原文低估了):**
> 拿到硬盘的人读不到凭证**值**,但读得到 **存在性 · 类别 · 用途 · 使用时间线**。
> 一份「你在哪家银行 · 报不报税 · 有没有加密货币恢复密钥 · 每个多久用一次」的清单,
> 对钓鱼与胁迫的价值高于「一个账户」。
> **准确说法:凭证值读不到;凭证的存在性、类别与使用时间线仍以明文可读。**

#### 6.9.2 三种取值模式

| 模式 | 状态 | 可用阶段 |
|---|---|---|
| **你自己填,不经过助手** | ✅ **P1–P5 唯一形态** | 现在 |
| **手动输入(带外控件)** | ⏸ P6 上线 · **永久保留** | P6 起 |
| 外部加密应用接口 | ⏸ 待应用建成,**前置为 P7** | 见 6.9.7 |

> **手动输入必须永久保留**(用户明确要求):外部应用可能未装、不可用、或你在另一台设备上。
> **它是唯一不依赖任何外部系统的路径。**

**★ 把这条从注释变成断言**:`provider` **不是** `secret.request` 的参数
(理由同 §6.3.1:参数可被不可信计划者操纵),而是**你在授权控件里当场选的**。
授权控件**永远**渲染 `manual` 按钮,其存在性是**编译期常量,不是配置项**。

**§10 否定用例**:`external` 已配置且健康时,授权控件仍必须渲染 `manual` 入口。

#### 6.9.3 记忆库里存什么

```
Thing "德国工资账户"
  secret_ref         : "bank.de.sparkasse-payroll.iban"   ← 句柄
  issuer             : "Sparkasse"          ← 结构化辨识字段
  last4              : "0000"               ← 让你认出是哪个账户的最小充分信息
  purpose_tag        : "salary"             ← 受控枚举,非自由文本
  sensitivity_domain : "S2"                 ← 强制
  (值不在记忆库中,任何层都没有)
```

**三条裁决:**

1. **`note` 自由文本字段取消**,改为上述结构化字段。理由:句柄不可辨识 → 你三个月后分不清
   `bank.de.a` 和 `bank.de.b` → **必然把值抄进 `note`**,而记忆面板的直接编辑是 §4.4.2 里
   `source_confidence=1.0` 的最高可信路径。**消除动机比堵路径有效。**
   若仍保留任何自由文本字段,**服务端强制过正则族并拒绝保存**。
2. **凭证元数据一律 `S2`**:登记表 · 携带 `secret_ref` 的实体 · 取用审计。
   排除出 `v_memory_nons2`,Qdrant 侧只入 `mem_s2`。
   理由:值被移走后,这些元数据**反而失去了原本跟着值一起获得的 S2 保护** ——
   **这是 D23 自己引入的新泄露面,不是旧的。**
3. 记忆面板上 `secret_ref` 条目渲染成显式徽章:「**值不在这里** · 取值方式:你自己填(当前)」。

#### 6.9.4 ★★ 凭证正则族是四点入口过滤器,不是 Gate 的一条规则

> **原文的失效点**:把正则族挂在 Memory Gate 上,而 Gate 是**写入时**才生效的 ——
> 那时 prompt 早就形成了,L1 摘要也照常生成。

**正则族**(`config/cred-patterns.toml`,受 §6.7.6 CFG-1 保护):

| 类别 | 模式 |
|---|---|
| `iban` | `[A-Z]{2}\d{2}[A-Z0-9]{11,30}` **+ mod-97 校验**(校验位滤掉绝大多数误报) |
| `tax_id_de` | Steuer-ID(11 位 + 校验)· Steuernummer(各州格式)—— **两个都叫「税号」,都要** |
| `card_pan` | 13–19 位 **+ Luhn** |
| `id_doc` | 德国身份证 / 护照号格式 |
| `secret_phrase` | 「密码是」`password is`「recovery key」「seed phrase」「助记词」+ 其后 N 字符 |
| `high_entropy` | 长度 ≥32 且 Shannon 熵 ≥3.5 的连续 token。**误报率高 → 只用于 E1/E4,不用于 E3 拒绝** |

**归一化前置(必须,否则语音通道命中率接近零)**:去空格 · 去 `-` `.` `/` · 中文数字→阿拉伯 · 全角→半角。**ASR 输出必过此步。**

**★ 五个强制点(缺一不可,与 §4.6.1 三层强制同构):**

| # | 位置 | 命中行为 |
|---|---|---|
| **E1** | **入口**:用户输入 → 组装 prompt **之前**。**在网关侧,不信任前端**(Open WebUI 是第三方前端) | **拦下本轮**:不发送、不落 L0、不记正文。提示「这一轮没有发送,也没有记录」+ 两个按钮:「删掉这段」/「这不是凭证,继续」。**「继续」记审计(只记类别,不记值)** |
| **E2** | **L1 压缩器**:输入侧 + 摘要落库前(两侧都挂) | 该轮**整体不进摘要**(不是脱敏后进)。理由:摘要器倾向保留「具体数字」这类它认为关键的信息 |
| **E3** | **Memory Gate**:候选 `body` **+ `provenance` 快照** | 拒绝写入,**不落盘**(见 6.9.8) |
| **E4** | **出境载荷**:已组装的 prompt 字符串,与 §4.6.1 渲染层**同一个点** | **fail-closed**。命中片段替换为 `<secret?>`,逐处裁决才能发送。**与来源无关** —— L1「你手打的问题文本」不构成豁免 |
| **E5** | `worklog/` 写入前 + 运行日志 filter + **pre-commit 钩子** | 拒绝并告警。理由:`00-docs/worklog/` **是 git 跟踪文件**,`.gitignore` 无排除项 —— 一次填表失败回显 + 一次 commit = 凭证进版本历史,**删不干净** |

> **★ E1 与 §4.6.2 的关系**:§4.6.2 说「不得声称记忆零外发是被证明的,无法阻止手动复制粘贴」。
> E1 不推翻这句 —— 它把「意外」变成「必须显式点确认的行为」。
> **能拦住意外,拦不住坚持。** 这个区别必须写清,不要让 E1 被理解成保证。

**★ S2 定级与拒绝是一族两用,不是二选一**(推翻原文「正则族**改作**此用」):

- 命中 → (a) E3 拒绝并提示登记;**且** (b) 若经任何路径已写入,强制 `sensitivity_domain='S2'`
- `sensitivity_domain` 列 **`NOT NULL` 且不设 DEFAULT** —— 忘记定级 = INSERT 失败 = **响亮**
  (§4.11.4「漏了 collection 句柄是响亮的」的应有延伸),而不是静默落进 `v_memory_nons2` 被手机读到
- 调用方声明的 `sensitivity_domain` 在正则命中时**一律被服务端覆写**(同 §4.4.2 对 `user_explicit` 的处理)

#### 6.9.6 授权粒度与预览

**每次使用都要授权,不做会话级。** 理由同 §12.4 铁律 3。

**★ 裁决「精确动作预览」与「模型看不到值」的冲突**(§12.4 vs 6.9.5 约束 2):

> **预览 = 掩码值 + 完整目标。**
> `DE89 •••• •••• •••• 0130 00` —— 掩码由 UI 层就地生成,**不进任何可序列化载荷**;
> **完整显示** `sink`(工具身份 · origin · 字段选择器),且 origin 由**执行器上报,模型不可写**。

**★ 授权控件版面强制**:系统生成、模型不可写的区域固定显示
`provider` · `ref` · `sink.origin` · 发起会话 · 发起时刻;
模型的 `intent` 只能出现在一个受限长度、标注「**以下文本来自助手,不可信**」的框里。

> 对照 §4.7.3:打扰提名这种低危通道已经上了模板锁,索要 IBAN 这种最高危通道反而留自由文本,是刺眼的不一致。

**★ 审批级别提升**:凭证类动作从「逐次确认」提升到 **§12.4 哈希绑定批准** ——
执行前复核 `(ref, sink)` 哈希。**哈希对 `secret_ref` 与 `sink` 取,不对值取;值不进计划文本。**

#### 6.9.7 ★★ 接口预留:完整契约(原文最大的洞在这里)

> **原文只定义了入参,没有定义返回值。** 按工具调用的默认语义,工具结果**无条件回到模型上下文** ——
> 也就是说,一个完全按 §6.9 实现、你完全按规矩操作(走控件、不碰对话框)的系统,
> **会在第一次真实使用时就把 IBAN 送进 prompt,而没有违反任何一条写下来的规则。**

```jsonc
// 请求 —— 模型可填的字段全部受约束
{
  "refs":        ["bank.de.sparkasse-payroll.iban"],  // ★ 数组:原子多值,同一次授权同一次兑换
                                                       //    (API key + secret 必须同时取、版本一致)
  "value_kind":  "string",                             // string | file | certificate | otp
                                                       // 后三者现为 not_provisioned,但槽位必须留
                                                       // (ELSTER 登录需 .pfx + 密码)
  "intent":      "fill_form",                          // ★ 受控枚举,取代自由文本 purpose
  "plan_hash":   "<§12.4 已批准计划的哈希>",
  "sink": {                                            // ★ 必填。取值与用值合成一次不可分割的批准
    "executor_id":    "browser@workstation",
    "target_kind":    "form_field",
    "target_locator": "<selector>",
    "origin":         "<执行器上报的实际已加载 origin,模型不可写>"
  },
  "request_id":  "<客户端生成,服务端去重>",            // ★ 幂等
  "timeout_ms":  30000,                                // ★ 必填
  "on_provider_unavailable": "fail"                    // ★ 唯一合法取值
}

// 返回 —— ★★ Schema 层禁止出现值
{
  "status":          "granted | denied | timeout | provider_error | cancelled",
  "fill_token":      "<一次性句柄,执行器侧兑换>",       // 兑换只发生在策略层/执行层进程内
  "max_redemptions": 1,                                 // ★ 重试走 TTL 内的第二次兑换,
  "ttl_ms":          15000,                             //    而不是缓存值(那是会话级授权改名)
  "sink_ack":        "<执行器回执的 origin 与字段>",
  "expires_at":      "<ISO8601>"
}
```

**★ 五条不可协商的 Schema 约束:**

1. **返回值不含值。** §10 否定用例:断言 `secret.request` 的任何返回路径都不含高熵字符串
2. **`provider` 不是请求字段**(6.9.2)
3. **`purpose` 自由文本取消**,改 `intent` 枚举 + `plan_hash`。理由:模型上下文里一旦有过凭证片段,
   它会自然写出 `purpose: "为 DE89... 的转账填表"`,而**审计表的保留期是不删**
4. **`fill_token` 在兑换点给目标参数打 `secret_bearing: true`**,任何可能接收它的参数强制
   `log_args: redact_marked`(记 `ref` + 位置,不记值)
5. **`on_provider_unavailable` 只允许 `fail`。** 回落手动只能由**你在失败提示上重新发起** ——
   否则这就是一个**可被注入按需召唤、文案由模型控制的索要凭证窗口**

**其余预留项:**

| 项 | 本期要做 |
|---|---|
| **命名规范** | 固定四段 `<domain>.<region>.<entity>.<field>`,`entity` 只允许 `[a-z0-9_-]`(**禁点号**),全小写。`entity` 用稳定标识,**不用 `main` 这类相对别名**(开第二个账户即歧义)。**★ ref 本身不得含机构名与账号尾号** —— 它们进登记表独立字段,标 S2 |
| **引用登记表** | `ref` · `value_kind` · `issuer` · `last4` · `purpose_tag` · `version` · **`provider_kind`** · **`provider_locator`**(不透明 JSON,预留给 1Password 的 `vault_id+item_uuid+field_label` / Bitwarden 的 `cipher_id`)· 创建时间 · **绝不含值**。登记表随 PostgreSQL 进 STATE 备份;`provider_locator` 属 S2 |
| **审计** | 记 `(ts, refs, intent, plan_hash, sink.origin, outcome)`。**「不记是否成功取到」删除** —— 它与 §12.3「失败可见」直接冲突,而其理由(怕反推值)不成立:成败只泄露「该 ref 是否存在」,而存在性本来就明文写在登记表里 |

| **`desktop_floor`** | ★**你设的「至少给桌面留多少」**。服务端设置项,跨会话持久,**不是逐请求参数** |
| **`vram_budget`** | **导出值**,不单独设置:`15.92 − desktop_floor − SAFETY_MARGIN(0.8)` |
| **准入白名单** | `component_id ∈ committed_resident_set ∪ permitted_on_demand_set` |
| **静态闸** | `Σpeak(申请后的 AI 驻留集合) ≤ vram_budget` |
| **动态闸** | `NVML 实测 free − 本次申请(peak) ≥ SAFETY_MARGIN(0.8 GiB)` |
| **余量核算** | ★**必须用组件的实际 peak 之和,不能用 `vram_budget`**。预算是上限不是占用 |

> **★ 为什么设「桌面预留」而不是「AI 上限」——两者数值等价,心智模型不等价。**
> D24 花了大篇幅纠正一个误解:**降 AI cap 腾不出一个字节**(cap 本来就不含桌面)。
> 这个错误在「桌面预留」这个单位下**不可能犯** —— 「提高桌面预留能给桌面留出显存」是对的。
> 且它与 A7 梯级表共用同一条式子(`上限 = 15.92 − P99 − 0.8`),推荐组合不必另发明。
>
> **UI 必须同时显示两个数**(它们是同一个滑块的两端):
> 「给桌面至少留 **3.5 GiB** ／ AI 最多可用 **11.62 GiB**」。

**`desktop_floor` 的三条规定(用户 2026-07-26 拍板)**

| | |
|---|---|
| **默认值** | ★ **6.6 GiB**(P1-A7 实测,2026-07-26)· 标记 **`calibrated: partial`** |
| ~~原默认 1.06~~ | 已作废 —— 那是**轻载**实测值,而 A7 证明日常工作负载是 **6.53 GiB**,差 6 倍 |
| **改它的审批级别** | **§12.4 哈希绑定批准** —— 与 §6.7.7「新增 rw 权限区域」同级 |
| **理由** | 它是**唯一能突破 Σpeak 上限的旋钮**,整个「防止上次勾多了」的保护强度由它决定 |

> **★ 必须写明的张力(不掩饰)**:默认 1.06 意味着第一次打开界面能勾到 **14.06** ——
> 包含一批桌面一忙就装不上的组合。**这道闸在默认状态下几乎不设防,
> 而那恰恰是它最该设防的时候**;同时哈希绑定批准又让调整它变贵。
>
> **处置**:默认值**不是**一个标定过的数,它是占位。
> `desktop_floor` 带一个 `calibrated: false` 标志,**预览第三段固定显示「未标定(A7 未测)」**;
> **A7 出结果后提示设一次真实值**,那一次改动同样走哈希绑定批准。
> 不加摩擦,但不假装它经过标定。
>
> **这条本身就是 D25 推翻条件 ① 的观察对象** —— 「勾完才发现桌面被挤」月度 > 2 次
> 就说明这个默认值选错了。
>
> **⚠ `cap` 这个词全文废止。** 不是美学问题:D24 已经把「cap」与「降它能腾显存」的误解
> 永久绑定在文档里,留着这个词等于给下一个读者留一个已知陷阱。

**★ 三层检查防的不是同一件事,不能合并**(这是 D25 从原「一个 cap 管一切」拆出来的):

| 检查 | 防什么 | 何时求值 |
|---|---|---|
| **准入白名单**(集合成员) | bug · 重复 spawn · 泄漏租约 · 未授权组件 | 每次租约申请 |
| **静态闸**(算术) | 「上次不小心勾多了」· 跨会话持久 · 给桌面留地方 | **提交时** 且 每次租约申请 |
| **动态闸**(实时) | 此刻装不下 · 桌面临时涨了 | 每次租约申请 |

> **为什么 bug 那一类必须靠白名单而不是靠闸**:闸是**算术**,可以被凑数凑过去;
> 白名单是**集合**,漏了会响亮报错。这是 §4.11.4「漏了 payload filter 是沉默的,
> 漏了 collection 句柄是响亮的」在显存侧的同一条道理。

**所有预算表一律用 `peak`。Broker 按 peak 发租约。**

#### 8.1.3 ★ 组件选择器(取代五档定义表)

**你直接勾选要装哪些组件,不选档位。** 勾选之和就是分配量 —— 中间没有一层需要你换算的抽象。

**为什么取消档位**(完整理由见 **D25**,这里只留一条最重要的):

> **档位表是 O(n) 维护,勾选是 O(1)。** 每加一个组件,五个档位的组成都要重新推导一遍,
> 而且每次都可能推错 —— v2.1 → v2.2 那两处算术错误(daily 漏算三个 CUDA context、
> 4B 的 KV 按参数量缩放)正是这么来的。加一个模型只该是加一行。

**第二条理由是穷举得出的**:模型 × 上下文 × 语音 × 视觉共 30 个组合,
**帕累托前沿 = 全部 30 个,零个被支配**。同价位存在能力剖面完全不同的多个非支配选择 ——
例如 peak **11.4** 有三个:`8b@16k`+`full` ／ `8b@16k`+`lite`+`vlm` ／ `4b@8k`+`full`+`vlm`。
**在一个零支配的前沿上钉三个点是武断的**,而且档位模型表达不了这种差别。

##### 互斥与依赖(UI 是单选组 + 复选项的混合,不是纯复选)

| 组 | 语义 | 成员 |
|---|---|---|
| **LLM** | **单选** | `4b@8k` `4b@16k` `8b@8k` `8b@16k` `8b@32k` |
| **语音** | **单选** | `speech.cpu` `speech.lite` `speech.full` |
| 视觉 | 可选 | `vlm.small` |
| **出图** | **按需槽,不是常驻** | `comfyui.sdxl` `comfyui.sdxl.lowvram` |

> `resident.assistant`(Vigil)**不出现在本界面** —— 它跑 CPU、恒为 0.0 显存、不持 GPU 租约。
> 它的开关在 §17,与显存无关。把 0.0 的东西放进显存界面只会让人以为它有代价。

##### 三段预览(缺一段就是在骗人)

```
已选组件            8b@16k 6.8 + speech.full 4.6              = 11.4   ← 估算,见下
你的桌面预留        desktop_floor 3.5  →  vram_budget 11.62
此刻实际可用        NVML free 14.86 − 0.8                     = 14.06
─────────────────────────────────────────────────────────────
可以确定 ✓          还能让桌面再涨 2.66 GiB 才会出问题
```

**★ 最后那一行是本界面存在的理由。** 只显示「装得下」是不够的 ——
桌面占用是**波动**的,用户需要知道自己离墙有多远,而不是知道此刻没撞墙。

##### 「确定」按钮的启用条件

```
Σpeak(已选)  ≤  min( vram_budget , NVML free − 0.8 )
```

**★ 撞到哪一边,提示必须不同 —— 合并成一句「显存不足」是有害的:**

| 撞到 | 提示 | 用户能怎么办 |
|---|---|---|
| **`vram_budget`** | 「桌面预留 3.5 GiB,AI 最多 11.62,当前选择 12.5,超 0.88」 | 取消组件,**或改桌面预留** |
| **实时可用** | 「此刻只有 10.4 可用(桌面正占 4.72)」 | **改预留没用** —— 关掉占显存的程序,或选小的 |

合并显示的后果:用户会去调预留,调完发现没用,因为撞的是物理墙。

##### 确定 = 一次事务

1. **点确定时重新求值,不用预览时的快照。** 「预览过、确定时不过」是必然会发生的 ——
   挑组件要花几十秒,期间桌面会变。
2. 预检不过 → **回到编辑态,不卸载任何东西**。
3. 装载中途失败 → 回滚到上一个成功集合;回滚也失败 → `DEGRADED_SAFE`。
4. **有任务在跑 → 弹提示**(见 §8.1.6,该规则的主语已从「降档」改为「变更驻留集合」)。

#### 8.1.5 Off 与完全 Off(电源轴 —— 不是档位)

> **★ D25 后的定位(用户 2026-07-26 拍板:二态)**
>
> | | 位置 | 理由 |
> |---|---|---|
> | **ON / OFF** | **主界面二态开关** | 日常动作 |
> | **完全 Off** | **托盘菜单**,不在主界面 | 它更像「**紧急全停**」而不是日常档位 —— 其**唯一真实用途是安全事件的紧急切断**(Off 已经是 0 显存,「省资源」在数字上不成立) |
>
> Off / 完全 Off **都不属于组件选择器**,它们是**电源轴**上的位置。
> 组件选择器管「装什么」(意图轴),总开关管「通不通电」(电源轴)。
> **不变式 I4 保证两轴不互相污染**:`power == off` 时 `actual` 清空,
> 但 `intended_resident_set` **不变** —— 一次 OFF 不会吞掉你的勾选,ON 回来按原样重装,不用重勾。

| | ON(已选组合) | **Off** | **完全 Off** |
|---|---|---|---|
| AI 侧 GPU | Σpeak(已选) | **0** | **0** |
| PostgreSQL / Qdrant | ✅ | ✅ | **❌ 停止** |
| 网关 / MEMORY 平面 | ✅ | ✅ | **❌ 停止** |
| **记忆双轨检索** | ✅ | **✅** | ❌ |
| 记忆写入 | ✅ 即时 | ⚠ **入队延后**(Gate 无本地模型,**绝不送云**) | ❌ |
| `escalate.cloud` | ✅ L2 | ✅ L2 | ❌ |
| **云端基于你的记忆回答** | ❌ | **❌ 永远不做** | ❌ |
| Vigil | ✅ CPU | **✅ CPU 零降级** | ❌ |
| **记忆库文件本身** | 可读 | 可读 | **仍可读** ⚠ |

> **Off 是「AI 不再用显卡,但它还记得你」;完全 Off 是「所有服务停止」。**

##### ⚠ D22 让「完全 Off」的含义变窄了(必须写清)

原表这一行是「`memory.vhdx` 挂载 / 挂载 / **卸载**」,那时完全 Off 意味着**记忆库上锁**。
D22 取消加密卷之后,**没有可以卸载的东西了** —— 记忆库是普通文件夹,始终可读。

因此完全 Off 的实际作用缩小为:

| 还能防的 | 不再能防的 |
|---|---|
| 网络侧访问(网关停了) | **任何能登录这台机器的人直接读文件夹** |
| 服务被利用(进程都停了) | 硬盘被取走 |

**完全 Off 仍有意义**(「我怀疑网络侧出事了,先全停」),
但**它不再是「记忆库上锁」** —— 这个说法在 D22 之后是假的,不得保留。

#### 8.1.6 切换与中断

**硬规则:一律先卸后装。** 卸载后**轮询 NVML 直到 free 回升到预期 ±0.2 GiB**(超时 10 s 报 `vram_not_reclaimed`)。

**`requires_swap` 必须有事务语义**:
1. 进入前做**整组预检**,不过直接拒绝、**不卸任何东西**
2. 卸载后若任一新组件加载失败 → 尝试回滚
3. 回滚失败 → `DEGRADED_SAFE`(等价 Off + 托盘红 + 不可忽略通知)

**★ 变更驻留集合时有任务在跑 → 弹提示让你选**「优雅中断」或「等它跑完」。先给 **5 秒排空窗口**。

> **★ 主语已由「降档」改为「变更驻留集合」(D25)。** 原文的主语是档位,
> 档位取消后这条安全规则会**字面失效** —— 而它保护的是「一键套用推荐组合」这条
> 最容易静默杀掉运行中任务的路径。**先搬走并改主语,再删章节**,顺序不能反。

`blocking_set = {USER_BLOCKING, USER_ASYNC, RESIDENT_TASKED}`。
**Vigil 的空闲观察循环不在集合内** —— 它跑 CPU、不持 GPU 租约,**天然不在,不需要特例代码**。

**ComfyUI 中断语义**:**不保存 latent,重跑不续跑**(ComfyUI 不支持跨进程恢复采样器状态)。
**批量 JOB 按产物单元**:已完成的 N 张正常入 draft 池;正在采样的第 N+1 张标 `partial=true, steps_done=18/30`;记录 `completed_units` / `next_unit`。弹窗给可验证的具体数字:

```
已完成的 12 张会保留;正在出的第 13 张作废(已算 18/30 步,重跑约 9 秒);
剩余 8 张可在改选更大的组合后从第 13 张继续。
```

**MODEL 平面截断的输出不进 Memory Gate**(半句话是误记源)。

**不用「记住我的选择」复选框** —— §12.4 铁律 3:批准的是具体计划,不是一类操作。替代:设置项 `resident_change.default_action`(**冷静时定的,不是着急时点的**)。

#### 8.1.7 「不做自动触发」的精确边界

| 允许 | 禁止 |
|---|---|
| 自动**拒绝租约** | 自动改变**驻留集合** |
| 自动**通知**「疑似过订,建议改选更小的组合」 | 自动卸载/换装 |
| 自动驱逐 `WARM` / `MAINTENANCE` 类租约 | 中断 `blocking_set` 成员 |

> **★ D10 的「不做自动触发」完整存活,只是主语从「档位」扩到「驻留集合」。**
> 这是 D10 里唯一不随档位概念一起作废的部分 —— D25 点名保留它。

##### 四个集合(不变式的锚点;不先定义,不变式就无从求值)

| 集合 | 是什么 | 谁能写 |
|---|---|---|
| `intended_resident_set` | 你在主机面板勾选并点了确定的常驻集合 | **只有主机变更面** |
| `committed_resident_set` | Broker 事务成功后写入的实际目标 | Broker(提交成功时 `committed := intended`) |
| `actual_resident_set` | 租约账本 + NVML 反映的**真实**驻留 | 运行时 |
| `permitted_on_demand_set` | 授权「允许在需要时申请」的按需槽 | 只有主机变更面 |

> `permitted_on_demand` 与 `intended` **是两个字段,不合并** ——
> 合并会让 `intended` 里出现永远不参与 I2 判定的成员,三元组语义就脏了。

##### 不变式

**I1**(一字不改):自动机制只能拒绝新租约,**永不撤销已授租约**;只有用户显式动作才能撤销。

**I2 · 该在的都在**(作用域限 `residency_class = resident`):
```
state == READY   ⟹   actual_resident_set == committed_resident_set
```
不等时 `state` 必须是 `STARTING` / `RECONCILING` / `DEGRADED_SAFE` 之一,且 **UI 常驻显示差异**。

> **保留蕴含形态是关键**:`DEGRADED_SAFE` 不是 `READY`,前件为假,I2 自动成立 ——
> 不存在「永久违反不变式、告警无法消解」的状态,也就不需要让系统自动改写锚点
> (那恰好会违反 D10 存活下来的「不做自动触发」)。写成双条件就会造出那个两难。

**I3 · 在的都该在**(★ 新增。**无状态前件,任何状态下恒成立**):
```
∀ c ∈ actual_resident_set ∪ actual_transient_set :
      c ∈ committed_resident_set ∪ permitted_on_demand_set
```
违反即 §9.3 告警。**这条才是接住「某个 bug 装了不该装的」的那一条。**

> 原 I2 的「严格等于」把 I2 与 I3 压成一句 —— 这正是它一取消档位就**同时**崩掉两件事的原因。

**I4 · 电源轴与意图轴分离**(★ 新增):
```
power == off   ⟹   actual_resident_set == ∅   ∧   intended_resident_set 不变
```
**ON/OFF 总开关不写 `intended`。** 否则一次 OFF 就吞掉你的勾选,等价于系统改写了用户配置。
ON 回来时按 `intended` 重新装载,**不需要重勾**。

##### ★ 检测器(没有检测器的不变式等于没有)

`RECONCILE_WATCH`:周期比对 `actual` vs `committed`,**只报告不修复**(修复即违反「不做自动触发」)。
§9.3 告警最小集新增「**常驻组件掉线**」。

> **这是原 I2 最大的实际缺陷**:全文今天只有 §17.3 的 W0 讲 Vigil 托盘进程存活,
> **没有任何机制能发现「3 个装了 2 个却仍报 READY」** —— 而 I2 本来就是为禁止这件事写的。

##### 状态机(原文只有 READY / DEGRADED_SAFE 两个点)

```
STARTING ──▶ READY ──▶ STAGING ──▶ PRECHECK ──▶ APPLYING ──▶ READY
   │           │          ▲            │
   │           │          └────────────┘  预检不过:回编辑态,不卸任何东西
   │           ▼
   └────▶ RECONCILING ──▶ DEGRADED_SAFE(回滚失败终态,等价 Off)
```

- `STARTING`:开机装载中,`actual ⊊ committed`。**不红托盘**(那是正常过程),有超时 → `RECONCILING`
- `RECONCILING`:worker 掉线 / 装载失败。**必须继续按 `actual_resident_set` 提供服务**,
  复用 §8.1.4 既有的 `contract_changed`(默认放行 + 回带真实契约 + `X-LocalAI-Contract` 头)。
  > 否则一个语音 worker 掉线会连带把仍然可用的 LLM 也判成不可用,**比故障本身更糟**。

##### ★ 失败落点(原文完全没有定义 —— D24 排查带出)

五件事叠加:A7 的 3.5 是 **P99**(1% 采样点更高)· 真实缓冲可能只剩零点几 GiB ·
I1 不撤已授租约 · KV **启动即预分配全量** · sysmem fallback 已关闭。
结果是桌面尖峰时,**先撞上分配失败的很可能是 Chrome / UE5,而不是 AI 侧** —— 与设计意图相反。

**规定**:驱逐 `WARM` / `MAINTENANCE` 后仍不足时,**失败落在 AI 侧**(拒新申请 / `DEGRADED_SAFE`),
**不得由桌面承担分配失败**。

> **诚实边界**:这条是**策略**,不是保证。WDDM **不按优先级驱逐** ——
> 已经发生的驱逐落在谁头上,本项目控制不了。本文档不得声称档位/预算能保证桌面不被挤。

**「检测独占全屏游戏」这条特例删除**,替换为通用规则:`free_vram` 1 Hz 采样,5 s 内降幅 > 1.0 GiB → `admission_guard`;全屏进程名**仅用于生成告知文案,不产生策略动作**。理由:这台机器上比游戏更常见的显存大户是 UE5 与多标签 Chrome。

### 8.4 存储生命周期与 GC

| 根 | 可自动删 | 策略 |
|---|---|---|
| CODE | ❌ | git 管理 |
| **STATE** | ❌ | **只归档不删。记忆库与交易账本进白名单 + 独立备份链** |
| MODELS | 🟡 | **引用计数**,非 LRU;只提示不自动删 |
| ASSETS | ✅ | 三池分级 |
| CACHE | ✅ | 纯 LRU/TTL — **但 `cache/hf` 例外,见 §8.4.1** |

**产物三池**:`draft`(TTL 后回收,永久保留 Asset Spec + seed)· `adopted`(永久 + 备份)· `exported`(只留元数据引用)

> **可复现性把「存储」变成了「缓存」。** 删掉一张 2MB 草稿只损失几 KB 记录。

**水位线**:75% 提示 · 85% 清 CACHE · 92% 回收超期 draft · 95% 拒发新 JOB 租约。

**回收器要求比人工整理更严**(它无人按确认键):永不 `delete` 只移隔离区 · 每次产出清单与释放报告 · 除 CACHE 外先报告后执行 · **备份目录对回收器不可见**。

**第一个月只观察不清理。**

#### 8.4.1 `cache/hf` 例外

`cache/hf` 语义上属 CACHE 根,但**不参与自动清理**。

| | 一般缓存 | `cache/hf` |
|---|---|---|
| 体积 | 几 GB | 十几到几十 GB |
| 重建耗时 | 秒到分钟 | **实测 ~11 MB/s,17GB 约 27 分钟** |
| 能否重建 | 一定能 | **不一定** —— 模型可能下架或改许可 |

> **分界不该只看「能不能重建」,还要看「重建的代价」。** 一个能重建但要花半小时且可能失败的东西,不该被静默删除。

| ASSETS · draft/exported | Asset Spec 可重放 |
| CACHE | 可随时清空 |
| **STATE · 记忆库** | **不可重建。没有任何来源可以重放。** |

#### 8.5.2 单轨:手动全量到移动盘

| 目标 | 频率 | 加密 | 保留 |
|---|---|---|---|
| 移动固态 G:(Disk 2,独立物理盘) | **你插盘时手动触发** | **不加密**(D21) | 12 代 |

> **2026-07-26 决议 D17(修订)**:用户明确决定**不做每日自动到 C: 的增量备份**,只保留手动到移动盘。
> 设计阶段曾提出自动增量方案(公钥加密到 C:),**已作废**。

**★ 但「送达度提醒」保留,而且在纯手动模式下更重要。**

每台设备(含手机)每次连上时读一个只读状态端点,比对上次成功备份时间:

```
6 天前  → 托盘角标
14 天前 → 进日报(§4.7.5 L1)
30 天前 → 确定性 L4 白名单,强提醒
```

它不需要自动备份存在,只需要知道「上次备份是什么时候」。**这是纯手动模式下唯一能对抗「取决于你是否记得」的低成本机制。**

##### ⚠ 手动模式必须明确接受的代价

| 事实 | 后果 |
|---|---|
| 记忆库(P3a 起)**每天都在变** | 一周不备就可能丢一周的记忆 |
| **Vigil 上线会把日变更量再提高一个量级** | 间隔越长丢得越多 |
| 移动盘不常插 | 备份间隔取决于你的习惯,不取决于任何机制 |
| 唯一副本在工作站的 Disk 1 上 | 而 code 根(E:)与数据根(D:)**同在 Disk 1** —— 该盘故障时两者一起没 |

**推翻条件**(写进 D17):
- **实际备份间隔中位数连续 4 周 > 14 天**,或
- 发生过一次「想恢复却发现备份太旧」

→ 重新评估自动备份。届时若恢复自动方案,**必须用公钥加密**:一个无人值守的任务必须能自己取到密钥,而任何本地可读的对称密钥都能被同用户的进程取到 ——「工作站被入侵时备份仍然安全」这句话在对称密钥下是假的。

#### 8.5.4 六条铁律(铁律 1 于 2026-07-26 修订)

1. **~~备份必须加密~~ → 全链路不加密(D21 + D22)。**

   `backup.ps1` 由 `paths.toml` 的 `[backup].require_encryption` 控制,当前为 `false`。

   > **★ 必须写清、不得含糊的一句话:**
   >
   > **记忆库在工作站磁盘上是明文,在备份盘上也是明文。**
   > 拿到任一者的人可以直接读取全部记忆 —— 家人关系、偏好、习惯、所有对话事实。
   >
   > D22 之前曾有一条「备份 `.vhdx` 文件本身则介质上仍是密文」的性质。
   > **该性质随 D22 一并失效** —— 没有加密卷,就没有文件内部的加密。

2. **~~恢复密钥离线保管~~ → 不适用(D22 后无密钥)。**

   > 这条铁律的消失是 D22 的**收益**而非疏漏:
   > §15 原本把「BitLocker 恢复密钥丢失 = 记忆库永久不可读」列为**高**风险,
   > 而对一台家用单人机器,密钥丢失的概率高于定向窃取。**D22 消除了这个风险。**
   > 代价写在铁律 1,收益写在这里,两边都不抹掉。
3. **恢复演练** —— **没演练过的备份不算备份**。P3a 上线前跑通一次完整恢复,此后每季度一次
4. **备份不可由助理自身的文件工具触及**(进 §6.7.4 硬禁止清单)
5. **备份失败必须告警**(进 §4.7.6 确定性 L4 白名单)
6. **校验清单必须可移植**:无 BOM · LF · 正斜杠 · GNU `sha256sum` 兼容格式。灾难恢复的典型场景就是 Windows 起不来 —— 清单只能被 PowerShell 读,等于把恢复路径限死在「Windows 还能启动」这个前提上

#### 8.5.5 ⚠ 仍未解决:活数据库怎么备才能真的恢复出来

> **D22 让这一节简单了一半,但没有让它消失。**

**已因 D22 消失的问题**:VHDX 挂载态被占用、`.vhdx` 复制到 exFAT 时的稀疏文件膨胀、
备份前后要挂载/卸载 —— **这些全都不存在了。** 记忆库是普通文件夹,直接 robocopy 即可。

**仍然存在、且与加密无关的问题:**

> 对一个**正在运行**的 PostgreSQL 做文件级复制,得到的是**不一致快照**。
> 恢复出来的数据库可能无法启动,或丢掉最近的事务。

这是数据库的固有性质,跟加不加密、放不放 VHDX 都没关系。而它属于
「**备份看起来成功了,但需要时恢复不出来**」—— 正是铁律 3 要防的情形。

**标准解法(简单且成熟,P3a 实现时采用):**

| 组件 | 做法 | 说明 |
|---|---|---|
| PostgreSQL | **`pg_dump`** 逻辑备份 | 单文件输出,不用停服,恢复用 `pg_restore`。2–10 GB 的库通常几分钟 |
| Qdrant | **snapshot API** | Qdrant 自带,生成一致的快照文件 |
| 其余 state | 直接 robocopy | 票据 · 日志 · 隔离区(已排除) |

> **不要用「停服 + 文件复制」** —— 它需要备份脚本去停止/启动服务,多两个会失败的步骤,
> 而且用户会因为「备份还要停服」而干脆不备。`pg_dump` 不用停服。

**待 P3a 落实**:`backup.ps1` 增加 PG 与 Qdrant 的导出步骤。
**在此之前,`backup.ps1` 对记忆库的备份能力仍未经验证** —— 但因为记忆库要到 P3a 才存在,
这不构成当前阻塞。

## 9. 可观测性与日志

### 9.1 三类记录

| 类 | 记什么 | 存哪 | 保留 |
|---|---|---|---|
| 运行日志 | 元数据:时间 · 别名 · token · 延迟 · 显存 · 成本 · 工具名 | `{state}/logs/` | 90 天 |
| 审计日志 | 谁对什么做了什么 · 批准链 · 哈希 · 回执 | PostgreSQL | **不删** |
| 指标 | 显存/磁盘水位 · 任务时长 · 失败率 · API 累计花费 | 时序表 | 1 年 |
| **区域访问** | Vigil 与主助手读了哪些区域(含 `rel`) | `{state}/logs/zones/` | 30 天 |

### 9.2 ★ 隐私规则(v2.2 收紧)

```
永远记录:元数据
工具调用的**结果**:默认只记类型、字节数与 sha256,**不记正文**
默认不记录:对话正文、语音原始转写
永不记录:记忆库内容
按需开启:单会话显式开关 + 短 TTL(D22 后无加密可用,TTL 是唯一约束)
eval 语料:显式「捐赠本轮」按钮采集,非默认全量抓取
```

> **审查 P-2**:v2.1 的「永远记录工具调用参数与结果」会把文件正文写进明文日志。

工具注册表每个工具加两个字段:`log_result: none | digest | full` 与
**`log_args: none | schema_only | redact_marked | full`**。
**凡具备读取能力的工具默认 `log_result: none`**;设为 `full` 必须在 `DECISIONS.md` 留条目。

> **★ 为什么必须有 `log_args`**:`log_result` 只管**结果**,而带值的从来是**下一个**工具的**参数**。
> 凭证工具强制 `log_args: schema_only`;任何可能接收 `fill_token` 的参数强制 `redact_marked`。

**★ 原有的「区域访问日志进加密卷是 §6.7 上线的前置条件」已随 D22 取消。**

那条前置条件在 D22 之后**永远无法满足**(没有加密卷了),留着就是一条系统不可能执行的规则。
裁决:**正常记录 `rel`,不做削减**。理由:

> **日志不可能比它记录的对象更敏感。**
> 记忆库本身已经是明文躺在同一块盘上,再去保护「谁读了哪个文件」的访问日志,是安全剧场。
> 真正该做的是 §6.8 的账户隔离 —— 它同时保护记忆库和它的日志。

保留 30 天上限与 §6.7.4 硬禁止清单里的 `{state}\**`(Vigil 与主助手都读不到自己的访问日志)。

## 10. 测试策略

| 组件 | 风险 | 最低要求 |
|---|---|---|
| **文件回收器 / GC** | **最高** — 无人按确认键的自动文件整理器 | 单元测试 + **干跑模式** + 隔离区可恢复性测试 |

| **出境闸门** | 最高 | 断言覆盖 **str 拼接 / f-string / 模板渲染 / 日志格式化** 四种取值方式 |

| **打扰评分** | 高 | 注入用例:构造带恶意 deadline 的文件,断言最高只能到 L1 |

## 12. 执行协议

### 12.1 记录协议

| 文件 | 回答 | 更新时机 |
|---|---|---|
| `STATE.md` | **现在在哪** | 每个节点结束;中断前 |

| `worklog/YYYY-MM.md` | **做了什么、测出什么** | 每次实作或实测 |

`DECISIONS.md` 条目格式:背景 / 选项 / 决定 / 理由 / 代价与已知风险 / **推翻条件**。

> **「推翻条件」是本格式里最重要的字段。** 半年后你需要知道的不是「当时决定了什么」,而是「这个决定现在还成不成立」。
> **★ 不得把新决定伪装成旧决定的延续** —— 那恰好绕过了这个字段。

### 12.2 节点循环

```
1. 读 STATE.md → 2. 做一件事 → 3. 写 worklog → 4. 若有不易反悔的选择则写 DECISIONS
→ 5. 更新 STATE.md → 6. 若跨阶段则对照验收标准逐条确认
```

> **不更新 `STATE.md` 就不算做完。**

### 12.3 首轮门禁

| 门禁 | 说明 |
|---|---|
| **路径合规** | 配置全部来自 `paths.toml` |
| **显存申报** | 声明峰值;P4 后走 Broker 租约 |
| **失败可见** | **不静默降级** |
| **可回退** | 知道怎么关、怎么恢复 |
| **数据边界** | 能读什么、能写什么;出境须过闸门 |

### 12.4 审批规则

| 级别 | 适用 | 机制 |
|---|---|---|
| **自动** | 只读、可重放、无外部后果 | 事后可查 |
| **逐次确认** | 写文件、点击提交类控件、单次出境 | 执行前展示**精确动作预览** |
| **哈希绑定批准** | 批量文件操作 · GC 回收 · **L4 写入** · 交易提案 · 新增 rw 区域 | 计划哈希绑定 → 批准 → **执行前复核哈希** → 执行 → 回执 |

**三条铁律:** 永不 `delete` 只移隔离区 · 除 CACHE 外先报告后执行 · **批准的是具体计划,不是一类操作**。

## 17. ★ 常驻清醒助手 Vigil

### 17.1 它是什么

| 维度 | 定义 |
|---|---|
| Agent id | `vigil` |
| 能力别名 | `assistant.resident`(唯一) |
| 权限档位 | `resident-observer`(最低) |
| 运行时 | **CPU 独立进程**,llama.cpp,IDLE 优先级 |
| 模型 | Qwen3-1.7B Q4_K_M(备选 Qwen2.5-1.5B)· **不得选 4B 级** |
| 上下文 | **2048,硬上限**;前缀缓存是硬性要求 |
| **GPU 占用** | **0 MiB。硬断言** |
| 内存 RSS | ≈ 1.87 GB(估算待实测) |
| 工具池 | **只读三件套**:`fs.stat` / `fs.read_head`(≤4 KB,白名单内)/ `embed.query`。**无写、无删、无网、无进程、无剪贴板** |
| 记忆读 | **只有** `mem.exists`(布尔)与 `vigil_context` 投影(用户逐条勾选,≤50 条) |
| 记忆写 | **只能 INSERT 到 `vigil_observations`**。不能写 L0–L4 任何一层 |
| 出境 | **L0,永久。配置层不接受其他取值,代码里不存在通往云的路径** |
| 会话 | 单次脉冲 = 单个会话,结束即销毁 |

### 17.2 它不是什么

- **不是屏幕监控。** 它**读文件,不看屏幕**。任何未来版本引入屏幕采集必须另开一章、另走审批
- **不是记忆写入者。** `vigil_observations` 不在 L0–L4 之内。进入 L2/L3 必经:你点开交接单 → 主助手接手 → **主助手重读证据** → Memory Gate → 写入并记来源
- **不是打分者。** 模型只填受约束的槽,总分由它读不到的确定性公式合成
- **不占显存。** 组件表里它是恒为 **0.0** 的一行,且**不出现在选择器界面上**(把 0.0 的东西放进显存界面只会让人以为它有代价)
- **不持 GPU 租约**,因此天然不在「运行中任务」集合内 —— **不需要任何特例代码**

### 17.3 「清醒」的可验收定义

| 层 | 是什么 | 恒真? |
|---|---|---|
| W0 进程存活 | 托盘进程、事件循环、DB 连接 | ✅(除完全 Off) |
| W1 事件捕获 | 文件变化进持久队列,一条不漏 | ✅(除完全 Off) |
| W2 模型驻留 | 权重已加载 | 🟡 按开关态 |
| W3 持续算力 | 真的在跑推理 | ❌ 只有脉冲 |

> **清醒 = W0 + W1 恒真。清醒的本质是「不漏事」,不是「一直在想事」。**
> **文档必须写「除完全 Off 外,无时无刻清醒」** —— 不留一句字面上不成立的承诺。

| # | 判据 | 阈值 |
|---|---|---|
| A-1 | 原始事件落进持久队列 | **< 1 s** |
| A-1b | change-set 成型(15 s 去抖 + 60 s 合并) | **≤ 90 s** |
| A-2 | 关机/休眠期间的变更,开机后由 T0 补扫产出 | **≤ 120 s** |
| A-3 | 状态可查(今日脉冲/CPU 用时/待处理/上次补扫) | 恒可查 |
| A-4 | watcher 缓冲溢出必须告警 + 立即补扫,**不静默丢事件** | 恒成立 |

### 17.4 四层漏斗

> **功耗低不是因为模型小,是因为绝大多数事件根本不进模型。**

```
文件系统事件
 ↓ 层0 授权闸(0 token):白名单∩¬黑名单 → 扩展名/大小/深度 → 去抖15s → 合并60s   过滤 ~70%
 ↓ 层1 特征提取(0 token):{root,rel} · size · mtime · sha256 · 首4KB · 结构化diff  过滤 ~20%
 ↓ 层2 语义预筛(CPU embedding,0 LLM token):bge-m3 复用,余弦 < 0.35 丢弃         过滤 ~7%
 ↓ 层3 LLM 脉冲(CPU 1.7B):受约束槽,≤160 token,GBNF 强制 JSON                  ≈3%
 ↓ 层4 打扰评分(§4.7,纯代码)+ 交接单
```

**必须自带的编译产物排除模式**(否则任何真实工程目录一加进白名单就打爆配额):

```
**/Intermediate/**  **/Saved/**  **/DerivedDataCache/**  **/Binaries/**
**/node_modules/**  **/.venv/**  **/__pycache__/**  **/target/**  **/dist/**
```

### 17.5 节奏与配额

| 触发 | 周期 | 调 LLM |
|---|---|---|
| T0 补扫 | 启动 / watcher 溢出 / 休眠恢复 | ❌ |
| E 事件脉冲 | 去抖 15 s,合并 60 s | 🟡 仅过层 2 |
| T1 轻扫描 | 每 10 分钟,纯 stat | ❌ |
| T2 小时汇总 | 每 60 分钟,**队列为空直接跳过** | 🟡 |

| T4 周终 | 每周日 22:10 | ✅ |

**日预算(估算,待 P1-E5 实测)**:≈29 次脉冲 · ≈45K token · ≈6 分钟 wall clock · ≈**2088 核心秒** · < 8 Wh · **0 MiB 显存**。

**配额**:`cpu_core_seconds_per_day = 5000`(**必须高于日均 2088**,否则正常使用日就会 halt,几天后你会把配额调到无穷大或直接关掉);`pulses_per_hour = 12`;配额告警按同一原因 24h 内只报一次折叠。

### 17.6 项目状态投影(而非读原文)

Vigil 对 `{code}/00-docs` **只有元数据级权限**。项目状态经编排器每日 03:00 生成的结构化只读投影获取:

```
project_state_projection
  phase          : "P1"
  next_steps[]   : ["P1 基准测试", ...]     ← 纯字符串,≤3 条
  blockers[]     : ["活数据库备份方式待定"]
  active_topics[]: [{id, name}]
  generated_at   : ISO8601
```

**原始 markdown 永不进 Vigil 的 prompt。** 这同时消解**自指循环**(它读不到 DECISIONS.md 的「推翻条件」原文,那种句子可能被当作可执行指令)与**注入**(投影是纯字段,无自由文本)。

### 17.7 交接单(唯一输出形式)

Vigil 不直接对你说话,它产出**交接单**:

1. **交接会话不继承你当前的档位权限。** 强制挂载只读工具池(`fs.read` / `mem.search`),无写、无执行、无网。写权限需要你**看过证据之后**发起**第二次、独立的**动作
2. **`evidence` 原文默认只渲染到 UI,不进模型上下文。** 主助手确需读原文时,走一个**禁用全部工具调用**的只读子会话做结构化提取
3. **UI 上证据在上、Vigil 的说法在下**,并标注「不可信来源的转述」

### 17.8 独立开关

| 态 | W0 | W1 | W2 | 说明 |
|---|---|---|---|---|
| `on` | ✅ | ✅ | ✅ | 完整 |
