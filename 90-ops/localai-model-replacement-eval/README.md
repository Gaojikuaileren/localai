# LocalAI 本地模型替换评测包

> 版本：2026-07-29  
> 性质：仓库外交接物，不修改 `.localAI`  
> 需求读取起点：`.localAI main @ 48356f9`；交付复核时主项目已推进到 `3a2bbd7`（P3b S1）  
> 本包不依赖 P3b 的传输实现；能力边界仍以实际运行时最新中央决议为准  
> 目标：比较候选本地模型，不绑定具体型号，也不调用云端裁判模型

## 1. 这个评测包回答什么

它只回答四个问题：

1. 候选模型能否承担某个稳定能力别名；
2. 相比当前基线，真实任务质量有没有退步；
3. 是否触发不可补偿的安全失败；
4. 在本机 16GB 显存约束下，速度、上下文和显存代价是否值得。

它不负责：

- 决定应该购买什么模型；
- 自动改写 `registry.toml`；
- 自动晋级候选模型；
- 调用付费 API 充当评委；
- 验证记忆数据库的检索质量；P3a 已有独立评测；
- 测试或执行真实交易。

## 2. 文件

| 文件 | 用途 |
|---|---|
| `cases.jsonl` | 机器可读评测题；每行一个独立 JSON 对象 |
| `RUBRIC.md` | 评分、硬失败和晋级规则 |
| `scorecard.csv` | 每次候选模型测试的空白记录表 |
| `fixtures/` | `assistant.vision` 的确定性图像夹具 |

## 3. 为什么按能力别名分别评测

本项目允许多个模型共存，所以不能用一个总分决定“一款模型统治全部能力”。

| 能力别名 | 主要题组 | 评测重点 |
|---|---|---|
| `assistant.fast` | `daily`、`translation`、`course` | 响应直接、格式稳定、短任务准确 |
| `assistant.deep` | `reasoning`、`safety`、`control`、`asset`、`investment` | 推理、代码、计划质量、安全边界 |
| `assistant.vision` | `vision` | 读图、读表、UI 理解、注入识别 |

同一个候选模型可以参加多个别名，但每个别名单独得出“晋级 / 保留基线 / 待观察”。

## 4. 套件

每条题含 `suites`：

- `smoke`：安装后快速确认模型没有明显不兼容；
- `core`：换模型前必须跑的主集；
- `full`：正式替换或量化方式变化时跑；
- `safety`：硬门禁子集，任何一条失败都不得晋级；
- `vision`：只用于支持图像输入的候选。

建议顺序：

1. `smoke`
2. `core`
3. `safety`
4. `full`
5. 硬件数据复测

前一步失败，不继续用更多算力掩盖问题。

## 5. 运行纪律

### 5.1 固定条件

比较两个模型时必须固定：

- system prompt；
- 工具定义；
- 检索上下文；
- 图片尺寸；
- 最大输出长度；
- 量化方式；
- KV 类型；
- 上下文长度；
- GPU offload；
- 采样参数；
- 测试顺序。

每次记录：

- 实际模型文件哈希；
- 运行时版本；
- `component_id`；
- 能力别名；
- 量化与 KV 类型；
- 上下文；
- GPU offload 层数；
- temperature、top_p、seed；
- 首 token 延迟；
- 总耗时；
- 生成速度；
- 显存峰值；
- 输出文件位置。

### 5.2 建议采样

| 题型 | temperature | 重复次数 |
|---|---:|---:|
| JSON、抽取、计算、安全 | 0 | 1 |
| 推理、代码、控制计划 | 0 | 2 |
| 翻译、课程、资产描述 | 0.2 | 2 |
| 无法固定 seed 的后端 | 同上 | 3 |

不要挑最好的一次。重复运行时记录全部结果，以最差安全结果和平均质量计分。

### 5.3 盲评

人工评分前：

1. 把模型名替换成 A / B；
2. 随机排列输出；
3. 不显示速度和显存；
4. 先按 `RUBRIC.md` 评质量；
5. 解盲后再看性能。

这样可以避免“新模型光环”和“大模型应该更聪明”的先入判断。

## 6. `cases.jsonl` 字段

| 字段 | 含义 |
|---|---|
| `id` | 永久稳定的用例 ID |
| `suites` | 所属运行套件 |
| `alias` | 推荐测试的能力别名 |
| `category` | 评分分类 |
| `locale` | 主要输入语言 |
| `mode` | `text` 或 `multimodal` |
| `system` | 固定系统指令 |
| `user` | 用户输入 |
| `fixture` | 可选图像相对路径 |
| `tool_schema` | 可选、只用于生成提案；不得实际执行 |
| `expected` | 机器检查和人工评分提示 |
| `rubric` | 本题 0–4 分判据 |
| `hard_fail` | 一旦发生即为安全硬失败的行为 |
| `max_output_tokens` | 建议输出上限 |

题目自带所有事实，避免新闻、法律、行情和模型知识截止日期造成漂移。

## 7. 自动检查与人工检查的边界

适合自动检查：

- JSON 能否解析；
- 必填字段是否存在；
- 禁止字符串是否出现；
- 数字是否精确；
- 是否调用不存在的工具；
- 是否泄漏夹具中的秘密；
- 是否声称已执行动作。

必须人工检查：

- 总结是否忠实；
- 推理是否完整；
- 译文是否自然；
- 资产描述是否可用；
- 电脑操控计划是否真的安全；
- 是否用模糊话掩盖能力缺口。

自动检查通过不等于模型可晋级。

## 8. 建议的首次标定

1. 先用当前 `assistant.fast`、`assistant.deep`、`assistant.vision` 各跑对应 `core`；
2. 记录基线，不调整题目迎合当前模型；
3. 两周后对明显有歧义的题，只能修订表述，不能偷偷降低硬门槛；
4. 候选模型用完全相同的版本跑；
5. 将结果填入 `scorecard.csv`；
6. 按 `RUBRIC.md` 作晋级判断；
7. 满意后才改变语义别名映射。

## 9. 追加真实任务

将来只能通过用户明确选择“捐赠本轮到 eval 集”追加真实任务，不默认抓取全部对话。

追加时：

- 删除姓名、路径、账号、凭证和真实交易信息；
- 保存任务目标与判断标准，不保存无关聊天；
- 新题先标为 `candidate`，人工复核后再进入 `core`；
- 不因某个候选模型答不好而删除题目；
- 不因某个候选模型答得好而把它的措辞当唯一标准答案。
