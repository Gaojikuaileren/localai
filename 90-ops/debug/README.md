# 调试工具箱 — **产品化时整个目录删掉即可**

> 用户要求(2026-08-05):做一套 debug 工具,**后期产品化的时候可以一键移除**。

## 一键移除

```bash
git rm -r 90-ops/debug
```

**就这一条**,门禁会自动跳过这套工具,不会因此变红。
(唯一残留:`90-ops/run-tests.ps1` 里那一小段 `if (Test-Path …selfcheck.py)` 会变成空操作 ——
想彻底干净就顺手删掉那 15 行。★ 如实写出来,不说"一步都不用"。)

之所以能一条命令了事,是因为下面这条纪律被断言钉死:

> ★★★ **生产代码不得 import / 引用本目录的任何东西。**
> 检查它的是本目录的 [`selfcheck.py`](selfcheck.py),
> 它扫 `10-core` 与 `20-client-win` 全部源码,出现任何对 `90-ops/debug` 的引用即判红。

> ★★★ **2026-08-05 审计更正**:这一段原来写着「检查它的是
> `10-core/gateway/test_debug_removable.py`」—— **那个文件从来没存在过**。
> 而真正在检查的 `selfcheck.py` 因为不叫 `test_*.py`,门禁的扫描器根本不收它 ⇒
> **这条承诺当时既没被正确记录、也没被自动检查过**。
> 一份自称"专治『看着有防护、实际没有』"的工具箱,自己就栽在同一个形状上。
> ⇒ 现在 `run-tests.ps1` 会条件执行 `selfcheck.py`(存在才跑),承诺进了门禁。
>
> ★ 为什么不在 `10-core` 下建那个测试:那条判据要扫"生产代码里不得出现 `90-ops/debug`",
> 而测试文件本身必须写出这个路径 ⇒ **它会绊倒自己**。守卫必须待在它所检查的范围之外。

★ 为什么这条要靠断言而不是靠自觉:调试工具最自然的演化方向就是"顺手被生产代码用一下"
(某个诊断函数写得挺好、某个常量正好需要)。**一旦发生,"一键移除"就变成了一次重构**,
而那时人已经忘了曾经承诺过可以一键移除。

## 里面有什么

| 工具 | 一句话 | 什么时候用 |
|---|---|---|
| `doctor.py` | **链路体检** —— 从模型文件到客户端逐环报 up/down + **为什么** | 「打不开」「连不上」「没反应」时第一个跑 |
| `probe_switch.py` | **模型切换实测** —— 逐组件装/卸,量耗时与显存,验三道闸与不变式 | 改了 Broker / 装载器 / 显存闸之后 |
| `probe_sync.py` | **主副机同步实测** —— 可在两台机器上各跑一半,验范围/冲突/实时性 | 改了同步之后;两机实机验收时 |
| `scan_fake.py` | ★ **假防护扫描器** —— 找恒真断言、没有调用点的函数、已过期的「尚未接入」文案 | 收工前;它专治本项目的签名失败模式 |
| `selfcheck.py` | **这套工具自己的自检** —— 不需要系统在跑 | 改了本目录任何东西之后;门禁也会自动跑它 |

`scan_fake.py` 的两个开关(审计时用):

```bash
python 90-ops/debug/scan_fake.py --full --prod
```

`--full` 列全部(默认每类只列前 12 条:噪声太大的扫描器没人看)·
`--prod` 只列生产代码(测试里的嫌疑多半是"断言正守着这句话")。

## 共同纪律

- **只读优先。** `doctor` / `scan_fake` 一个字节都不写。
  `probe_switch` / `probe_sync` 会真的动状态 —— 它们**在开头显式说明**,并只在
  明确传入 `--write` 时才动。
- **失败要说清是哪一环。** 这套工具存在的全部理由就是把「不好使」变成
  「**第 3 环挂了,因为 X**」。任何一条输出都不许只说"失败"。
- **不吞异常。** 探测本身出错要和"探到了坏消息"分开报 ——
  两者的下一步完全不同(前者是工具坏了,后者是系统坏了)。
